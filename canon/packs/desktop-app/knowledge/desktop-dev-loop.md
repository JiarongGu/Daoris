# The desktop dev loop

The invariants are in `desktop-verification`. This is the loop underneath them — what three independent
implementations converged on, and the traps each hit first.

## One instance, kept alive

Relaunching per change is the default and it is what makes desktop verification feel expensive. Start
the host once, rebuild the front end, reload the view. The loop becomes seconds instead of a restart,
and — more importantly — it stops rewarding the habit of *not* checking.

That only works if the pieces are separable: the host serving the UI, and the UI itself, built
independently. A host that embeds its assets at build time cannot be iterated this way.

## The debugging port, and why it should not be fixed

Attaching a debugger needs a port, and a constant one collides — with a second instance, with another
project, with a leftover process from a run you thought had ended. **Randomize it per launch and write
it somewhere the tooling can read.** A collision does not fail loudly; it attaches to the wrong thing
and answers questions about it.

Two related traps:

- **Setting the host's browser-arguments option can silently drop the environment variable** that
  carries the debugging flag, so the port is never opened and the debugger simply finds nothing. A host
  that sets any argument of its own must re-append the variable's value itself.
- **Secondary windows created with their own environment have no target.** They are not broken; they are
  not there, and a tool that lists targets will show one window where you expected two.

## Reading state versus driving input

The split is the whole point of the rule, and it is worth stating as a habit:

- **Reading state** — what is rendered, what the store holds, what messages crossed the boundary — is
  exactly what the debugging protocol is for, and it is faster and more precise than a screenshot.
- **Driving input** — clicking, dragging, typing, focusing — goes through the platform. Native input
  posts to the window and behaves like a person; it works while the window is occluded and steals no
  focus, which matters when the verification runs unattended.

## Selectors that survive a rebuild

Class names generated by a bundler are hashed and change whenever the build does. A selector written
against one is a selector that works today. Prefer a stable attribute added for the purpose; when
matching on a generated name is unavoidable, match on a substring and check it still selects one
element rather than three.

Some behaviours cannot be driven from the protocol at all — anything the platform gates behind a real
user gesture, fullscreen being the usual example. Those need native input or a manual pass, and the
honest thing is to say which.

## Captures are evidence, and evidence accumulates

Screenshots are cheap and a verification loop produces them constantly. Cap the retention and prune
oldest-first *before* each capture, so the newest is never the one evicted — an uncapped directory
reaches thousands of files and nobody deletes them, because deleting them feels like deleting evidence.

They are also transient: the record of what was verified belongs in prose and numbers, in whatever
document keeps that history. A screenshot nobody references is not documentation.
