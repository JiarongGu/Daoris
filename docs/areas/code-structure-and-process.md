# Code structure and the development process — how it works now

## What it does

This area says how the code is laid out and how a change is made, by a person or by an agent session. The code is cut into domain
modules, each layered as an onion and held by structure gates (D166). Every job is done one way, and a structure that supersedes
another retires it (D228). Units stay small and cohesive: new behaviour goes in a unit of its own, a file over the budget does not
grow, and comments say why (D231). Every change goes through the canon's `change` skill. The repository's gates check what a
session would otherwise have to remember. Verification runs as a local CI beside the work (D180). Inside a big scope, development
finishes first and the whole set runs once.

## Its rules

1. Every change goes through `change`. A session reads the area document and the lines it points to before any code. (from D230,
   CONSOLIDATE1)
2. New behaviour goes in a unit of its own: a named type in the subdomain that owns it, never a `partial` of a hub. (from D231,
   D166)
3. A composition root wires units and holds no rule. A domain's logic is a module that registers its parts at start, each with its
   phase and what it follows. A seam is a sealed `PartAttribute` subclass with its own phase enum, marking each part as
   `[Seam("name", Phase.X, "after", …)]`. The root reads the marks with `Parts.Declared` and orders them with `PartOrder.Of`: by
   phase, then each part after the ones it names, with ties broken by name. A name declared twice, an unknown or later part named
   after, and a cycle are refused there. The root builds each part with itself as the wiring (`Parts.Build`) and runs each phase's
   parts at that phase's anchor. A part names only its seam's wiring interface, never the root, so it lives in its own subdomain.
   `tools/orient-index.mjs` writes the order to `docs/index/registered.md`. (from D231)
4. A file over 40 KB does not grow, and a new file does not start over it. The ratchet's list only tightens. (from D231)
5. Comments say what the code cannot: why a choice was made, a trap, a boundary's contract. Row ids, decision numbers and history
   live in the commits and the decisions. (from D231)
6. Each job is done one way. A change that supersedes an older way removes it in the same chunk. A kept older reading has a register
   entry with its end. (from D228)
7. Each contract is declared once, beside its handler. The rest (clients, the page's types, tables, maps) is generated or
   registered, not written by hand. An HTTP route is its request record in `src/Daoris.Contracts/<Domain>/` (`IRoute<TAnswer>`:
   method, path, answer), which uses the standard library alone. The host finds its `IRouteModule`s by reflection and maps each
   handler through `RouteMap`, whose binder answers a value that does not bind 400 with no body, as the framework's binding
   did: a body is read only where the record has body values, is 415 when it is not JSON, and is required unless the record
   is `[OptionalBody]`; a POST's `[FromQuery]` value travels in its query. The driver sends the record through
   `ServiceClient.SendAsync`, its views read in `Service/Wire/<Domain>Views.cs`. The page's types and `ROUTES` table are written from the
   records into the ignored `src/Daoris.Web/src/data/generated/service.ts` by `tools/contracts.mjs` (`tools/contracts/`), whose
   first line stamps a hash of the declaring sources: `--check` in `verify` fails a stale file, and `quick` and the web's
   pre-scripts write it with `--if-stale` first, so a fresh worktree's `quick` passes and the web loop needs `dotnet` after a
   contract changes. The same file carries the node kinds (`NODE_KINDS`) and the provider censuses' table (`PROVIDER_VOCABULARY`),
   read off the driver's kit and its registrations, whose declaring files the hash covers. The generator builds into
   `_fixtures/contracts-build/` (`--artifacts-path`), never the contracts' or the modules' own `obj/`, so a web gate's pre-script
   builds beside the service's and the desktop's gates. Its runs take turns under `_fixtures/contracts-build.lock`
   (`tools/run-lock.mjs`, stale once its process is gone), and one that waited reads the files again and builds nothing fresh. `api.ts` sends a declared
   route as `send(name, request)`. The quest doors are `QuestRoutes` (the reads, the publish and the respond, on both hosts) and
   `QuestPersonRoutes` (a local host's person and driver doors: the close, the set-up and review doors, the workflow choice, a
   conflict's dismissal and a delete); the ask doors, a local host's alone, are `AskRoutes`, which answer through `AskAnswers` and
   send from `AskDoorViews`. The session doors are `SessionRoutes` (the list, answered by `SessionListAnswers`, which keeps each
   answer with the store's `StoreMark` in a `MarkedAnswers` and makes it again once any writer of the file has moved the mark; one
   record by its id, answered as the list answers it; the list's change since a mark it answered, `SessionListChanges`, which holds
   the last few answers and answers each record whose written answer moved with every id in the list's order, kept on the driver's
   side by `SessionListKept`; the two opens and the state move, on both hosts, with
   a keyed open's refusal in the answer's own record), `SessionKeepRoutes` (a local host's opens for the conversations the driver
   starts itself, and what it learned of a start), `SessionStoreRoutes` (a finished tree's record, a session's memory and its
   delete) and `SessionWordRoutes` (the person's words on a session); a refusal in a record of its own (a say's word, a delete's
   facts) is `Answer<T>.Else`, and `SessionAnswers` is the one place a record is turned into its answer. The driver sends
   them from a named type per family in `Service/`, reached as a property of `ServiceClient` (`SessionList`, `Words`, `Moves`, `Keeps`,
   `Store`, `Openings`, `Registry`, `History`, `Standing`) and by the one-line doors callers name; `SessionReads` reads the list's
   generated `SessionResponse` into the planner's views, and the page's `Session` and `SaidWord` are those records. A local host's second-opinion, helper, partner,
   brainstorm, history and addressed-channel doors are `OpinionRoutes`, `ParticipantRoutes`, `BrainstormRoutes`, `HistoryRoutes`
   and `AddressedRoutes`; the driver's door classes send their records, and the page's opinion list is sent by name. The registry, the
   code map and the rescan are `RegistryRoutes`; a shared host's feed and quest-operation doors are `FeedRoutes` and a local host's
   sync and claim doors `SyncRoutes`; the person's confirmations are `ConfirmationRoutes` (the ask, read no further than its limit,
   is `[OwnBody]`, which the binder leaves unread); the change stream and the journal are `PlatformRoutes`; a quest's handback and
   its files are `QuestFileRoutes`, whose file is `RouteMap.MapFile` and whose answer is no JSON. A wire Core writes as text (the
   code map, the session, channel and quest wires) is answered as a `JsonObject`, so the machines' client reads the one it always
   did. `Program.cs` maps no route, and `HostWiring` carries what a module needs of the start. A window
   route is its handler's marks in the desktop modules (`[DriverRoute]` and those beside it); the same tool writes from them the
   ignored `src/Daoris.Web/src/bridge/generated/routes.ts`: `DriverRoute`, which `call` takes, `PUBLISHES`, which the page's
   publishing seam reads, `PERSON_WORDS`, which the names check requires worded in every language, and `SETTINGS`, the driver's
   settings list, whose folder (`Settings/List/`) is the one part of the driver library the stamp reads. A handler takes its
   payload record, named for its route (`SetCap(SetCap press)`), which `RoutePayload` reads off the request by its parameters'
   types as the hand-written reads did, a `JsonElement?` field as sent and null only where absent (a shape another reader owns,
   or a field whose sending is the choice), and a list of records each by the same rules. A route serving a plan and its press is
   two handlers sharing a named helper, never one reading the route's name. The record and the handler's answer record are
   written into `DriverPayloads`, so the
   page's `call` and `useDriverChange` take that route with no payload type of their own. No handler takes the `IpcRequest`. A
   judge that holds a form exact (the role door, the role's acts, the steward's desk) is handed the payload whole as a
   `WholePayload`, the only field of its record, which the page sees as an object of anything. (from D231, D228)
8. Drift is the disk against the lock; the canon is reconciled, not imposed. (from D19, D230)
9. Only what must never reach history blocks a commit. The rest is verified as a local CI beside the work, and its reds are fixed
   forward. An install is staged only from a green run. (from D180)
10. Inside a big scope, a builder writes its tests and compiles, and hands back once, running none. The merges carry no gates, and
    every check runs once when the scope's development is done. (from D180's note of 2026-11-04)
11. A builder is briefed in about eleven lines: the task and why, the area section, the start, the change site and its folder, an
    exemplar, the tests, what not to touch, and "follow `change`". At most five run at once. (from D160, D187)
12. A builder's cost is measured: turns before the first edit, context at the first edit and at the end, and where the clock goes.
    The targets are the first edit under 30 turns and 100K context, the end under 200K, and an hour per merge. (from CONSOLIDATE1)
13. A decision is written only for a choice that rejected an alternative. A present fact is rewritten in place in its area
    document. (from D220, CONSOLIDATE1)
14. The backlog holds open work only, a line or two per row; a finished row moves to the archive with one outcome line. (from the
    canon's task lifecycle)
15. The FIX-LOG takes regressions only, with the root cause in the commit body as well. (from CONSOLIDATE1)
16. Never write into another repository; send a request. No machine path, private name or credential in a tracked file or commit.
    (from the canon's rules)
17. The tests' wall time is measured before it is cut, one gate or class alone, since a full CI run shares the machine between three
    light gates and a Process lane, which turns a minute of work into ten (CI run 7155c53, 2026-11-06: driver 17 m 48 s, web-types 17 m 19 s, tool-tests
    16 m 30 s, web-measured 13 m 18 s, web-unit 11 m, web-rules 8 m 39 s, service 7 m 59 s, modules 6 m 57 s, web 6 m 48 s, universal 6 m 26 s,
    test-map 6 m 8 s, censuses 4 m 51 s, service-process 3 m 17 s, devkit 2 m 4 s, cli 1 m 30 s). Alone, on a quiet machine: the driver's
    fast half runs 19,184 tests in 6 m 57 s (3,161 s of test time over 1,029 classes, run about seven at once), the rules gate 87 s, the
    typecheck 86 s after the contracts' cold build of 98 s (which the first web gate pays and the rest wait on), `test-map` 45 s, and the
    web's whole unit run 12 m 57 s, 73% of it in the tests themselves. The driver's slowest fast-half classes are `LineAccountTests` (310 s
    of 11 tests, a grid of 984 cases each building its own scratch home, 28 ms a build), `StructureTests` (105 s, Roslyn compiles of the
    driver's tree), `AcpBackgroundTests`, `SessionsOutliveTheirLookTests`, `StagedBuildTests` and `TreeScratchTests` (50 to 100 s each, fixed
    `Task.Delay` staging that is the claim of the case). The Process half's slowest passing classes in that run were the SSH, HTTPS and TLS
    git classes (`GitSshPinnedProcessTests` 359 s, `GitSshProcessTests` 300 s, `GitDoorsPinnedProcessTests` 227 s, `GitTlsProcessTests` 183 s,
    `GitPushActProcessTests` 178 s, `CheckoutLockProcessTests` 158 s); the 160 s a failed move-class test spent were timeouts. Cuts made: the
    merge tool's MOD9 read-scan built the tracked folders' set once per `.cs` file (247 s to 14 s); `LineAccountTests` reads each grid case
    once for its class (`Todays`, `Rules`) and runs the cases eight wide through `GridRun` (185 s to 84 s); `StructureTests` and
    `ShellStructureTests` share one analysis, `DriverTree.Shared` (one compile fewer, about 50 s of CPU, no change in either class's wall);
    the web's vitest keeps its transformed modules (`fsModuleCache`: the rules gate 87 s to 42 s warm). Still redundant: the `censuses` gate
    reruns the Census classes that the driver's and modules' fast halves already run (a full CI run could skip it when both run), and the
    modules' fast half did not finish in a worktree beside a long Process run. (from OPTIMIZE1d)

## Where a change goes

- A new rule of the process goes in this document, and in the canon when it holds for every repository.
- A new gate goes in `daoris.gates.json` or `npm run quick`. Its failure names the file and the row to add.
- A new HTTP route: its request and answer records in `src/Daoris.Contracts/<Domain>/` with the domain's JSON context (a new
  context is listed in `ContractJson`), and its handler in the host's `Routes/<Domain>Routes.cs`. The host's
  `RouteModulesTests` holds every declared route to one mapping.
- The tests that pin the process: `tools/*.test.mjs` (the ratchet, partials, markers, the census of tool tests), the merge tool's
  tests, and the CLI's doctrine tests.

## Contradictions

- `docs/development.md` still asks for archive, changelog and fix-log entries for every change. `change` asks only for the area
  document. `change` reads right; `development.md` is rewritten with the records' rules.
- The archive and the FIX-LOG hold years of per-row essays. They stay as history and are not read by default.
