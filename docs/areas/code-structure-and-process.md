# Code structure and the development process — how it works now

## What it does

This area says how the code is laid out and how a change is made, by a person or by an agent session. The code is cut into domain
modules, each layered as an onion and held by structure gates (D166). Every job is done one way, and a structure that supersedes
another retires it (D228). Units stay small and cohesive: new behaviour goes in a unit of its own, a file over the budget does not
grow, and comments say why (D231). Every change goes through the canon's `change` skill. The repository's gates check what a
session would otherwise have to remember. Verification runs as a local CI beside the work (D180). Inside a big scope, development
finishes first and the whole set runs once.

## Its rules

1. Every change goes through `change`. A session reads the area document and the lines it points to before any code. (from D230,
   CONSOLIDATE1)
2. New behaviour goes in a unit of its own: a named type in the subdomain that owns it, never a `partial` of a hub. (from D231,
   D166)
3. A composition root wires units and holds no rule. A domain's logic is a module that registers its parts at start, each with its
   phase and what it follows. A seam is a sealed `PartAttribute` subclass with its own phase enum, marking each part as
   `[Executor("name", ExecutorPhase.X, "after", …)]` for the driver's executors. The root reads the marks with `Parts.Declared` and
   orders them with `PartOrder.Of`: by phase, then each part after the ones it names, with ties broken by name. A name declared
   twice, phases of two enums, an unknown or later part named after, and a cycle are refused there. The root builds each part with
   itself as the wiring (`Parts.Build`) and runs each phase's parts at that phase's anchor. A part names only its seam's wiring
   interface, never the root, so it lives in its own subdomain. `tools/orient-index.mjs` writes the order to
   `docs/index/registered.md`. (from D231)
4. A file over 40 KB does not grow, and a new file does not start over it. The ratchet's list only tightens. (from D231)
5. Comments say what the code cannot: why a choice was made, a trap, a boundary's contract. Row ids, decision numbers and history
   live in the commits and the decisions; the comment gate refuses what a change adds against it. (from D231, D235)
6. Each job is done one way. A change that supersedes an older way removes it in the same chunk. A kept older reading has a register
   entry with its end. (from D228)
7. Each contract is declared once, beside its handler. The rest (clients, the page's types, tables, maps) is generated or
   registered, not written by hand. An HTTP route is its request record in `src/Daoris.Contracts/<Domain>/` (`IRoute<TAnswer>`:
   method, path, answer), which uses the standard library alone. The host finds its `IRouteModule`s by reflection and maps each
   handler through `RouteMap`, whose binder answers a value that does not bind 400 with no body: a body is read only where the
   record has body values, is 415 when it is not JSON, and is required unless the record is `[OptionalBody]`; a POST's
   `[FromQuery]` value travels in its query, and `[OwnBody]` is left unread. `Program.cs` maps no route, and `HostWiring` carries
   what a module needs of the start. The driver sends the record through `ServiceClient.SendAsync`, from a named type per family
   reached as a property of `ServiceClient`; a refusal in a record of its own is `Answer<T>.Else`, and a wire Core writes as text is
   answered as a `JsonObject`. The session list's answer is kept with the store's mark and made again once any writer moved it, and
   its change since a mark (`ListChanges<T>`) answers each moved record in the list's order. The page's types and `ROUTES` are
   written from the records into the ignored `src/Daoris.Web/src/data/generated/service.ts` by `tools/contracts.mjs`, with the node
   kinds and the provider censuses' table, stamped with a hash of the declaring sources: `--check` in `verify` fails a stale file,
   and `quick` and the web's pre-scripts write it with `--if-stale` first. The generator builds into `_fixtures/contracts-build/`,
   never the projects' own `obj/`, its runs taking turns under a run lock, and removes that output before it lets the lock go. A
   window route is its handler's marks in the desktop modules; the same tool writes from them the ignored
   `src/Daoris.Web/src/bridge/generated/routes.ts` (`DriverRoute`, `PUBLISHES`, `PERSON_WORDS`, `SETTINGS`). A handler takes its
   payload record, named for its route, which `RoutePayload` reads off the request by its parameters' types (a `JsonElement?` field
   as sent, null only where absent), written into `DriverPayloads` so the page's `call` needs no payload type of its own. A route
   serving a plan and its press is two handlers sharing a named helper, never one reading the route's name; no handler takes the
   `IpcRequest`; a judge holding a form exact is handed a `WholePayload`. Which route class holds which doors is the index's.
   (from D231, D228)
8. Drift is the disk against the lock; the canon is reconciled, not imposed. (from D19, D230)
9. Only what must never reach history blocks a commit. The rest is verified as a local CI beside the work, and its reds are fixed
   forward. An install is staged only from a green run. (from D180)
10. Inside a big scope, a builder writes its tests and compiles, and hands back once, running none. The merges carry no gates, and
    every check runs once when the scope's development is done. (from D180's note of 2026-11-04)
11. A builder is briefed in eleven lines: the task and why, the area section, the start, the change site and its folder, an
    exemplar, the tests, the words suites it cannot run read, what not to touch, the decision number reserved, what done is, and
    "follow `change`". At most five run at once. (from D160, D187)
12. A builder's cost is measured: turns before the first edit, context at the first edit and at the end, and where the clock goes.
    The targets are the first edit under 30 turns and 100K context, the end under 200K, and an hour per merge. (from CONSOLIDATE1)
13. A decision is written only for a choice that rejected an alternative. A present fact is rewritten in place in its area
    document. (from D220, CONSOLIDATE1)
14. The backlog holds open work only, a line or two per row; a finished row moves to the archive with one outcome line. (from the
    canon's task lifecycle)
15. The FIX-LOG takes regressions only, with the root cause in the commit body as well. (from CONSOLIDATE1)
16. Never write into another repository; send a request. No machine path, private name or credential in a tracked file or commit.
    (from the canon's rules)
17. The tests' wall time is measured before it is cut, one gate or class alone on a quiet machine, since a full CI run shares the
    machine between three light gates and a Process lane, which turns a minute of work into ten; no figure taken beside other runs
    is a measure. The web's unit run uses `vmThreads` and keeps its transformed modules (`fsModuleCache`), and its setup loads no
    Storybook; the driver's grid tests run eight wide through `GridRun`, its two structure classes share one analysis
    (`DriverTree.Shared`), and that analysis and the declarations' censuses read one compilation of each shipping desktop project a
    run (`DesktopCompilations.Of`, counted by `SharedCompileTests`), each tree bound in one semantic model every census shares
    (`SharedModels`). The figures, by gate and by class, and the cuts tried are OPTIMIZE1d's in the archive. (from OPTIMIZE1d)
18. Every process Daoris's work runs is under the application in the system's tree, since Windows lists a process under its
    parent only while that parent runs. A terminal verb that starts heavy work (`daoris gate run`, a gate or a command of the
    caller's) asks the running Daoris, which runs it as its own child and the verb only waits; where none takes it the verb says
    so in one line and runs it itself. Every other verb that can start a process asks the running Daoris first or is listed in
    `TerminalStartsCensusTests` with why it may not, and `node tools/process-tree.mjs` lists what still runs outside the tree,
    under what started it. (from PROCTREE1)
19. A branch is previewed (`--preview`) and queued with its message (`--message`); the queue's runner merges the queued branches
    into a candidate in `local/scope-tree` and promotes it to main by fast-forward once it is green. A merge runs the blocking checks
    (the universal gates, the code map, the census of test units) and the path checks its paths reach (the page's `tsc`, design and
    structure tests); every other gate is left to the CI (`--ci`), `--gated` and `--full` (alternatives) run more, and `--ci
    --stage` stages the install from a green run. A CI run leaves a gate that only runs census classes of projects whose fast half
    it runs to those halves, recording its pass once they pass, and builds the page's contracts once as a step before the web gates
    that need them. A lane's globs are read by one translator (`lanes-file.mjs`: `*` in a folder, `**` across folders, `{a,b}`
    alternatives that nest) and a change's paths in one place (`paths.mjs`); a file a narrow lane row places names the gates of
    every wider row too. The queue's and admission records read as empty only where missing or unparseable, so a failed read stops
    the writer. Every lock (the verdict store's, the gate tree's, the CI watch's) is put in place complete (`locks.mjs` over
    `run-lock.mjs`), names its holder by pid and creation time, and is taken over only from a holder judged dead and still the one
    judged; a take-over ends only that holder's children. One run at a time holds a checkout's open merge
    (`local/merge-run.lock`): a second is refused naming the holder's pid and start, never let to collide. A queue entry whose
    process is gone is never left stuck: `--queue` names a candidate that says it runs while neither its run nor the runner is
    alive, and `--queue --recheck` starts the runner, which resumes it, and clears a request or candidate whose tips main already
    holds into the landed record. New merge behaviour is typed
    TypeScript in `tools/merge/` (strict, run by type stripping, checked by `npm run typecheck:tools`), which `merge-branch.mjs` calls,
    tested beside it on Vitest (`tools/vitest.config.ts`, a process per file): the `unit` project (`*.test.ts`) runs whole in `npm run
    verify`, the `e2e` project (`*.e2e.ts`, a seeded scratch repository per case) in `npm run tooltests`, and their folders are made
    under `_fixtures/tool-tests/`. A typed module reaches an untyped script through a `.d.mts` beside the script, which
    `declarations.test.ts` holds to the script's exports (D287). (from D180, MERGEFLOW1, D287)
20. A test's fixture is built one way, by the shared builder linked into each project that needs it: a scratch home is
    `ScratchFolders.New` under `TestHomes.Root` and goes with `ScratchFolders.Remove`; the service stood in over HTTP is a
    `RoutedHandler`; a clock a test moves is `Daoris.Testing`'s `MovedClock`, the one copy; a wait on a signal is `Poll`; the web's window over a mocked shell is `test/doubles/appShell.ts` and its service
    over `fetch` is `test/doubles/fetchRoutes.ts`. The service's, the HTTP host's and the devkit's tests have their process's temporary folder at
    `_fixtures/test-homes/temp` (`ScratchTemp`), so what they root at `Path.GetTempPath()` stays in the checkout's scratch; the
    desktop's tests name `TestHomes.Root` and `TestHomesCensusTests` refuses the call. A golden holds one full render; each other
    case is held against it section by section, the sentence that makes a section differ asserted and every other section equal.
    (from TESTDIET1)
21. The development cycle keeps main green and the install current within the hour: a builder runs `node tools/worktree-setup.mjs`
    first (the main checkout's `local/*.props` copied as files, never linked; dependencies from the lockfiles through
    `tools/merge-branch/dependencies.mjs`, shared with the gate tree; the merge drivers, the index, the contracts and the restore
    primed); a branch lands through the merge tool, never a plain `git merge`. The merge also runs the CLI's verify (`MERGE_SUITES`:
    the lists, records and documents no path places) and `reached` (`tools/reached-checks.mjs` runs the test units the census says
    the paths reach in the driver's, modules', service's, page's and tools' suites, nearest the change first, bounded per suite by
    `tools/merge-branch/reached.mjs`, the rest counted), so a list, census or structure red never lands. `reached` reuses a pass
    per class: a class's key is the digest of every tree file that reaches it (its own files, the source areas it names, the build
    files above its project), its suite's declaration and the toolchain, with wiring (a project reference, a `Using`, a `global
    using` of a namespace, a comment, a group no file switches on) left out because the one build verifies it; a class whose key
    passed (`local/reached-classes.json`) is replayed, so a change to a widely referenced project runs exactly the classes that
    name it and a change no class reads runs none. A unit class runs when a changed path reaches it; a Process class, which
    names its real dependency with a `Needs` trait, runs only where a changed path is that dependency's code (`tiers.needs` in
    `daoris.gates.json`), and the summary names the count left to the nightly run (`--ci --night`) and the stage. The CI runs beside on
    main's tip, its reds fixed as small commits; the install is staged from the tree whose light lane and reached Process classes
    passed (`--stage --from-gated <commit> --light`, or `--passed --light`), the CI's rehearsals running on the staged commit
    after, and the full stage (`--ci --stage`) remains the one that owes every gate. A merge is fast and never blocked by a red that is
    main's: a gate declaring `reuse` (`reached`, `censuses`) replays a standing pass whose reaching inputs, command and toolchain are
    unchanged (the verdict's `key`, in the one store `local/gate-verdicts.json`, under the merge tool's one reach table, whose digest
    the key holds); a failure main already stands in under the same signature (its open findings, its failing verdicts on its own tree)
    is named as main's and does not fail the merge; a test project is built once per tree (later gates run `--no-build`); a gate's
    declared `regenerate` command makes a generated input current before the gates; a gate that ends abnormally is said so and the run
    goes on; what a gate left running is stopped by pid and creation time; and a gate past its budget (`timeoutMinutes`, else five minutes
    in a merge and ten in the full set or the CI; `--no-timeout` for an investigation, taken by `--continue` and `--rerun` alike and
    said in the summary) is killed and fails as over-budget. The time ratchet (`tools/time-ratchet.mjs`) is judged once inside a merge, after every gate has finished, on the
    timing records that merge's own gates wrote (`--since` its start), as a last check that fails like a gate and is named in the
    summary; verify's own run of it stands aside inside a merge, and outside one judges what the records hold. Each merge appends a record to `local/merge-record.jsonl` (the gating's wall time, each gate's time and slowest classes, the
    tests that passed only when run again, first pass or not, reds set down as main's, what ran over budget), read by
    `tools/dev-metrics.mjs`. A gate never inherits a test runner's own variables (`NODE_TEST_CONTEXT`, `NODE_ENV`, `VITEST*`). `TASKS.md` merges by its rows' ids
    (`tools/merge-backlog.mjs`; `.gitattributes`). Measured 2026-11-05 to 2026-11-11: 18 CI runs, median 240 minutes, each red in
    a gate a merge now runs, the last green on 2026-11-02.

    locator, counted per subdomain by the census's ratchet, which only tightens and starts at zero, and one a root sets once. The

22. The test budget is the owner's: a unit test runs in seconds, a Process case under two minutes, a gate under five minutes and a
    whole suite under ten. It is enforced once per tool, in config, never at a call site: .NET's `VSTestBlameHangTimeout` in the
    root `Directory.Build.props` (the kill bound: 60 seconds for a half with no run-settings file, two minutes for a Process half, which ends the
    run and names the test; the 30-second unit budget is held by the time ratchet, not by this bound), the page's `testTimeout` and `hookTimeout` in `vite.config.ts` (ten seconds), the tool tests'
    `--test-timeout` in `src/Daoris.Cli/package.json`, and each merge tool project's in `tools/vitest.config.ts` (ten seconds a unit
    test, two minutes an end-to-end case). Those are the backstop for a hang; `tools/time-ratchet.mjs` holds each test to
    its own limit (30 s, 2 min for a Process half, 10 s for the page and a merge tool unit test, 2 min for a tool test) from the durations the gates record, and
    `tools/time-ratchet.json` names the tests over their limit and the time each may take: a listed test does not get slower, an
    unlisted one over its limit fails, and `--write` only cuts the list. A test that needs longer says so and why where it is
    declared. Every gate records each test's duration under `_fixtures/test-timing/` (a trx per .NET gate, `web-unit.json`,
    `tool-tests.xml`, `tool-unit.json`, `tool-e2e.json`), so a census reads them and runs nothing. A Process class names each real dependency it needs with
    `[Trait(Category.Needs, Needed.X)]` (git, process, harness, browser, network, filesystem) beside its category, and
    `NeedsTraitTests` holds it; a test with no such trait is a unit test, with no process, git, clock wait or network. (from TESTTIME1)

## Where a change goes

- A new rule of the process goes in this document, and in the canon when it holds for every repository.
- A new gate goes in `daoris.gates.json` or `npm run quick`. Its failure names the file and the row to add.
- A new HTTP route: its request and answer records in `src/Daoris.Contracts/<Domain>/` with the domain's JSON context (a new
  context is listed in `ContractJson`), and its handler in the host's `Routes/<Domain>Routes.cs`. The host's
  `RouteModulesTests` holds every declared route to one mapping.
- The tests that pin the process: `tools/*.test.mjs` (the ratchet, partials, optional locks, the census of tool tests), the merge tool's
  tests, and the CLI's doctrine tests.

## Contradictions

- `docs/development.md`'s "The CI between releases" still lists an archive move, the changelog and a fix-log entry in every
  merge's records commit, while its "Integrate and record" and `change` ask only for the area document, a decision for a rejected
  alternative, and the fix log for a regression. `change` reads right.
