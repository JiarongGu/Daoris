## D161 — Development runs itself, is judged where it is met, and starts from Ask Daoris (2026-10-11)

**Decision (the owner's direction, after D160's first batches).** The owner: *"so the purpose is make the development as
much as automated as possible and make sure it perform good, and Ask Daoris is a good main entry point to start any
task"*. It settles the three questions D160's trial left with the owner, and sets one direction for the work after it.

1. **A rule an agent drops belongs in a mechanism, not a sentence.** `file-tool-discipline` is always loaded, and every
   worker's prompt restated it. Still, 6 of 14 Sonnet workers edited through the shell, one by deleting lines at
   computed offsets (D160's second SUBLOAD1c note). A `branch-worker` now runs `tools/shell-edit-guard.mjs` as a
   PreToolUse hook in its definition. The hook refuses, before it runs, a shell command that writes a file of the work,
   with the same pattern `tools/subagent-usage.mjs` counts. Reading, searching, gates, logs and `local/scratch` stay
   open, and a call the guard cannot read passes. Where a transcript shows another step dropped (watching a test fail
   first), its mechanism is the next candidate, measured first.
2. **The work is judged where the person meets it.** Gates prove a branch builds, and the installed window proves it
   serves. After a batch that changed what a person sees, the parent owes the full set, the install republished and
   the shots the archive names (UXFIX2bi, ACCTUX4i, ASKHIST1di, UX6i2i). D160's model split is judged on those shots as
   well as on gates and counts. MODELROLE1 waits for that judgement.
3. **Ask Daoris is the main entry point to start any task.** A person starts with words in Ask Daoris, and it either
   answers, takes them to the place (`go_propose`), or starts the work: an ask that the intake turns into quests and
   sessions (D65), or a proposal the person applies. So every place the window has is one a go can name (UX6g2b: the
   workspace page's tabs and sections become go parts). Every control the page offers is judged again against "start any
   task" (ENTRY1). `HelpCoverageTests` already lists each control with its door or its exemption, and each exemption is
   reread with this question.

**Rejected:**
- **Leaving the shell rule to prompts.** It was measured, and it cut the edits without ending them.
- **Judging the model split by gates alone.** Every Sonnet branch passed its gates, and gates cannot see a row's height
  or a refusal's place on the window.
- **A second entry point.** A command palette, a menu and the activity bar each reach a place. Only Ask Daoris takes
  words and starts work, so the others stay ways to a place.

**Limits.** The hook runs only in a `branch-worker`, not in the parent or a scout. Its first refusal on a live worker is
its proof; a test proves the guard, not the harness calling it. Its pattern errs low: a write the pattern does not know
passes, as the count misses it. ENTRY1 is an audit before any door is built: which starts are missing is measured from
the coverage table, not assumed.

### ENTRY1 — what Ask Daoris is for, and what it is not (2026-10-11)

The owner, after the ENTRY1 audit (`docs/2026-10-11-entry1-audit.md`): *"so Ask Daoris is a entry that regularly can
solve anything within the app or analyze the task, but the quest or session itself has its own conversation logic, Ask
Daoris is an entry point when user does not know where to go more like a general entry point for all"*.

- **Ask Daoris is the general front door.** It solves what lives in the app (a setting, an account, a plugin, a
  set-up, a repository), it analyzes a task into an ask that the intake turns into quests (D65), and it takes a person
  who does not know where to go to the place.
- **A quest or a session keeps its own conversation.** Landing its work, answering it and its go-aheads, trusting a
  folder for it, and publishing a quest by hand are done in that quest's or session's own place and conversation. Ask
  Daoris takes the person there and does not take them over. This answers the audit's §4.6 (ENTRY1e): none of them
  becomes an Ask Daoris proposal.
- **Reaching a place therefore matters as much as starting.** A go must reach below Quests, Sessions and Overview, to
  what needs the person (ENTRY1b). The coverage table gains a third answer beside a door and an exemption: *its own
  conversation*, a control whose work belongs to a quest or a session and that Ask Daoris reaches by a go (ENTRY1a).

### ENTRY1a — the coverage table reads every start (2026-10-11)

`HelpCoverageTests` now reads the page's own service calls (`queries.ts`) beside the bridge, and every source file of the
page but the tests, the stories and the files that define the hooks. Each press of a hook that changes something is
answered by where it is pressed (`Starts`: `App`, `QuestsView`, `asks`, `help`, `work`, …), unless a Settings domain's
control or `Elsewhere` answers the same act already: the answer is the act's, not the place's. A file that defines the
hooks presses none of them, so a domain that imports `queries.ts` presses only what it calls. Each start takes one of
four answers, by this rule:

- **Its own conversation** (`Conversation`, naming one of `HelpPlaces.Views`): a quest's or a session's own act, done in
  its place and reached by a go: on Quests what a quest or an ask is answered with, on Sessions what a conversation is
  said, stopped, answered or landed with.
- **A door** where a kind already takes the act, beside the place's own press: retry (`setting`), `accept`, `hand`,
  `delete`'s quest and ask, and `ask` for the composer.
- **Exempt** where nothing changes (an open, the index's refresh, Sync now, which runs the next tick's pass and is not
  the `sync` kind's), for a discard or a retire (D89), for a decline or a close, which carry the person's reason (D37), for
  the person's own words moved (D133 §1), for Ask Daoris's own conversation and history, and for a card's Apply.
- **Owed** to a named row: pause and resume (PAUSE1f), a session's archive and delete (SESSUX1h), an ask's review choice
  (ENTRY1c), and a repository registered, imported or moved to a workspace (ENTRY1d).

A press that is not a mutation, as *Look now* is, is no start. The table answers each start; it builds no door.

### ENTRY1c — an ask proposed with the person's review choice (2026-10-11)

The audit's §4.3: a person who asked Ask Daoris to have the work reviewed before it lands got an ask that dropped it, though
the composer and `daoris-driver ask` both send a review choice (D154's REVIEWENV1j note).

- **What an ask proposal carries now**: its sentence, workspace and why, and the review choice the person said with their
  words, `review` and `reviewWords` in the proposal's file. The choice is the composer's: `on`, an environment's name or
  `off`; left out, blank or `rule`, none is written and each repository's rule decides, as the composer's default does.
- **Judged where each side can.** The service's box checks the shape only (words go with a choice, and a choice is one
  word), as the setting kind's `review` door does. The driver's plan judges it with the composer's own judgement,
  `AskReviewCommand.Compose`, and so with the rule's `ReviewRules.NameProblem` for a name. Whether the ask's workspace
  declares a named environment is the ask door's, at Apply, with `AskReviewCommand.UndeclaredAsync` as the terminal reads
  it, since the facts a plan holds name no repositories per workspace. The card shows the choice in the composer's words
  (*review it in the default environment*, *in `dev`*, *no review*) and its terminal twin `--review … --review-words "…"`.
- **Not the kind or the workflow.** An ask's kind and workflow are the person's (D157 point 10: an agent proposes a kind
  and never sets one; WORKFLOW1i), so no proposal carries them. The person chooses them on the ask.

**What the gates do not cover.** No window was driven: the card renders the driver's describe verbatim, so it is the
describe the tests hold. The modules' ask door is held in a fast class of its own, `HelpAskDoorTests`, beside the

### §2 on the window, corrected: the retire ask's focus was the instrument's (2026-10-11)

The "§2 on the window" note above named `CLOSES_ITSELF` as why the retire ask gave the focus to the drawer's Close. It
was not the cause, and the defect was not one a person meets (UXFIX2d; D153's UXFIX2d note and the FIX-LOG entry).
- **The instrument pressed without focus.** `npm run desktop -- eval`/`click` press with a script's `element.click()`,
  which moves no focus. The focus stayed on Close, where the drawer put it on opening, and the ask took Close for its
  opener. A person's click moves the focus to the press first, as jsdom's `userEvent` does, and the ask gives it back
  to the press.
- **The ask is now right either way.** It records the press a click went to, so it holds for any click that moves no
  focus. `CLOSES_ITSELF` is unchanged.
- **The window check must click as a person does.** DESKCLICK1 makes `desktop click` focus the press before it clicks,
  or say that it did not. Until then, judge focus on the window from a test's pointer, not a script's click.
- **What it says of the split stands.** The window found one defect of the work (the repeated sentence, UXFIX2b1r) and
  one of the instrument, and no difference of quality between the Opus and the Sonnet rows.
