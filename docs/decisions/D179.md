## D179 — Daoris estimates how much work each usage window holds, from its own turns and the makers' readings: history first, the estimate in reference-equivalent tokens with its range, reported before it is ever acted on (2026-10-19)

**Decision (USAGECAP1).** The owner, 2026-10-19, after USAGERESET1 (the walk's last day weighing what would lapse):
*"I think you can probably calculate, or find out, the total usage of each reset, more like a better estimation"*, then
*"since input, output and model type probably all affect the usage, you should bring them into the counter too; this
is more complex, so we need to design this properly."* The makers publish no absolute allowance: Claude Code and Codex
report each window only as a percentage with its reset (the switch design §1, `docs/2026-10-07-codex-usage-evidence.md`).
So 40% of one plan's week and 40% of another's are not the same work, and the walk can compare accounts only in
percentages. A read-only opinion from Codex was taken on the model, the estimator, its validation and the data to keep
first; this entry adopts it.

1. **What can be known, and its unit.** Within one window between two readings, the percentage rises by Daoris's
   turns' tokens, weighted by model and kind, over the window's capacity, plus use Daoris never sees (the person's own
   sessions, the web app: it only adds), plus rounding and lag:
   `Δp = Σ(model m, kind k) w(m,k)·x(m,k) / C + u + ε`, `u ≥ 0`.
   - **Only the ratio `w/C` is observable**: scale every weight and the capacity alike and nothing changes. So one
     reference kind (a reference model's input token) weighs 1, and the estimate is in **reference-equivalent tokens**,
     never raw tokens, never work done, never money.
   - **Unseen use makes Daoris's work over the rise a lower bound on capacity.** A point estimate needs the stated
     assumption that some intervals held little unseen use; the estimate says that it rests on it.
   - **Weeks of correlated data cannot fit four weights per model.** The relative weights are fixed from a table
     (point 3), and one capacity is fitted per provider, plan variant and window scope. An account's own deviation is
     fitted only once evidence shows one.

2. **History first (USAGECAP1a).** Two append-only logs beside `windows.json`, machine-local, never on a shared host
   and never synced, bounded by age and size together (90 days and 64 MiB to begin with), a pruned gap said where a
   reader meets it, each record versioned with its own id and the time it was written:
   - **A reading**: the account's opaque local id and its binding epoch, the agent, the window (identity, scope,
     duration), the used fraction or null, what is known of its precision, the reset or null and where the reset came
     from (said, carried a week, or made up: `ClaudeUsage` makes one up for an unopened window at zero, which is no
     boundary to calibrate on), the source (a turn's frame, `get_usage`, Codex's server), when it was observed, the
     session and turn where one said it, the plan as last read and how, and the reader's version. Scoped windows
     (per-model weeks) are kept, which today's reader drops.
   - **A turn**: the account and its epoch, the agent, the session and turn, when it started and ended, the four token
     kinds each nullable, the split by model where the door reports one, where the attribution came from and how whole
     it is (a cancelled turn, a helper model's tokens outside the main total), and the token report's meaning (per
     turn or cumulative, cached input inside input or not) with its version.
   - **Never** a prompt, a word, a raw frame, a key, an email, an organisation or who signed in. A null stays null:
     absent is never zero (D57).
   - **Per-turn model attribution is missing today**: the session log keeps the four counts per turn, no model, and a
     session can change model mid-way. The slice captures the model per turn where the door reports it, and marks a
     turn's model unknown or mixed otherwise.

3. **The weights are a reviewed, dated, sourced table of ratios: never prices** (amends D57's "no price table", narrowly).
   Per maker, model identifier and token kind, a relative weight, with its source, the date it was read, the date it
   took effect, its assumptions and the table's version. For Claude, the maker's published API ratios between kinds
   (input 1, output 5, cache read 0.1, cache write 1.25 for five minutes and 2 for an hour) and between models; for
   Codex, its published credit ratios rather than unrelated API prices. Both makers say their subscription accounting
   is not their API price list, so the table is a prior, checked by sensitivity: the estimate is refitted under each
   neighbouring ratio, and a fit that moves more than its own range under them is said as weak. A new table version
   never reweights history silently; a fit says the version it used. Nothing turns a weight into money.

4. **The estimator (USAGECAP1b): a low quantile through the origin, over intervals long enough to read.**
   - Intervals between two readings of one window, inside one reset and one calibration epoch, joined until the
     percentage rose by **at least five points**, each end allowed one point of rounding until the reading's precision
     is known (both measured doors answer whole percents today; Claude's frames carry hundredths). An unchanged reading
     is not zero spend.
   - A **low-quantile regression** (0.1 to begin with, its neighbours compared), non-negative, with no intercept, of
     the rise on the weighted work: least squares would fold the unseen use into the slope and understate capacity, and
     the smallest ratio alone is too sensitive to a late reading.
   - **Pooled only within one plan variant** (`subscriptionType` and what else names it, ACCOUNTID1's `LoginRead`); an
     unknown plan stands alone.
   - **Shown only when it has earned it**: twenty such intervals across three reset cycles, one whole cycle held out
     and predicted, and a range narrower than a factor of two. Otherwise *insufficient evidence*.

5. **It checks itself.** Before each new reading is taken in, the fit predicts the rise Daoris's turns since the last
   should have made; the prediction, the interval, the signed error and the fit's version are kept. The page shows the
   recent median and 90th-percentile error in points. A positive error may be the person's own use; repeated negative
   errors mean the attribution, the timing or the maker's accounting is wrong, and the estimate is withdrawn until it
   holds again. A plan or an account rebound, or a token report's meaning changed, starts a new epoch; a reset that
   moved unexpectedly splits its interval and holds the fit until it is confirmed.

6. **What the person sees (USAGECAP1c)**, per account and window: *estimated weekly capacity X to Y
   reference-equivalent tokens; about A to B left at the last reading, for this model mix*, with the reset, the
   reading's age, the error and the table's version; the tightest applicable window bounds what is left. Never a price,
   never an exact allowance, never the same unit across makers, never a promise that a session will fit.

7. **Acting on it waits** (amends D130 point 9 and its rejection, *learning capacity and acting on it*, conditionally).
   D130's reason stands for the readings: Daoris sees only its share, so a learned capacity must never cool an account
   or pass one as near or over; the maker's percentages stay the only authority for that. What may change, once an
   estimate has passed point 4's gate and point 5's check, is one order: USAGERESET1's last-day horizon may compare the
   conservative end of each account's absolute room over the hours to its reset, where every account compared has a
   standing estimate; anywhere else, and wherever one is weak or missing, percentages decide as before. A row of its
   own builds it, after USAGECAP1c.

8. **Codex** uses the same machinery with its own weights and capacities. Its windows are named by their duration and
   their limit's scope, never by their slot; neither is assumed present, and their room is never added together. Its
   token reports are normalized against recorded fixtures (cumulative or per turn, cached input inside or not, reasoning
   inside output or not, a cancelled turn); a kind it does not report stays unknown.

**The traps**, each a test its slice owes (Codex's list, kept): flat readings under rounding; a burst of unseen use;
a late reading; an interval across a reset; a model switch and a helper model's tokens; turns overlapping; a turn
replayed twice; a cancelled turn and null counts; a cumulative report; a plan rebound; a malformed or pruned history.
Each keeps its uncertainty, never counts twice and never makes a zero up.

**Rejected.**
- **Billing, a price, or money in any form** (D57).
- **Probing an account to calibrate** by spending it, and **reading a maker's console or credentials** (D130).
- **Fitting every model's every weight freely** now: the data cannot carry it.
- **Least squares, or the smallest ratio, as the estimator** (point 4).
- **Converting between plans by their advertised multiples** (a 20x and a 5x label) without this measurement.
- **Acting on an estimate before it is validated**, and **ever letting it decide near or over** (point 7).

**Amends D130 point 9** (the measured use and limit history: now kept and fitted, still reported first) and its
rejection of learning capacity (conditionally, point 7), **and D57's "no price table"** (ratios only, point 3).
**Held by:** nothing built here; each slice's row names its proof.

**Note, 2026-10-19 (USAGECAP1a1, every usage reading kept).** Point 2's readings log is built in `Accounts/Usage/UsageHistory.cs`,
under the home entry `usage-history`, a data folder by the install layout design's §2 (no key, no agent works in it, nothing
fetched, no process holds it, not the machine log), in the three home tables. What the build settled:
- **The files.** `usage-history/readings-YYYY-MM.jsonl`, one JSON object a line, the month in UTC, and `epochs.json`. Each record
  carries `v` (1), `kind`, `id` and `written`. USAGECAP1a2's turns log goes beside it on the same writer.
- **A reading** writes every field, a null as null: `agent`, `account` (the profile folder's name, `""` for the tool's own),
  `epoch`, `door` (the adapter that carried or asked it), `window`, `walk`, `scope`, `minutes`, `used`, `precision`, `reset`,
  `resetFrom`, `source`, `seen`, `session`, `plan`, `planFrom` and `reader`. `window` is the maker's identity: Claude's key
  (`seven_day_opus`), `limits:<kind>` for a row of `get_usage`'s `limits[]`, and `<minutes>-minute` for Codex, never its slot.
  `walk` is Daoris's name where the walk reads it. `scope` is a Claude key's rest after `seven_day_`, a row's `scope`, or Codex's
  `limitId`; null for the whole plan's. `source` is `frame`, `get_usage` or `account/rateLimits/read`. `seen` is the moment
  `windows.json` keeps beside it. `planFrom` is `get_usage`, or `status` for the plan the status question read (`LoginRead`,
  held in memory). `reader` is each parse's version, 0 for a test stand-in's walk readings.
- **Precision** is the step the number shows as written: 0.01 for `23` of 100 or `0.88` of 1. It is a floor, since trailing zeros
  are not written. The maker's rounding is for USAGECAP1b to read from many.
- **A reset's source** is `said` or `made-up`. Carried a week is not a reading's: `AccountWindows.Next` carries a week when the
  walk reads it. No reset is made up beyond the walk's two windows.
- **The parse beside the walk's.** `AccountReadings.Seen` reads a frame. `ClaudeUsage.Read` and `CodexUsage.Read` answer a
  `UsageAnswer`: the walk's readings as before, with the history's windows, the plan, the source and the reader beside them, so
  every caller of the walk's is unchanged. `AccountReadingsTests`' row that the walk drops `seven_day_opus` stands. `get_usage`'s
  `limits[]` rows are read by the usage-read evidence's field table (`kind`, `scope`, `percent`, `resets_at`), never `severity`;
  no recorded answer holds one yet. `extra_usage` and `spend` are never read. Codex's other limits in `rateLimitsByLimitId` are
  kept by their `limitId`; its plan is still not read.
- **The bound** prunes whole months: a month once it ended 90 days ago, then the oldest while the files and the write exceed
  64 MiB. A `gap` record (`from`, `to`, `why` `age` or `size`, the files) heads the write that pruned. The month being written is
  never pruned: alone at the cap it gets one `full` record and drops the rest of the month, which the reader says as a gap to the
  month's end. Since a month goes whole, up to about 120 days stay.
- **A duplicate** (the same agent, account, window, scope, source and moment) is written once. It is remembered per home for the
  process's life, 4096 keys; a restart's readings fall at other moments.
- **The epoch** begins at 1 with an account's first reading. A different plan as read begins the next; a plan first learned is
  the epoch's own. A sign-out read (`Keep`, which `SignedOut` calls) or the account's removal marks it, and the next sign-in or
  reading begins the next. Only an account the history has met is marked. An `epochs.json` that does not read is left as found,
  and its readings say `epoch: null`. An organisation changed under one plan with no sign-out begins none: the organisation is
  not kept, even hashed.
- **What is never written.** A maker's name (a key, a scope, a plan) is kept only as a plain name: letters, digits and `_ . : -`,
  at most 64. `UsageHistoryRosterTests` drives an email, an organisation, a key and words through both seams and finds none.
- **Never a reason to fail.** An `IOException` or `UnauthorizedAccessException` is dropped inside, and the `windows.json` write
  follows as before.
- **The tool's own sign-in** is kept only from its asked reads, under `""`: its frames reach no `windows.json` either (D125 §3.7).
- **Two processes** append through an in-process gate only, as `windows.json` and a session's events do. Two Daoris processes
  writing one home's history at once could split or overwrite a line, which the reader counts as one that does not read.

What the checks do not cover: no real `get_usage` answer holding a `limits[]` row or a scoped week has been recorded, so those
parses stand on the evidence's field table. The Process halves were not run on this branch.

**Note, 2026-10-19 (USAGECAP1a2, every turn's tokens kept, with the model).** Point 2's turns log is built beside the readings on
the same writer (`Accounts/Usage/UsageHistory.cs`), with the model's reading in `TurnModels.cs` and the watch in
`UsageTurns.cs`. What the build settled:
- **The file.** `usage-history/turns-YYYY-MM.jsonl`. A turn writes every field, a null as null: `agent`, `account`, `epoch`, `door`,
  `session`, `seq` (the turn's event's `Seq` in the session's record), `started`, `ended`, `input`, `output`, `cacheRead`,
  `cacheWrite`, `model`, `split` (each `{model, input, output, cacheRead, cacheWrite}`), `attribution`, `whole`, `cancelled`,
  `meaning` and `reader` (1). `UsageHistory.ReadTurns` reads it back with the readings' gap rules.
- **The bound is the readings', shared, not a share of its own.** The 64 MiB counts both logs' files, and a month pruned for size
  goes from both at once, each log's gap said in its own; the age rule and the month being written stand for either. A month of
  readings without its turns, or of turns without the readings around them, is nothing point 4 can fit, and two caps would let
  one log keep months the other had lost.
- **Whose.** `Driver.Said`, which every driver start holding a session asks once (driven, intake, carry-on, an opinion's or a
  helper's pass), and the chat runner's start bind the session: the owner (AGT7), the profile's folder name or `""` for the tool's
  own sign-in, the door. A watch on the record (`UsageTurns.Watched`, once per record, from the loop's context and the chat
  runner) writes each turn it ends. A session no start bound (a brainstorm's or a meeting's pass, one begun before this process)
  is written with `agent`, `account`, `epoch` and `door` null. A turn is a session that ran: it begins an account's first epoch,
  or its next after a sign-out, as a reading does, and changes no plan. Bindings are held in memory for the process's life.
- **When.** `started` is the turn's ask where the session took it (a `user` event without `reaches`, as the machine log's
  `turn.ended` times a turn), null where this process did not see it; `ended` is the turn's event's stamp.
- **A turn heard twice is written once**, keyed by its session and `seq`, remembered per home as a reading's duplicate is.
- **The model rides the turn's event in memory only** (`SessionEvent.Models`, never serialized), so the session's record and every
  page still keep no model's name (D24, TOOL3). The native door names it by each top-level answer's `message.model` (a subagent's
  names none) and splits by `result.modelUsage`; the protocol door names it by the turn's `usage_update`s'
  `_meta["_claude/model"]` and splits by the response's `_meta.quota.model_usage`. The ACP option of category `model` is not
  read: its values are the adapter's aliases (`default`, `sonnet`), not the ids a split names.
- **A split is taken only where it agrees with the turn's measured total** on every kind the total reports: the models the
  answers named (or, named by none, the one entry equal to the total) sum to it. It is read first as the process's running total
  less the door's previous split (`attribution` `modelUsage-since`, `quota-since`), then as the turn's own (`modelUsage`,
  `quota`): whether `modelUsage` runs on across a process's turns is not recorded, and for a turn that ran only one reading can
  agree. Neither agreeing, `split` and `whole` are null and the named model stands (`message`, `usage_update`). `model` is the one
  model, `mixed` for several, `unknown` for none. A model switched mid-session is so split by turn.
- **A helper model's tokens** in the split and outside the total make `whole: false`, kept beside the total and never added in.
- **A cancelled turn** is kept, `cancelled: true`, its counts as reported: the protocol door's all-zero report stays no report
  (CONV5), so its counts, `split` and `whole` are null.
- **The meaning** is the door's own `HarnessToolchain.TurnReport`, never its owner's, since a report's meaning is its wire's:
  `per-turn` on Claude Code's native door and on claude-code-acp (CONV5's measure); `unknown` for Codex, dsh and every other door
  until a frame is recorded. On both Claude doors the cache counts are outside `input` (the evidence's sum).
- **What is never written.** A model's name is kept only as a plain one (letters, digits and `_ . : - [ ]`, at most 100); a split
  holding another is not written. `UsageTurnsTests` drives an email, an organisation, a key and words through the native door's
  frames and finds none.

What the checks do not cover: no frame on this machine holds `message.model`, `modelUsage`'s counts, `_meta.quota`'s counts or a
`_claude/model` beside a turn's end, so the doors' tests stand on the evidence's words and the SDK's declared `ModelUsage`; the
quota's counts are read by `usage`'s names, the SDK's and the API's. The Process halves were not run on this branch.
