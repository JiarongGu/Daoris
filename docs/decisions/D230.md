## D230 — A repository owns its context and reconciles with the canon through its own session's model; Daoris manages only the sessions it runs, each scoped to the session (2026-11-03)

**Decision (CONTEXTONE1, the owner's direction and answers of 2026-11-03; designed under D191; round 2, proposed for its reads).** It
follows `docs/2026-11-03-context-one-design.md`, with no second route (D228).

1. **The repository owns its context.** Its rules, skills, knowledge and setup are versioned files that work without Daoris, for any
   developer and any agent. *Doctrine works without a service* stands, and so do D13 and D19: drift is the disk against the lock.
2. **A canon update can be seen, and the canon is reconciled, not imposed.**
   - `daoris status` reports what a sync would update or add, whatever the stamps say.
   - The lock's canon digest orders the canons, and a newer lock is never rolled back.
   - A reconcile is a case of the set-up press. Its brief is composed offline by `daoris reconcile` and worked by a model in the
     repository's own session.
   - That session adopts each item, keeps it (recorded with its reason and the canon digest in `daoris.json`), or proposes it
     upstream (a quest's words to the canon's repository). It commits in its own line.
3. **Daoris manages only the sessions it runs, each scoped to the session.**
   - The driver composes one standing block, handed at the start and at a move, never on a resume. It replaces exactly the routing
     line, the standing answer's preface and the instruction's "where things are" pieces.
   - The whole first prompt is bounded by the native door's single argument.
   - The tools are loaded at the start.
   - The tree's skills and the per-session plugin copy are the skills. Auto-memory is off for the session.
   - No account home, vendor set or person's tool home is written.
4. **The standing answer stays the person's machine choices.** Its lines that state a repository's own rule move into that repository
   through its reconcile (amending D135 §3 for those lines only).
5. **Older shapes are converted by ONEWAY1's rows,** not here.

**Rejected:**
- doctrine served by Daoris alone;
- a sync that overwrites a repository's differences;
- a reconcile beside the set-up press;
- a C# copy of D19's table;
- writing into account homes;
- a block handed again on every resume.

**Note, 2026-11-04 (CONTEXTONE1d2, the owner's ask): the tools at the start are the session's own.** Point 3's tools load whole at
the start, so a session is listed only what it may call. The kind is the work of the record the session's `DAORIS_SESSION_ID` names,
which the connector already read to refuse calls; its one table, the call layer's (`CallTable`), now also filters `tools/list`. A
session working in a repository is served the core set (18 tools: knowledge, memory, quests, its line, the registry, a helper's ask,
the channel, handbacks) and its own kind's: a quest's session its go-ahead, question, hand-over, rule proposal, opinion answer and a
set-up step's two; a conversation the first four; a helper its answer; an intake none. Ask Daoris keeps every tool. Measured in
`CoreSetTests`: 28,341 characters of definitions for the core set, 39,229 at most for a repository kind, 102,191 for all 58. Rejected:
a second list passed on the spawn (the driver's kind would be a second table beside the one that refuses calls).

**Note, 2026-11-04 (CONTEXTONE1e): skills and memory scoped by the session's own settings.** Every Claude session's settings file
(`SpawnSettings`, the command-line tier on both doors) says `autoMemoryEnabled: false`, `syncClaudeAiSkills: false`,
`syncClaudeAiPlugins: false` and `disableClaudeAiConnectors: true`, and is written for every such session. Read in Claude Code 2.1.314's
shipped schema and code: from that tier the two sync keys stop and hide the account's synced skills and plugins for the invocation alone
and move nothing (a prune runs only when the key is false in user or managed settings), the connectors key wins from any source, and auto
memory reads the merged settings. So an account's home is never written. Left as they are: the build's bundled skills (the same for every
account; `CLAUDE_CODE_DISABLE_BUNDLED_SKILLS` would remove them) and any skill a person put in an account's own folder. Codex is
unchanged. Proof: `OwnContextTests`, two fixture accounts' spawns on either door handed the same settings and arguments, both homes
byte-identical after.

**Note, 2026-11-04 (CONTEXTONE1c): the standing block, composed by the driver for every kind of session.** Point 3's block is
`StandingBlock`, composed in Context from the plain `StandingFacts` each start sets: a quest's session, a helper, a partner, a reviewer,
an intake and a brainstorm's pass on `SessionTarget.Block`, a conversation and Ask Daoris on `ChatPlace.Block`. The facts sit in Agents and
the composer behind `IAgentContext`, since the structure gate orders Agents before Participants and Context. It ends the first prompt, after
the boundary or after the person's words. It says, in order:
- where things are: the repository's documents, code and history; the knowledge and memory tools; the checkouts the instruction lists; its
  indexes and code map;
- on a harness that loads none itself (`ISessionAdapter.LoadsTreeSkills`, false for Codex), the tree's skill folders;
- past a cut `AGENTS.md` (`InstructionFileLimit`, Codex's 32,768 bytes), the repository's rules by their knowledge ids;
- the routing, for a build, a design or a chat (`RoutingStanding` keeps the judge; its ROUTEQUEST1 words moved here);
- the person's choices (the standing answer, quoted; its preface's sense said once);
- the repository and workspace;
- at a move, the memory the line read, which the brief now hands on (`ComposedBrief.Memory`) and no longer says itself.

A kind with no repository gets the workspace's part alone: Ask Daoris and an intake the knowledge tools and the workspace, a brainstorm's
pass (which reads only its room) the workspace. Removed in the same chunk: the routing line (`SessionTarget.Routing`, `ChatMessage.Routing`,
`ResumeAsk.Routing`), the standing piece and `StandingText.Beneath`'s preface, and the map, look and indexes pieces, with their
said-absent sections. The look's behaviour sentence opens the asking section and points to the block. A go-on is the same conversation
and is handed no block. The account's section is `block` (source `machine`, cut `block-filed`); a conversation's record keeps
`chat.told-block`. The older codes (`map`, `look`, `indexes`, `standing`, `chat.told-routing`) stay declared and worded for the records that
hold them.

*2026-11-04, CONTEXTONE1b built: the reconcile, the keep and `upstream`'s request.*
- **The keep.** `daoris.json`'s `kept` maps a canonical file's target to `{ "reason", "canon" }`, the canon digest being
  that one file's as `canonDigest` hashes each (`keep.ts`'s `canonFileDigest`); one without a reason or a 64-hex digest is
  refused at the manifest. `sync` and `--force` pass over a kept file and carry its lock entry as it was, so the disk
  against the lock stays what the repository changed; a kept rule's span keeps its text when the region is rebuilt.
  `check` names each keep and never calls it drift; `status` names it apart from an update, with `reopened` once the
  canon's file moves, and lists a keep the canon no longer ships under `keepsDropped`. D19's kept rows, D4 and D71 are
  amended in their files: a core file kept absent is refused, a dropped keep leaves D19's retirement rows to apply, and a
  kept file waits out a move.
- **`daoris reconcile`**, a doctrine command at the root (`cli/reconcile.ts`; `fixtures/command-tree.json` is not in the
  tree yet, so the CLI's table and usage golden carry it). Offline and writing nothing, it prints a brief in the canon's
  words of only the differences: what `planChanges` says a sync would change, add or retire; the copies edited here; a keep
  reopened, held absent for a core file, or dropped; and the set-up gaps `check` reports (the root instruction file over
  32,768 bytes, the budget over, a room or a declared document absent, an own document no index lists, an own skill one
  agent alone reads). Each item has the canon text's path and the keep line with its digest; the brief says the direction
  (behind, or equal versions over another canon, where only the text can say which is newer), the three decisions, and
  the checks kept green. A newer lock is refused as `sync` refuses it; a repository never synced is refused.
- **`upstream`.** Only where the canon it reads sits inside the repository (`insideCanon`) does it write; elsewhere it
  prints a request's words for the repository that keeps the shared doctrine, carrying each file's text whole, and writes
  nothing. The region's preamble and `canon-authoring.md` name the route (neither text lives in `canon/`: the preamble is
  `tierrender.ts`'s, and `canon-authoring.md` is this repository's own); this repository and both examples are synced.
- **The press's case.** `SetupCase.Reconcile`, `SetupQuests.Reconcile` (so one is open per repository, beside any
  set-up), `SetupPress.PlanReconcileAsync` and `ReconcileBrief`. Its rule is `SetupPressRules.ReconcileVerbs`, the
  set-up's verbs with `daoris reconcile` and `daoris upstream --all`. The quest carries each line of the standing answer
  for the session to judge (D135's note). The desktop program has no hand-off that reads the CLI's `status --json`, so the
  case is offered for a repository the registry marks adopted, refused with `not-adopted` otherwise, and its body says one
  that finds nothing closes done.
- **Proof.** `keep.test.ts`, `reconcile.test.ts` and `upstream-request.test.ts` in the CLI, the usage golden;
  `SetupBriefTests` and `SetupPressTests` in the driver. Not built: a door that presses the reconcile (the place's adoption,
  the page), and the install run of one adopter reconciled on the owner's yes.

**Note, 2026-11-04 (CONTEXTONE1 follow-ups): the reconcile offered on the page, read from the tool's own status.**
- **The read.** `ISetupWorld.StatusAsync` runs `daoris status --json` in the checkout through the `daoris` a child finds, the
  one the press's tool check finds and the session runs: in an install the launcher whose program hands the doctrine commands
  to the CLI it carries (`DoctrineConsole`, `CommandWords.CarriedCli`). `DoctrineStatus.Parse` takes the tool's verdicts as
  they are (the update's direction as `behind` or `differs`, the lists' counts, the keeps `reopened`, `newerLock`); no table of
  the tool's is kept. `Offers` is an update or a reopened keep over a lock the tool may read.
- **The plan.** `PlanReconcileAsync` asks it of an adopted, synced checkout the tool runs in, holds it on the plan and says it in
  the body, which still closes `done` where `daoris reconcile` finds nothing. A newer lock is refused `newer-lock`, a status the
  tool did not print `status-unread`. A status that moved nothing refuses nothing, since the standing answer's lines are the
  reconcile's too (point 4): where it is offered is the page's door.
- **The door.** `RECONCILE_PLAN` {repository} (by event) and `RECONCILE_APPLY` {repository}, the person's press (the census's
  Person card, confirmed in the page; Ask Daoris proposes none). An adopted repository's place page draws the note between its
  head and its sections only where the plan offers it. The design names no *What needs you* row, so none is drawn.
- **The kept reads.** CONTEXTONE1c's retired codes are register entries: `handed-before-block` (the account's `map`, `look`,
  `indexes`, `standing`) and `chat-told-routing`, each waiting out CONTEXTONE1c's build, ended by no file of the home since the
  records are the service's and the logs every session's, deleted by `ONEWAY1af`.
- **Proof.** `DoctrineStatusTests`, `SetupPressTests` and `SetupBriefTests` in the driver; `DriverModuleReconcileTests`, and
