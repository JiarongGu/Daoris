## D230 — A repository owns its context and reconciles with the canon through its own session's model; Daoris manages only the context of the sessions it runs, one block on every harness (2026-11-03)

**Decision (CONTEXTONE1, the owner's direction and answers of 2026-11-03; designed under D191 and proposed for its reads).** It
follows `docs/2026-11-03-context-one-design.md`, with no second route (D228).

1. **The repository owns its context.** Its rules, skills, knowledge and setup are versioned files that work without Daoris, for any
   developer and any agent. *Doctrine works without a service* stands.
2. **The canon is reconciled, not imposed.**
   - Drift is judged by each file's content against the canon's, never by the stamp.
   - A reconcile brief, composed with no model, is worked by a model in the repository's own session.
   - That session adopts, merges, keeps (recorded with its reason in the lock) or upstreams each item, and commits in its own line.
   - On the install the reconcile travels as a quest. Nothing is written into a repository from outside it.
3. **Daoris manages the sessions it runs.** Each one gets:
   - one standing block, at most 12 KiB, composed by the service at every start, go-on and move, the same on every harness and
     kind, which replaces the per-kind prefaces;
   - its tools at the start;
   - one skill set on every account it runs in, with the account's own memory off.

   A session Daoris does not run, and a person's own tool home, are never changed.
4. **No repository rule lives in machine configuration.** Such a key reaches its repository through the reconcile and is removed.
5. **Older records and keys are converted once,** each with the condition that ends its reading.

**Rejected:**
- doctrine served by Daoris alone;
- a sync that overwrites a repository's differences;
- clearing context outside Daoris's sessions;
- a preface kept beside the block.
