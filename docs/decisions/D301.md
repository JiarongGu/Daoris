## D301 — An update waits on a run's plugin step in flight: a plugin's attempt recorded, sent or unknown on a run that goes on (2026-11-16)

**Decision (UPDATEINFLIGHT1, STAGENOTNOW1).** Idle, for an install's update, is also no run's plugin step in flight
(`PluginStepsInFlight`, area `install-home-update.md`, rule 39). In flight is an attempt whose step is a plugin's
(`<plugin>/<node>`) in the state `recorded`, `sent` or `unknown`, on a run that has not ended, that the runtime governs now at a node
its graph declares, while its plugin's process is up, and whose step waits on no role's act outside its plugin (a progress naming the
role, an approver or a deployer, whoever holds it). The loop counts them through its evaluation runtime and hands the count in its
work beside the driven sessions and the turns; the updater never reads the run records itself. A publish's `--stage --not-now`
writes the person's *not now* for the build before the build is visible, one act.

**Why.** On 2026-11-16 a staged build installed 22.6 s after staging while a run's release step ran beside it: the drain counted
only driven sessions and turns, so the swap cut the release's call off and its outcome was not known until the restart asked after
it; and a `--stage` followed by `update --cancel` raced the idle install. Only what the runtime asks after can settle: an attempt on a
record it does not govern, at a node no graph declares or of a plugin whose process is down is never asked after, so counting it held
the install for good.

**Rejected:** counting every attempt the home's run records keep (a retired repository's run, a version that no longer reads, a plugin
removed or crashing at its start each left one `unknown` for good, and the drain never ended); counting a `held` attempt, or one whose
step waits on a role's act (it waits on that act, not its plugin, and would hold the install until someone acted; its plugin's watch
resumes after a restart, so the swap loses nothing); telling a role the person holds from one an agent holds (the engine does not tell
them apart, D304); counting Daoris's own kinds (a check, a close, a request), which a restart asks after or sends again itself;
counting an ended run's attempt or a record that does not read (nothing moves either, so the drain would wait for good); a deadline
past which a sent attempt stops counting (the plugin may still be performing it; *Update now* is the person's way past a step that
never settles); a stage then a cancel for *not now* (the race itself).

**Left:** a plugin step a pass sends after the apply's second read of the work, just before the close, still meets it; the runtime's
starts during a drain are not changed here.

**Amended (2026-11-17, D309's fix wave):** a watch, a step whose plugin declares it acts on nothing outside (`perform.acts: false`),
never holds the install, since cut off it loses nothing and its plugin watches again after the restart; and an attempt whose outcome is
not known holds it for at most 15 minutes from when the loop first counts it so (`PluginStepsInFlight.UnknownBound`), then the install
goes on and its plugin is asked after it at the restart. A release's watch ran for up to two hours, and an unknown attempt had no bound.
