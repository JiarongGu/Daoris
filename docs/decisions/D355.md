## D355 — A repository's declaration keeps only what travels with it, as a folder of small files accepted gate by gate; what is the machine's lives in the home, learned (2026-11-20)

**Decision (GATESPLIT1; the owner's direction of 2026-11-20, designed through the brainstorm `gatesplit-1120`, Fable and Sol;
replacing the field rule of D350 and D353 and the acceptance of the whole file's blob; whether a change needs a yes is D354's
`command.change`).**

1. **One test sorts every member: must every clone hold the same value?** Then it is the repository's: tracked, reviewed in branches.
   Is it tuned to one machine, a private binding or a grant of power? Then it is the home's: per machine and repository, never in git.
   Is it the same for every repository? Then it is the product's: a default or the format's documentation. `daoris.gates.json`:

   | Member | Goes to | Why |
   |---|---|---|
   | a gate's `name`, `run`, `cwd`, `regenerate`, `handback`, `reuse` | repository | its commands and what its verdict depends on |
   | a gate's `paths` | repository | its reach, the same in every clone |
   | a gate's `clock` | repository | says its tests read the wall clock, a fact of the code; the priority that follows is the machine's |
   | a gate's `timeoutMinutes`, `timeoutWhy`, `memoryGb` | home | tuned to one machine's speed and memory, and learned there (point 4) |
   | a gate's `alone` | home | a load setting: whether a gate shares this machine |
   | `tests.sets`, each but its `timeoutMs` | repository | which files each runner runs, and how |
   | a set's `timeoutMs` | home | a timeout tuned to one machine |
   | `tests._why` and the format's other grammar | product | it documents the format, the same for every repository |
   | `tiers.needs` | repository | which code needs which tier |
   | `generated` | repository | a generated file and the command that writes it |
   | `reached` | repository | a command, its clock mark and its outcome line |
   | `doctrine` | repository | the doctrine's command |
   | `integration.merge` | repository | how its files merge |
   | `version.source` | repository | where its version is read |
   | `docs` (`changelog`, `graceDays`, `tracked`) | repository | its documents' rules; `graceDays` is a rule of the repository, not of a machine |
   | `sensitive.reviewedObjects` | repository | objects of its history reviewed once, the same in every clone |
   | `sensitive.patternsFile` | home | the place of a private file |
   | `localInputs` | home | private files of this machine bound into its trees |
   | `treeBaseline` | home | a tree's preparation is this machine's, set where its cost is paid (it held each open about four minutes, D298) |
   | `devkit` | home | the devkit this machine runs; the portable pin is `daoris.json`'s `source` |
   | `verifyBudget`'s `budgetMinutes` and `fullRunReasons` | repository | this workspace's own rule (D349), the same on every machine |
   | `verifyBudget`'s `overruns` | home | a journal of this machine's runs |
   | `unasked` | home, as the risk policy's rows (D354) | a grant of power, changed only through the owner's door, never by a branch |

   `daoris.json` stays whole in the repository: `source` (the portable canon pin), `packs`, `target`, `coreBudget`, `documents` (its
   `gates` pointing at the folder below), `domain` and `present` are the same in every clone. `daoris.lanes.json` stays whole too: its
   `lanes` and `laneless` travel, and only the grammar its `_why` explains goes to the product's documentation; the lanes are split
   only once their churn is measured, and never without a rule for which lane owns a path first.

2. **The repository's side is a folder, `daoris/`, one file per gate and a small file per other concern.** `daoris/gates/<name>.json`
   holds one gate (its commands, `clock`, `reuse`, `paths` and the test sets it runs); `tiers.json`, `generated.json`, `reached.json`,
   `doctrine.json`, `docs.json`, `merge.json`, `sensitive.json`, `verify-budget.json` and `version.json` hold the rest, one concern
   each. There is no index: adding a gate edits no shared file. Order keeps its meaning without one: a tracked test file held by two
   sets is refused unless one names the other by `of`, so which set holds a file never depends on order; where a reader depends on
   the order of gates today the converter finds it and the gate names `after`. The folder is tracked, apart from the ignored `.daoris/`
   runtime folder, and gets its lane and the `cli` gate's reach in the change that adds it. Agents edit it in branches like code.

3. **Acceptance per unit, by a digest.** Each gate file, `generated`, `reached` and `doctrine` is a unit. Its digest hashes its
   canonical form (members sorted, no whitespace) with only the named inert members set aside: the `_` explanations and the reach (a
   gate's `paths`, a set's `files` and `whole`). Every other member is in it, an unknown one included, so a part nobody named fails
   safe, as D350 found. The home keeps the accepted digest per repository and unit, and a run waits only on the units it runs. A change
   of a unit's digest is D354's `command.change` on that unit, and the judge's verdict decides: by the seed it passes under full access,
   recorded as standing by the policy, never as approved, and waits on the owner under restricted access. A change of reach alone reruns
   what it touches with no yes, and a narrowing (paths or test files dropped) is D354's `check.narrow`, said in one line on *What needs
   you* by the seed. The whole-file acceptance standing today is converted at first read, each unit's digest computed from the accepted
   blob, so no press is owed. It ships on the single file first, each gate entry a unit, and follows the units into the folder.

4. **The machine's values live in the home, per repository and gate.** The home keeps each gate's green wall times and derives its
   timeout from them by the product's factor and floor; a pin with its why stands over the learned value, and a learned value that
   rises past the product's bound is said once, so a gate that grows slower is never absorbed in silence. Beside them sit `memoryGb`,
   `alone`, each set's `timeoutMs`, the tree baseline, the devkit version and the overruns journal; the private bindings
   (`localInputs`, the patterns file's place) are set through the owner's door and never come from a branch. With no home the product's
   defaults apply. One door writes them, with a form in the repository's Setup and a CLI verb (`daoris settings checks`), as the workflow
   values are written (`SettingDoorsCensusTests`).

5. **One reader contract.** `daoris declaration --json [--at <commit>]` returns the resolved declaration: each gate with its commands,
   expanded reach, test sets, digest and budget, each value marked with its layer (repository, product, machine). The merge tool and
   the CLI read it; the readers that stay in process (the driver, the devkit) are held to the same answers by one shared fixture. The
   canon names only `documents.gates`. It needs no service: with no home it resolves with the product's defaults.

6. **Migration, one way per job.** One command, `daoris declaration split`, converts a repository in one commit: it writes the folder,
   moves the machine's values into the home through its door, deletes `daoris.gates.json` and points `documents.gates` at the folder,
   after proving that the new declaration resolves to the old one member for member (every gate's commands, its expanded reach, the set
   holding each tracked test file, the gates' order); a difference stops it and is named. Every reader refuses a checkout holding both
   formats, naming the command. A branch cut before the split converts its own edit with the same command. The older reader of
   `daoris.gates.json` is registered (`compatible-builds`) with its end: when no repository the home knows, and none of the examples,
   holds the file.

7. **The home's large files are measured before they are split.** For `files-found.json` and `landings.json` in the home's data:
   their writers, readers, keys and retention, the bytes rewritten per change, parse time, growth, and the share of entries nothing
   still owes. A later decision chooses on those numbers: a record derivable from disk becomes a cache rebuilt when missing; durable
   records split by life (the entries still owed apart from the rest, appended), or stay as they are.

**Why.** The file held 35 KB and changed in 37 commits in a week: branches conflicted on it, and each change, even a timeout's, stalled
every run in flight until the whole file was accepted again. Most of its churn was machine tuning (timeouts retuned, memory, load), and
its private paths named one machine in a tracked file. One file per gate lets two branches change two gates without meeting; a digest
per unit lets a change elsewhere keep the acceptance; values learned in the home stop the retuning commits; and one resolved reading
keeps the driver, the merge tool, the devkit and the CLI from parsing four ways.

**Rejected.**

- *Narrowest pattern wins instead of the first set* (Fable's layout): it changes which tests run without a word; overlap refused keeps
  the meaning.
- *Order files beside the folder* (Sol's layout): a shared file every new gate or set edits, conflicting as the old one did.
- *Acceptance per file by its blob*: a path or a pattern edited in a gate's file would stall its runs as today.
- *Acceptance by naming the members that run, or by semantic dependency hashes* (Sol's): a member added later keeps an acceptance
  nobody gave (D350's reason); setting aside named inert members fails safe.
- *Machine values kept in git with a local override*: two sources for one value, and the retuning commits stay.
- *`daoris.json` and `daoris.lanes.json` split too*: nothing in them is per machine, and the lanes' churn is not measured.
- *The older reader ended at a major release* (Sol's): no major release is one every home crosses; the census of known repositories
  ends it exactly.
- *`unasked` kept tracked*: a grant of power a branch could change (D354).
- *The home's files split by size now*: neither schema was read, and landings are records live runs depend on.
