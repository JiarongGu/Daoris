## D169 — The driver's state reaches every window as events a pipeline middleware publishes, and the page invalidates its queries at one place (2026-10-15)

**Decision (the owner's direction).** The owner, 2026-10-15: *"also the 采纳 status does not read properly when switching
tab (aren't we following the Shenora message pipeline with an event hub system? so we should maintain a proper state
server/client side; also this design allows plugins as middleware in the message/event pipeline)"*. The cause, read off
the code: after a done *Accept* nothing invalidated the session's landing plan (`keys.landing`) nor the driver's key, so
the old plan answered after a tab switch until a tick that saw a change (`DriverLoop`, DRIVER_TICK only on a change) or a
focus refetch past fifteen seconds; a press made in another window, or by the terminal, had no path to an open page at
all; and a press in flight lived in the one component that pressed it. `docs/DAORIS_FUTURE_DIRECTIONS.md` §38 (events as
the conceptual source of workflow state, no heavyweight framework) is the direction; this is its first build.

1. **The driver holds what is true and what is under way.** Its records (the files under the home, the service's ledger,
   the trees) are the truth. A window holds no copy of driver state beyond its query cache, and that cache is invalidated,
   or written, from the driver's events. What is under way (a landing, a discard, a sweep, a start) is the driver's to hold
   too, not a component's (point 7).
2. **A route declares what it changes, and the pipeline publishes it.** Beside each route's mark in its domain's handler
   class (`DriverRoute`), a declaration (`Publishes`, naming the route, since one handler may answer a plan and its press)
   says what a successful answer changed, as named scopes, and which payload field names the session the change was about
   where it is one session's (`Session`). A declaration naming a route its handler does not mark fails the module's first
   use, as a route marked twice does. `StatePublisher`, a `MessageMiddleware` in the
   application's slot of the kit's dispatcher after `OffTheWindow`, emits `DAORIS.STATE_CHANGED` on the kit's bus once the
   route has answered. A handler emits nothing by hand; a read (a plan, a list, a gate) declares nothing; a route nobody
   declared publishes nothing. The bus does not wait for its subscribers (`Emit`): the press's answer never waits on a
   window, nor later on a plugin.
3. **The event says what moved, never what it is now.** `STATE_CHANGED { scopes: string[], sessions?: string[] }`. A scope
   names a family of the page's queries in the driver's words: this slice's are `sessions`, `landing` (every session's
   plan and gate, its second opinion and what of them waits), `diff`, `handOff`, `sweep`, `treesSync` (which repositories
   hold Daoris's branches) and `lines` (each repository's rules); later ones are added beside them (`quests`, `asks`,
   `rules`, `registry`, `accounts`, `plugins`, `history`, `git`, …). `sessions` names the sessions the change was about,
   where the route named one; absent is any. It carries no words (a sentence is the answer's, to the window that asked),
   no answer, and no machine path: each window reads again through the query it already has. It is a wire shape: a scope
   or a field is added, never changed in place, and a page ignores a scope it does not know.
4. **Shell-only (D47).** The event is this machine's: the kit's notification pump forwards the bus to every window of the
   desktop (each with its own query client), and nothing forwards it to a service or a remote. A plain browser has no bus,
   and its queries keep their polling.
5. **A refusal answered as data publishes too.** The publisher reads the response's success, never an answer's `done`: a
   landing refused for a conflict fetched the line its plan reads against, a gate that moved answers as it now stands, and
   a list that was out of date is read again. An invalidation is cheap, and reading each answer's shape would tie the one
   publisher to every route. A refusal thrown as an error publishes nothing: the driver refused before it acted.
6. **The page invalidates at one place.** `bridge/stateHub.ts` maps each scope to the `keys` it invalidates
   (`sessions` narrowing the per-session families, `diff` and `handOff`), and `ShellSignals`, mounted in both roots,
   mounts it. So the window that pressed, a second window and a view mounted later all read the same cache the event
   invalidated. A mutation hook keeps only what writes its own answer into the cache (`setQueryData`, as `SET_LANDING`'s
   driver state) and what no declaration covers yet; an event that *is* the state, as `SESSION_QUEUED` carries the whole
   queue (D137), is still written whole where it lands.
7. **Operations in flight: decided, built after (STATEHUB1c).** First the kit's request tracker (`IIpcRequestTracker`,
   the `SHENORA.REQUESTS` module and its `REQUEST_UPDATED` event, read by `useShenoraRequests`): a press that outlives its
   grace period is listed by every window, so *落地中…* is shown by every view of that session and after a remount, read
   from the tracker rather than one component's `isPending`. Then a driver-owned registry of what is under way (which
   session, which step), told whole on each change as `SESSION_QUEUED` tells the queue, with a route a late mounter reads.
8. **The terminal's verbs: decided, built after (STATEHUB1e).** `daoris-driver trees land`, `remove` and `clean` run in
   another process, which has no bus of the desktop's. The loop learns of them from what they write (the landings record
   and the trees, or the request folder `SessionRequestWatch` already reads) and publishes the same `STATE_CHANGED` with the
   same scopes, so a terminal's press reads in an open window as a window's does.
9. **Plugins observe the pipeline, beside it: decided, built after (a row).** A plugin is a middleware in the event
   pipeline in the only way D64 allows one: a contained-observation hook point, `state/changed`, which the driver feeds
   from the bus and the plugin answers by stdio. Never a .NET `MessageMiddleware`, never code loaded into the host, never
   a view (D52), and never able to hold, change or refuse the route's answer.
10. **The rest of the routes, domain by domain (STATEHUB1d).** Sessions, conversations, work, rules, history, git, plugins
    and sync each declare what their presses change, and their hooks' hand-written invalidations go as they do. The tick
    stays the loop's own report of what moved without a press.

**Rejected: polling faster** (a shorter stale time, a refetch interval): a git look per window per interval on a machine
already loaded, and still the old plan for one interval. **Rejected: an emit by hand in each handler**: a list somebody
eventually forgets to append to, the reason `DriverModule` maps the driver's refusals once rather than at each throw; the
declaration sits beside the route's own mark and the publisher is one. **Rejected: a store held by the page** (a mirror of the
driver's state, or state kept in a view): a second copy in each window, which is the disagreement this removes; the query
cache already is the page's one copy. **Rejected: the new state carried in the event**: an answer is the asking window's
shape, with its sentence and what it asked; carried to every window it would carry words and grow with every route,
where an invalidation reads through the query each window already holds. **Rejected: the publisher reading `done`**
(point 5).
