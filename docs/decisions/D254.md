## D254 — A session works in its department's own place by default; isolation for parallel work is a workflow's step, and a department need not be a git repository (2026-11-10)

**Decision.** Each driven session grows a git tree of its own by default (D51, D167), and the trees, their landing and their tidy
are built for git alone. Its changes live in that tree until a landing carries them back, so what the person sees in the place is
not what the session changed, and a place that is not a git repository (a folder of documents, designs or spreadsheets, a system
reached through its web console) cannot be driven at all. The direction is reversed:

1. **In place by default.** A session works in its department's own place, the folder the department is, one writer at a time:
   the place's single process runs one session, and the next waits for it (driving rule 12's tree-less mode, made the default for
   every place). A change is where the person and the next session see it.
2. **Isolation is a workflow's step.** Work that needs to run beside other work in one place says so in its workflow: a node opens an
   isolated copy, the session works there, and a node brings the work back. For a git department the copy is a worktree and the
   return is today's landing; for any other department it is the mechanism the design chooses from the survey (a copy-on-write
   clone, an overlay, a snapshot, declared path claims). The trees, the tree pool and the landing become what those nodes run, not
   what every start does. A place's workflow is set per repository or workspace, so parallel work is that place's workflow choice,
   and how many sessions run at once there is configured with it. The design starts from the count living on the isolation step
   (a workflow with no isolation step runs one session at a time in place; one with the step says how many at once, its option
   like any node's), so a count above one without isolation cannot be said; a place setting beside the workflow is the alternative
   it weighs. The machine's cap still bounds every place.
3. **A department is any place.** Registration, the brief, the access setup, the workflow and review read a place, of which a git
   repository is one kind. What only git can give (a branch, a diff against a line, a push) is offered where the place is a
   repository and is a workflow's step there, never a precondition of driving it.
4. **Git stays the file control where a place uses it; it stops being the core.** Git is how most work controls its files today, so
   a repository keeps it whole: its history is the record, its worktree is that place's isolation kind and its landing that kind's
   return, and every git capability Daoris has stays. The non-git system (a writer's lease, a manifest per run, isolation providers and
   a merged return, the survey's first candidate) serves the places git does not. What changes is that the start, the brief and the
   workflow no longer assume a repository. The backlog's git rows go on as written.
5. **Designed before it is built.** The survey of isolation beyond git comes first, then a design that keeps today's git workflows
   working as one choice of the new step, then the rows it names. Until that design lands, today's trees run as they do.

*Rejected:* keeping a tree per session as the default and adding non-git places beside it, which would keep two ways to start a
session (D228) and keep the person's place out of step with the work; one isolation for every kind of place, since a folder of
documents and a cloud console have no common copy to make; dropping isolation altogether, which would lose parallel work in one place.

**Amends** D51 and D167 (trees by default), and the driving area's rule 12. **Held by:** PLACEWORK1.
