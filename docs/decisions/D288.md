## D288 — A release step acts only on a declared target: the step's options name the pipeline, the definition, the stage, the action and success by stable id; anything unresolved holds in the step with its candidates, a creation is bound to the merged build and never made twice, and an ask declares its cross-repository release order (2026-11-13)

**Decision (RELEASETARGET1, 2026-11-13).** Found on a real install: a repository's line fed three release definitions (one
labelled disabled that still created a release on every merge, one for a retired environment, and the real one, started by hand),
and the release step, which creates or starts a release on the forge for the merged build, could have started a stage nothing
should start; a person stopped the step by hand. Another line had no release for its merged build, and the step ended without
saying so where the person reads. One ask spanned three repositories whose releases must go in order, and each released after its
own merge. The steward decided from an independent proposal (Codex, on gpt-6.1-sol).

1. **A declared target.** A release step's options name, by stable id, the build pipeline, the release definition, the exact
   stage, the action (observe, start a stage, or create and then start) and what counts as success. A repository's values are
   options over the shared workspace workflow, never a forked copy of it. Discovery only proposes candidates; it never chooses.
2. **Everything resolved before any write.** No target declared, several matching, or the declared target changed: the step
   holds, listing the candidates, even one. No release for the build: an observe waits its declared period, then holds visibly. A
   release is created only where the action says so, bound to the exact merged build and reconciled after an interruption, so a
   retry makes no duplicate; the stages a creation triggers are disclosed before it. Every hold is a wait inside the step and shows
   in *What needs you* (`docs/2026-11-12-access-model-design.md` §4).
3. **A cross-repository release order is the ask's.** The ask declares it as edges between its own runs' release steps, on
   success only. The first build puts a person's gate before each downstream release, showing the order and the upstream evidence;
   a generic step that waits on another run's step follows.

**Rejected.**
- *Choosing the target by a definition's label, its trigger or the releases already made*: they describe the forge's behaviour, not
  the intent.
- *Ordering releases by the ask's channel or by a joint Accept*: neither keeps a downstream release from starting first.

**Held by:** RELEASETARGET1.

**Note, 2026-11-13 (D290, delivery across repositories).** Point 3's first build, a person's gate before each downstream release,
goes unbuilt: the order's edges are the ask's delivery plan's, each with its evidence, and a downstream release waits through
`wait.unit` on the upstream deployable's release receipt. A go, where wanted, is the workflow's `go-ahead`. Points 1 and 2 stand, the
target naming the deployable its node releases and the earliest act that deploys into it.
