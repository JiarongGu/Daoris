## D350 — A check runs under the accepted declaration unless the work's own change alters a command; a change that alters none keeps the acceptance (2026-11-20)

**Decision (GATEACCEPT1).** A run's check always runs under the `daoris.gates.json` the person accepted, read from its blob
(`CheckDeclaration`). It holds `changed` only where the work's own change, its declaration against the one where it left its line (the
merge base with the local branch of the line the acceptance look reads, `CanonicalLine`), alters what runs; a work that predates a
change on the line, or merged it since, is checked as accepted. "The accepted blob" is the one accepted now, whatever the work's base:
the person's word is the authority. Daoris starts only the commands the person accepted; they run the work's own code (its scripts, its
test sets). What alters what runs is one rule (`DeclarationCommands`), read strictly (a member written twice, a comment or a trailing
comma is no declaration, and waits): two declarations run the same where they are equal once their inert parts are set aside (members
named with a leading `_` at the top and directly inside a check, each check's `paths`, `timeoutMinutes`, `timeoutWhy` and `memoryGb`, and
the top-level `tests`, `tiers` and `docs`). A landed change that keeps every command keeps the acceptance as it lands, said in one
sentence naming what it set aside; any other is offered once in *What needs you* with the checks whose commands it adds, removes and
changes, and once it is accepted each check held `changed` is run again by itself (`ChangedChecks`).

**Why.** The acceptance guards what a work may run on this machine, not which commit carries the file. Comparing the work's blob with
the accepted one held every run in flight at each change of the line's declaration (four runs on 2026-11-20, one for 14 hours), and an
acceptance of the line's newest blob freed none of them, while the window promised work went on.

**Rejected.**

- *Run under the work's own declaration where its commands equal the accepted ones*: a third source of what runs; the accepted text
  runs the same commands and is the one the person read.
- *Name the parts that run (`run`, `cwd`, `handback`, `verification`, …) and keep the acceptance across every other change*: a part
  added later, or one only a tool reads as a grant (`unasked`), would keep an acceptance nobody gave. Naming the inert parts fails
  safe: an unknown part waits for the person.
- *Free the held checks at the acceptance doors*: four doors accept (the press, the terminal, the set-up review, a full-access line's
  landing) and a fifth keeps; one look comparing the acceptance a check held under with the one standing frees them whichever door moved it.

*Amended by D353 (GATEACCEPT2, 2026-11-20): this holds under restricted access only. Under full access (the repository's permission
prompts unrestricted) nothing waits: a work's check runs its own declaration as committed, the line's is taken as it lands and said in
one line, and a held check reruns once its repository takes full access.*
