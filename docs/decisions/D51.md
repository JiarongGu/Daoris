## D51 — The tree is the unit of exclusion, and a repository may have more than one (2026-09-21)

**Decision.** SURF1's first question, settled before any screen was drawn (the research named it as a
numbered decision rather than a layout choice). **The session lock keys on a working tree, and a
repository may have several trees** — a registered root plus session trees Daoris creates as linked
git worktrees. The mechanism is `docs/2026-09-21-working-surface-design.md` §2.

**Why this is a smaller change than it reads as.** "One active session per repository" was two claims
welded together. The first — *two agents in one working tree corrupt each other's git state* — is the
reason, and it does not move an inch. The second — *a repository has one working tree* — is not a fact
about git at all; it is a fact about how the registry was built, because `connect` runs in one
checkout and `Registration.Root` holds one path. Unwelding them keeps the guarantee and drops the
incidental cap.

**What it does not license.** D46 §9 stands: *wanting parallelism within one domain is a reason to
split the domain, not the tree.* The planner keeps its own rule — one **driven** session per
repository, oldest open quest first — because pacing a domain and preventing corruption are different
jobs with different reasons, and one mechanism serving both would silently make one answer the other.
What the second tree buys is **the person and the driver coexisting in one repository**, and the
person is not a second workstream; they are the operator. Parallel driven sessions, if real use ever
argues for them, are a change to the planner and not to the ledger.

**The rules that make it safe**, each argued in the design: the registered root is the only tree that
feeds knowledge, so WSP4's provenance model is untouched and a session branch is simply not the
canonical line; Daoris owns the *location* of a session tree and git owns its contents, the same
arrangement as a credential profile (D49 §4); a tree exists only on request, so silence means today's
behaviour byte for byte; a fresh tree holds nothing git does not track, and **the sentence that creates
it says so**, because the missing dependencies are the real price of this decision; the clean-tree rule
stays on the registered root and is vacuous in a fresh one, which is how a person's work in flight
stops holding the driver without a session ever being entangled with it; nothing merges itself and
nothing deletes itself; `connect` from a linked worktree is refused naming the main one, because a
registration re-pointed at an ephemeral tree keeps working right up until that tree is removed; and a
tree path is machine-local material carrying the transcript's three guards (D47 §4), since a path
leaks through whichever half somebody forgot.

**Rejected: keeping the repository as the unit.** Coherent, free, and already honest in its refusal —
rejected for what it caps permanently: the working surface's central act refused whenever the driver
works, the repository being actively edited undrivable forever, and "concurrent sessions" collapsing
into "concurrent repositories", which D46 already shipped. Nothing is deployed, and the unit of
exclusion is the worst thing here to retrofit once records exist — D48's "draw the boundary
deliberately rather than around data", applied one layer down.

**Rejected: a container per session** — the field's other answer. It isolates the toolchain as well as
the filesystem, which is more than the problem needs and more than this family can carry: every
harness, every credential profile and every repository's gates would have to live inside an image
somebody maintains. Git's own mechanism composes with what is already here; an image replaces it.
**Rejected: one directory switching branches** — it serialises exactly what needs to run at once and
destroys the person's working state on every switch.

### TREEDEPS1 — a new tree starts with its checkout's npm dependencies, copied (2026-10-19)

The price above was paid in full: each session tree of a Node repository ran `npm ci` from nothing,
170–221 s on the owner's machine, twice in one hour for one repository. **A tree now opens with the
dependencies its checkout installed at the same lockfile, copied in**, and only where they are
provably that install; every other part of the price stands, and the opening still says it.

**The gate**, per npm project (each folder of a tracked lockfile, judged alone): npm installs it, no
`pnpm-lock.yaml` or `yarn.lock` beside it; the tree's `package-lock.json` is the checkout's, byte for
byte; the checkout's install is at it (npm's hidden `node_modules/.package-lock.json` there and not
older than the lockfile, npm's own staleness rule); a workspace's own lockfile, where one has one,
matches too, and a workspace's own `node_modules` is copied with its project; and git ignores what is
copied, in the tree as in the checkout, so a copy never reads as the tree's work. A miss copies nothing
of that project and the opening says why, one coded line per reason; a repository with no npm project
says nothing more. `started.tree` keeps its words, since every opening recorded before said no
installed dependencies; a tree that holds a copy opens under `started.tree-copied`.

**A copy, never a link.** A session's `npm ci` deletes and rewrites `node_modules`, and its tools
write caches there (`.vite`, `.cache`), which a link would carry into the checkout; node resolves a
module through its real path. Copied under a name of its own beside where it goes and renamed into
place once whole, while the tree is still locked as opening, so a cut-off open leaves no half copy
(OPENCUT1's undo takes the tree; the copy deletes its own first). Caches at the top of a `node_modules`
are left behind, since each names where it was made. A link inside it is made again as a link leading
to the same place **in the tree**, and one that leads anywhere else declines the copy. 🔴 This is
load-bearing, not tidiness: npm links a workspace on Windows as a junction to its absolute path in the
checkout, and **`git worktree remove --force` follows a junction** (probed on git 2.53.0.windows.3: a
junction in a tree to a folder outside it, and the removal deleted that folder's file). A link copied
as it stood would have handed the checkout's workspace sources to the tree's removal. .NET's recursive
`Directory.Delete` throws on any junction here, though it removes it; the purge's never-following
delete does not.

**The agent is told.** The copy saves nothing if the session runs the `npm ci` it always ran, which
deletes it first: its instruction names what was copied and says to skip `npm ci` there unless that
folder's lockfile changes.

**Measured** (2026-10-19, a scratch copy of this repository's `src/Daoris.Web/node_modules`, 17,069
files and 228 MB): 20.7 s one file at a time, 9.3 s four at once, 5.9 s eight at once, 6.2 s sixteen;
its `npm ci` with npm's cache warm took 70 s. Inline, eight files at once, well under the minute that
would have moved it off the open's path.

**Rejected:** a junction or symbolic link to the checkout's `node_modules` (above); hard links, since
nothing shows that npm and every tool replace a file rather than write into it, and one written in
place would change the checkout's; warming npm's cache alone, which `npm ci` already reads and which
leaves the extraction and the install scripts, most of the time; copying off the open's path, which
the measurement does not need and which would start an agent beside a half copy; comparing the
lockfile modulo line endings, since bytes are what npm installed from (a checkout whose lockfile git
wrote with other endings copies nothing, which the opening says). Code: `TreeDependencies`,
`SessionTrees.OpenAsync`, `DependencyCopy.Told`; proof `TreeDependenciesTests` and four
`SessionTreesTests` rows.

*TREELINK1, 2026-10-19: a tree's removal never follows a link out of it.* TREEDEPS1's probe (above) found
`git worktree remove --force` following a junction in a tree and deleting the file it pointed at, outside the tree; the test
reproducing it found the unforced removal doing the same where the junction sat in an ignored build folder the checkout also
holds. **Decided**: before git deletes a tree's folder, on every path that has it do so (the removal, a landing's tidy, the
clean-up's press, an undone opening), each link in the tree is taken off as a link, its target untouched (`TreeLinks`): the
walk never enters a link, skips the tree's own `.git`, and looks at no more than a million entries, a bound a tree's installed
dependencies stay far under; it takes nothing off unless it read the whole tree. A tree it cannot finish, one whose link will
not go, or one whose own folder is a link, **stays, said**: removing it is never worth what git could reach. Forced or not,
since `--force` says to discard the tree's work, never what lies outside it. What a removal lets go with the tree is unchanged
(SQUASHTIDY1c); the links TREEDEPS1's copy makes inside a tree go as links like any other. The look's own
tidy and the strays needed nothing: they move a folder aside whole, and the purge takes a link as a link (D88's TIDIEDLINK1
note). **Rejected: deleting the tree with a walk of our own and letting git drop only its record**, as the set-aside does: it
would skip git's own refusal of an unforced removal with untracked work, the second check behind the proof. The FIX-LOG's

*TREELOCK1, 2026-10-20: a session's tree is locked while the session holds it.* DOGFOOD1's first finding (the FIX-LOG's
2026-10-20 entry): a session's tree is on a branch at its line's tip until its first commit, so its branch reads as merged and
its tree as clean, and a repository's own merge tool removed one mid-session. **Decided**: a driven session's own tree is
locked with git's own lock, `git worktree lock --reason "daoris session <id>"`, from its record's open until the session lets
it go, so `git worktree prune` and a `git worktree remove` without `--force` twice refuse it, whoever asks (`SessionLocks`).
Locked once the record is open, since the id is the record's, and while the start still holds the repository's trees for
starting (`TreeLock`); a resume, a carry-on or a further part in a tree an earlier session locked takes the lock over in its
own name, and a run going on in its own record (`DriverContinuations`) locks it again. Let go as the run ends, on no token,
unless the record still holds the tree: a park, or a run ended for a changed setup that goes on at the next look. The look's
tidy first lets go of every session lock whose tree no session running or waiting holds (asked again with the trees held
alone), so a record ended elsewhere (an orphan's sweep, a person's end of a park) never keeps one, and its own tidy, which
refuses a locked tree, takes it in the same pass. A lock whose reason names no Daoris session, a person's or an opening's
(OPENCUT1), is never changed or lifted. A tree git would not lock is the machine log's `tree.unlocked`, never a hold on the
start. **Not covered**: a conversation's own tree (`ChatRunner`) is not locked; the seconds between the opening's own lock

**Rejected: a lock the look alone keeps from the ledger**: a lock taken up to a pace late is the window this closes. Proof

*TREEGONE1, 2026-10-20: a session never runs with its tree gone.* A driven session resumed after a repository's merge tool

so the start is held for the person, said once on the record (`tree.gone`), its words left waiting, and no harness starts:
not in the checkout, a leftover folder, or a fresh tree on another branch. Not made for any other reason (git cannot list or
add it, another tree holds its branch, or it is no tree this home opened): held the same way (`tree.unmade`). A further part

### GITWORKTREECONFIG1 — the merge tool never writes through a tree git binds to another checkout (2026-10-29)

A `core.worktree` in the shared git configuration, under `extensions.worktreeConfig`, makes a linked worktree report the main
checkout's root as its own, so a `reset --hard` or `checkout --force` run in it acts on the main checkout's files (the tree link of
TREELINK1 gone wrong from the configuration side; `docs/2026-10-27-branch-recovery.md`). The merge tool asks git once per tree per
run for `rev-parse --show-toplevel` and, where it is another folder, refuses with a sentence before any write
(`treeBindingRefusal`, pure; `requireOwnTree`, the caller): in `prepareScopeTree` before its `merge --abort`, reset and forced
checkout, in `mergeMember` before its forced checkout, in `prepareGateTree` before its status and checkout, and in the prune's
`removeOne` and `removeGateTree`, where the tree is kept with that sentence. The tool runs no `git config` write: the value is
another tool's, and the person moves it into the owning checkout's own worktree configuration or unsets it.
