## D160 — A row is oriented by a scout and built by a worker, each with its own model (2026-10-10)

**Decision (SUBLOAD1).** The owner: *"first we do need to optimize the token usage by subagents"*. Offered
earlier compaction, they answered *"instead of compact we do need to optimize how it initial loads"*. On
models: *"let's try the best of practice, if Sonnet + Opus can have a better result Daoris managed session
should follow the same and also this should be configurable as multi model design purpose"*.

The measurement (`docs/2026-10-10-subagent-load-evidence.md`) covered 356 branches before this decision.
The median branch started at 50K tokens of context and spent 57 turns orienting. It reached its first edit
at 256K, then carried that load through its remaining 70 turns. Startup and orientation were 65% of the
weighted cost, and the work's own reading was 16%. Every turn re-reads the context, so a branch's cost
grows with the square of its turns.

So a row is now built by two agents, each defined in `.claude/agents/`:

1. **`branch-scout`** orients the row read-only and returns an orientation pack: the contract's sections,
   the knowledge `doc-loader` routed to, the code to change, the exemplar, the tests, the words read by
   tests a worker cannot run, the lanes and the row's size, all as file:line ranges. Its context is handed
   back, not carried. Pointing to a range costs one line, and quoting it would cost twice.
2. **`branch-worker`** builds the row from the pack in its own worktree. Its definition is the subagent's
   half of the brief, moved out of the dispatch skill, so the harness loads it as the worker's
   instructions. A worker therefore no longer reads the parent's half, and spends no turn loading a skill.
   Its tool set is limited to what a branch uses, to shrink the fixed startup. It reads by range, searches
   narrowly, batches independent calls, trims gate output, and hands back at the row's proof. It names the
   pack's gaps so the next pack improves.

The parent sizes a row to about a hundred turns and splits larger rows before dispatch. A branch of
100–200 turns cost three times one under 100, and one of 200–300 cost seven times.

**Each role's model is configuration**: the definition's `model:` is the default, and the Agent call's
`model` overrides it for one dispatch. The trial runs scouts on Sonnet. Workers run on Sonnet for a single
lane where the pack names the change exactly, and on Opus for design, UI, several lanes or a decision to
write. The parent keeps the session's model. Whether the split does better is measured, not assumed:
gates passing on the first run, review findings and the window. Cost is compared by
`tools/subagent-usage.mjs` against the evidence's numbers. If the split holds, Daoris's managed sessions
take the same roles with a model chosen per role (MODELROLE1, design first).

**Rejected:**
- **An earlier compaction threshold.** A replay put compacting at 200K at 56% of the cost. The owner
  chose a smaller initial load instead. Compaction drops a load only after turns have paid for it, and
  the harness's setting would also have applied to the parent's session.
- **Trimming only the startup.** Replayed, a startup 15K smaller saves 4.5%. The orientation that every
  later turn carries is the cost.
- **The parent writing the pack itself.** The parent's context outlives every merge of the day. A scout's
  context is thrown away when it hands back.
- **One model for every role**, chosen by guesswork. The trial measures the split before Daoris's sessions
  copy it.
- **Skipping discovery in the worker.** The scout runs the discovery skills for the row, and the pack names
  what they routed to. The worker reads those sections and runs the skills again when the scope leaves the
  pack (`skills-workflow`).

**Limits.** A custom agent definition loads only at the harness's session start, so the first dispatch
after this change is also the probe: its tools, its hand-back and its startup context (SUBLOAD1b). The
weighted figure compares runs on one model and is no price, so a Sonnet run is compared by its columns. A
wrong pointer in a pack costs a worker more than a missing one; the parent checks a pack before passing it on.

### SUBLOAD1b — the first scouts and workers (2026-10-10)

Three scouts (UXFIX2b, ASKHIST1d, ACCTUX4) and three workers (ACCTUX4's web half and ASKHIST1d1 on Opus,
UXFIX2b1 on Sonnet) ran from the definitions; `tools/subagent-usage.mjs` read their transcripts.

- **Both definitions load, with their model and tools.** A scout started at 25K tokens and a worker at 34K,
  against 50K for a `general-purpose` branch. Each worker ran in its own worktree. Every scout handed back
  through the harness's hand-back with the restricted tool list. A scout took 27 to 40 tool calls, 70K to 98K
  tokens and under two minutes, and its pack ran 50 to 70 lines.
- **Discovery was skipped.** Two of the three scouts never called `doc-loader`, and one wrote that it was
  not available, though the Skill tool was and each scout's startup listed it among 35 skills. The
  instruction was in the definition, and the Sonnet scouts passed over it. The scout's definition now
  preloads `doc-loader` and `pattern-finder` through its `skills:` list. Until a run shows the preload
  working, the scout's dispatch prompt also says to call `doc-loader` first.
- **Packs correct their brief.** The parent's scout prompt named a UXFIX2a that never existed. The scout
  found the pattern's real entry (UXFIX2) and said so. Every pack sized its row, and two rows split on its
  word (UXFIX2b into three slices, ASKHIST1d into a driver half and a web half).
- **A definition loads with the session.** The first probe failed because the `agents` folder was new. The
  harness's documentation says an edited definition is used at the next dispatch, but here the scout
  dispatched after the edit ran the body from before it (its prompt snapshot holds the old text). Treat an
  edit as live only after a restart, or after a transcript shows the new text.

### SUBLOAD1c — the trial's first rows (2026-10-10)

Against the evidence's median branch (127 turns, 57 before the first edit, 256K of context there, 375K at
the end):

| Row | Worker | Turns | Context at end | Gates on the first merge |
|---|---|---|---|---|
| UXFIX2b1 | Sonnet | 27, 8 before the first edit (69K there) | 103K | 8 of 8 |
| UXFIX2b2a | Sonnet | 20 | 80K | 8 of 8 |

- **The Sonnet workers built what the packs named, and the gates held.** Each hand-back carried its branch,
  counts and pack gaps in the brief's shape.
- **Both Sonnet workers edited through the shell.** UXFIX2b2a edited every file through `python -` heredocs
  and `sed -i` (9 edits), and UXFIX2b1 made 5 such edits. `file-tool-discipline` forbids both. UXFIX2b2a
  also wrote its tests after the code, against the brief's TDD rule. The merged files were checked for a
  changed line ending, a byte-order mark and an outsized diff, and none was found. The habit is not the
  model's alone: 112 of the 356 Opus branches before D160 did the same, 394 times.
  `tools/subagent-usage.mjs` now counts shell edits, leaving out searches and writes into scratch. Before
  the count existed, such an edit hid a worker's first edit from the load measure. The worker's
  definition says which tools edit, and so does every worker's dispatch prompt: UXFIX2b2b, told so in
  its prompt, had made none by its fifteenth turn.
- The Opus workers (ACCTUX4's web half, ASKHIST1d1) were still running when this was written.

### SUBLOAD1c — the first batch, built and merged (2026-10-10)

Eleven workers ran (seven on Sonnet, four on Opus), each with a scout's pack. Seven rows merged and three
more were built and waiting when this was written. Every merge passed its gates the first time, except one CLI
flake under load, which passed on a rerun (FLAKE1). Against
the evidence's median branch:

| Workers | Turns | Before the first edit | Context at it, at the end | Weighted per row |
|---|---|---|---|---|
| Before D160, Opus | 127 | 57 | 256K, 375K | 4.0M |
| Opus, design, UI or cross-lane rows | 75 to 96 | 26 to 28 | 114K to 151K, 201K to 235K | 1.7M to 2.2M |
| Sonnet, single-lane or named rows | 4 to 62 (median 18) | 1 to 7 | 35K to 67K, 37K to 160K | not comparable |

- **On one model the scout's pack halved a branch.** The Opus workers reached their first edit with about 140K of
  context against 256K and cost about half the earlier median, on rows the parent had judged hard.
- **The Opus workers still oriented for 26 to 28 turns** with a pack in hand. They read more than the pack named,
  where the Sonnet workers started within a few turns.
- **The Sonnet workers did the narrow rows well, but skipped process.** No gate failed on their work, and hand-backs
  kept the brief's shape. Besides the shell edits above, ACCTUX1b counted no tests before its change and ran
  neither `verify` nor `post-feature`; the merge's gates are what caught nothing missing. After the prompt's
  *How you work* line, no Sonnet worker edited through the shell (0 in 5).
- **The scout's preload works.** A scout dispatched after the definition was edited carried the edited body and
  started 2.7K larger, with `doc-loader`'s and `pattern-finder`'s text already in context. It routed without a Skill
  call. The scout dispatched minutes after the edit had run the old body, so a definition edit reaches a later
  dispatch, not necessarily the next one. The scout's prompt no longer names `doc-loader`.
- **Packs were right where they pointed.** Most hand-backs found every pointer right. The gaps were files the
  pack did not name: a test, a story, a twin's reader. One gap left a test looping over nothing (UX6i2a's
  `where.test.ts`), and its merge takes the fix.

The split's quality is judged on the window as well (UXFIX2bi, ACCTUX4i). MODELROLE1 waits for that.

### SUBLOAD1c — the second batch: told is not followed (2026-10-11)

Nineteen workers had run: fifteen on Sonnet and four on Opus. The Sonnet workers' median was 17 turns, 4 of them
before the first edit, with 50K of context there and 60K at the end. Every merge's gates held, apart from the flake
and one README freshness check that the merge itself answered.

- **The prompt's *How you work* line cut shell edits, and did not end them.** Before the line, both Sonnet workers
  edited through the shell (14 edits). After it, 5 of the next 13 made one edit each. One of those is the kind the
  rule names first: `sed -i '74,76d'`, a deletion by line offsets (RAILSRCH1b). Another was a `cat >>` append into a
  test file, which the first count missed; it now counts a redirect into a source or record file. Counted that way,
  139 of the 356 branches before D160 edited through the shell, 459 times. No Opus worker edited through the shell.
  UX6i3, dispatched after this was first written, made four `sed -i` edits and said so: 6 of the 14 told.
- **TDD is the step a Sonnet worker drops, even when told.** UX6g2a and RAILSRCH1b each said in the hand-back that
  they never watched their new tests fail, and ACCTUX1b counted no tests before its change. All three said so
  plainly, and the merge's gates held, so what the skipped step costs is the proof that a test can fail, not a
  green merge. The Opus workers each reported failing first.
- **What follows.** A rule an agent must keep, and that a transcript shows it dropping, belongs in a mechanism, not
  a sentence. The count now sees redirects as well. Whether a hook should refuse a shell edit in a branch-worker
  is the owner's call, and it waits for the trial's end (MODELROLE1).

### SUBLOAD1c — failing first, counted (2026-10-11)

D161 put the shell-edit rule in a hook (`tools/shell-edit-guard.mjs`). The next dropped step is watching a test fail
first, and the hand-backs count it. Of the Sonnet workers after the prompt's *How you work* line, six said they never
watched their test fail: UXFIX2b2a, UX6g2a, RAILSRCH1b, UXFIX2b1r and ENTRY1h, and UX6i3, whose change was comments
only. Each Opus worker named the tests it saw fail first. Every merge's gates held either way.

A mechanism is possible: a hook is handed the session's transcript, so one could refuse a worker's first edit to a
source file until the transcript shows a test run that failed. It would also refuse a row that changes no behaviour (a
comment, a sentence, a record), which needs no failing test. Whether to build it, and which rows it spares, is the
owner's call (D161 §1).
