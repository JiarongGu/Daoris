## D26 — Gates are declared in a file the devkit owns, not in `daoris.json`

**Decided 2026-08-05, settling DEV1.** `daoris.json` names *which* devkit version a repository uses.
What to run lives in `daoris.gates.json`, which the CLI never reads.

**Why.** Every field in the manifest today is a noun: a source, a list of packs, a target directory, a
byte budget. It is inert data, and the CLI's whole safety story rests on that — it never executes
anything and never opens a socket, and there is now a test for each. Gates are verbs. Putting command
strings into the manifest makes the file the CLI parses on every invocation into a file that contains
things that run, and the next reasonable-sounding step is "since we already parsed them, let `daoris
verify` run them".

Splitting on noun/verb keeps the boundary visible instead of merely observed. The manifest still pins
the devkit — a version is data — so there is exactly one place to look for *which* toolkit, and exactly
one place for *what it does*.

**Not chosen: one file for both.** Fewer files is a real benefit and it loses to the above. A reader of
`daoris.json` can currently be certain nothing in it executes; that certainty is worth more than the
saved file.

**Built 2026-10-07 (GATE1b): with a merge open, the docs gate judges the commit the merge would make.** GATE1
found the gate blind to a merge gated before it is committed: it dated each side by `git log -1 -- <path>` from
HEAD, still the branch being merged into, and this repository answered with a wrapper, `tools/as-merged.mjs`. The
devkit now does it itself: when a `MERGE_HEAD` exists, `ProposedMerge` in `DocsGate.cs` builds that commit (the
checkout as `git add -A` would stage it, on HEAD and each `MERGE_HEAD`, on a copy of the index, named by no ref)
and the gate logs each path from it. The verdict says so, and a merge with unmerged paths fails the gate naming
them. Outside a merge the gate runs the same `git log` and says the same words. `DocsGateMergeTests` holds both
sides over real repositories; the devkit README's *`docs` during a merge* says it for adopters.
**Chosen over documenting the wrapper** because the blindness is the gate's, and every repository gating a merge
before committing it would otherwise have to find the wrapper after its main went red. The change stays in the
gate's own file and leaves the run outside a merge as it was. **Not chosen: dating every path the merge changes as
today**, the smaller-looking form. Once the merge is committed, `git log` dates a path the merge took from one side
by that side's commit. Dating it as today would fail a merge whose README the other side updated later, and pass a
branch that had already left its README behind. The wrapper stays, and this repository's gates still run the
devkit through it, where the devkit sees no merge and HEAD already the commit; the docs gate no longer needs it.
