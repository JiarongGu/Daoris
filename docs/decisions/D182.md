## D182 — The .NET host owns the machine's state and pushes it, with its data, to the windows, the way the owner's other .NET shells do; the page renders what is pushed, and the domain's judgement lives in .NET once (2026-10-19)

**Decision (the owner's direction).** The owner, 2026-10-19, after D181: *"not the fabric events design, it's more the regular
event design from other .NET shells"*, *"I think you heavily develop things running in TS rather than in .NET"*, and *"yes,
please refactor and build this properly, since this is our bottleneck"*. The UI kit Daoris is built on carries that design:
correlated request and response for commands, and host-to-page notifications that carry their data
(`IpcNotification { module, type, payload, scope }`), batched by the kit's `NotificationPump` (50 ms, a bounded queue that
drops its oldest). Daoris uses the kit's bus but chose the opposite rule (D169 point 3): `STATE_CHANGED` and `DRIVER_TICK`
say what moved, never what it is, so every window invalidates query families and pulls again; one tick re-read about
seventeen lists, several running git across every checkout (IDLECPU1). Measured: C# product code about 218,000 lines, the
page's 79,000 with 80 `useQuery` pulls, the CLI's 27,000 carrying twins of .NET logic. A read-only Codex opinion on the
shape, its consistency, its threading and the migration was taken; this entry adopts it.

1. **.NET owns each slice of the machine's state, once.** Files, git and the database stay the truth; each slice's
   in-memory projection is a rebuildable judgement of them, with one owner shared by the desktop and the headless host,
   kept by the background judges D181 runs (bounded workers, one judgement per subject, independent topics at once). A
   snapshot is immutable and swapped under a short lock; nothing slow runs under a lock or on the UI thread.
2. **Judged state is pushed with its data** (amends D169 point 3 and the events design's A1 "never a fact" for this
   path). Source events still wake judges; a judge's committed state goes out through the kit's pump as a notification
   carrying an approved projection: an allow-listed DTO, never a credential, an arbitrary request payload or a machine path
   outside a desktop-only projection, coded verdicts with their values (the page translates the chrome and shows authored
   text as written). Command answers are not broadcast. Invalidation notifications stay for slices not yet moved and for
   plugins.
3. **Versions make it safe.** Each partition carries `{ epoch, seq, status, data }`; a delta names its `baseSeq` and its
   removals. A late or reordered push never regresses a window: a full replacement may skip sequences, a delta needs its
   base or the window requests that partition's snapshot. A judge's stale completion is refused by its input's generation.
   A window subscribes before it asks its first snapshot, buffers, installs the baseline, then applies newer pushes. A small
   version manifest is pushed periodically through the same pump, so a dropped batch, including a lost final update, is
   repaired by one bounded resync; a mismatch after a resume or a remount does the same.
4. **Every window keeps its own projection cache; more windows never mean more judges or more git.** Where an action's
   availability depends on several facts agreeing, one composite projection is published, not several to be joined.
5. **Writes that bypass the host still reach the windows**: an agent's connector writes the database directly, so the
   service's change stream (FABRIC-EVENT3b) wakes the owning judge, which rereads and publishes; its coverage grows to the
   families it misses, with reconciliation kept behind it.
6. **The domain's judgement lives in .NET once**: grouping, attention verdicts, eligibility, rule resolution, milestones,
   capacity, usage curves, account listing and the home table's twins. The page keeps rendering, accessibility,
   translation, selection, filtering, sorting and view state. The doctrine CLI stays offline and independent of .NET; the
   CLI's management verbs become clients of the running instance over D171's pipe (the same handlers, refusals and
   publications), or, with no instance, the same .NET implementation under the home lease, never a re-implementation in
   TypeScript, and never a standalone retry after a request whose result is unknown.
7. **The page's store is its existing query cache, fed by the pushes**: no second state library, no new bus, no
   event-sourced database. Each moved slice turns off its broad invalidation and its refetch on focus; an older host keeps
   the pulls (capability per slice).
8. **Measured on the installed app, never declared**: CPU, UI latency, git starts, bytes pushed and judgements, with
   several windows open.

**The migration, smallest first with the biggest win** (each its own row): PUSH1a, the push path (versioned partitions,
first snapshot, buffer, manifest) with its first slice, the driver's choices, holds, operations underway and sync
standing; PUSH1b, the resolved lines and repository rules, from PARALLEL1a's machine-facts service; PUSH1c, sweep
summaries, work milestones and session groups; PUSH1d, sessions, quests, asks and attention on the change stream; PUSH1e,
accounts and usage, with their twins moved into .NET; PUSH1f, the CLI's management verbs as clients of the running
instance (D171 point 3).

**The traps**, each a test its slice owes: reversed delivery never regresses state; out-of-order enqueues keep the newest
and deltas are never coalesced; a dropped final update is repaired by the manifest; a hostile field in a fixture never
reaches a projection (the allow-list) and no workspace leaks into another's; unchanged reconciliation publishes nothing;
and success is the installed app's numbers, not a test's.

**Rejected.**
- **Keeping wakes-only events with smarter invalidation**: every window still pulls, and pulls still run git.
- **Another bus, a reactive framework, a second page-state library, an event-sourced database.**
- **Broadcasting command answers**, and **pushing bulky detail** (diffs, commit graphs, blame, document bodies, search
  results, transcripts, raw usage samples, detailed plans stay on demand).
- **The page or the CLI deriving the domain's verdicts in TypeScript**.

**Amends D169** (point 3: judged state is pushed with its data), **the events design's A1** (an event wakes a judge; the
judge's state carries data), **D171** (point 3 is how the CLI's management verbs reach .NET). **Held by:** the PUSH1 rows,
measured on the install.

**Note, 2026-10-19 (PUSH1a, the push path and the driver's state).** Built for every slice to come, the driver's state first.

- **The host half** (`Platform/StateSlices.cs`). A `StateSlice` is one owner: a judge function returning named partitions, each
  compared with what was last pushed as the wire writes it, a changed one numbered and pushed whole, one no longer judged
  pushed `gone`, an unchanged one (a reconciliation's too) pushed nothing. A wake only writes one waiting wake; the slice's
  worker judges at once, at each wake, and at its period (15 s) judges again and tells the manifest. One judgement at a time is
  the ordered outbox: every push and manifest is told by the judgement that numbered it, outside the snapshot's short lock, so
  a stale completion cannot exist and the pump receives them in order. `StateSlices` finds a slice by name; the shell's loop
  runs them from `Start`.
- **The wire.** `DAORIS.STATE_PUSH { slice, epoch, partition, seq, status: ready|gone, data, baseSeq?, removed? }`, coalesced by
  the kit's pump per partition (a whole replacement; a delta never sets the key), and `DAORIS.STATE_MANIFEST { slice, epoch,
  partitions: [{partition, seq}] }`, coalesced per slice. The snapshot is the driver's route `STATE_SLICE {slice}`: `{ slice,
  epoch, status: ready|notJudged, partitions: [{partition, seq, status, data}] }` from memory, never judged for the asking, and
  nothing for a slice this Daoris does not push. Wire shapes, added to and never changed in place.
- **The page half** (`bridge/slices.ts`), kept beside each window's query client. `ShellSignals` hears both events, then asks
  each slice's snapshot (in both roots, the secondary root mounting it first so its views wait for it); pushes heard before the
  answer wait (64 at most) and the newer apply after it; a push numbered at or below what is held changes nothing; a delta off
  its base, or of a slice with no merge, and an owner of another epoch, read the slice again; a manifest is read once its
  batch is applied (the pump keeps a coalesced push in the later place) and a number the window does not hold reads the slice
  again once. A host that refuses the route or answers nothing leaves the slice pulled, as before; `notJudged` pulls until
  the first push.
- **The first slice** (`Loop/DriverStateSlice.cs`): `STATE`'s own answer (one builder, so the pull and the push cannot
  drift), allow-listed into `shell` (ready, the home and its two notices), `choices` (everything `driver.json` says that a view
  reads, holds among them) and `running` (what runs, who drives the browser, the set-ups in review). Never pushed:
  `configPath`, `cap`, `adapter`, `pollSeconds`, `released`, and a press's own `retried`, `reviewed`, `shownAgain`; a field
  `STATE` comes to answer fails `DriverStateSliceTests` until it is classed. Woken by the look, a `STATE_CHANGED` naming
  `driver`, `sessions` or `harnesses`, `SESSION_ENDED` and `DRIVER_READY`. The home is a machine path: this projection is
  desktop-only (point 2). On the page `useDriver` reads it from memory once live (no focus refetch, never stale), the tick's,
  the hub's and `DRIVER_READY`'s invalidations of the driver's key pass over it (`notPushed`) and still ask what is read beneath
  it, and a press's answer is written only where the state is pulled, the push being its one writer.
- **Left, each a row's.** Sync standing: its truth is the service's `/api/sync`, which a plain browser reads too, and its
  `tried` moves at every pass, so a driver judge would read every circle at every look; it moves with PUSH1d's change stream
  or a pass-result projection. `UNDER_WAY` stays its own whole, numbered telling (D169's STATEHUB1c notes), already this
  shape. The notices are still the driver's sentences, not codes. The owner lives in the modules beside the loop it reads;
  it moves into the driver library when a headless consumer needs it (PUSH1f).
- **Measure on the install** (point 8): the page's bridge reads per minute idle and on a change, before and after, with two
  windows open; `STATE` should be read once per window at most and never at a tick.

**Note, 2026-10-19 (PUSH1b1, the resolved lines and repository rules, the host's half).** Built: the `lines` slice
(`Loop/LinesStateSlice.cs`), judged from PARALLEL1a's machine's facts and `driver.json`, with no git and no service call.

- **One builder, two doors.** `LINES`' answer is `LinesRoutes.Answer(rows, config, adapters)`, the six resolutions and the wire
  helpers beside it; the route writes it over the lines git resolved, the slice over each repository's rows. The line itself is
  `CanonicalLine.Judged` (what is set, with no checkout what is set alone, else the checkout's guess as the facts judged it, null
  where it was not judged yet), which `HelpFacts.Read` reads too, so Ask Daoris's room and the slice cannot disagree. `LINES` keeps
  answering, field for field as before (an older page pulls it); `LinesStateSliceTests` classes its fields against the slice's.
- **The partitions, per repository and named by it**, each `{lines, landings, languages, reviews, opinions, helpers, commits}`
  holding that repository's rows, `{repository, workspace}` keyed as `LINES` answers them: a refs move judges one repository's
  line (`HelpFacts`), so it pushes one partition, and a line set for a workspace pushes only its repositories'. A repository whose
  checkout's guess was not judged yet is pushed with its rules and a line row `branch: null, source: none, notReadYet: true` (the
  room's *not read yet*; the page reads the flag before the source), never left out, which would read as removed; one the
  registry no longer names is pushed `gone`. No path: a row names its repository and its workspace.
- **First judgement and wakes.** The slices start at `DriverLoop.Start`, the facts once the service answers: a judge may now answer
  null, *nothing to judge from yet*, which leaves a slice `notJudged` and pushes nothing (`StateSlice`), so no window holds an empty
  entry as the truth. A slice may also be handed `Hears`, hearings that wake it while its worker runs: this one hears the facts
  landing (the service's answers or a repository's guess, by the value's reference, a snapshot told after a newer one passed over;
  the sessions, the history and the work wake nothing), and its bus wakes are `STATE_CHANGED` naming `driver`, `lines` or
  `harnesses`, and `DRIVER_READY`. A terminal's `daoris driver line` reaches it through the home's watch (the config topic, through
  `DriverWatch.Heard`), which judges the service's answers again, whose landing wakes it.
- **The registry, settled.** A registry change moves no ledger family, so the service's answers reach a new repository at their
  deadline (one minute, the facts' ten-second look on top). A change a press declared (`STATE_CHANGED` naming `registry`) has the
  slice's owner judge them again at once, so a window's import is a partition at once; a terminal's import, which no event tells,
  waits for that minute where `LINES` saw it at the next tick's pull. The tick already reads the registry (`DriverLoop`'s
  `lastRegistered`): its change waking the service's answers is the row that closes it.
- **Left.** The page's read is PUSH1b2: until it lands no window reads the slice, and nothing changes for a person. Measure on the
  install (point 8) once it does: `LINES` read at no tick, the slice's judgements per refs move.

**Note, 2026-10-19 (PUSH1b2, the page reads the lines pushed).** `linesSlice` (`bridge/lines.ts`) composes the partitions, in
repository name order, into the seven arrays `LINES` answers; `useLines` reads it through `readPushed`/`usePushedLive` (never stale
and no focus refetch while live), and `ShellSignals` mounts it in `PUSHED`. No press wrote `keys.lines` (the `SET_*` answers
write the driver's state), so `writeAnswered` needed no change. Nothing judged yet composes nothing, so the pull stands until the
first push; a `gone` partition leaves with its rows. A line row's `notReadYet` is read before `source`: the repository's Setup says
*line not read yet*, and Ask Daoris's machine reading does not count it among the repositories whose line names none. Counted in
`pushedState.test.tsx`: a tick and a focus read neither `LINES` nor `STATE_SLICE`, a push changes the lines with no read, a second
window asks one snapshot per slice. Left: the measurement on the install (point 8); `RepositoryLine`'s `notReadYet` is typed in
`settings/Lines.tsx`, which this lane touched for that one field.
