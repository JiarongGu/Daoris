## D156 — A door only the person may use: the local host gates its writes on a key minted for each start, held by the window in memory and never by a session; a terminal asks the window to confirm; and what a session reaches beyond the doors is said, not assumed (2026-10-09)

**Decision (PERSONDOOR1).** A second agent's (Codex's) read-only review of D154's record claimed seven defects.
REVIEWENV1b3 fixed six, and left the seventh: the local host trusts the loopback (`Program.cs:309`), every session is
handed its address (`DAORIS_SERVICE_URL`, `Adapters.cs:1149`), and so one `curl` from a session's shell keeps a skip of
a review, a yes, a go-ahead's answer or the person's own words as the person's. The contract is
`docs/2026-10-09-person-door-design.md`.

1. **The person key** (design §2). A random 256-bit value, minted for each start of the host by whoever starts it, and
   held in memory by that starter and the host. The starter hands it on the host's first input line
   (`DAORIS_PERSON_KEY_ON_INPUT`), the channel only it holds; a host handed none mints its own and prints it once. It is
   presented as `Daoris-Person`, compared in constant time and sent only to a loopback address. Daoris never writes it
   to a file, an environment, a command line, a URL, the page's storage or the log; only a person with no window, or a
   gate playing one, puts it in a terminal's environment.
2. **Who holds it.** The window: the shell mints it, proves its own host holds it before use (`/api/status?prove=`),
   presents it from its modules and its driver loop, and answers it to the page over the bridge, kept in memory there. A
   host the shell adopted gets none, and the window says so. On a machine with no window, the terminal the person gives
   it to (`DAORIS_PERSON_KEY`), and the gates that start their own hosts. **Never a session**: it is not in the shell's
   environment, every start Daoris makes removes the name, and no file holds it.
3. **Which doors are whose** (design §3). Authority is the key's; attribution is the body's, which may narrow and never
   widen. Without the key the caller is an agent. Reads stay open (18). An agent's doors stay open and are judged as an
   agent's (3): `respond` without `whileOpen`, and a keyless publish at `POST /api/quests` or an ask's publish, which is
   `byAgent`. The driver's own take the key and are recorded as what it read (11, and `set-up` naming a session):
   evidence, session records and states, sync, a registration, refresh. The person's alone take the key (19, and
   four forms): the review and their own set-up, the set-up step, every door that sets a review, the yes and the done,
   `whileOpen`, go-ahead answers, their words on an ask, closes, deletes, clears and re-wiring. An unclassified write is
   refused, held by a test that lists every route the local host maps.
4. **The terminal cannot be told apart** (design §4). A session can run `daoris-driver` and `daoris`, and nothing a
   binary reads tells whose run it is, so neither holds authority by itself. With a window, a keyless call is refused,
   and the client asks: `POST /api/confirmations` with the exact request and a secret's hash; the window shows it in the
   host's terms with *Daoris cannot tell whether you ran this or an agent did*; the person's **Confirm** lets the client
   send that request once, within two minutes. Five may wait. With no window, the key in the terminal's environment,
   whose costs are said where it is printed.
5. **What the record says** (design §5). An act recorded as the person's was taken behind the key or a confirmed grant.
   A publish gains `byAgent` where an agent named no session, so an agent's publish no longer reads as the person's;
   additive, and a record from before reads as it did. The machine log gains `person.refused` and `person.confirmation`,
   codes only. A refusal is `403` with a sentence and a code (`person-only`, `driver-only`, `stale`, `grant`,
   `confirmations-full`), never a `500`.
6. **A shared host is unchanged** (design §6). It maps no door that is the person's alone, its minted keys (D47 §7) stay
   its gate, and it never reads a person key. What it trusts is a machine's key, which a session's connector holds today
   for a claim by push (D69); PERSONDOOR2 moves it.
7. **What a session reaches beyond the doors is said, not assumed** (design §1, §7). This defends against an agent's
   ordinary reach: what its environment, tree, repository, tools and the home's files hand it, and every command it runs
   against the doors. It does not defend against the account's own reach: another process's memory, injection, UI
   automation of the window, the store's file (the connector opens it, D36), the home's files (`daoris agent rules
   accept` run by a session widens its own rules), or a dev run's debug port. A harness's permission rules narrow
   ordinary reach and never tell the person from an agent. Only a boundary between the person and their agents closes
   the rest, and PERSONDOOR2 designs it.

The build is PERSONDOOR1a–i, the design's §10, ordered so that main keeps working: a host enforces only once a starter
hands it a key, the clients and the page learn the key before the shell hands it, and a bare host enforces last.

**Why.** The review's verdict, the yes, a go-ahead's answer and the person's words are what the gate and every later
session read as the person's (D133, D135, D154 point 8). A door any process on the machine can call makes each of them a
self-report, and the record cannot say otherwise. Every session is told the host's address, and stubs use it as their
door on purpose, so the loopback's trust (D21, D47 §7) held only while nothing Daoris started was on it. The starter's
input is the one channel no other process is handed. The key per start costs nothing to configure. The window already
holds the bridge, which carries every other act of the person's, so the key there adds no reach. The terminal's
confirmation keeps the key in one process, and it puts what a session asks in front of the person, where a refusal is
their default.

**Rejected.**
- **Loopback trust as it is.** D47's amendment retired D36's single configured write key because two credential stories
  drift and the weaker wins. That key was static and the same for every writer. This one is minted per start, never
  configured, and read by local hosts only, which never read a minted key.
- **A file under the home**, with an ACL or sealed with DPAPI: any process of the account reads it.
- **An OS identity**: a named pipe's client or the socket's owning process is the same account, and the caller's
  ancestry is the shell's for every session. The real boundary is another identity for sessions, PERSONDOOR2's.
- **The `Origin` header**, which any process sets.
- **Positive identity for agents instead**: absence would mean the person, REVIEWENV1b3's defect, and a start that forgot
  its token would make an agent the person.
- **The key in the shell's environment or the host's**: every start copies its parent's, and Linux reads any
  process's. **In the page's storage, a cookie or its URL**: each is on disk in the engine's profile.
- **The engine adding the header** for the page: unmeasured, and no safer than a script that already holds the bridge.
- **Signing each request** instead of a bearer key: the proof of possession and a key per start already guard a port
  someone else took.
- **The key shown in Settings, to copy into a terminal**: it would reach every process started there, an agent the person
  runs by hand included.
- **The account's password at the terminal**: Daoris would hold it, and every verdict would cost it.
- **A keyless call becoming a confirmation by itself**, and **every refusal shown in the window**: a session could fill
  the person's attention. The client asks explicitly; refusals are logged.
- **Every keyless act of the person's turned into a proposal**: a verdict, a yes or an answer has no proposal form, and
  agents have go-aheads. Only the publishes have an agent's form.
- **Gating reads**, which the connector answers anyway; and **a field on every operation saying it came from a
  terminal**, which would travel and tell a teammate nothing.

**This amends:**
- **D47 §7, as amended**: a local host gates its writes on the person key. The shared host's gate is unchanged.
- **D46**: the driver presents the key on its own doors, so a session cannot report its own state or evidence. It still
  holds no identity on the record.
- **D50**: a terminal on a machine with a window acts through the window's confirmation, and on one without through the
  key in its environment.
- **D92**: the page holds a key the bridge gives it. **LOG2a**: the host's input carries its key first.
- **REVIEWENV1b3's `ByAgent`** (D154's note): a keyless publish is an agent's at every door, and the record keeps it.

**These stand:** D21, D37, D52, D53, D72, D74, D78, D133, D135 and D154 point 8, whose doors are now the person's in fact.

- **Any key that is not this start's reads as `stale`**, a header that is no key included, and is refused at every door but

**PERSONDOOR1b, built 2026-10-09: confirmed in the window** (point 4; design §4.2), the service's half, held by
`ConfirmationTests`, `ConfirmationProcessTests` (the real host: an escaped path, and a body read by the grant and then the
door) and the census in `PersonDoorTableTests`, 68 routes at this build. Nothing asks yet: the clients are PERSONDOOR1d and
1e, and the window's card 1f. What building it settled:
- **Five routes, a local host's alone.** `GET /api/confirmations` and `/{id}` are reads and answer no secret's hash;
  `POST /api/confirmations` is any caller's, as a session can ask; `/{id}/confirm` and `/{id}/refuse` are the person's.
  The ask carries `method`, `path` with its query and `body` as text, exactly as sent, and `secretSha256` in hex. The
  secret is made as a key is, 32 random bytes in base64url, and one in any other form grants nothing.
- **Only a door that wants the key, in the form that wants it.** The ask names its request's door by the table's patterns
  (literals over parameters, one trailing slash ignored), and refuses a read, an agent's door, `respond` without
  `whileOpen`, the confirmations' own doors and an address no door answers, each 400. The card names the door's act, or
  its form's.
- **The card shows only what binds** (`DoorContracts`). Each door's contract is read from its own endpoint: the body's type
  the framework records for the parameter it binds, and the handler's simple parameters the route does not fill, which
  are its query. An ask is refused when its body or query carries a name the door does not bind, or one name twice as the
  binder reads names (ignoring case), or a body on a door that binds none. Each value is named by its JSON pointer
  (`/setUp/machine`, `/units/0/id`) and keeps its JSON type, so no two bodies show alike.
- **The grant is held to the request exactly**: its method, the pattern of the door that answers it, the path as sent
  (unescaped), the query as sent and the body to the byte, labelled `application/json` with no charset or UTF-8. Its secret
  and address are judged before a byte of the body is read, and the body is read no further than the confirmed one and a
  byte. A call that differs uses nothing up, and the exact one is answered once. A grant presented at any door but a read
  is judged first, and refused `grant` where it covers nothing, as a stale key is never quietly an agent's. The body is
  held in memory and handed to the route, never buffered to a file. A body not labelled JSON never reaches the gate: the
  router answers 415 first.
- **An ask is bounded before it is read whole**: read to 512 KB (413 past it), its body to 64 KB and 256 values, and while
  five wait a sixth is refused before its body is parsed.
- **Two minutes from the ask**, for the wait and the grant's use both: one confirmed at 1:59 has a second left. Each
  expires once, logged once, and is forgotten two minutes later, so the terminal can still read how it ended.
- **The sixth** is the design's: 403 `confirmations-full` with its sentence, asking nothing, and one `person.refused` line
  by `/api/confirmations`. Only what waits for the person counts, so one answered frees its place.
- **The grant's sentence is wider than §5.2's.** One code, `grant`, also answers a grant the person refused or never
  confirmed within its two minutes, so the sentence names those beside another act and a second use.
- **Logged**: `person.confirmation` with `state` (`asked`, `confirmed`, `refused`, `expired`), the method and the door's
  pattern. A used grant writes nothing; a refused one is `person.refused` with `presented: grant`. Never the id, the
  secret, its hash, the path's values or the body.
- **A host handed no key** maps the routes, lists none, refuses an ask 409 with a sentence, and ignores a grant.
- **The clock is the services' `TimeProvider`**, the system's unless a test moves one, so the gate is built after the app.

**Changed after a second agent's (Codex's) read-only review**, each with a failing test first: the card showed a body's
