## D183 — Ask Daoris runs in an access mode the person chooses: restricted, with access the person configures, or full; and it shows what it was handed (2026-10-19)

**Decision (the owner's direction).** The owner, 2026-10-19, after Ask Daoris answered a request to clean up a tree
Daoris had made with *"I can't change anything on this machine myself … Removing a folder stays your press"* and a list
of commands to run by hand: *"same issue again, I think you're making Ask Daoris too restricted, we'd better take the
approach like Codex does, into modes (restricted + config access, so we need a UI design for this mode, or full access),
and also we do need to show what's been wired for Ask Daoris, because this is blocking me for development."* Earlier the
same day it had lost the browser (HELPPLUG1c), whose approval was not on the page at all. D89 made Ask Daoris a session
that reads and proposes, run in its harness's asking mode so that nothing off its allow-list could act (HELP1a), and every
reach since (checkouts, plugins, the browser) has been one more grant to wire and approve.

1. **Two modes, the person's choice, like Codex's approvals.**
   - **Restricted** is what Ask Daoris is today (D89): it reads, and it proposes changes the person applies with a press.
     On top of that, the person grants **configured access**: named capabilities, each one listed with what it lets the
     agent do and where (HELPMODE1c designs them and their screen).
   - **Full access** runs Ask Daoris in its harness's own unrestricted mode: shell, file edits, Daoris's commands, and
     every plugin server the machine has, with no per-call asking. Mapped per harness: Claude's permission mode that
     skips asking, and Codex's full-access sandbox with no approvals. What the agent does there is its own act, not a
     proposal, so no card stands between it and the change.
2. **Chosen where the person sees it.** The mode is set under Settings → *Daoris's own AI* → Ask Daoris and switched from
   the panel's own chip, as Codex's mode is. It is machine-wide for now (D158's ASKSCOPE1 note, point 7). A switch takes
   effect at the next start, or at once where the harness can change mode mid-conversation. Restricted stays the
   default; full access is never chosen for the person.
3. **Never silent.** The mode a conversation ran under is kept on its record and shown on its panel, in its history row,
   and in the room's first lines, so the agent knows it too. Full access wears a plain warning chip. A conversation
   resumed after the mode changed runs under the new mode and says the change.
4. **What it was handed is shown.** The panel shows what this conversation was wired with: its mode, its agent and
   account, its working folder, Daoris's tools, the plugin servers and whether each is approved, its permission rules,
   and the checkouts it may read. In restricted mode it also shows what it lacks, each with the door that grants it.
   This is read from what the start actually handed, recorded at the start, never derived again.
5. **The doctrine still speaks.** In full access the room still tells the agent that a repository's work is asked for
   through a quest, and that the machine's own housekeeping (Daoris's trees, its home) is its to do. These are words,
   not a gate; the mode is the gate.

**Rejected.**
- **More grants one at a time** (the path since D89: checkouts, plugins, the browser, each its own wiring and approval):
  every gap blocks the person until a row closes it.
- **Full access as the default**, or switched on by anything but the person's press.
- **A mode per workspace now**: settings stay machine-wide until the owner asks (D158's ASKSCOPE1 note, point 7).
- **A wired list worked out again from configuration**: it could disagree with what the agent was actually given.

**Amends D89** (Ask Daoris proposes, and every change is a press: now in restricted mode only; and HELP1a's asking mode,
now restricted mode's), **D107** (no shell: restricted mode only), **D170** (plugins handed to Ask Daoris: every
installed server in full access, approvals in restricted). **Held by:** HELPMODE1a (the mode in the driver and the
record), HELPWIRED1 (what was handed, recorded and answered), HELPMODE1b (the panel's chip, Settings and the wired list on
the page), HELPMODE1c (restricted mode's configured access and its screen, designed first).

**HELPMODE1a1, built 2026-10-19: the mode chosen at each start, per harness.** The driver's `helpMode` is `restricted` until the
person names `full`. It is written only while full, a value it does not know reads as restricted, and the CLI's `driverconfig.ts`
reads it by the same table. `daoris-driver help mode [restricted|full]` says it, or sets it under the home's lease. No proposal
names it. Each start reads it, a conversation going on among them (`HelpAccess`):
- **`claude-code`, the native door.** Restricted is unchanged: `--permission-mode acceptEdits` with the room's allow-list.
  *Finding:* HELP1a's asking mode never reached this door, only the protocol one; over `-p` an unlisted tool is never allowed, so
  it read and proposed all the same. Full passes `--permission-mode bypassPermissions`, measured on 2.1.281 (CONV4a's probe).
- **`claude-code-acp`.** Restricted asks `default`. Full asks `bypassPermissions` through `session/set_mode` as a *required*
  posture: an agent that does not offer it, or offers no modes, fails the open naming what it offers. It never runs narrower under
  the full label.
- **`codex-acp`.** Restricted is as before: it asks `default`, which Codex does not offer, so it runs in the mode it starts in.
  Full is `agent-full-access`, the `dangerFullAccess` sandbox with approvals `never`. That was read from codex-acp 2.1.1's bundle
  on this machine, which offers it on every session and keeps a `session/set_mode` for the prompts after. Codex takes no rules
  file, so the person's denies reach it in neither mode, and its start line says so.
- **dsh and plugin-declared harnesses** have no mapping (`ISessionAdapter.FullPosture` is null). A full start on one is refused,
  naming it. A new start is refused before any record opens; a start going on ends `failed` saying why.

In full access, the start is handed no allow-list and asks nothing. Every deny the person's rules compose still goes, the shipped
`no-push` among them while it is on. It is handed every server the plugins here declare, for it or for sessions, approved or not.
It gets **no tree guard**: PERM3's PreToolUse hook refuses an `Edit`/`Write`/`MultiEdit`/`NotebookEdit` outside the session's
tree. Here that tree is the room, and the housekeeping point 5 names is outside it; a shell's writes were never the guard's call.
The lineage hook and the classifier's hard denials stay. D52's refusal of any ask that still reaches the driver is unchanged.

The mode the start got is the first line of its transcript (`— Ask Daoris runs …`), apart from the mode chosen. It is not a note
on the record: a coded note needs the page's note catalogues, and an uncoded one would show English to every reader. HELPMODE1a2
records it. The room's first lines say the mode. *What you may do* says that restricted's limits are the mode's, and where the
person chooses full. In full it says the helper acts itself, a repository's work is still a quest, Daoris's housekeeping is its
own, and a push or a key stays the person's.

*Not checked here:* that Claude's bypass still honours deny rules and blocking hooks (the maker's word). Whether claude-agent-acp
lets `set_mode` reach `bypassPermissions` without its being allowed at session creation could not be read, since the adapter is
not installed outside Daoris's own home; if it does not, the open fails plainly, and the installed window shows which. A resume
whose answer is no object skips the posture, since `AcpSession.ResumeAsync` calls `SetPostureAsync` only for an object.
*Left:* the record's mode, its route, the history row and a switch mid-conversation (HELPMODE1a2); what was handed (HELPWIRED1);
the page (HELPMODE1b).

**HELPMODE1a2, built 2026-10-19: the mode on the record, its route, the history row, and every switch at the next start.**
- **The record** keeps the mode a start got, the effective one (`help_mode`): told at the open (`mode` on `POST /api/sessions/help`)
  and again by `POST /api/sessions/{id}/help-mode` when a conversation goes on under another. It is machine-local like the profile:
  answered as `helpMode` on loopback only, written with no revision, on no feed. A record from before reads `restricted`; a mode the
  ledger does not know is a 400.
- **The route** `SET_HELP_MODE {mode}` sets the key `help mode` sets (D50), and the state answers it as `helpMode`, pushed with the
  choices. **The history row** names each conversation's mode (`mode`, after `live`) at both doors; the terminal marks full access.
- **Going on under another mode** records the new one before the spawn. The transcript's first line says the change ahead of what it
  runs under (`— Ask Daoris's mode changed since this conversation last ran: it ran restricted, and goes on with full access. …`).
- **No live switch, on either door.** A start hands its mode five ways: the harness's posture, the rules (restricted's allow-list and
  asks, or none), the tree guard, the plugin servers (approved, or every one), and the room's words. `session/set_mode` changes the
  first alone. Restricted to full while it runs would ask nothing, yet the guard still refuses edits outside the room (point 5's
  housekeeping), the unapproved servers are missing, and the room still says to propose: a full label on a half switch. Full to
  restricted is worse. Claude's `default` with no allow-list asks for every tool, the proposal tools among them, and D52 refuses every
  ask, so it could not even propose. Codex offers no `default`, so the lenient posture would leave it in `agent-full-access` under the
  restricted label, which point 3 rules out. So a switch takes the next start or resume on every door, which hands all five again.
  A conversation running under another mode is told so on its console (`HelpModes.TakesNextStart`); ending it and writing to it
  resumes it under the mode chosen. `AcpSession.SetModeAsync` was not built. That line is the console's, not a note on the record,
  for the reason above; the page's chip shows a pending switch from the record's mode and the state's (design §1, HELPMODE1b).
- **HELPMODE1a5, built 2026-10-19: a narrowing switch holds at once.** Full to restricted no longer waits for the next start: `ChatRunner
  .HelpModeChosen` ends the full-access conversation the way a person finishing does (`Finish`, the turns asked for, then the close),
  at once where it is idle and as its turn ends otherwise (`HelpTurnChanged`, from each start's turn queue), never mid-turn; its console
  says which (`HelpModes.EndsForNarrowing`). Its next words resume it restricted, the go-on already reading the mode chosen and
  recording it, with the transcript's change line. A widening stays at the next start; choosing the mode it runs under again withdraws
  a scheduled end. Words already queued behind the turn run before the end, as finishing is not withdrawing.
- **HELPMODE1a4:** a resume answered with no object now sets the posture too, so a required one fails the open; the *Not checked
  here* sentence on it is closed.

*Not built:* the page (HELPMODE1b). The narrowing switch's end was built after (HELPMODE1a5).

**HELPWIRED1, built 2026-10-19: what each start handed, kept as a receipt and answered (point 4, the modes design §6-7).**
- **Recorded at the start, from the spawn.** `ChatRunner.RunAsync` keeps it for Ask Daoris once every input is composed and before
  its process starts (`HelpWired.Compose`, `HelpHanded`): the effective mode, whether it is a new start or one going on, the harness,
  its version and the account it ran as, the door and the posture it asked (or the native door's permission mode Daoris named,
  null where the adapter's own was kept), the folder, the rules list for list as the settings file holds them, Daoris's own tools
  (the allow-list's `mcp__daoris-knowledge__…`, none in full access), the tree guard, the checkouts its rules grant, the skills, and
  each server. Whether a file reached the agent is read from the spawn, not assumed: the native door's command line or environment
  names it, or the protocol door's `session/new` meta carries it (`HelpWired.Names`, `Carries`). So an agent that takes no rules
  (`codex-acp`) records none, and a native door that takes no servers file records each server withheld, `no-door`. The protocol
  door's servers list is now composed once, before the start, and handed to `session/new` as is, so the receipt names that list.
- **Each server's state:** `handed` (approved for Ask Daoris, or Daoris's own connector), `full-access` (on the spawn by full access
  with no restricted approval), `withheld` with why (`not-approved`, `changed`, `refused`, `no-door`, `not-found` for a connector not
  found, or the browser note's code: `browser.no-host` where no browser host runs, design §7, never an unresolved endpoint), and its
  declared tools where known. `unverified` is a skill handed on the protocol door, read from claude-agent-acp's sources and never run
  (D170's HELPPLUG1b note). In restricted mode it lists what it lacks with each door: a server not approved (`plugins`, its plugin
  named), one refused, or declared for sessions alone (`mode`), one the browser's host would bring (`host`), one the agent has no
  door for (`harness`), and the shell and file edits (`mode`, until HELPMODE1c's grants).
- **Cleaned by allow-list** (design §7): a receipt names its fields and copies nothing of the spawn's environment, an account's key,
  or a server's command, arguments or environment; it is read back field by field, so what a file holds beyond them is never
  answered. Its machine paths (the folder, the checkouts, the rules) keep it desktop-only.
- **Kept** in `<home>/sessions/<id>.wired.json`, oldest first, one per start: a going-on adds one and the earlier stay, a mode change
  among them. A file that does not read is none kept. `SessionHomeFiles` takes it under Ask Daoris's own name (`help`), so a delete
  and a history clear remove it, and the delete's words for `help` need no new catalogue entry. A receipt the disk will not take does
  not hold the start; its console says so.
- **The route** `HELP_WIRED` {session} answers `{session, recorded, receipts}`, the newest first, each as the file keeps it with its
  nulls; a conversation from before answers `recorded: false`. A read: `Open` in the pipe's census, no declaration, no page hook yet
  (HELPMODE1b's, which then needs no coverage row, a read being none).

*2026-10-20, HELPMODE1c2a: the housekeeping grant's channel, settled before it was built.* The connector is a process of its own
that references the service alone: it cannot call the clean-up's judges and holds no pipe to the driver. So each housekeeping
tool is a request the driver judges and answers:
- **The folder every loop already watches.** The tool writes a keyed request into the home's session requests (SESSUX1g,
  `sessions/requests`), for the conversation's own session, with the move `housekeep`, `by: help`, the operation and its targets
  by name. The loop whose registry runs that conversation takes it once (REQTAKE1), judges it, and writes its answer beside it,
  as a terminal's say is answered (MSG1e). The tool waits ten seconds for the take and withdraws one nobody took (REQTAKE2),
  then waits for the answer within a bound below an agent's own tool timeout, and says where it stands if none came.
- **Rejected:** a box the loop reads at its tick, as a helper's ask is: a tick may be a minute apart, and a tool call waits on
  it. The instance pipe: its census classes the clean-up's routes as the person's, which a tool's call is not, and the
  connector reads no address file (the hosts are the service).
- **The driver judges every call, whatever the agent.** The record it names is Ask Daoris's; the operation is chosen in the
  grant's record now and was handed at this start (its newest receipt), so a revoke refuses the next call and a widening takes
  the next start, as the room and the allow-list do; the repository is registered in the conversation's workspace, read from
  its record (ASKSCOPE1c), and has a checkout here; the targets are a repository and branch names, never a path. Then the
  judges are called, never copied: the clean-up's git half for a look (it asks no plugin, D148 point 2, since a tool's call is
  no person's look), the clean-up's press with the branches named (each judged again before it goes), and the discard
  unforced (a running or waiting session keeps its tree). No recovery ref is dropped and nothing is forced. The connector
  itself refuses a session that is not Ask Daoris's, since a driven session shares it.
- **The record** is the home's `help-access.json` (`help-access`, in the home table's three twins): the operations chosen per
  grant, `{ "housekeeping": ["inspect", "clean-up", "discard-branch"] }`, the page's codes. None, or a file that does not read,
  is none chosen; `drop-recovery` grants nothing yet. Its writer is HELPMODE1c2b's route.
- **A revoke ends no conversation.** Nothing of the grant acts without a call, and every call is judged then. Full access's
  narrowing ends one (HELPMODE1a5) because its shell acts without Daoris; a grant has no such reach. The same grant governs
  the tools under full access, whose shell reaches further anyway.
