## D144 — A requirement may name evidence Daoris reads itself, and a met answer without it holds the quest as a departure does: a path in the done's commit first, a gate read from the queue's verdict later (2026-10-03)

**Decision (EVID1).** The owner brought in an outside analysis on 2026-10-03, `docs/DAORIS_FUTURE_DIRECTIONS.md`. Its §1
asks that *the model should not be the authority that declares its own success*. The review
(`docs/2026-10-03-future-directions-review.md`, its §1 row and EVID1 slice) found that since D133 a done answers each
requirement, but a met answer is still the agent's word, and the gate results D46 §4 names are not recorded. The contract
is `docs/2026-10-03-evidence-design.md`.

1. **A requirement may name its evidence**: a list of up to five items, each a repository-relative `path` the done's
   commit must hold or a `gate` the receiving repository declares. The exchange judges its shape at every publish door.
   The check stays the words a person reads, and the evidence is the part of it a fact settles. Whoever writes the
   requirement writes it: the intake from the person's words, or the person. The session it will judge never does
   (D133 §3). A chain step to another repository inherits the requirement without its evidence.
2. **A met answer on such a requirement closes the quest done and held until Daoris reads the evidence**, with D133's
   hold (`Quest.Held`): its next step is not published, it stays outstanding, and its ask is not done. The service
   cannot read a commit, and a step publishes in the done's transaction, so the hold is set by the done itself.
3. **The driver reads it when the session that made the done ends**, at the tree's `HEAD` then, and reads only. It keeps
   per path whether it was found, the object id, whether this work changed it, and whether it was left uncommitted.
   It posts the verdict to one local door. The exchange keeps the verdict as an `Evidenced` operation. Found, it lifts
   the hold and publishes the held step in the same transaction. Missing, it keeps the hold with that cause. The orphan
   sweep reads it the same way. `daoris-driver quest check <id> --commit <sha>` reads it again at a commit on the same
   history, and it is the only way to read a done no driven session here made.
4. **Missing evidence waits for the person as a departure does.** The page and the terminal name the cause and what
   was read. The yes (`Accepted`) is reused unchanged and accepts the done as it stands. *Check again* lifts the hold
   with evidence that came later. Sending the work back waits on DRIFT1e's reopen. It is no strike. The record
   concludes `completed`.
5. **A gate is read from the queue's verdict, and Daoris runs no gate for evidence alone.** Under the queue a done means
   landed, and the landing's entry keeps each gate's verdict. The entry's set gains every gate its requirements name. A
   repository that does not land through the queue has no run that is Daoris's, so its gate evidence waits unread, and
   says so. Until the queue is built, a `gate` is refused at publish, naming it.
6. **It keeps the facts it chose by** (D143): the commit read and how it was chosen, who read it and when, and each
   item's code (`found`, `missing`, `uncommitted`, `case`, `not-declared`, `not-run`, `failed`, `no-queue`). They are kept
   on the quest's operation, with no machine path, and in the record's evidence bundle (D46 §4). They are read on the
   quest's page, by `quest check` and `trace`, and by Ask Daoris. A met answer always says whether Daoris read it or it
   stands on the session's word.

**What is not checked:** whether a file's content meets the requirement, which is a judgement (D54) and the verify
step's (DRIFT1e). Also not checked: the deployment, an API response and performance, which are outside the repository
and behind a credential (D37). A `command` named by a quest is refused for good: the receiver would run the asker's
verb, and gates stay the repository's declared verbs (D26, D32). The design's §7 says when each might be checked.

**Why.** D133 made the person's words the measure and kept the agent from reading them away. It left the agent the last
word on whether the work meets them. Presence is a weak fact, but it is a fact, and it catches the drift's own shape: a
close that says met while the thing the person named is not there. Holding through D133's hold, with D133's yes, adds
no state, no status and no new act for the person. Gates already run in one place, the queue, so evidence reads that
place rather than building a second runner beside it.

**Rejected.**
- **A candidate status before done**, as the analysis draws its lifecycle. A new status reaches every surface and parser
  (D104), and the held done already means it.
- **The service reading the branch.** It is spawn-free (D46), and a file in a working tree is not a file in a commit.
- **A carry-on that closes after the check**, as the queue does after landing. A session per done, for an outcome the
  done already wrote.
- **The person's yes on every done with evidence.** The check would save them nothing.
- **The hold derived from the session record.** Every list would join two stores, and a record write would publish a
  quest.
- **The driver running a gate when the session ends, or reading a run it saw in the session's events.** That run would
  cost a landing's time and FLAKE1's load and duplicate the queue. The agent spells the run's command line, and a pipe
  hides its exit code.
- **Reading a path out of the check's words**, which is a judgement. **Refusing the done**, which the service cannot judge.

**This amends** D46: the driver still moves no quest. It never takes, closes, declines or reopens one. It may record on
a done a fact it read, through one door the exchange judges, and that record lifts only the hold the done set. D115 §10's
rejection of the queue closing a quest stands, because a close writes the outcome. D133 §3 and §4: the evidence beside
the check, and a met answer held until it is read. D65 §4: the next step also waits for its evidence. D115 §5: an entry's
gate set gains the gates its requirements name. D68 gains one operation kind, which an older build refuses as not
whole, as it did `accepted`. D46 §4 is unchanged: the record moves on the exit code and the quest, and the verdict is
evidence in it.

**What the checks do not cover.** Documents only, and nothing is built. The amendment to D46 is the judgement the owner
may most want to reverse. If reversed, the design's §9 lists the alternatives, and each costs the person a press or a
session per done. No real intake was asked to name evidence, so whether the paths it names are the ones the work
leaves is not measured. `verify` checks this entry's place and the design's links, and none of their words.

**EVID1a, built 2026-10-07: path evidence holds the done, in the service.** A requirement carries `evidence`
(`QuestEvidence`), judged at every publish door and at a remote's (`JudgeEvidence`, `JudgeReceived`); a gate is refused,
naming the landing queue. A met answer on such a requirement closes the quest done and held: `Quest.Hold` reads
`departed`, `evidence-unread` or `evidence-missing`, and `Held` is any of them, so the outstanding list, the ask's done
and the yes follow unchanged. `POST /api/quests/{id}/evidence`, local mode only, takes the driver's verdict
(`QuestExchange.EvidenceAsync`) and keeps it as an `evidenced` operation (`QuestStore.EvidenceAsync`). All found lifts
the hold and publishes the held step in the same transaction; anything else keeps it held. Choices the design left open:
- **A path is named one way.** Beyond §2's rules, an empty or `.` segment is refused and `.git` is matched in any case,
  so a verdict's fact is about the path the person named. Two items naming one path are kept once.
- **A departure comes first.** A done that departs and also waits on evidence reads `departed`, since only the yes lets
  it go; `AwaitsEvidence` says separately that its evidence is still to be read, and a found verdict is kept beside it.
- **A verdict reads exactly what the done waits on**: every item of every met requirement, as named, once, with a
  result its kind may have. That is the replay's own rule (`QuestLog.Applies`), so a remote and a rebase refuse what
  the exchange refuses. A second found verdict, or one after the yes, is no move and rebases away as a second yes does.
- **Who read it** is the operation's machine, kept with its time on the quest's verdict (`At`, `Machine`), and the
  session whose end was read (`session`). The terminal's check names none.
- **The step's history says so** as its publish operation's note, which the replay never puts on the quest.
- **The yes's words** stay as they were for a departure; for a done held for its evidence alone it says it accepted the
  done as it stands.

What EVID1b needs: the door's body and codes above; `awaitsEvidence`, `hold` and `evidence` on every quest; the
requirements' `evidence` on every read; and the done's answer, which already tells the session what is read in its
last commit. The commit's place on the history, the record's evidence bundle and the `evidence.checked` log line are
the reader's, which has the tree.

Proof: `QuestEvidenceTests` (the shape's fifteen refusals and the gate's at publish and at a remote; the hold; found,
missing then found later, beside a departure; the yes on each hold; twelve verdicts refused; the chain to another
repository and to the same one; the wire, the cache and the replay's rule), `QuestSyncTests` (a verdict releasing on
every machine, two found verdicts as one, a verdict on a lost done going with it, missing then found from two machines),
`LocalHostTests` (the doors' 200, 400, 409 and 404), `SharedHostTests` (no evidence door; a machine's path refused on a
push, a named one kept) and `McpToolsTests` with `McpToolDescriptionTests`, each seen failing on stubs that kept and
judged nothing. The replay's coverage rule and the chain's dropping of evidence were each seen failing again with their
line changed; a rebase branch that would have forgotten a lost verdict's step was found dead, since the lost done's
conflict already takes it, and removed. Not covered: nothing reads a commit yet (EVID1b), so no verdict here was read
from a tree; the family rehearsal publishes no evidence; and nothing is drawn, so there is no look.
