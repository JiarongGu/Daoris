## D140 — The plugins page is a catalogue, and a plugin wears an icon: declared in its manifest, handed as its bytes, a monogram in its place (2026-10-03)

**Decision (PLUGUI2, amending D64 §3, D119 §3.1 and §3.2, and D120 §6).** The owner, 2026-10-03: *"plugin page design
(and plugin icon)"*. Read from the code at `a1117db0`: the list read as manifests (a row's one line said *2 points · 1
agent*, and a plugin's description appeared only on its page), and nothing drew an icon. The contract is
`docs/2026-10-03-plugin-catalogue-design.md`.

1. **The list is a catalogue of three sections**: *Installed* (waiting on you first, then on, then off, the state the
   row's word and no longer a heading), *Daoris's own plugins* not installed, and *Available* from a package source,
   which PLUGDIST1e builds and is absent until then.
2. **A row** is the plugin's icon, its name and version with its state's word, its description (what it gives, cut to
   the row), then a meta line: where it came from, what it adds, and *update available* where its source declares
   something different. **A page** leads its header with the icon at 48 px, sets *update available* beside its state,
   and says in its Source why a declared icon is not drawn. **Every block of a plugin's detail takes the pane's width**:
   no paragraph keeps a measure of its own, and LAYOUT11 sets the measure for every page in one place.
3. **The manifest gains `icon`**: a path inside the plugin's folder to an SVG or a PNG. Both readers hold four rules of
   the manifest (none for `null`; text; a path inside, names joined by `/`, none empty, `.` or `..`, no `\` or `:`; an
   `.svg` or a `.png`) and four of the file (there and a file; at most 32 KiB; a PNG's signature and header, at most
   512 px a side; an SVG that is UTF-8 text holding `<svg` and declaring no entity), in that order, in the same words.
4. 🔴 **An icon's problem never refuses the plugin.** It is how a plugin is recognised, never what it does: the plugin
   stays sound, wears its monogram, and the sentence is said on its page and by `daoris plugin list`. A refused plugin
   keeps its icon.
5. **The page is handed the bytes, never the path.** `PLUGINS` is to answer each plugin and offer with `icon`, a
   `data:image/svg+xml;base64,…` or `data:image/png;base64,…` URI that `PluginIcon.Read` builds from the bytes it
   judged, and `iconProblem`. The page draws only such a URI, in an `<img>`: none of an SVG's scripts run, nothing outside
   it loads, and no plugin markup enters the page's document (D64 §7, D52).
6. **With no icon that draws, a monogram**: the name's first character (the id's where the name is blank), in capitals
   where the script has them, on one of six identity hues picked by the FNV-1a hash of the id. The id, not the name,
   because an id is the folder's and unique while a name may repeat and change. The hues (`--ident-*`) are computed:
   each glyph at least 4.5:1 on its 15% field in both themes, each hue at least ΔE 20 from every status hue and the
   accent, so a monogram is identity and never a state.
7. **Chrome translates and content does not**: a plugin's name, description and version stay as declared, and the
   icon's sentence is the reader's, passed through whole.

**Why.** A catalogue says what each plugin is for and where it came from before the person opens it, and an icon is
how a person finds one in a list. Bytes rather than a path keep the page from reaching for anything on the machine,
and the list's answer stays bounded at 32 KiB a plugin. A monogram keyed by the id gives every plugin a stable face
without asking its author for anything.

**Rejected.**
- **An icon by address**, which the page would fetch once per row from wherever a plugin says.
- **An SVG inlined** for crispness or `currentColor`: its markup would be in the page's document.
- **A route per icon** (`PLUGIN_ICON`): one request per row for files the catalogue has just read.
- **More formats** (JPEG, GIF, WebP, ICO), and **a second icon for the dark theme**.
- **A monogram's hue from the name**, and **the status hues for monograms**: a red tile reads as declined.
- **Keeping D119's three state headings**: the order within *Installed* keeps what they were for.
- **Refusing a plugin for its icon.**

**This amends:** D64 §3 (the manifest's `icon`); D119 §3.1 (the groups become the catalogue's sections) and §3.2 (the
header's icon, *update available*, the icon's sentence in Source, one width); D120 §6 (*Find plugins*' packages are the
catalogue's *Available* section). D64 §7 and D52 stand: no plugin adds a view, and none of its code or markup runs in
the page.

**What the checks do not cover.** The host's answer of the two fields is PLUGUI2b's (the modules' `PLUGINS`), so on the
window today every plugin wears its monogram; the page reads the fields and the stories show both. No real SVG or PNG
has been drawn at 20, 32 and 48 px on the window, and neither the rows at 280 px nor the hues have been looked at in
either theme or language. The computed check holds the hues' numbers, not their look.

**Built (PLUGUI2, 2026-10-03).** The twins: `plugins.ts` (`readManifest`, `readIcon`, `plugin list`'s *icon not drawn*)
and `Plugins.cs` with `PluginIcon.cs` (`Declared`, `Read`, which builds the data URI), one table held by
`plugin-icons.test.ts` parsing `PluginIconTests`. The page: `plugins/icon.ts` (the monogram, the hash, what is drawn),
`plugins/PluginIcon.tsx`, the catalogue's rows in `PluginList.tsx` and its sections in `catalog.ts`, the icon on the
strip (`StripMark`'s `face`), the page and the offer's page (`PageHead`'s `icon` and `measure`), and the `--ident-*`
tokens computed by `plugins/icon.test.ts`.

**PLUGUI2b, built 2026-10-03: the host answers a plugin's icon.** `PLUGINS` (`DriverModule.Plugins.cs`) answers each
plugin and each offer with `icon` and `iconProblem` from `PluginIcon.Read(folder, manifest)`: the data URI or null, and
the reader's sentence or null, never the icon's path (point 5). `DriverModulePluginPageTests` holds a plugin with an SVG,
one with a bad icon (still sound), one with none, the same for offers, and no string in the answer naming an icon's file.
What only the window proves stands: a real SVG and PNG at 20, 32 and 48 px in both themes, now on an install.
