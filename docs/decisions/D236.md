## D236 — The service's store writes ahead into a log beside its file, each commit synced in full (2026-11-05)

**Decision.** The store every host on a machine opens (`knowledge.db`: sessions, quests, asks, the index, the registry) writes in
SQLite's write-ahead mode, with `synchronous = FULL`. A commit took 13 to 16 ms in the default rollback journal, which makes and
deletes a file beside the store at every commit; in write-ahead mode with the same sync it measured 3.8 ms. The mode is kept in the
file, so every host that opens it after the first writes the same way, an older build's included; the sync is each connection's, so
the store sets both at every open. A copy of the store is the file and its `-wal` log together: the home's migration keeps both, a
home moved across volumes moves its folder whole, the wiring's sizes count both, and the family rehearsal reads both.

**Rejected.**
- Keeping the rollback journal. Every write of every door waits for a file to be made and deleted, and PERF1 measured the writes
  as a large part of what a person waits on at a home's real size.
- Write-ahead with `synchronous = NORMAL`. It is faster again, but a commit can be lost to a power cut after it was answered, and a
  session's state move, a quest's publish and a memory decision are answered as kept.

**What it asks of a deployment.** The log needs the file's folder on a local disk that every opener shares memory with: a store
on a network share is not supported, as it was not safe in the rollback journal either.
