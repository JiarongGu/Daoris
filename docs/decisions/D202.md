The direction (GITAPP1, 2026-10-23): Daoris's git as comprehensive as a git management app, and Review (审阅) fast. Measured on
this machine under its working load, one Review open made `12 + I + M + Uᵣ` serial git starts before the Accept offer (I an
independence read where the candidate bases differ, M REVIEWBASE3's merge, Uᵣ the untracked files sent to git before the patch budget
stops), and the offer a comparison per eligible branch after six: 16.2 s for 368 committed files, 44.1 s with 50 untracked, 8.4 s for
1,771 files. A start costs 0.2-1.6 s here; the likeliest cause, an inference from PROC1a's and UIFREEZE1's stacks and two probes, is
process creation slowed by a real-time scanner and load: programs that open no repository cost as much, and eight starts together
finish in the time of one or two.

1. **Review is a dependency graph** (design §3), built as data in the driver (`ReviewGraph`) and held by a test: each node a read with
   its kind, its key and the nodes it needs, each started the moment its inputs answer, the selection Σ and the final barrier V among
   them. The layout, the branch name and the grown base come from disk and the records; the refs, and git's guess at an unset line,
   from one observation (point 4). **The paths are generated** from every combination of the review's conditions (the observation, the
   line's three sources, the recorded and grown bases, the candidates, untracked files, the landed and gone reviews), each held to its
   depth and ceiling. **Ordinary cold** (the recorded base an ancestor, no grown base apart from it, a line, both its refs, one
   candidate): **depth 2, at most nine starts, ten with untracked files**; the general ceiling depth 5 and fourteen. Every start is
   counted under one launch seam in one of four budgets reported with their total: the graph, the context read, the watch's
   establishment and the one retry. **None per untracked file**: each is a display addition read from disk, exact for a stated subset of
   ordinary text files, never a staging patch, one start for all their attributes. **None on an open where a valid watch says nothing
   moved**; otherwise a counted validation read of two to four. ReviewBase's semantics are kept whole. The Accept offer and the hand-off
   plan are asked after the diff answers, and timed apart.
2. **The targets, provisional**, under the brief's load, median and p90: 368 files **≤ 3 s / 6 s** (16.2 s today); with 50 untracked
   **≤ 3.2 s / 6.4 s** (44.1 s); 1,771 files, a complete list with bounded patches, **≤ 4 s / 8 s** (8.4 s); opened again with nothing
   moved **≤ 0.1 s**; a live session's commit shown **≤ 3 s** after its ref write. They are acceptance targets for the bench and the
   installed window, not derived from arithmetic; the graph's depth and start counts are the gate.
3. **No lock and no index refresh in a tree Daoris does not own: REVIEWLOCK1's rule as it measured it.** `git --no-optional-locks
   <command>`, the option before the subcommand, on every `status` and `diff`; and `-c diff.autoRefreshIndex=false` on a diff against
   the working tree, which git 2.53 refreshes whatever the option says, its stat-only rows dropped. REVIEWLOCK1 has landed; this
   decision points to it, widens its census to the reader's one launch seam, and states which configured programs each read kind may
   run: no external diff or textconv on an object read, each command given only the controls it accepts; **`merge-tree` keeps the
   repository's own merge semantics and is not started where the configuration defines a merge driver**, the only way git runs one,
   Review then reading from the line's base and the conflict preview saying it did not preview.
4. **One `GitReader` per common git directory** (§4-§5), identified by that directory, one registry per process, in the driver library.
   Every git it starts goes through one launch seam that classifies, flags, budgets and counts it, then `WorkingTree.GitStart` and the
   gate of four as `StartClass.Background`. **Two schedulers, said apart**: the gate bounds creation; the reader bounds whole runs, one
   place of eight reserved for attended reads and the rest handed attended first among queued reads, long reads one per reader and two
   per process. **The refs observation** is identified, never an atomic view: stamps and the watch generation taken before and after
   its `for-each-ref`, the refs a review rests on read whole at each use, git's racy-time rule, linked trees' membership and the stash's
   log included, failing closed on a layout it cannot read; **it is kept only while the reader's ref watch validates the repository**,
   and a repository with no valid watch reads its refs again on every use. **One head id answers both halves of a review**, and **a
   final barrier** over every returned component validates the refs, status's own `branch.oid`, the tree's watch generation and the
   context before anything is kept or published; a mutable read joins only reads of its own generation. The cache's keys carry ids,
   options, the parser's version and a **context id**: the hash of what one counted context read found (the binary and its version, the
   environment given to git, every configuration file git names or would read and their conditional includes, the attribute files
   `--attr-source` does not replace, the repository's shape), heard by the reader's watch with a deadline behind it, validated before
   lookup, joining and completion, and carried to the page as a context revision through a `git` scope. **Floors are git's release
   notes**: `--attr-source` 2.41, `git var`'s file paths 2.42, `--no-lazy-fetch` 2.45, each passed as a global option an older git
   refuses, each with its fallback below; a partial clone never fetches on a read. Nothing kept where replace refs, grafts or a shallow
   history change git's answer. **Who owns each read's git process** is one table. **No held git process**: the held object reader is
   deferred to its own design.
5. **Invalidation, never expiry.** A review depends on its tree's actual `HEAD`, the branch it names, the line here and on origin, its
   recorded base and the context: a line move invalidates every review in the repository. The reader's ref roots are a watch of their
   own, beside today's, so its widening wakes no judgement; every attended mutable tree, live or ended, keeps its uncommitted answer
   under a tree watch installed before the answer is read, **its index file watched too**, whose move publishes the review and revokes
   the watch's ignored-folder exclusions until they are proved again; any loss of the watch costs a counted validation read. The page
   says *Read at … · HEAD …* and, where the tree moved during the read, *Changed while it was read*.
6. **The person's reads** (§7.1), which are the capability boundary: a commit's page, diff views, LFS pointers, the history graph,
   blame, a file's history, compare, search, stashes, tags, remotes, worktrees, a branch's reflog, the conflict preview, content across
   history and submodules; deferred and said: an image diff, interactive history editing, a free three-way editor, a held object reader
   and others. **The person's acts and writes are D204's** (GITAPP2): until it is accepted, Daoris offers none beyond what is built.
7. **A session's tree is the session's.** The person reads it in full and reaches it by words. Agents get nothing new.
8. **Nothing of Daoris's own choosing written into `.git` by a read and nothing cached on disk**: objects only where
   `merge-tree --write-tree` writes them; no `commit-graph`, fsmonitor or untracked-cache press, the command shown to copy where one
   would help.
9. **The terminal door** (D50): `daoris-driver git review <session> --time` is the measurement door, built first on today's chain;
   each read has its verb. The reads stay exempt from Ask Daoris's kinds.
10. **The rows**, each landing alone, **the first alone before anything else**: REVIEWLOCK1 (landed); GITAPP1a-i the launch seam and

**Why.** Review's cost is the number of dependent starts on a machine where a start is slow: fewer starts and fewer dependent steps
are cheaper under any cause, and git's binary already gives parallelism, so no library is needed (D147 §4.3 stands). A graph held as
data makes its depth a fact a test can hold, where a count of "rounds" was a scheduling label. An answer named by ids cannot change, so
the second look is free once a reader keeps it and knows when the ids moved; but git moves between any two reads, so what the reader
knows is an observation it identifies and validates, never a view it assumes current, and keeps only where a watch can say it moved.
The acts were split out (D204) because nothing in the reads depends on them, and the reads are wanted first.

**Rejected.**
- **Claude's ≤ 1.5 s and four starts**: met only by changing what Review shows. **Codex's 4-5 s**: not taken as the targets; the
  targets stay provisional and the bench decides.
- **Three rounds as the promise**: the cold path's depth is the graph's, per path.
- **Codex's manual worktree for the person** and **Fable's acts in an idle session's tree**: rejected in round 2, now D204's to
  carry.
- **An empty attribute source for `merge-tree`** (round 2): it neither stops every merge driver nor keeps the repository's merge
  semantics (round 3).
- **A stamp census standing in for the watch** past a bound of loose refs (round 2): a folder's time misses a nested ref and every
  in-place write; without a valid watch nothing is kept (round 3).
- **Review on the person's place in the gate**: a level of starts would take the reserved place, and an agent the person asked for
  would queue behind git; `waitedMs` decides any later priority inside the background class.
- **A held process for two idle minutes, or a cap across the machine**: it keeps packs open while a repack runs, which Git for
  Windows answers with a prompt; a registry is per process, so the cap is too. Round 3 defers any held object reader to its own design.
- **A hand-built untracked patch claimed byte-equal to git**: exact only for a stated subset, and never staged.
- **The `commit-graph`, fsmonitor and untracked-cache presses**: nothing measured needs them, and D147 §4.2 stays whole.
- **`ahead-behind` for both counts**: not REVIEWBASE1's union when the line here and on origin diverge.
- **libgit2, a reader of git's files, an index or cache on disk, polling, a patch per file from git, a free three-way editor,
  interactive history editing this round, fetching on a timer, a wider gate.**
