## D145 — A branch rule may accept done work automatically: the quest's done lands it, the rule's plugin pushes it and opens the pull request, and the pull request is the last human step (2026-10-04)

**Decision (LAND2).** The owner looked at a ticket's work in the work repository that Daoris recorded as done: *"so the
thing is it's closed? but there is no PR branch opened and there is nothing I can really review on and there is no proof
it's completed if the server is stopped (for local development) it should take some screenshot for its completion state
since there are tasks not really related to code, it's configuration based"*. Then: *"also I found the 审阅 loads really
slow and there should be a setup that auto approves since we still have PR as the last human step"*, and *"and auto
approve should be a configurable setting"*. Read from the install: five done sessions sat in *To review* with their
commits only on Daoris's session branches. The work workspace's rule was a branch rule with no plugin, and Daoris's own
pull-request plugins were offered and not installed. Every repository in that workspace lives in Azure DevOps. Work
lands only at the person's Accept (D87), and it had not been pressed. The contract is
`docs/2026-10-04-landing-and-proof-design.md`, Part I.

1. **A branch rule may accept automatically.** *Accept automatically* (自动采纳), the owner's auto-approve, is
   `"autoAccept": true` on a branch rule. When a quest is done, its work lands as though the person had pressed Accept:
   the branch is made and recorded (D102), and the rule's plugin pushes it and opens the pull request (D100). It is off
   until the person sets it, and today's Accept stays the default. Its scope is the rule's (D87): set per workspace, and
   a repository may override it with a rule of its own, which replaces the workspace's whole, the switch included.
   `--clear` on the repository hands it back. The pull request is where the work is judged, so the review is
   optional reading, not a gate. A merge rule with the switch is refused at both doors. With no plugin, the switch is
   allowed and warned: the branch is made, nothing is pushed, and the person's push is the last human step. The doors
   are Settings → Workspace → How work lands, on the workspace's rule and each repository's own, `daoris driver
   landing <repository>|--workspace <name> … --auto-accept`, and Ask Daoris's landing proposal, which also gains
   `--plugin`.
2. **The look lands each due session.** A driven session in a tree of its own whose record concludes on a done quest,
   in a repository whose rule accepts automatically, is due (`<home>/sessions/auto-landings.json`). Each look lands it,
   running beside the look as a start does, only while its quest is done and not held (D133's departure, D144's
   evidence), the session is the newest on its tree, and the tree holds work no branch of the person's holds (D88). It
   lands as the press does, and the rule's tidy follows. A plugin that cannot land here does not stop the branch: it is
   made, the push is not tried, and the sentence names the hand-off (D102). A done with no commits, trees off, a
   conversation, or an end that is not a done lands nothing, and the conversation's record says so. A refusal is tried
   again only when the tree's tip or status changes, or at the person's press.
3. **A chain lands on one branch per repository**, named for its first quest (WSR5). The first done makes it, and each
   later step's done there advances it as a fast-forward: only a branch Daoris made and recorded, standing at the
   recorded tip, checked out nowhere, moved by compare-and-swap and never forced. A press advances the same way. A next
   step grows from the chain's landed branch when the step before's session branch is gone (D82). The plugin's frame
   gains `pullRequest`, the one the record holds, so a plugin pushes and does not open a second, and `acceptedBy`
   (`person` or `auto`). Both example plugins learn the fields.
4. ***To review* keeps its rule** (D126 §2.1): work no branch of the person's holds. With the switch on, that is only
   what could not land: a refusal, or a hold. A landed session's review reads as landed (D113), and its note says it was
   accepted automatically, with its pull request.
5. **Pushing is outward-facing, and the switch is the person's standing say-so.** Every door says so as it is set:
   *when a quest here is done, its work is put on its branch, and `<plugin>` pushes it and opens a pull request without
   asking you each time.* Only the person's doors write it. An agent never writes `driver.json`.
6. **It keeps the facts it chose by** (D143). The landing record gains `acceptedBy`, the rule as it stood and each
   advance. The due list keeps each try's tip, tree status and code (`landed`, `advanced`, `nothing`, `held`,
   `uncommitted`, `exists`, `plugin-unready`, `plugin-failed`). The machine log gains `landing.auto`. They are read on
   the review's note, by `trees land --plan`, by `trace` and by Ask Daoris.

**The worked example** is the design's §7: the work workspace's rule names Daoris's own `azure-devops-pull-request`
plugin. The rule is refused at both doors until that plugin is installed, switched on, sound, and speaking on
`work/land`. The plugin needs `node`, a `git` that can push to `origin`, and `az` signed in with its `azure-devops`
extension. Daoris holds no credential for it.

**Why.** D87 left the push to a plugin and the press to the person, so work reached a branch only when someone pressed
Accept, and five dones had not been. The owner's reason for the switch is the pull request: a person still judges the
work before it reaches the line, on the platform where the team reviews. A review in Daoris before that would be a
second gate on the same diff, and the owner found it slow. A setting on the rule already scoped to a workspace or a
repository adds one field, and every act it takes is the press's own: no new landing, no new state and no new review.

**Rejected.**
- **Landing every done, with no setting.** It would push for a person who chose to review first.
- **Naming it *auto-approve*,** the owner's word. *Approve* is the go-ahead's press (放行), a different yes, so one act
  would carry two names (D116). The review's press is *Accept* (采纳).
- **A setting apart from the rule,** with its own workspace and repository scopes, as reading across has (D107). It
  could read *on* for a repository whose rule merges or names no plugin, and the switch means nothing apart from the
  branch and the plugin it lands through.
- **Refusing the switch without a plugin.** Nothing leaves the machine without one, and a platform with no plugin would
  lose the setting.
- **A merge at done.** It writes into the person's checkout with no human step after it (D51 rule 6).
- **A branch per quest.** It gives a ticket two pull requests. WSR5 names a chain's landing for its first quest.
- **Landing a held done.** It would push a departure before the person's yes.
- **Refusing the branch when the plugin cannot land,** as a press does. Nobody is there to fix the plugin, and the
  branch is the half Daoris owns.
- **A mark that keeps a landed session in *To review* until it is read.** With the pull request as the human step, it
  would make the review a gate again.
- **Landing inside the session's conclusion.** A plugin's two minutes would delay the record, and a hold released later
  would need a second path. The look covers both.

**This amends** D87: a branch rule may accept automatically, and a branch Daoris made may advance as a fast-forward.
D100: with the switch on, the rule naming a plugin is the say-so for a push with no press. A plugin that cannot land
does not stop the branch at done, and the frame gains `pullRequest` and `acceptedBy`. D113 §3: a second landing may
advance a standing branch the landing made, and the note says who accepted it. D82: a next step grows from its chain's
landed branch when the step before's session branch is gone. D51 rule 6 stands: nothing merges itself, and the tidy runs
only because the person's rule asks for it, behind D88's proof. D46 stands: a landing writes no quest state. D126 §2.1's
rule stands. What it lists narrows.

**What the checks do not cover.** Documents only, and nothing is built. The install's facts were read by the parent and
relayed. This branch read the landing code (`Landing.cs`, `SessionTrees.LandAsync`, `SessionGroups`, `driverconfig.ts`,
`Adapters.Landing`) and the Azure DevOps plugin's manifest, README and `land.mjs` from this repository, not from the
install. The plugin has never run against a real Azure DevOps organisation (D100's note). The review's slowness is the
parent's row, and is not measured here. `verify` checks that this entry names what it rejected, and reports the router
row's length. It checks none of the words here or in the design.
