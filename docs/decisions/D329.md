## D329 — Daoris publishes its own releases as GitHub releases of its public repository, and an install's update reads them (2026-11-20)

**Decision (RELEASEFEED1; the quest asked that the workflow run only on a tag the owner pushes).** A workflow of its own, `.github/workflows/desktop-release.yml`,
runs on a pushed `vX.Y.Z` tag and on nothing else: it checks the tag names `canon/canon.json`'s version, stages the desktop as `desktop-publish --stage` does,
zips the staged folder as `Daoris-<version>-win-x64.zip`, writes `Daoris-<version>-win-x64.zip.sha256` (`sha256sum`'s line) and makes the GitHub release as a
draft with both attached, publishing it only then (a release the release workflow already made for the tag gets the two files added and stays as it is). The release
workflow is unchanged: it stays `workflow_dispatch`, and the tag it pushes with the repository's token starts nothing, since a push by that token starts no workflow.
An install's update reads those releases: `daoris update --fetch` (`UpdateFetch`) asks `DaorisReleaseSource`, Install's third `IReleaseSource` beside Claude's and Codex's,
for the newest published release that carries both files (a draft, a prerelease and a release lacking either is passed over, so a release made without them hides no
older one that has them), and when it is newer than the install's own build fetches the package, holds it to its checksum file and, where the API states one, to the
asset's own digest, unpacks it into a staging beside `update/staged/`, holds the build there to its manifest (`StagedBuild.CheckAt`) and to the release's version, and only
then moves it whole into `update/staged/`, where the application installs it by the one path every staged build takes. A build another publisher staged meanwhile is kept.

**Alternatives rejected.**

- *Adding the package to the release workflow, which the owner dispatches.* It creates and pushes the tag itself after every gate, so the release is made by the workflow
  and not by a tag the owner chose; and a package job after the release job leaves a public release without its package while it builds.
- *A feed of Daoris's own (a hosted manifest, a server).* A host to run, and local operation would then need a remote. The GitHub release is
  the record the repository already publishes, and the checksum beside the package is what D27 already uses for the devkit.
- *An installer (MSI or a self-extracting program).* The launcher's swap, its manifest check and its rollback (rules 40 to 46) already take a staged build
  whole; a second way to replace `app/` would be a second set of those.
- *A signature key.* No key exists to pin yet. The trust is HTTPS to GitHub, the account that owns the release, the checksum and the build's own
  manifest; a package replaced together with its checksum is not caught, which a pinned signing key would catch.

**Consequences.** The first release waits for the owner's go: nothing is built or published until they push a version tag. The tag's commit is the one the release workflow's
gates passed, so the package is built without the publish's own gate (`--force-ungated`). A fetch stages and never installs; the application installs the build when idle, at
the person's word as any staged build is. The desktop is a Windows program, so the channel publishes `win-x64` only and refuses another machine in one sentence. Left
(RELEASEFEED1): the running application looking for a newer release by itself.
