## D329 — Daoris publishes its own releases as GitHub releases of its public repository, and an install's update reads them (2026-11-20)

**Decision (RELEASEFEED1; the owner's direction of 2026-11-19, as the quest recorded it: Daoris publishes its own releases).** The release
workflow (`.github/workflows/release.yml`) gains a `desktop-package` job after `release`: it stages the desktop as `desktop-publish --stage` does, zips
the staged folder as `Daoris-<version>-win-x64.zip` and writes `Daoris-<version>-win-x64.zip.sha256` (`sha256sum`'s line), and attaches both to the GitHub
release `release` created, under the same name and notes and still a draft where it is one. An install's update reads those releases: `daoris update
--fetch` (`UpdateFetch`) asks `DaorisReleaseSource`, Install's third `IReleaseSource` beside Claude's and Codex's, for the newest published release (a
draft or a prerelease is none), and when it is newer than the build running fetches the package, holds it to its checksum file and, where the API
states one, to the asset's own digest, unpacks it into `update/staged/` and holds the build to its manifest (`StagedBuild.Check`) before it counts as
staged, so the application installs it by the one path every staged build takes.

**Alternatives rejected.**

- *A workflow run by a tag the owner pushes.* The `release` job bumps the version, commits it and pushes the tag itself after every gate passes, so a tag
  trigger would run on a tag the workflow made, or ask the owner to tag a commit nothing had gated. The workflow stays `workflow_dispatch` alone: no tag
  push, no schedule, so nothing is built or published unless the owner dispatches it, and a dry run builds the package and attaches nothing.
- *A feed of Daoris's own (a hosted manifest, a server).* A host to run, and local operation would then need a remote. The GitHub release is
  the record the repository already publishes, and the checksum beside the package is what D27 already uses for the devkit.
- *An installer (MSI or a self-extracting program).* The launcher's swap, its manifest check and its rollback (rules 40 to 46) already take a staged build
  whole; a second way to replace `app/` would be a second set of those.
- *A signature key.* No key exists to pin yet. The trust is HTTPS to GitHub, the account that owns the release, the checksum and the build's own
  manifest; a package replaced together with its checksum is not caught, which a pinned signing key would catch.

**Consequences.** The first release waits for the owner's go: nothing publishes until they dispatch the workflow with `dry_run` off. A fetch stages and
never installs; the application installs the build when idle, at the person's word as any staged build is. The desktop is a Windows program, so the
channel publishes `win-x64` only and refuses another machine in one sentence. Left (RELEASEFEED1): the running application looking for a newer release by itself.
