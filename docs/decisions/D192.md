## D192 — How work moves begins at a start node that routes each piece of work into a pipeline: a pipeline is a named workflow its route chooses; a development pipeline's sessions run only light checks, the heavy gates refused to them; verification is a pipeline of its own, a `check` Daoris performs on landed work, batched, superseded within a bound, its failure made a fix ask (2026-10-21)

**Decision (FABRIC-PIPELINE1, proposed).** **Status: proposed**, revised once under D191 after Codex's read of 2026-10-21 (the
design's §9: twenty-three findings, every one checked against the code and taken). Fable's read of the design's §2 to §4 is owed,
since the design still changes a foundation: a workflow that lands nothing, a node Daoris performs itself whose job outlives the
runtime's pass, a run on a repository's line, a slot per home, and a result contract with a repository's runner. The direction is
D173's note of 2026-10-20: how work moves is configured in the fabric, a workflow begins at a start node routing each piece of work
into a pipeline the person configures, and development is kept apart from a CI-like verification. Read at `300626e52`, a driven
session is told its heavy gates in a sentence (`HeavyTold.cs:43-46`), this repository marks none heavy (D180's HEAVYRUN1c note), and
its CI beside is a command the parent runs by hand (D180 point 2). The contract is `docs/2026-10-20-pipeline-design.md`.

1. **The start node routes on facts.** A chain's work by D157 §4.1's order (the person's choice for the task, the kinds, the
   defaults, Current), unchanged; landed work, a person's ask to verify, and a fix Daoris asks for by the repository's `landed` route
   and the kinds. A kind's declared paths are read against the paths the work changed before its first gate; outside them, where
   the kind's pipeline lowers the person's part, the run holds for the person's choice of route, and nothing switches by itself
   (D157 §4.4). No route reads a model's judgement. Design §1.1.
2. **It sits before the graph.** The start node is the choice table D157 point 5 keeps, gaining `landed` (`{ workflow, gates }`),
   which names only a verification pipeline and keeps the digest of the declaration the person accepted; it is resolved at the bind
   D190 §8 placed, and is no node of a version's graph. The binding keeps the route that chose it. A route changed applies to the
   next run. Drawn first on the *Workflow* tab, with the pipelines it routes to as one graph; changed at Setup and by `workflow use …
   --landed`, and by Ask Daoris's proposal once its proposal carries a route and a graph version. The person's part is lowered only
   by the person's press: the lowering table gains a route removed or narrowed, a verification pipeline's check dropped, narrowed or
   made skippable before a stage, a check's `failed` moved off `wait`, and `light` with nothing running the heavy gates, each shipped
   with the first row that lets its change be set. Design §1.2, §1.3.
3. **A pipeline is a named workflow, chosen by its route**, each versioned and bound alone, governed by D190. A sub-graph and a path
   through one graph are rejected for their costs. A workflow's file marks its pipeline, `development` (absent) or `verification`: D190
   point 4's one landing holds a development pipeline; a verification pipeline's versions are graphs holding at least one `check` and
   no `claimed`, `opinion`, `look`, `go-ahead`, `handed` or `quest.close`, judged by both readers. Design §2, §2.1.
4. **A development pipeline says its sessions' checks**: `checks` on its work (`claimed`'s option, schema 1's `work` field, or under
   Current the repository's `sessionChecks` rule), `light` or `heavy-at-end`, absent being today's. Under `light` a session runs the
   gates its repository does not mark heavy and the checks its change reaches, filtered; the heavy gates are the verification
   pipeline's. Design §3.1.
5. **A heavy gate is refused, and said, by four layers**: the start's words composed from the bound version; `run-heavy` refused
   from a tree a session holds under `light`, on every harness; where the harness takes Daoris's rules (Claude Code), each declared
   heavy command denied exactly, with a sentence for auto mode's classifier, and where it takes none (Codex, dsh) that layer absent and
   said; and a call past `callMinutes` said once at urgent level, never ended by Daoris. Design §3.2.
6. **Verification is a pipeline of its own, its node `check`**: a built-in Daoris performs through the performer, no agent session,
   its attempt written before anything runs and its job run off the pass by `run-heavy`'s executor made asynchronous, heard and
   reconciled as a plugin's answer is. It runs the repository's declared runner (which owns its checkout and answers gate by gate in
   a result file, or is one opaque check) or its heavy gates in a verification tree of Daoris's, as the person accepted the
   declaration by its digest (every gate and key, `heavy` among them). It holds the repository's heavy-run slot and the home's
   verification slot, taken in one order without waiting; it runs below normal with clock-bound gates raised, never counted against
   the cap; its bound is the node's `timeoutSeconds` (7200 by default), counted once both slots are held, the executor ending its job
   before either slot goes. Design §4.1, §4.2.
7. **A run per batch on the line.** A landed run binds the line's tip, its batch every commit since the newest verdict (the line's
   history, for its first); one runs per line at a time; a newer landing supersedes it within one look, its record `superseded` and
   its job ended, while the line's newest verdict (or, before one, its first run) is younger than `settle` (60 minutes), past which it
   runs to its verdict. The line keeps no record of its own: it is read from its runs, each transition one edit of a run's record, so
   a late result never becomes the line's verdict, publishes a fix ask or frees a successor's slots. A person may verify a branch or a
   commit as a run never superseded. Design §4.3.
8. **Its verdict** is the check's on the run's record, each gate's verdict, exit, wall and log its evidence, shown on the tab, the
   run's view, the repository's *Details* and *What needs you*, and asked by any door. **A failure becomes work**: `wait` (the person's
   *Ask for a fix…*), or `ask`, the person's standing say-so, publishing one fix ask per gate to the repository, under a key written
   first, with the gate's log as its file and the kind the person named, so the start node routes it into development. **A stage**
   after the check takes its verdict by a `data` wire, the check not skippable, and reads the exact commit's verdict at its dispatch;
   the install's `--from-gated` stage keeps its rule and holds the gate tree's lock through its build. Design §4.4 to §4.6.
9. **This repository**: `universal`, `code-map` and `orient-index` light; its suites, Process halves and rehearsals (the release and
   family rehearsals declared beside them) marked heavy once its development pipeline is `light`; its runner `node
   tools/merge-branch.mjs --full --beside`, handed the batch's tip, running the declaration's gates alone and writing its result. On
   the owner's install, `daoris-development` (`light`) and `daoris-verification` on `main`, and the kind `fix`. Design §5.

**Why.** A sentence an agent can drop held this repository's sessions back, and three of them still ran a whole test project,
held their place in the cap to the timeout and committed nothing, while the full set beside was run by hand and superseded as main
moved. A route the graph holds, a refusal Daoris and the harness enforce, and a verification Daoris runs on landed work move each
of those out of anyone's memory and into the process. A route that only selects keeps each pipeline whole and versioned under
D190, and a run on the line is what lets verification batch and supersede, which a node of each development run could not. The
check reuses what already holds: the performer's attempt, answer and reconcile, `run-heavy`'s slot and job, and a repository's own
runner with its checkout, so what is new is the executor's place off the pass, the run on the line, and the runner's result.

**Rejected** (design §6): a route by a model's reading or a kind inferred from paths; the start node inside a version's graph, a
pipeline as a sub-graph or a path; a verification pipeline told by a dummy landing, a mark per version or its graph's shape; landed
work routed by its paths; a versioned route set; verification as nodes after every `handed`; the instruction as a standing text; a
heavy run guessed from command text; a `light` pipeline refusing a harness that takes no rules; Daoris ending a session's call; a
bound of a session's own on its background work; Daoris's own CI engine with lanes; a landed edit of the declaration run unasked; an
install of Daoris's own in the verification tree; the check awaited inside the pass; a `timeoutMinutes` beside `timeoutSeconds`; a
machine-wide slot outside every home; a record of the line's own; superseding with no bound; a stage after a check by `after` alone;
a checkout pinned per stage; a fix ask published with no say-so of the person's by default; an automatic bisect, revert or rollback;
a verification run counted against the cap or run in the main checkout; this repository's suites marked heavy before its
development pipeline is light.
