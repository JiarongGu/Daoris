## D167 — A session is one line of work in one repository, its records its parts, and an ask's sessions and the person talk on one channel (2026-10-14)

**Decision (the owner's direction).** The owner, 2026-10-14: *"we created more sessions than we needed, this is kind of
confusing too, for example I raised 2 tasks, with 1 task need 2 repo co-work so there should be just 3 sessions"*. Asked to
choose between one session per repository per ask and a grouping on the page only: *"we can have multiple requests work
together within the same repo, but one that continues should belong to the same session entry (not 100% the same session,
but the entry should be the same), since we are moving towards a co-working session logic, so we might also need a
centralized communication channel too"*. Then: *"please update the Daoris app and continue to finish my 2 tasks (quests)
with the design we just mentioned"*. On the install, one ask over an app (repository A) and its database repository
(repository B) had made seven records and four repository sessions: a failed start's retry, and each request between the
two, became a record and a tree of its own while that repository's session for the ask was still at work. The design, its
evidence and its rows are `docs/2026-10-14-co-working-design.md`.

1. **A session, on the window, is one line of work in one repository.** It is an *entry* holding one or more ledger
   records, its *parts* (段). A part is still one harness conversation and one record (D131 §4, D137 §8); its lifecycle is
   unchanged, and there is no new ledger state.
2. **The entry is a key on every record**, `entry`: `<origin>/<repository>`, written by the ledger at the open. The origin
   is the ask a quest was asked by (`ask:<id>`), else the origin of the session that published it, else its chain parent's,
   else the quest itself (`quest:<id>`); a conversation is its own (`session:<id>`) and one handed over or started from
   another's words is that one's. So a retry, a carry-on, a resume, a hand-over and a sibling's request of the same ask to
   the same repository join one entry; a request of another line of work starts its own.
3. **The key travels and is not rewritten.** It rides the session wire, naming no path and no account. Records from before
   are answered a key derived by the same rule, never written back, so the install's records group as soon as the reader
   lands. One rule in the service; the driver groups by the key it is answered (`SessionGroups.Read`), and the page and the
   terminal show the same entries.
4. **The entry is what a tree belongs to.** Its parts share its tree, one live part at a time (D51): a new request of the
   entry goes into it when it is free and waits, saying so, while a part holds it; a tree removed after a landing is grown
   again from the entry's landed branch. Different entries in one repository run side by side (PAR1), which is the owner's
   *multiple requests within the same repo*. The person may split a waiting request off as a session of its own, with its
   own tree. An entry lands on one branch, as a chain does (D145 §3), so the ask has one pull request per repository.
5. **The list shows entries.** One row each, its group the first its parts qualify for (D126 §2.1), a *Parts* strip on its
   page and every act on the part shown. An ended intake whose ask became quests belongs to its ask's page. The list's ⋯
   gains *Group by ask*.
6. **Each ask has one channel**, where its sessions and the person talk: messages addressed to everyone or to one of its
   repositories, and Daoris's lines read from the ask's quests, so the exchange between repositories reads in one place.
   Work, a change in another repository, and any answer a session cannot go on without stay quests (D79): ownership stays
   local.
7. **A session posts and reads through the knowledge server**, `channel_post` and `channel_read`. A message reaches a
   running session at its next step where its door takes words then, marked as the poster's claim, and otherwise waits for
   the entry's next part. **An agent's message never starts, reopens or extends a run**; the person's message is their words,
   with every reach D137 gives them.
8. **The channel is service records**, travelling within the ask's workspace as session records do, cleaned of machine
   paths, served by the shared host with no UI. On one machine with no remote it works whole.

**Why.** The person counts lines of work, and the ledger counts conversations; both are right, and the window showed the
second. A key every record carries lets the one reader show the first without a fold every reader must learn, which is what
D131 rejected: the key travels, so a teammate's view agrees. Sharing a tree within an entry runs a sibling's request on the
work it depends on, where a fresh tree held only the base. The channel answers the owner's *centralized communication*: what
the repositories asked each other sat on separate quest pages, and nothing carried what one session could tell another
without a quest.

**Rejected:** a session per repository per ask forced into one process (a session is one turn, and a process ends at every
wait, limit, hand-over and crash); one harness conversation across an entry's parts (D131 §4, and a conversation that only
grows); grouping on the page only (the terminal and a teammate's mirror would disagree, and the planner needs the entry); an
entry record of its own (a store, a wire and a merge for what one key says); the ask on the quest record (a field every
quest operation's places must carry, while the publisher is already recorded); a channel per repository pair (three places
for one task, each hiding from the third); replacing quests by messages (a message has no take, done, evidence, landing or
strikes); a message that starts or reopens a session (agents talking each other into turns, D155). The design's §5 says why.

**Amends:** D126 §2 and §2.4 (the list shows entries, grouped by their parts), §4.1 (*Group by ask*) and §5.2 (archive marks
an entry's parts); D51 and the driver design §3 (the entry is the unit a tree belongs to; the tree stays the unit of
exclusion); PAR1's rule that only a resume or a carry-on goes back into a tree; D145 §3 (one branch per entry, holding its
chains); D82 (a part grows from its entry's landed branch); D133 §2 (a sibling's request is on the ask, so its sessions are
handed the ask's words); D137 point 6's held words (a channel word marks its poster, never the person's); the glossary's
*session*, and its new *part* 段 and *channel* 频道. D131's rejected fold stands for one conversation over two records.

**What the checks do not cover.** Documents only, and nothing is built. The evidence is the install's records as read on
2026-10-14, not re-read here; the code facts were read at `9377ab7f`. Whether a request waiting for its entry's tree costs
the owner more than the shared work saves, and how much a real ask says on its channel, are not measured; the channel's
bounds are first values. That an agent keeps work in quests rests on its instruction, which no gate reads. `verify` checks
this entry's place and the design's links, and none of their words.

**Amended 2026-10-14 (the owner's choice on point 4): a request runs alongside, under the same entry.** Asked whether a second
request of the same ask, reaching a repository whose part for that ask is still at work, should wait for the entry's tree or
run at once, the owner chose *run alongside*, matching their *"we can have multiple requests work together within the same
repo"*. So point 4 reads: a new request of an entry goes into the entry's tree when it is free, and otherwise starts at once
in a tree of its own, as a further part of the same entry; nothing waits (`EntryBusy` is not built). An entry may therefore
hold more than one live part and more than one branch: a part in the entry's tree advances its branch, and an alongside part
lands its own, so the ask has a pull request per branch, not always one per repository. The person's *Run as its own session*
press is not needed and is dropped (SESSONE1e), as is the one-branch rule's row (SESSONE1f); the parts strip shows which tree
and branch each part holds. Rejected again: waiting by default, which would have held the evidence's second request 33
minutes behind the first. The design's §1.5 is read with this amendment; its waiting rows are superseded here.

**As built 2026-10-14 (SESSONE1a, points 2 and 3): the key, in the service.** The rule is `SessionEntries` in the Sessions module, over
`ISessionEntryFacts` (a quest and a session by id), so one function answers the open, the read and the wire. The ledger writes
`entry` at every open: a quest's session under the origin of its quest, an intake `ask:<id>/intake`, a conversation `session:<id>`
or the origin of the one it continues (`from`), a helper and a reviewer their own. A record that holds none is answered the rule's
key by `SessionLedger.WithEntryAsync` and `WithEntriesAsync`, which the HTTP host calls for every session it answers, and nothing
writes it back. Three readings the design left open. **The ask comes from the quest's sender**, `ask #id` (`AskDesk.AskOf`),
which a chain step carries too and a teammate's mirror of the quest carries as well, so no ask is looked up and the key is the same
on every machine though asks are this machine's. **A publisher is found by the id its own machine knew it by**: `PublishedBy`
names `283ef343`, and a teammate's mirror of that session is keyed `origin/283ef343`, so the lookup reads either, this machine's
first (`SessionStore.FindOrMirrorAsync`). **The conversation-took-a-quest rule (design §1.2 rule 2, CHATTAKE1) is not built**: a
chat's take is marked on its record without the quest's id (`MarkTookAsync`), so no fact says which quest it took; a quest a
chat took joins that chat's line only where the chat published it (rule 4). A fact that is gone passes to the next rule, and a record
left with none is `session:<id>/<repository>`. On the wire the key is the session record's `entry` (`SessionWire`, the feed and the
page), written only where present; a push sends the stored key or the derived one, so a teammate's mirror groups an old record as this
machine does, and a remote or a machine from before sends none and is answered the derived key at read. The HTTP session carries
`entry` to every caller, since it names a line of work and a repository, no path and no account. The split's `+n` is SESSONE1e's, and
the key's repository half is the quest's receiver, which an intake replaces with the word `intake`.

**As built 2026-10-14 (SESSONE1d, point 4 as amended): a further part's tree, in the driver.** **The planner reads a new quest's
entry from the records and never re-derives it** (`EntryParts.KeyOf`): the quest's own last record here holds its key (a start that
failed before it); else the record of the session that published it, this machine's or a teammate's mirror keyed `origin/id`, holds
the origin its sessions share, joined to the quest's receiver as the key's two halves. The publisher of an ask's quest is the ask's
intake, whose origin is the ask, so the ask's line is read the same way. No service route answers a quest's key, so none is asked; a
quest no record names (a person's publish, a chain's step to another repository) has no key here and starts as before. **The rule**
(`Planner.Joining`): a first start whose entry has a part here, in a repository whose sessions open their own trees, goes into the
tree of the entry's newest part (its last run here by `created`) when no active session holds that tree, and otherwise starts at once
alongside in a tree of its own, its sentence naming the holder; nothing waits. A tree a start takes at one look holds it for the rest
of that look, both ways: a second request of the entry runs alongside, and a resume or a carry-on into it waits, *queued behind* the
request (`RepositoryBusy`, as a live holder makes it). A chain's step in its parent's repository keeps CHAIN2's growth, and a
repository whose sessions run in its checkout is unchanged. **A tree gone since its landing** grows again from the branch the
entry's newest landing here stands on, else from the line (`SessionTrees.OpenAsync`'s `partOf`), and its opening says which and
whose tree went. **The new part is handed** the parts before it, newest three by name with their quest, state, note's first line,
tree and branch, the rest counted, and how its tree stands to theirs, with what the part before it left uncommitted where it went in
(`SessionPartsText`; the goldens `part` and `part-alongside`); its account counts it as the carry-on section from the records, so
no page catalogue changed. **Not built:** a note line on the record for a part gone into a tree (its start says nothing there, as a
start in the root does), which needs a code the page words; the publisher-less ask quest and the conversation that took a quest
(CHATTAKE1) are not read. **What the checks do not cover:** the planner and the instruction are held by tests; the tree's growth and
one look's going-in are held by Process tests; the owner's install, and whether a part in a shared tree lands its predecessor's
commits with its own as the owner expects, are not.

**As built 2026-10-14 (SESSONE1b, the design's §1.6): the driver groups by entry.** `SessionGroups.ReadEntries` (Trees) places each
entry over the rows `Read` still answers: the key is read as an opaque string (`SessionRecord.Entry`, a record with none is
`session:<id>/<repository>`), the group is the first of D126's any part's row qualifies for, and the leading part is the newest of
that group. `SESSION_GROUPS` answers `entries` beside `sessions`; `daoris-driver sessions` prints one line per entry with *N parts*
and the parts indented under it, and `--json` keeps the rows and adds the entries (`SessionsCommand.JsonEntryFields`,
`JsonPartFields`). **How a part began** is read from the record's `from` and its quest, in this order: `from` is *handed-over*; an
earlier part of the same quest is *retried* (it failed), *carried-on* (it was stopped or stood down) or *resumed* (any other
ending, D79's resume among them); a quest a session published is *asked*, naming the asking repository; a chain step (`Parent`) is
*carried-on*; otherwise *opened*. An ended intake leaves the entries where a quest of the look was asked by its ask or a session of
its ask remains, and stays while it runs or when nothing was published; the rows keep it until SESSONE1c draws entries.

**As built 2026-10-14 (SESSONE2a, points 6 to 8): the channel's record and doors, in the service.** `ChannelStore` and `ChannelDesk` are in
the Asks module (`Asks/Channel.cs`): a `channel` table, one row per message (its own `id`, the ask and its workspace, the moment, the poster's
session, repository, adapter and entry, or none for the person, `to` (none is everyone), `re`, `question`, the words, and an `origin` that is
null for this machine's own, which SESSONE2d fills as `origin/id`), and a `channel_marks` table of one read mark per ask and entry, the
person's entry the word `person`. The bounds are `ChannelBounds`: 4,000 characters, ten messages a part (counted on the session record, in
the insert's own statement so two posts cannot both pass), twenty the next part is handed (for SESSONE2b). A refusal is `ChannelRefusal`, a
code: the tools say it in a sentence, the HTTP door answers `ErrorResponse.code` (`empty`, `too-long`, `bad-to`, `bad-re`, `not-found`). Readings
the design left open. **The ask a session speaks on is its entry's origin** (`ask:<id>`), by the one rule (`SessionLedger.WithEntryAsync`), so a
quest's session, an intake and a sibling's request all find it, and a conversation, a helper (`Serves`) and a reviewer (`Opinion`) do not: a
helper or reviewer is refused its own code, and neither reads. **The repositories a `to` may name are the ask's quests' receivers and its
repository askers**, matched ignoring case and stored as the registry spells them. **Daoris's lines are the ask's quests as they stand**, those
asked by it or whose entry's origin is it: `published` at the quest's filing and one line of its present state (`taken`, `done`, `declined`,
or `awaiting` for a done that waits on the person's yes), so a quest taken then closed reads *published* and *done*, never *taken*; a wait
and a request waiting for a tree are not read (the driver knows the second; the first is not a quest's state). **A mark is a moment**, the
newest item read, which never moves back, so a late arrival from a teammate is not skipped by a clock; the unread count is the items after
it, lines included. The person's post is kept on the channel and on the ask as the new word kind `channel` (`AskWordKind.Channel`; an older
build passes a kind it does not know over), and where the driver also reports it as `added` to a running session (SESSONE2b), the ask holds
it twice, which that row must not do. On the wire, `GET /api/asks/{id}/channel` (an open read, moving no mark) answers `items` in time order,
messages and lines as one flat shape (`ChannelItemResponse`), with `unread` and `mark` for the `entry` named; `POST /api/asks/{id}/channel` is
the person's post; `POST /api/asks/{id}/channel/read` moves an entry's mark to `through` or the newest item, which is how a page and a driver
clear unread. All three are a local host's alone, as asks are, and a shared host maps none until SESSONE2d. Deleting an ask forgets its
channel, since the same words asked again are the same ask. History's clear does not yet (the same `AskStore.DeleteAsync` inside its
transaction), and is SESSONE2d's with the travel.

**As built 2026-10-14 (SESSONE1c, point 5): the window shows entries.** `SESSION_GROUPS`' `entries` are read beside its rows under one
query key (`useSessionEntries`, the page's `work/entries.ts`), so the page groups by nothing of its own. **The rail** lists each entry's
leading record only (`listedSessions`), which also leaves out the ended intake whose ask became quests, since no entry holds it; a host
before entries answers none and the list is the records it always was. The row is named by its ask where an ask began the line of work
(`askName`, the ask's page's own word) and says *N parts* on its line; it is marked attended while any of its parts is. **A session's page**
gains a *Parts* strip under its head (`PartsStrip`), oldest first, each part's word, how it began, its quest and the tree or branch it
held (the row's `ownTree` and `SESSION_WHERE`'s landing), *Part 2 of 3* beside the title; a press attends that part, so every act
stays the part shown's, which was already the page's rule. **Archive reaches the entry**: `useSessionActs` is handed the entries and sends
every part's id to `SESSION_ARCHIVE`, for the row, the header and *Archive what ended…* alike, counting entries as the list does.
**Group by ask** is a third choice of the list's ⋯ (`work.list.byAsk`), offered only where entries are answered: each ask under its name,
its lines of work under it with their repositories, and *Not on an ask* last for conversations and lines rooted in a quest alone. **The ask's
page** lists its lines of work, one per repository with its parts counted, as a *Sessions* section (`AskLines`); its intake keeps its own
section. Two readings the design left open: under *Group by ask* a row keeps its leading part's own name, since the heading is the ask's;
and the strip's first words for a part that followed another name it by its number (*retried after part 1*), or by its id where the
strip does not hold it. The glossary gains *part* 段 and *session*'s meaning of one line of work. Not built: the channel's unread count
under an ask (SESSONE2's rows), the monitor's list by entry (it stays the present tense, by record), and the strip's own rail marks.

**As built 2026-10-14 (CHATTAKE1, the design's §1.2 rule 2): a quest a chat took joins that chat's line.** The take now names its quest:
`SessionLedger.MarkTookAsync` passes a chat's quest id to `SessionStore.MarkTookAsync`, which writes the new `took_quest` column (added after
the table rebuild, `NULL` for a record from before) and moves the revision so the team's copy learns it; a session on a quest of its own
records none, as it needs none. `Session.TookQuest` travels with the record (`FedSessionRecord`, `SessionWire`'s `tookQuest`, written
only where present, the push, the feed and the mirror), since it names a quest and no path. `SessionEntries.OriginOfQuestAsync` reads it
right after the ask and before the publisher and the chain parent, through `ISessionEntryFacts.ChatTookAsync` (`SessionStore.FindChatTookAsync`:
this machine's chat first, else a teammate's mirror, the earliest taker), and the quest takes that chat's origin. A chat from before the
field marked its take without the quest, so it names none and its quests key as they did; nothing is back-filled. This replaces the
"not built" reading in SESSONE1a's note above.

**As built 2026-10-14 (SESSONE1h, SESSONE1g): one reader of a key, and a part's going-in said.** `EntryKey.Parse` (Quests/Domain) is the
driver's one reader of an entry's key, split at the first slash: `Origin`, `Repository` and `HasSlash`, a key with no slash being all
origin with no repository; `EntryParts.KeyOf` and `SessionGroups.ReadEntries` both use it. One reading changed, for the better: a key with
no slash gave the entries' `repository` the whole key and now gives it empty. **A part gone into its entry's free tree now says so**: its
start writes the note `started.joined` with the earlier part's session (`Driver.StartingNote`'s `joinedSession`), in both catalogues and
the page's `NOTE_CODES`; a start in the root still writes none. A part grown again after its tree went keeps its opening `started.tree`,
whose `basedOn` already names the branch it grew from, so no second note is written there. This replaces the "not built" reading of the
note line in SESSONE1d's note above.
