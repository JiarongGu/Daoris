## D88 — A session's branch goes once git proves its work is on a branch of the person's (2026-09-28)

**Decision (WSR3, from the owner's *"after merge to master or feature branch we should cleanup daoris
branches"*).**
- **The proof.** A session branch's work is landed when every commit on it is on a branch that is
  not Daoris's: a local branch outside `daoris/`, or a remote-tracking branch. The line, a feature
  branch the branch form made, and a branch the person pushed all count. Commits only Daoris's
  branches hold are unlanded, including a chain's earlier step, whose branch is also Daoris's. One
  proof serves every door: a tree's removal without `--force`, the tidy after a landing, and the
  clean-up.
- **The tidy is the person's rule.** A landing rule may say `tidy`: once a press lands the work,
  its tree and branch go, if the proof holds. Without it, the tree stays, as it always has.
- **The clean-up is the person's press.** Every session branch on this machine is listed first with
  what it holds: landed, empty, unlanded, holding uncommitted work, or in use by a session still
  running or waiting. Then one press removes those the proof clears, checking each again right
  before it goes. Unlanded work, uncommitted work and a session in use are kept and named. The
  terminal twin is `daoris-driver trees clean`, which lists and, with `--yes`, removes.

This amends **D51 rule 7** (*nothing deletes itself*): a removal now happens only by a person's press
or a rule the person set, and always behind the proof.

**Why.** Branches piled up: FG5 left sixteen empty ones in one repository before they were deleted
by hand. The line alone is the wrong proof once work lands on a feature branch: it would call that
work unlanded forever, and a person forcing removals by hand is the risk the proof is for.

**Rejected.**
- **Proving against the line only.** It refuses every branch the branch form landed (D87).
- **Deleting a branch git calls merged (`branch -d`).** Git asks only about the checkout's HEAD, so a
  branch landed on a feature branch would stay, and one merged into whatever the checkout happens to
  be on would go.

*Amended by D102 (WSR5a, 2026-09-30): the clean-up also lists the branches landings made and recorded,
in a group of their own, and the same press removes those whose work reads on the line by content, or
that are inside another that does. The session branches go first, since this proof may count a landed
branch as holding their commits.*

**AUTOTIDY1, built 2026-10-09: an empty session branch goes without a press.** On the owner's install a session branch that
held nothing beyond the line, left after its pull request merged, stayed until *Clean up* was pressed. Now the watch's look
removes such a branch, and its tree, by itself. This amends the clean-up above, and D51 rule 7 again: one more removal happens
without a press, and only where nothing is lost.
- **What goes.** The clean-up's `empty` kind: every commit on the line, read from the line here with no fetch (the local
  branch, else origin's copy as last seen). It goes with no tree. With a tree, it goes only where the tree is this home's and
  holds nothing at all, with no uncommitted, untracked or ignored path, a build's output the checkout also holds included. Its
  branch must also have moved since it grew (`session-branches.json`'s `from`): its work is what the line took.
- **What stays, exactly as the press finds it**, each at the press as before: commits the line lacks (unlanded, landed on a
  branch of the person's, and a squash merge's content-held or carried branch, never `empty`); anything in its tree; a tree
  outside the trees home; a tree a session running or waiting names, asked inside the repository's `TreeLock` held alone, so a
  start choosing a tree is never raced; a tree a review step in progress shows from (REVIEWENV1d), asked with the sessions:
  the tree of the session that said each set-up still waiting for the person's verdict, read from the service's records as
  the review's gate reads them, with a desk or none, and each build a shell's desk serves; and a guard git could not read. A
  tree whose branch never moved stays too. Words to its session go on in that tree (D137), and removed, a chat could not go on
  at all (`ContinueWhy.Tree`).
- **The look's last guards**, asked after the press's judgement and its judgement again, each keeping the branch for the press
  and said: a tracked path marked `assume-unchanged` or `skip-worktree` (`ls-files -v`), whose edit reads as clean to status;
  another repository in the tree, a `.git` below its top found by reading the folders, which the tree's own status skips; a
  link anywhere below the trees home on the way to the tree, which makes the tree somewhere else; a locked tree; and a folder
  of this home's for the branch that git lists no tree for.
- **One path, and never a delete of a tree's folder.** `SessionTrees.TidyEmptyAsync` runs per repository whose root is a
  repository of its own (a `.git` folder, then `rev-parse --show-toplevel`, since git walks up). Its candidates are
  `for-each-ref --merged=refs/heads/<line> refs/heads/daoris/`. They go through the press's own sweep, which takes the press's
  `Removable` or the look's `GoesByItself` and judges only the branches named. Each is judged, then judged again before it goes,
  and its branch is deleted only at the commit judged. A status check cannot close the moment between the last look and a
  delete, and a process may write into the tree then. So the look moves the tree's folder aside, in one rename on the same
  volume, into `trees/.tidied/<workspace>/<repository>/<name>-<moment>`. Then git lets go of that tree's record alone: `git
  worktree remove` of a tree whose folder is gone deletes only the record, where `prune` would take every stale entry. A late
  write lands in the folder moved aside. On Windows a folder whose files are held open cannot be renamed, so a refused rename is
  a tree in use (`busy`), kept for a later look; where git will not let go of the record, the folder is put back. A later look
  deletes a folder moved aside fourteen days after its move, and only where nothing in it was written after the move (newest
  write older than the moment in its name). Otherwise it stays and is said once. The press keeps `git worktree remove`. Once a
  removal begins, each git command runs to its end whatever the loop's token says, and the repository's hold is kept until it
  has. The record forgets what went.
- **The line by its full name, the working trees as git lists them.** The line is compared as `refs/heads/<line>` (else
  `refs/remotes/origin/<line>`), in `ComparableAsync` and in the line's forms, for the press and the look, since git reads a tag
  of the same name before the branch. A list of the working trees that git could not give is never read as "no tree here":
  the look judges nothing in that repository, and the press's list says each branch is unread. The deletes and tidies that ask
  it keep the branch, and the bringing up to date and the advance refuse. A tree a session names through a link and the same
  tree git names where it is are one: the busy match compares paths with each link resolved.
- **Said once.** `BranchTidying` runs beside the watch's looks once each five minutes, from the first look, as WSSETUP5's
  following does. Its `tidy  …` lines join a later look's report, each repository's said as it is done. The machine log has
  `branch.tidied` (with the folder moved aside), `branch.kept` once while the reason lasts (unread, refused, busy, hidden,
  nested, linked, starting, sessions), `tidied.purged` and `tidied.kept` (the machine-log design §4). A branch kept for what it
  holds is the press's and says nothing.

Judgements made in building: only the watch tidies, the shell's and the headless `drive`'s, so a one-look run and a gate's
driver change no branch. No setting turns this off, since none existed: a landing rule's `tidy` (D157's landing step carries
it) is the after-landing tidy, and an empty branch whose tree holds nothing loses nothing. No *Branches tab history* exists to
write to. The log's `branch.tidied` lines are the record, readable with `daoris-driver logs --event branch.tidied`, and a tab
showing them is web work. A second agent's read-only review (Codex) found eight defects before the merge; each is above, and
each was seen failing first, as a test over real git or under a sabotage of its fix. A list git could not give is the one case

table, the words said once by each code, the pace, the trees a review shows from) and `BranchTidyingProcessTests` (`Process`

busy match resolves links, and its removal is never cancelled halfway. A start the tidy's hold meets says
`TreeLock.Replaying`'s words (*being brought up to date*). The held-open rename is Windows' refusal; elsewhere the rename goes
and the holder's writes land in the folder moved aside. Nothing was looked at on the window.
