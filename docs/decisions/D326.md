## D326 — Claude Code renders a session's prompt and tools fresh at every request; its record of them is off on both doors (2026-11-19)

**Decision (TOOLSCHEMA1).** Every Claude Code session Daoris starts, resumes or converses with runs with the harness's record of its
system prompt and tools off: `--system-prompt-snapshot off` ahead of `-p` on the native door's every recipe (so a driven run on the layer
carries it in its program), and the preset `{ type: "preset", preset: "claude_code", snapshot: false }` in the protocol door's options on
every open and resume, the person's memory appended to it where it is handed. Each request then carries the tools its servers serve now.

**Why.** A session resumed after an install that added `question_ask`'s `site` was sent the tool without it and put the address in its
words. Its harness had started a fresh connector of the installed build (the connector's log: started 2026-11-18T21:32:52Z for the
session's tree), but Claude Code (2.1.284 to 2.1.325, read in the binary) records the system prompt and tools at a conversation's first
request (`prompt_snapshot` in its transcript) and sends that record at every later request and resume until a compaction: a new tool name
is added as a mid-conversation change, a tool whose description changed is re-described only in some turns, and a tool whose parameters
changed under the same description never is. The transcript's request shapes, hashed over the system prompt and every tool's schema, show
the resumed requests at 21:33Z and 22:39Z carrying the shape recorded at 18:23Z, before `site` existed, under two installs that served it.
`ClaudeResumedToolsProcessTests` reproduces it on the real program with a stand-in server and a keyless stand-in model.

**Alternatives rejected.**

1. *The record off only for a resume whose tools changed.* Daoris would need every server's tool list at the last request (the
   plugins' and the person's own included), and the stale record stays the last one until a compaction, so once off it must stay off for
   that conversation anyway: more state for the same end.
2. *Say in the session that its tools changed, the record left on.* A second description of a tool beside the harness's, which the model
   must trust over the schema it is sent; and it says nothing of a rule or memory that changed.
3. *Restart or reorder the connector.* The connector already starts fresh at each resume; the stale list is the harness's, not the
   server's.

**What it costs.** A prompt or tool list that did change between two launches changes the request prefix: that request misses the prompt
cache, and with extended thinking the model's earlier reasoning is dropped, as the SDK's own note says. A resume a few minutes after the
turn before, with nothing changed, renders the same prompt and keeps the cache. A harness older than the flag refuses it at the start;
every Claude Code Daoris measured since 2.1.284 takes it.
