## D299 — A run's check judges the work as merged onto its line's tip; a moved line is no red (2026-11-16)

**Decision (CHECKCHASE1).** A workflow run's `check` judges the work merged onto its line's current tip: where the work does not hold
the tip, a merge commit is made from git objects alone (`LineMerge`: `merge-tree --write-tree`, then `commit-tree`, the tip its first
parent) and the verification tree checks that out; the session's branch is never rebased or moved. Only a conflict (gate `hand-back`,
naming its paths) or a real red sends the work back. The verdict still names the work's commit, which the landing lands onto the line as
it stands then (area `workflows-review-landing.md`, rule 40).

**Why.** On 2026-11-16 the install's run of quest #82406c797e18 failed its check `hand-back` each time main moved under it ("N commits
behind `origin/main`… rebase it and commit again"), so on a line that moves every few minutes the run chased main, and the steward held
pushes to let it land. This repository's own merge tool already judges a branch as merged onto main.

**Rejected:** rebasing the session's branch in the check (it rewrites work a session holds and its kept words name); keeping the
`hand-back` refusal and asking the session to merge (the chase itself); and checking the work as it stands while ignoring the line
(it lands untested combinations).
