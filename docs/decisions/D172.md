## D172 — The Daoris folder is laid out by what a thing is and who may lose it: the program, your settings and records, sign-ins, the work, what can be fetched again, what a run holds, and the logs, each a top folder (2026-10-16)

**Decision (HOMELAYOUT1, amending D63 and D93's layout).** The owner, 2026-10-16: *"we also need to shape the Daoris folder
into a better separation since we will have more files now (data, app, res, …)"*. An install is `Daoris.exe`, `app/`,
`data/` and `update/`, and `data/` holds 5.1 GB at one level on the owner's install: the person's settings and records
beside the agents' account homes, two browsers' profiles, downloaded runtimes, session trees, locks and logs. Nothing tells
a person which part is theirs to keep, which holds a sign-in, and which Daoris fetches again. The contract is
`docs/2026-10-16-install-layout-design.md`; this records what it settles.

1. **Seven categories, each a top folder of the Daoris folder.**

   | Folder | What it holds | Who may lose it |
   |---|---|---|
   | `app/` (with `Daoris.exe`, `INSTALLED.md`, `update/`) | the program: everything a build ships | nobody: an update replaces it whole (D139) |
   | `data/` | your settings and records: every choice, the knowledge store, the conversations, the plugins you installed | only you have it; back it up |
   | `profiles/` | sign-ins: the agents' account homes, API and deployment keys, Daoris's browser's and the window's own profiles | you, at the cost of signing in again; never shared |
   | `work/` | where agents work and the files records keep: session trees, rooms, attachments and proof | work in progress lives only here; Daoris cleans it |
   | `cache/` | what Daoris fetched and fetches again: agents' and tools' versions, the service's installed copy | anyone: the next use downloads again |
   | `run/` | what a running Daoris holds: its locks, its address file, spawn and start files | anyone while Daoris is closed |
   | `logs/` | the machine log | evidence only; it keeps 30 days by its own rule |

2. **`DAORIS_HOME` names the Daoris folder**: an install's own folder, beside `Daoris.exe`, or a development or scratch
   root. Every default still derives from it (D63), and nothing of Daoris's goes under the user profile. A value that names
   an install's `data/` (a folder named `data` whose parent holds `INSTALLED.md`), which every account that met D63 holds,
   names that install, so no account's variable is rewritten. There is no variable per category; the per-file overrides
   (`DAORIS_DRIVER_CONFIG`, `DAORIS_KNOWLEDGE_DB`, …) still win where set, and D105's rule for an inherited home stands.
3. **`data/` holds no secret.** A file that holds a key is a sign-in and lives in `profiles/` (`keys.json`, `remotes.json`),
   so `data/` can be copied, backed up or handed to someone helping without handing over an account.
4. **One shape for an install, a development run and a test.** A scratch root is laid out as an install is, less `app/`
   and `update/`. The window's own memory, the UI kit's data area (D22's THEMESTART1 note), is `<kit root>/profiles/window/`
   by the kit's `ShenoraPathsOptions.DataDirectory`; `--app-root` still names the kit's root, so the dev loop names one
   scratch folder for both, and `--real` keeps a development window off the installed window's profile.
5. **An entry is where it is.** Each entry has a new place and an old one (under the old home: an install's `data/`, or
   for any other root the root itself). It is read and written at its new place if that is there, else at its old place if
   that is there, else at its new place. The three home twins (the driver's and the service's `DaorisHome`, the CLI's
   `home.ts`) hold the same table, and nothing joins a home path by hand (HOMELAYOUT2).
6. **What moves, and what never does.** At a start after a confirmed update, with no other process of the folder
   running, Daoris renames into place each entry only it names, by a path it derives at each use: the logs, the downloaded
   versions, the keys, the browsers' and the window's profiles, what a run holds. What anything else names by path is
   never moved: an agent's account home (the tool's own folder, which records paths inside it), a session tree and a room
   (an agent's conversation and git's worktree links name them), a kept file (handed to agents by path), and the home's
   `bin/` (other repositories' `.mcp.json` name it). Each stays and is read where it is; what replaces it is made in the
   new place. A name the table does not hold stays where it is. Nothing is deleted, every move is a rename on one volume,
   and the machine log has a line for each.
7. **Backup, move and clean-up mean one thing per folder** (the design's §4): back up `data/`, and `work/` for work in
   progress; never back up `cache/`, `run/` or `app/`; keep `profiles/` as private as the machine. A category is cleaned
   by Daoris's own acts, never by deleting a folder while Daoris runs.

### What this does not decide

The page that shows each folder, its size and its source is WIRING1a's (`docs/2026-10-16-this-daoris-design.md`). Moving
what point 6 never moves waits on measuring each harness (HOMELAYOUT5, proposed). A cache on another volume is not offered.

### Rejected

- **Categories inside `data/`, the install's top left as it is**: the owner asked for the folder itself to separate, and
  `data/` stays the one folder worth backing up only while it holds only what is the person's.
- **`DAORIS_HOME` kept naming `data/`, the other folders found beside it**: a scratch home's parent is not Daoris's, so a
  test handed a home would write next to it.
- **`res/` for what is fetched again**: the UI kit's `res/` is read-only resources that ship with a build. What a build
  ships stays in `app/`, which an update replaces whole; a second shipped folder would need a second swap.
- **A record of which entries moved**: point 5 reads the disk itself, so there is no second truth to drift from it.
- **Moving every entry at once**: a tree, a room or an account home moved under a conversation or a tool that names it by
  path is broken work, which no migration may cost.

### Amends

- **D63**: the home is the Daoris folder, and `data/` is one category of it (point 2); its `$DAORIS_HOME/bin` is
  `cache/bin/` for a new home.
- **D93**: the install's top holds `profiles/`, `work/`, `cache/`, `run/` and `logs/` beside `app/`, `data/` and `update/`.
- **D124's WSSETUP3 note**: the install's `app/bin/` is the home's own `app/bin/`, no longer the home's sibling.

**HOMELAYOUT2 (2026-10-16).** The three home twins hold the table (`HomeEntry` in the driver and the service, `HOME_ENTRIES`
in the CLI), every new place still the old one, and every reader asks for an entry by name (`DaorisHome.Entry`,
`homeEntry`); the CLI's `home-census.test.ts` fails a join of a home by hand in the desktop, the service and the CLI, with
three joins owed and their reasons. A design review added one rule to point 5: **an entry's new place is taken only where it
holds what the entry is** (a file that is not empty and, for JSON, parses; a folder that is not empty; or, for an entry known
by the names it holds, one of them), so an empty or half-made new place never shadows a populated old one; **where both hold
it, neither is chosen**: the refusal names both (`DaorisHome.Twice`, `HOME_TWICE`), for the caller to say. An old place that
does not read is still read where it is, for its reader to say so. A list of an entry's items reads both places, and an item
asked short of its parts is the folder holding them, never refused. The census found one entry §3 did not hold: `usage-read`,
the empty folder the tool's own sign-in's usage read runs in, placed in `work/`. Left to HOMELAYOUT3 with the new places: the
doors that say a refusal for an entry in two places, the trees' code reading both places per tree where it holds one root
(`TreeContext.TreesRoot`), and the readers that take the home from a file's folder (`DriverConfig.HomeOf`,
`HarnessSettings.HomeOf`). Merged after HOMEID1, HOMELEASE1 and HELPPLUG1a, the table took the three places they made:
`home-id` (`home.json`, in `data/`: a new id would be another home to every terminal), `home-lease` (`home.lease`, in `run/`,
read before `driver-lock`, which an older build's live lock still answers) and `plugin-approvals` (`plugin-approvals.json`, in
`data/`). The launcher compiles the driver's table in beside the lease, so its swap finds the lease where the desktop does.

*2026-10-20, HOMELAYOUT3:* the new places are on in the three twins, and an install's old home moves into them once.
`PENDING_TESTS` is empty. Each entry's new place is its design §3 place under its category's folder, and the table took one
entry more: `home-move` (`run/home-move.json`), the move's journal. What this settles:

- **Point 2, as built.** A home's Daoris folder is found from the home (`DaorisHome.FolderOf`, `homeFolder`): a folder that
  holds `INSTALLED.md` is that install; a `data` folder whose parent holds it names that install; any other root is its own
  Daoris folder. An install's `data` entries are one place by both spellings and keep the old spelling, so the home handed
  down stays `<install>/data`. D63's `DAORIS_HOME`, every account's variable and every child's environment are unchanged,
  and the move runs on a home named that way. A home taken from a file's folder (`DriverConfig.HomeOf`,
  `HarnessSettings.HomeOf`, `EngineBrowser.HomeOf`, the CLI's `homeOf`) strips the entry's new parts, else its old ones.
  Asking for a new place makes its category's folder where the Daoris folder is there, so an empty `run/` or `work/` may
  appear. The System page counts a folder as there only where it holds something.
- **The lease** is taken at `run/home.lease`. A live holder at the old `home.lease`, or at `driver.lock` in either place,
  still holds the home. Neither is an entry of the move: a held lease is never renamed under its holder.
- **One root each, as found.** The trees keep the one root the table resolves (the old `trees/` while it holds any,
  `TreeContext.TreesRoot`), so a new tree is made beside the old ones. A session's pid is not moved: it is read beside the
  session's record in both places (`SessionHomeFiles.PathsOf`).
- **The move** (`HomePlacing`, run by `InstallHome.Establish` after D63's move-in) runs only when three things hold. The last
  update is at rest: no `update/previous/`, and no swap moving, started or confirmed. The first start after a swap therefore
  moves nothing, since D139's roll-back reads only old places. No other process of the install's folder runs but its
  launcher (`HomePlacing.OthersRunningFrom`). And it takes a `migration` lease without waiting. Short of any of these it
  moves nothing, and the next start tries again. It renames each entry the design marks *moves* whose old place holds it
  and whose new place does not. The window's two folders go through `profiles/window.moving/` before the kit opens, and the
  kit's data area is `InstallHome.WindowMemory`, the window entry where it is. The journal names each rename before any is
  made. A start that finds the journal or the staging folder first puts back what a stopped start left mid-way, then plans
  again. A rename that is refused (a host adopted from an earlier start holding `logs/`) leaves its entry where it was.
  Nothing is deleted but an empty folder at a new place. The machine log says `home.moved`, `home.move-recovered`,
  `home.move-failed` and `home.move-held`. The start's notice names what moved and what could not.
- **An older `daoris` on a `PATH`.** The install's own programs are swapped together (D139); a CLI installed apart from it
  and older than this build reads every entry at its old place. It reads and writes `data/`'s entries as before. A moved
  entry (the keys, the remotes, `running.json`, the lease) it finds absent, so it finds no running Daoris for its verbs and
  acts alone, and the desktop's lease at `run/` does not hold it back (its own lease at the old place holds the desktop's
  writers back). An entry it writes again at an old place beside the moved one is then in both places, which this build
  refuses, naming both, for the person to keep one. Updating that CLI with the install ends it.
- **Not built.** The design §7.4 repair of the trees' links after a person moves the whole folder: this move renames no
  tree.

*2026-10-20, HOMELAYOUT4:* the dev loop is one Daoris folder, as an install is (the design §6.1). `npm run desktop -- run` makes
`_fixtures/desktop/daoris/` with `app/` and the category folders, names it as `DAORIS_HOME` and as `--app-root`, and lays the plugin
offers in its `app/`; the family copy stays beside it. The readers that looked beside the home (`Tools.InstallBin`, `installBin`,
`ToolResources.BesideHome`, `builtInList`, `PluginOffers.BesideHome`, `offersFolder`) now look in the home's Daoris folder
(`DaorisHome.FolderOf`, `homeFolder`): an install's `app/` whichever way its home is named, and a scratch root's own, which has
no marker and is its own home. A `data` folder of no install is therefore a root, not a sibling of an `app/`. A run told
`--app-root` outside an install is handed the kit `DataDirectory` of that root's `window` entry (`InstallHome.AppRootOf`,
`WindowMemoryOfRun`), so its window's memory is `profiles/window/` as an install's, and `engineLogOf` reads it there. `--real`
keeps the kit's own `data/` under the build's folder.
