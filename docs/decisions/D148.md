## D148 — A plugin may answer a query: a landed branch's pull request state is asked of the plugin that opened it, and a completed pull request's work counts as landed where git confirms its merge commit on the line (2026-10-04)

**Decision (PLUGHOOK1).** The owner completed a pull request in the work repository's Azure DevOps by squash. The session
branches whose commits it carried still looked unmerged to git: `git merge-base --is-ancestor <session tip> <line>`
failed, though the line's tree equalled the merged branch's. So neither LAND3's tidy nor D102's clean-up could see that
work as landed. The owner: *"this is more like an Azure DevOps related logic so we need to do this as a plugin change,
and also this is a good chance to design plugin hooks into other processes"*. The contract is
`docs/2026-10-04-plugin-hooks-design.md`.

1. **A fourth kind of point, the query, and its first point, `work/state`.** A query asks a plugin for a fact only its
   platform holds. Daoris acts on the answer only where git confirms it, and an unanswered query is *not known*, never a
   default. `work/state` asks about a landed branch's pull request. It asks the plugin that pushed the branch, which the
   landing entry names, else the plugin the repository's landing rule names. Only one plugin is asked, never a
   waterfall, and only one that is installed, switched on, sound and speaking there (D100's four reasons).
2. **It is asked only where git cannot tell, at the occasions that may remove.** Daoris's own proofs run first (D88,
   D102). An entry is asked about when its kept answer is not `completed`, it was not asked in the last minute, and its
   answer could remove something now. The occasions:
   - LAND3's tidy, after a landing's plugin step;
   - the clean-up's look;
   - bringing up to date's look, after its fetch;
   - *Ask again*: the review's press, and `daoris-driver trees state`.

   It is never asked at a press that removes, at a read, on the loop's look or on a timer. Each occasion starts one
   process per plugin. A frame waits 30 s, its handshake included, and no frame starts after 60 s.
3. **The frame and the answer.** The frame is sent `repository`, `workspace`, `root`, `branch`, `line`, `pullRequest`
   and `pushedTip`. The answer is `{ state, pullRequest?, mergeCommit?, sourceCommit?, target?, how?, at?, message? }`:
   - `state` is `open`, `completed`, `abandoned` or `unknown`;
   - `completed` requires the full ids of the merge commit and of the source commit it merged;
   - `how` is `merge`, `squash`, `rebase`, `rebase-merge` or null.

   Anything else is not an answer, and a tool that fails is the plugin's error.
4. **A completed answer counts where git confirms it.** It clears a landed branch when three things hold:
   - its target is the line;
   - its merge commit is held here, on the local line or on `origin/<line>`;
   - the branch's recorded tip is the source commit, or an ancestor of it held here.

   The landed branch then goes at the press of the clean-up or of bringing up to date, marked
   `removedAs: "pull-request"`. A session branch goes at LAND3's tidy and at the clean-up's press when its tip is the
   source commit, an ancestor of it, or an ancestor of a tip the answer cleared. Every keep of D88, D102 and LAND3
   stands. Where the answer does not clear a branch, the row names why with a code: `open`, `abandoned`, `unknown`,
   `other-target`, `merge-not-here`, `beyond` or `source-not-here`.
5. **Without an answer, nothing is removed.** A plugin may not be ready, stay silent, answer late or wrongly, refuse,
   or not be reached. Each leaves every branch where it is. A failure never overwrites a kept answer: absent is never zero (D57).
6. **It keeps the facts it chose by** (D143). The landing entry gains:
   - `pullRequestState`, the latest answer, with the plugin and when it was asked. `completed` is final;
   - `pullRequestAskFailed`;
   - `removedAs: "pull-request"`, with `removedOn`;
   - `carried`, each session branch removed on its answer.

   The machine log gains `plugin.*` lines by `state`, with no address and no words. The facts are read on the review's
   note, by `trees land --plan`, on the rows of the clean-up and of bringing up to date, by `trees state`, on Git's list,
   by `trace` and by Ask Daoris.
7. **Daoris's own plugins answer it.** The Azure DevOps plugin works in the checkout. It finds the pull request by its
   address, or by `az repos pr list --source-branch … --status all`, then reads `az repos pr show --id …`. It maps
   `status`, `lastMergeCommit`, `lastMergeSourceCommit`, `targetRefName`, `closedDate` and
   `completionOptions.mergeStrategy`. The GitHub plugin reads `gh pr view … --json
   state,mergeCommit,headRefOid,baseRefName,mergedAt,closedAt`, or uses `gh pr list --head …`. It gives no `how`.
8. **A new point is additive.** A handshake naming a point this build lacks no longer refuses the plugin: the point is
   named once and never asked. The kit stays strict, and `protocolVersion` stays 1.
9. **The other processes are weighed, and none gains a point now** (design §3):
   - review threads back to the session (`work/review`), held until LAND2c lands and the first change request is
     carried over by hand;
   - a pipeline's verdict as evidence (`work/checks`), which waits on EVID1b and on the order of D145's landing;
   - work items as asks, a session's capabilities and a quest's close, which get no point. A declared server, the rules
     handed, `session/ended` and the platform's own completion already serve them.

**What is not checked:** whether the merge commit really merged that source commit. That is the platform's word, kept
as its word. Git confirms the rest.

**Why.** D102 judged by what this machine knows, and a squash removes what git would need. The platform knows, and only
the plugin speaks for it: Daoris runs no platform CLI and holds no credential (D87, D100, D145). The answer names which
commit carried the work, and git confirms that commit is on the line. So D102's rule that a branch goes once its work
reads on the line still holds. The platform supplies the link a squash removed. Asking only where git cannot tell, at
looks that may remove, keeps reads fast and spends no platform call that nobody is waiting on.

**Rejected.**
- **Daoris asking the platform itself**, with `az`, `gh` or an API in the driver. D102's reason stands for core: a
  network call and one platform's API, which D87 left to plugins.
- **Comparing trees**: a `git merge-tree` of the merge commit's parent and the branch, against the merge commit, as the
  owner's observation did. It fails once the line has moved, where the platform resolved a conflict, and for a rebase.
  It still cannot say the pull request completed. Patch equivalence stays rejected (D102).
- **Trusting the platform without git**: removing when the merge commit is not on the line here. It would remove work
  for a pull request completed into another branch, or on a plugin's mistake.
- **Asking at every read, on the loop's look, or on a timer.** That is a network call nobody waits on, and a read that
  waits on a platform. D147 rejected a timed fetch for the same reason.
- **Asking again at the press.** What was listed is what goes. A press that asked again could remove what the person
  did not see listed.
- **A waterfall over every plugin.** One platform holds a branch's pull request, and two answers would need a rule to
  choose between them.
- **One frame carrying every pull request.** One slow lookup would make all of them late.
- **A failure read as `unknown`, overwriting the kept answer.** Absent is never zero.
- **The state on the session record**, which travels to the team's remote (D47 §4), or in `session-branches.json`. A
  landing is this machine's (D102).
- **A new `protocolVersion`.** A point is additive. A new version would refuse every plugin written before it.
- **LAND3's tidy removing a landed branch.** A landed branch goes at a press (D102). The tidy removes session branches.
- **For the other processes:**
  - polling review comments, which would carry someone else's words without a press;
  - a pipeline's verdict before EVID1 and its order are settled;
  - a work-item intake point, which would start work from words the person never said (D133);
  - secrets in a session's environment, which the agent can read;
  - a close hook that writes to the platform before the pull request, the last human step, completes.

**This amends:**
- **D102.** Its rejection of asking the platform holds for core and is lifted for the plugin. A landed branch gains a
  fourth proof, `pull-request`. A hand-off refuses a branch that proof clears, as work that already reads on the line.
- **D88, and LAND3's note on D102.** A session branch's work is landed where a completed pull request carried it, as git
  confirms.
- **D113 §2–§3.** The review's `landed` answer carries `pullRequestState`, and its note says it, with *Ask again*.
- **D147 §3.4, and its GIT1a note.** The field they leave for LAND2 to name is `pullRequestState`, named here, and Git's
  list reads it.
- **D64 §4, and the plugin design §4 and §9.** They gain a fourth kind, the query. A point this build lacks is named and
  ignored rather than refused.
- **D101.** The kit gains the point's entry.
- **D100.** Both example plugins speak a second point.
- **LAND2c (D145 §3).** It must say what it does with a branch whose pull request completed, since advancing that branch
  would push work no pull request carries.

D37, D87, D51 rule 7, D46 and D52 stand.

**What the checks do not cover.** These are documents only, and nothing is built. The parent relayed the owner's case;
this branch read no install and no work repository. The Azure DevOps fields are taken from `az repos pr show`'s
documented output and Azure DevOps's pull request reference, and were not run against a real organisation. The first
slice has to measure two things: whether `lastMergeCommit` names the squash commit on the target after completion, and
whether `completionOptions.mergeStrategy` is present on every completed pull request. The check that the merge commit is
on the line keeps a wrong reading safe. The GitHub fields are `gh`'s documented JSON, also not run. LAND3, LAND2b and
GIT1a were read from their notes on D102, D145 and D147, on the integration branch they were merged into, not yet on main
when this was written. The bounds (30 s, 60 s, a minute) are judgements, not measurements. `verify` checks this entry's
place and that it names what it rejected. It checks none of the words here or in the design.
