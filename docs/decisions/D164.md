## D164 — A session commits on its tree's branch as it goes; the person's Accept makes the pull request's branch (2026-10-12)

**Decision (the owner's direction).** The owner, 2026-10-12, after a report's conversation sat on its session branch with its
work uncommitted, the review saying there was nothing: *"so currently we should have logic to update rules in the repo and
because I think our setup is until it has a pr branch currently it stops at daoris branch"*. The repository's own rules
asked its agent to commit only on a yes and only on a branch of its own (`feature/<ticket>-…`), while Daoris gives each
session a tree on `daoris/s-<id>` and makes the pull request's branch at the person's Accept: the two met, and the work
stopped between them, uncommitted, on the session branch.

1. **In a Daoris session tree an agent commits as it goes, on the tree's branch.** It does not create, switch or push
   branches, and it asks no one before committing there: the tree's branch is the session's scratch, nothing outside it
   moves, and the person's **Accept** in Daoris is the yes that lands it. Outside a session tree, the repository's own rules
   stand.
2. **Daoris says so twice.** As doctrine, a canon rule synced into every adopted repository's instructions (the way Daoris
   updates a repository's rules); and to the agent itself, in its first instruction on both doors, as the browser's line is
   said (BRWHINT1), so it holds before a repository has synced.
3. **Accept makes the pull request's branch as the repository names its own:** by the repository's landing pattern, with a
   ticket key found in the title or the request (`feature/<KEY>-<words>`), never a web address's slug (LANDNAME2); squashed
   to one commit where the repository's landing rule asks for that.
4. **Daoris reads what the tree holds, committed or not** (REVIEWDIRTY1), **and follows a tree an agent moved anyway**
   (TREEFOLLOW1).

**Rejected:** Daoris committing a session's work on the person's behalf (the agent commits, by its repository's
conventions; Daoris lands); leaving each repository's "ask before committing" to stop every session; Daoris editing an
adopted repository's own text outside its doctrine region (a repository's own rule that contradicts point 1 is changed by
that repository, through a request: D32).

**Amends:** D51 (what a session tree's branch is for), D145 (Accept's branch name and squash).

## Amendment, 2026-10-12: the process is configured per workspace and repository

The owner, the same day: *"this is not just about how we process, this also about how we config the process because each
workspace will be different even each repo, so this need to be clear for user and for the work sessions"*. Points 1-3 above
stated one process; each workspace and each repository chooses its own, as review, opinions and helpers are chosen. Read
from a design pack (2026-10-12): Daoris's per-repository rules share one shape (a repository's whole rule replaces its
workspace's, absent is the default, a CLI twin on a shared table, an `Inheritable` row in Setup); the landing rule holds the
branch pattern and nothing of committing; a conversation is told nothing of landing; D154:126 kept a rule that applies to
either landing form off the landing rule.

1. **A commit rule**, its own map pair in `driver.json` (`commits`, `workspaceCommits`), resolved as review is: `mode`
   `as-you-go` (the default: commit on the tree's branch as you go, never switch or push, the person's Accept lands it),
   `ask` (ask the person before each commit: a repository that wants a yes says so here, and Review's press says the yes in
   the conversation), or `at-end` (one commit when the work is done); and an optional `convention`, the person's words on
   how commit messages are written, bounded, quoted to the session. It applies to either landing form and to conversations.
2. **The landing rule names the branch as the repository does.** Its pattern may use `{ticket}`, a key found in the title or
   the request by the rule's `key` shape (a pattern per repository or workspace, e.g. `[A-Z]+-\d+`); where none is found the
   session's id stands in. The rule may ask for `squash`: Accept makes the pull request's branch as one commit carrying the
   session's commits' messages, bounded. (LANDNAME2's "never a web address's slug" stands for `{slug}`.)
3. **Clear to the person.** Setup shows both rules with what they inherit and where it was set, as the others; a session's
   Details shows the process it runs under and its source.
4. **Clear to the session.** Each session in a tree of its own is told its resolved process at its start, on both doors
   (replacing point 2's fixed words: SESSCOMMIT2); the doctrine rule (SESSCOMMIT1) says only *where Daoris tells you the
   commit and landing process at your start, follow it; otherwise your repository's own rules stand*, which keeps canon free
   of any one tool.
5. **Seeded, never read as authority.** Ask Daoris may propose a repository's rules from the repository's own instructions
   (its branch names, its commit rule), which the person applies (D110); Daoris never takes a repository's tracked text as
   the process itself (D154:123).

So a repository whose rules ask for a yes before committing and `feature/<TICKET>-…` branches squashed to one commit is
configured so (`ask`; `feature/{ticket}-{slug}`, `key`, `squash`), and Daoris and the repository agree without its text
changing.

**Note, 2026-10-13 (PROCESS1b-ii, decided before its build).** Point 2's `squash`, settled from its pack:

1. **The commit.** On the branch form, Accept makes the pull request's branch as one commit: the session's tip's tree, its
   parent the merge base with the line, made with `git commit-tree`. It is the first commit Daoris makes, so it takes git's own
   identity in that repository (`user.name`, `user.email`), and where git has none Accept is refused, saying so and how to set
   it or turn squash off. Uncommitted work is refused before, as today; a tree on its own branch (TREEFOLLOW1) lands as it
   stands and is never squashed.
2. **The message.** The subject is the quest's title (a conversation's own), at most 72 characters; the body lists the
   session's commits' subjects, oldest first, one line each, at most 50 lines and 4,000 characters, and ends *Squashed by
   Daoris from session `<id>`*. A plugin sees the one commit (D100).
3. **The proof that the session landed.** The landing record gains the session tip it squashed. The session's head, its
   unlanded count, Discard's offer and the clean-up read a session branch as landed while its tip is that commit or an
   ancestor of it: the record is Daoris's own word of what it squashed, so it vouches as a branch it made by ancestry would.
   A content proof (SQUASHTIDY1) stays as it is for every other case.
4. **A chain's later landing** squashes only what the session added since the recorded tip: one more commit on the pull
   request's branch, its tree the new tip's, its parent the branch's tip, the record moved to the new tip. Where the
   session's tip does not grow from the recorded one, the advance is refused as an advance that does not grow is today.
