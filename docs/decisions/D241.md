## D241 — Git stays built into Daoris's core and every git act passes the doors, the push included; a pull request is a place's workflow steps, its hosted-service act a plugin's that runs no git and no CLI and is handed the identity's token; the whole path proven in CI against stand-ins (2026-11-05)

**Decision (GITDESIGN1, proposed for the owner's yes).** This answers D240 points 3 to 5, and the contract is
`docs/2026-11-05-git-design.md`. It is the owner's choice because it reverses D87 and D100's rule that Daoris never pushes. It also
reverses D198's rule that a hosted service is reached through the person's own `gh` and `az` sign-ins.

1. **Git stays in the core.** Trees, reads, landing, integration and the person's acts are git: about 580 calls in 132 driver files.
   None of them carries a credential. The two doors stay the one place where a remote act gets an identity and a verdict, always
   installed. The publish lays them on every install, and `--git-doors` ends.
2. **One push.** Daoris pushes through one act on the act journal, under a grant bound to the address, the ref, its old commit and its
   new one. The person's press and a workflow's `push` step both use it, and a lightweight tag is the same act. No plugin runs
   `git push`.
3. **The transport judge decides dangerous transports itself.** Each update is judged by its kind (force, delete, tag, mirror, prune).
   A step's grant carries exactly its own refs. Anything else is decided by the place's Dangerous value, `allow` or `deny`, at the door,
   so no person is waited on. A read-only identity refuses every write at the doors.
4. **A pull request is a place's workflow steps, never a default.** The steps are `land` (branch), then `push`, then `pull-request`.
   `land` loses its `push` and `pull-request` methods. *Set up…* stops suggesting a pull request. A saved graph that lands by either
   method converts once.
5. **A hosted service is reached only for what git cannot do,** opening a pull request and reading its state. That is a plugin's
   performed step on `work/perform`; `work/land` ends. The plugin runs no git and no CLI. It is handed the API token of the identity
   serving origin, for its one process. It does not start where no identity serves, the identity is read-only, Write denies, or no
   token is set.
6. **Tokens live beside the keys.** HTTPS and API tokens are kept in `profiles/git/tokens/<id>/`, the folder limited to the person's
   account and plaintext at rest, as keys are. git's HTTPS act reaches them through the door's third name, `git-credential-daoris`,
   which answers only the identity's host. Git Credential Manager leaves Daoris.
7. **A session holds no credential.** Its environment carries no key path, token or grant. Its `gh` and `az` configuration folders
   are empty. The Claude doors' rules deny reading `profiles/git/`. As before, a session runs as the person's account, and Codex holds
   no rules.
8. **The proof runs in CI with nothing installed.** A loopback SSH host runs in the test process, and a TLS host serves git over HTTP.
   A stand-in service API serves the pull-request plugins. The pinned MinGit runs beside the runner's git. The installed window proves
   only a real host's key, the real API's acceptance, and the screens.

**Why.** Local git is the substrate of Daoris and needs no credential. Auth fails only at the four paths to a remote: the doors are not
laid on the install, a read-only identity and the grant are not judged at the doors, no HTTPS store is found on the managed git, and a
pull request runs as the person's CLI sign-in. Applying auth at the doors for git, and by a per-act token for a hosted service, gives
each act exactly one place where its credential is chosen and judged. One push and one secret home fold two ways into one (D228). Proving
the path against stand-ins answers D240 point 4 without installing anything on the owner's machine.

**Rejected.**
- **Git's processes in a plugin.** About 580 calls would move behind a process wire, the look's per-tick reads included, and the act
  journal's guarantees would become a plugin's promises. A plugin can be switched off, which leaves a session's push unjudged.
- **Only the remote half in a plugin.** The doors are already programs git starts. A plugin's switch would still make the judge
  optional, and git policy would have two owners.
- **Built-in git as it stands, proven** (the plugins keep `git push`, `gh` and `az`). It proves the doors but leaves the pull request
  on the person's sign-in. It also needs the hosted service's CLI installed for the work workspace, and it keeps two programs
  that push.
- **The person's `gh` and `az` sign-ins for a pull request.** That hands the person's credential to a step Daoris starts, which D198
  point 3 refuses everywhere else.
- **Git Credential Manager managed in the toolchain, or Windows Credential Manager called directly.** Each is a second secret home
  beside the keys. GCM's browser sign-in is a person's flow that a multi-agent system does not wait on.
- **Installing sshd, `gh`, `az`, git-lfs or GCM to measure the doors.** Stand-ins prove the same path in CI on every run.
- **A pull request as a `land` method, or suggested wherever a plugin serves the platform.** A default that the owner does not want
  (D240 point 5).

**Amends, once accepted:** D87 and D100 (Daoris pushes, as a step or a press); D198 points 3, 4, 13 and 16 and its §12 rejection of a
token for the hosted service; D148 keeps its rules on `work/state`. Each amended decision takes a dated note pointing here.
