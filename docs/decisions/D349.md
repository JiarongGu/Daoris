## D349 — A workspace's rules are kept by supervisors in a feedback loop, and this workspace's first is a ten-minute verification (2026-11-20)

**Decision (WORKSPACERULES1, VERIFY10; the owner's direction for actor flow).** A workspace (or a repository in it) may set rules for
the work done in it: what a verification may cost, what a design must hold, what a change must not touch. Daoris carries such rules as
the workspace's own knowledge (D325: a procedure is a repository's knowledge) and keeps them through actors, not hard-coded steps: a
supervisor role holds a set of rules and watches the work agents that the rules cover; when work breaks a rule it feeds the finding back
to the work agent (the short loop), and where the rule needs another actor's hand (a reviewer, a release manager, the owner) it asks
that actor through the one request door. Several supervisors may each hold a different set of rules or designs over one work agent or
many; that composition is actor flow. Nothing applies to a workspace that did not set it: Daoris supplies the framework, a workspace
chooses its rules (the owner sets them, or Daoris's assistant proposes them from the workspace's measures as a change it takes).

This workspace's first rule, and the framework's test case: verifying one task takes under ten minutes of wall time (a builder's checks
before hand-back, a run's check of the work, and a merge's gates for one branch); a verification is scoped to what the change's paths
reach, the heavy tiers and the full set run after landing in the background, a verification past ten minutes is said at once with
where its time went and filed as a defect (the scope was too big for the change, or the change is code-wide and should have said so),
and a full run is taken only for a reason the tools check against the change (a declared wide path: build and dependency files,
lockfiles, shared contracts, the gates and the test tools; a reach over most classes; the run after landing; a release), never on
request alone. It is written where this workspace keeps its own (`daoris.gates.json`'s `verifyBudget`, `docs/development.md`, a
knowledge entry its agents read), and this repository's tools hold it until the supervisor actor does.

The framework is built so a rule set or a supervisor is replaced by changing its own module and its wiring alone: rules are data a
supervisor reads, a supervisor is an actor behind the one request door, and a work agent knows neither; replacing one touches no
other module.

**Why.** Most of this repository's tasks are small, yet that week a fix of a few files took one to two hours to verify: about 95 hours
a week of gate time someone waited on, a merge's gates 25 to 40 minutes for one branch and hours with reruns, a run's check 30 to 60
minutes. A verification longer than its change's reach is a scope defect, not a cost of safety, and a budget kept by an actor that
says each breach turns that into findings. Repositories and workspaces need different rules, so the rule belongs to the workspace and
the product supplies only the means to keep it; several rules over several agents compose only if each is held by its own actor;
and a rule or supervisor that can be swapped alone is what keeps the framework cheap to change.

**Note (2026-11-27, HEAVYBATCH1; the owner's direction: no full run without a reason the tools check against the change).** The rule's
list of reasons named "the run after a landing", and by its kind that counted: a heavy tier followed every landing, and by D314's
take-over one ran almost all the time (104 tiers in six days, 57.9 hours; on 2026-11-27 the steward's tier held a heavy place for
three hours beside the sessions' checks). It no longer does, and a reviewer reads the same rule:

1. *The heavy tier is judged by the change, never by the run's kind.* After a landing the heavy tier runs only the classes of a landed
   change that bears a full run's reason (a declared wide path, the declared reach share), over only what those landings changed. A
   landing with none queues nothing heavy: no tier, no admission place, no tree. A reasoned landing's tier waits for a pause in
   landings (20 minutes), a newer reasoned landing carrying the waiting one's range (D314's supersession then covers a tier already
   running), and runs as a background run, which is D365's low class in the machine's admission: it takes a place only while no
   task's check waits, and no group starts while one does; a group in flight is not cut (D365 point 3). A release, a reason by its
   kind, asks the tier by hand. A landing that bears no reason leaves its heavy classes to the next reasoned landing, the CI beside
   and the nightly; a red they hold is found there.
2. *The rules are this repository's knowledge that every reviewer reads.* `.claude/knowledge/verification-budget.md` applies to
   reviewing a change as to verifying one, and the second opinion's instruction carries the repository's declared rule (its gates
   file's `verifyBudget`, as data) while a red check's words to the work repeat it, so no reviewer asks for a full or end-to-end run
   the rule gives no reason for, nor counts its absence as a finding. A gap in what the change's own tests cover stays a finding.

**Rejected.**

- *A product feature for verification budgets, or canon for every repository*: repositories and workspaces differ; a rule is the
  workspace's own, kept by an actor, and the framework is what Daoris supplies.
- *Rules as fixed workflow steps (a node that checks a budget)*: a fixed graph cannot hold several rule sets over many agents (D325's
  reason); a supervisor actor composes and is replaced alone.
- *A budget per gate only (the gates' `timeoutMinutes`)*: each gate stays within its own and the task still waits on their sum.
- *A full run whenever an agent or a person asks*: the full set is the slow path the rule keeps off the task's way.
