## D36 — The service is deployable: nothing needs to run between sessions; state persists and the HTTP host carries transfer (2026-09-18)

**Decision.** SVC1 closes without a daemon. **Local mode:** the MCP host stays spawn-per-session — the
client starts it, the session uses it, it exits — and the *database* is what persists. Every session in
every repository on this machine spawns over the same file, so a quest published from one repository's
session is waiting when another's starts. `.mcp.json` in this repository registers it; a sibling adds
the same entry to its own file. **Remote mode:** the HTTP host carries the transfer — registry and
quests (`POST /api/registry`, `POST /api/quests`, `POST /api/quests/{id}/respond`) — through the same
`QuestExchange` the MCP host uses, with `DAORIS_SERVICE_KEY` gating every `POST /api/*` when set and
absence meaning local trust (D21). It runs with **no model at all** and still carries all of it (D24):
a remote Daoris is purely a transfer of request and task unless a repository opts its knowledge in.

**Why.** "Nothing runs between sessions, so nothing can be published or pulled" conflated two different
gaps, and a daemon would have fixed neither. The first was **state that did not survive**: pushed
registrations lived in a dictionary, so a service restart silently dropped every repository that had
ever run `connect` — and for a remote service, pushed registrations are the only registrations there
are. They now persist in the same SQLite file as the index and the quests (one file to back up, one
answer to "which repositories exist"). The second was **a door that did not exist**: quests could only
be moved over MCP stdio, so a deployment anywhere else was a read-only mirror.

**The judgement moved to one place.** Publish/respond rules — who may be addressed, what a refusal
says, what declining requires, including the message text — live in `QuestExchange`, used by both
hosts. Written per host they would drift, and the same ask would be deliverable through one door and
refused at the other, which for a quest system is the worst available bug: it looks like the sibling
ignoring you.

**Verified on the artefact, not only in tests.** The host was driven live with a key: the unauthorized
write answered 401; `daoris connect` registered through the real endpoint; the host was killed and
restarted and the pushed registration and a taken quest were both still served; a publish to a
non-adopter was refused naming who *is* addressable.

**Not chosen:** a daemon or Windows service (once state persists, nothing needs to run between
sessions — a deployment cost buying no property); per-person expiring keys and OIDC now (deferred until
a deployment leaves a trusted network; the full model is designed in the service design §5); an MCP
relay from the local stdio host to a remote service (build it when a second machine actually exists —
the HARNESS1 reasoning).

**Consequence.** The quest-ledger pattern — holding outbound quests in this repository's backlog
"until a service runs" — ends, because the service runs. Addressing still gates on adoption (D33), so
a sibling that has stepped off the tool is not addressable until it re-adopts; nothing changes there.

**Amended 2026-09-20 (D47, as amended).** The interim single-key write gate is retired, with nothing
deployed. Two trust shapes only: **local** trusts the loopback outright and may bind nothing else (the
startup refusal enforces it), **shared** gates every route — reads included — with minted per-person
per-machine keys. `DAORIS_SERVICE_KEY` survives solely as the client-side "key I present", which
against a shared deployment is a minted key; no server-side code consults it.

**SQLITETX1, built 2026-10-08: no request meets another's open transaction.** The one file this decision chose is
opened by a host as ONE connection that every store shares (`ServiceFactory.CreateAsync`), and a host answers requests
at once. A `SqliteConnection` is not safe to use from two threads, and SYNC1's gate serialized only the transactions. On
the install a say answered 500 (*Execute requires the command to have a transaction object…*) with its words kept, and
earlier every knowledge route failed until a restart (KNOW500). The fix log's SQLITETX1 entry has the mechanism and the
measurements.
- **What changed.** `ConnectionGate` is the connection's one holder. Each store method runs its commands inside the
  gate, one unit of work at a time, and each transaction inside it too: `BEGIN IMMEDIATE`, committed when the work
  returns, rolled back when it throws, the work's token uncancellable once it has begun (REV3). A command made outside the
  gate is refused, and a source scan fails any Core file that makes one or opens a transaction itself. Within one flow
  of work the gate is reentrant, because a transaction's work calls the stores' own methods (the ledger's check and write
  inside `SessionStore.ExclusiveAsync`), and those join its transaction, as a command made while one is open always does
  on this driver (pinned in `QuestLogTests`).
- **A unit leaves the connection as it found it.** A transaction a unit left open is rolled back before the next unit
  begins, and a unit that left one without a throw fails, since nothing it wrote there was kept. A transaction the database
  holds and no object owns (a `BEGIN` that ran while the object meant to own it was never made, KNOW500's state) is rolled
  back before the next unit. A transaction a caller holds outside every gate is joined: no host does that, and
  `SessionLockAcrossHostsTests` plays another host that way.
- **What it costs.** A read now waits for a transaction in progress instead of joining it. The longest is one
  repository's replace in a refresh. D151 measured the whole index's write at 1.4–2.0 s, and one repository's is a part
  of that, but it was not measured on the install. In the burst test, 50 says beside 50 looks took 2.2–3.4 s in all,
  with the slowest say about 1 s, behind ten refreshes. Across processes nothing changed: the desktop's host and each connector open their own connection, and
  the file's locks order them, as `BEGIN IMMEDIATE` was chosen for.
- **Rejected.** A connection per unit of work, which the task offered first. A transaction's work calls other stores'
  methods, so the unit's connection would have to travel with the flow the same way the hold does. Every test that hands a
  store an in-memory connection would need a factory instead. Reads would gain concurrency only under WAL, which changes
  the file every process and every copy of it reads (a copy without its `-wal` misses the last commits). Gating at the HTTP door was rejected too: the
  MCP host and the console verbs reach the stores without it.
- **What the gates do not cover.** The burst test is in-process: Kestrel's own threads and the desktop's real driver loop
  were not run. The family rehearsal's two-machine and sync phases push through separate hosts and read them one request at
  a time, so their answers do not change; only a read that arrives while a push is being received now waits for it.

**KSCHEMA1, built 2026-10-08: an older build never touches a newer index, and refuses nothing else.** Every host on a
machine opens this one file, and a connector an update left in `$DAORIS_HOME/bin` is an older build. The index rebuilt
on any `user_version` but its own, so on the install an old connector dropped the newer host's index and stamped its own
version under it, and the newer host failed every knowledge route. The fix log's KSCHEMA1 entry has the mechanism and
the proof.
- **What changed.** An older version is rebuilt as before. A newer one is left as it is: nothing is dropped, created or
  stamped, `Rebuilt` stays false and `feed_provenance` is kept. The store opens, and every operation on the index throws
  `NewerIndexException`: the store's reads and replace, the search, and the service's search, read, summary,
  convergence, entries, feed, refresh and retire, each before it does anything else. The HTTP host answers it as 409 in
  the error shape, ahead of HOSTLOG1's 500, and the connector's index tools answer it as their text. Its sentence names
  both versions and no path, since a door answers it (D46, D47 §4). The registry answers with no entry counts, since
  quests are addressed by it; no implicit refresh is tried, so none is retried; each host says it once at start, on stderr
  and in its log as `index.refused`. A fed registration that stops sharing what it shared is refused whole, since what it
  fed could not be taken back. The read through the stamp is one `BEGIN IMMEDIATE` transaction, so an older build opening
  beside a newer one's stamp waits and leaves it rather than writing its own number back.
- **Why the index alone.** The branch first refused the whole store at open. An update that fails to confirm rolls back
  to the previous build by itself (D139; the update design's §5), and after a newer build has stamped a bump that older
  build is the one that meets the newer index: refused whole, the install's host could not start until a person updated
  it, which is worse than the incident, where only search broke. The index is derived and is rebuilt from the
  repositories with nothing lost; the quests, sessions, asks and keys beside it are not derived, and an older build works
  with them (the next point).
- **The stores that add columns** (quests, sessions, registrations, asks, keys) carry no version of their own: the file's
  one number is the index's. An older build's open of them drops nothing a newer build holds. Sessions'
  `DROP TABLE sessions` (`RelaxQuestAsync`) copies the rows first and runs only while `quest` is NOT NULL, which no build
  since D49 §3 leaves, and no build makes NOT NULL again; its copy names the sixteen columns it knew, so it would lose any
  later one, but no store that a build with the rebuild has opened meets its condition. Quests' `DELETE … WHERE home IS
  NOT NULL` and `DROP COLUMN home` run only where `home` exists: a build from before SYNC2 adds it back and fills it on the
  remote's copies alone, and the next newer open deletes those copies as SYNC2 did, keeping every quest of the machine's
  own. Registrations, asks and keys only create and add. What an older build can still do is write: its inserts name the
  columns it knows, so a record it writes reads as one from before the newer columns. Refusing that too would refuse the
  connector over every store a newer build had touched, a column or not.
- **What it costs.** Over a newer index, search answers nothing on that build until it is updated, and the registry's
  rows say no entries. A session's connector starts and takes and closes its quest as before; its knowledge tools answer
  the sentence. A local driver's sync pass reads a sharing repository's entries from its host to feed the circle's remote,
  meets the 409 there as a wall (`RemoteSync.RunOnceAsync`), and so the pass's later feeds, retires and registry mirror
  wait until the build is updated, said on every pass; quests and session records still travel in the host's half. A
  connector installed before this change still rebuilds: only builds from this one on leave a newer index alone.
