## D366 — A pass is kept by the content it read and never run twice; the agent proves its hand-back before done; a run's check runs only what has no pass, beside the second opinion (2026-11-27)

**Decision (VERIFY2, under D349, D362 and D365; the owner's direction: a task takes too long, find whether the review's
scope, its failures or its speed is the cause, and scope it).** Measured on the install for the runs bound 2026-11-25 to
27: 19 landed, a median 6.6 h from bound to landed; a run's check took a median 138 minutes of it over five check runs
of a median 27.7 minutes each (the budget is 10), 58% of runs passed, 25% failed (censuses 21, reached 15, hand-back 9,
each knowable in the session), 17% gave no verdict, and each re-check ran every reached gate anew. Brainstorm
`verify-1127` asked Fable 5.2 and DeepSeek; both answered one model and differed on four points, chosen below.

1. **One pass ledger, keyed by content.** A gate's or a test unit's pass is a record keyed by its unit, its command and
   tool versions, its toolchain and the blob ids of what it reads; a check, a re-check and a merge run only the keys
   with no pass, and the same key holds across rebases and worktrees, so the ledger is the machine's, in the home, not a
   tree's. A failure is never replayed. A unit that reads the clock, the network or the machine's state is declared
   never-replayed. REACHREPLAY1's and CLIREPLAY1's replays are this ledger, and their rows end in it.
2. **The agent proves its hand-back before done.** One command, `preflight`, runs with the check's own code and keys the
   reached censuses first, then the fast tier of reached-checks and verify:checks, and writes receipts into the ledger;
   `done` looks the tip's keys up and is refused in seconds, naming the command, where a receipt is missing or failed. The
   run's check replays the receipts and runs only what they do not cover.
3. **No bare unknown.** A check ends passed, failed, or not judged with a cause from a closed list (the runner died, the
   bound was passed, admission was lost, the result could not be read, the tip moved, it was superseded); an
   infrastructure cause retries once on the same keys, resuming only the units not finished, and is never charged to
   the change; an end with no cause is filed with its log's tail so it gets a code and a handler.
4. **Scope in bands, as the workspace's data:** before landing, the gates every merge runs plus the units the change's
   paths reach; a declared wide path runs every gate; the merge runs the keys the merged tree moved; the heavy tier and
   the whole censuses run after landing, a red there opening a fix with the priority to go first (D365).
5. **One check inside the budget:** one build per source-tree key shared by the hand-back and every gate, the reached
   gates side by side under the machine's one admission (D362, CHECKSLOTS1), each run recording each gate's minutes, its
   build and its wait, and what started it.
6. **The second opinion and the check run together** on one tip; landing needs a pass and the opinion's read for the same
   content. After a fix the check runs only the fix's keys; the opinion reads the change since the tree it named, and a
   wide-path change takes the opinion first.
7. **Framework and configuration** (D349): the workspace declares in `daoris.gates.json` its budget, wide paths, gates
   with their reads, tiers and the hand-back set; Daoris supplies the ledger and its keys, the runner, the shared build,
   admission, the refusal at done, the landing rule, the outcome set and the measure. Declaring nothing gives one key
   for the whole tree, so an unchanged tip is never checked twice.

**Rejected.** Keys by commit or by age (a rebase changes the commit, not what a unit read); passes an agent states
(only a receipt the runner wrote counts); a replayed failure; packing reached gates by measured minutes before landing
(it drops a gate for being slow, not for being unreached, and reached failures are 15 of 52); a reserved light slot (it
idles capacity outside measured admission, as D365 rejected a reserved urgent slot); a bigger budget; the heavy tier
before landing; the second opinion always first (its 27.6 minutes would add to every run); an unjudged run charged to the
change as a failure.

**First slice.** `preflight` with its receipts and done's refusal, the fast tier's content-keyed passes written by it and
replayed by the run's check, and the measure of every check run (gates, minutes, build, wait, trigger, units replayed),
so the next week's figures show the saving. Rows `VERIFY2a` to `VERIFY2e`.

**Note, 2026-11-27 (VERIFY2 a and b; the owner's two directions).**

1. **Preflight is run by Daoris, not the agent.** When an agent says done, Daoris runs the reached censuses, the reach computed from
   the change, and the fast tier in the session's tree, writes the receipts, and hands any red straight back to the session. What
   code can judge (structure, names, sizes, what changed and what it reaches, tests) is never left to an agent to remember or
   decide. The refusal at `done` in item 2 is then the answer to a `done` whose tip has no passing receipt, not the way the
   receipts come to be: the command is Daoris's to start.
2. **The run's summary is one record built by code**: what changed (by module and by rule), what is verified (each unit with its
   receipt), what is left for judgement. The second opinion reads it instead of finding the change again; it is the data of the
   window's Outputs panel (OUTPUTS2) and of the landing record: one record for all three readers. Part d builds the opinion and
   the panel's sides.

Built in a and b: `tools/merge/receipts.ts` (a receipt per unit keyed by the git tree it judged, kept under the home's `checks`
folder or the main checkout's `local/receipts/`, and one measure line per run: gates, minutes, wait, trigger, units replayed),
`tools/merge/run-summary.ts` (the record and its lines; a rule is a numbered rule of an area document, compared by number), and
`tools/merge/preflight-record.ts` (a result as a receipt, the declaration's `verifyBudget.preflightFirst` order that starts the
censuses before any test round). `merge-branch --preflight` writes them and prints the summary; `DAORIS_PREFLIGHT_TRIGGER=done`
is how the measure says Daoris started it. The key's reads stay the whole tree until a gate declares its own (item 7).
Left in rows `VERIFY2a` and `VERIFY2b`: the driver starting the preflight when a session says done and answering a done with no receipt
(a, driver half), and the home's ledger and the check's replay of receipts (b, driver half).
