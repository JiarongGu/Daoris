## D198 — Daoris's git acts as git identities of its own, one set on the machine that each remote points at, and never as the person's own sign-ins unless the person chooses it; what it may do on a remote is git access, part of the access setup, judged by one judge for the landing and an agent alike (2026-10-22)

**Decision (GITAUTH1).** **Status: proposed**, read by Codex under D191 (below); a foundation (where credentials live, how every
git Daoris starts is wired), so Fable reads it before the steward accepts it. The contract is `docs/2026-10-22-git-auth-design.md`.

Daoris's sessions reach git remotes and fail: nothing in Daoris sets up how its git signs in, so a session's git and Daoris's own
fetch run with the person's credentials, which the git on the path often cannot use (WSR7), and nothing remembers a failure, so
each path tries again on its own schedule and a pull request's moments say nothing at all (design §0.3-§0.4). The owner directed
git authentication done comprehensively (several accounts, SSH keys, a designed screen, learned from existing tools), then widened
it to a policy for what a repository, a workspace and a session may do on a remote.

1. **Git identities, one set** (design §3.1-§3.2). An identity is a host, a way (an SSH key or an HTTPS sign-in), the name and email
   it commits as, a label and its test's answer, kept in `data/git-identities.json`, which holds no secret. Several per host. No
   scope has a list: a repository points per remote, a workspace per host, a host has a default, and the answer names its source.
2. **The person's own sign-ins are never used, read or written** (§3.3) unless the person chooses *Your own git sign-ins* for a
   scope, a widening confirmed in place; the one read of the person's own is a key file the person names to import.
3. **Secrets in their homes** (§3.4): an SSH private key in `profiles/git/keys/<id>/`, limited to the person's account, plaintext
   at rest as D67's API keys are; an HTTPS sign-in in the OS store through Git Credential Manager in a namespace of Daoris's own;
   host keys in Daoris's own `known_hosts`, trusted only at a person's press (D73's rule).
4. **Every git Daoris starts is wired, and none prompts** (§4): D121 §2.5's git file (TOOLS6), moved to `profiles/git/`; the
   command scope's variables for what must beat a repository's own configuration; `GIT_SSH_COMMAND` naming Daoris's launcher, which
   hands the identity's key with `IdentitiesOnly`, no agent and strict host keys; GCM in Daoris's namespace with a user per URL;
   `GIT_TERMINAL_PROMPT=0` and `GCM_INTERACTIVE=never`. The terminal's shells keep the person's own git.
5. **A remote that cannot authenticate is held and said once** (§5): failures classed by the transport's words; no identity, a
   refusal or a host key unknown or changed holds the remote until something touching it changes or the person tries again; one row
   in *What needs you* with the press that fixes it; a session is told in its instruction not to try. Only the network's failures
   keep the minute's retry.
6. **Git access: read, write, dangerous writes, each allow, ask or deny** (§6.1-§6.2), per repository, workspace and machine with
   Daoris's default of *allow*, *ask*, *deny*; a session runs under the stricter of its start's and its repository's now, and the
   person may tighten a running session; an agent changes no access.
7. **Identity is who, access is what** (§6.3): no identity, no act whatever the access; a read-only identity on the host denies
   writes, the one bound no local process lifts.
8. **Part of the access setup, untouched by full access** (§6.4): `gitAccess`, `workspaceGitAccess` and `machineGitAccess` in
   `driver.json`, resolved, said and edited by `AccessRules` through `SET_ACCESS` and `daoris-driver access`, kept on the record.
9. **One judge, asked at the transport** (§6.5): Daoris's own acts ask it in process; the harness's rules are written from the
   policy for the flow; the binding check is where git must pass to reach the host, Daoris's ssh launcher and an HTTPS push relay
   through `pushInsteadOf`, which read every ref update. A `pre-push` hook and a refusing credential helper are rejected.
10. **An ask is a held call or a go-ahead** (§6.6): an `ask` rule's request is held for the person whatever the posture; elsewhere
    the transport refuses and names the go-ahead to ask; the person's answer writes a one-act grant the transport consumes.
11. **The landing meets the same judge** (§6.7): it asks before starting its plugin and grants exactly its push; *Accept…* is the
    yes, and a landing rule that accepts automatically is the person's standing yes for that push alone.
12. **Moving from today** (§6.8): `no-push`'s rules are written from git access, a switched-off `no-push` read once as the machine's
    Write *allow*; a landing rule naming the line keeps landing (its Dangerous written *ask*); every remote moves off the person's
    credentials with one row offering an identity or *Keep using my own sign-ins*.
13. **The window, the terminal and Ask Daoris** (§7-§9): Settings → Git (identities, defaults by host, the machine's git access and
    own sign-ins); each repository's remotes and git access on Setup, a workspace's per host; held remotes and asks in *What needs
    you*; a session's access in its head's *Details*; the `daoris-driver git` family and `access git-*=…`, each widening confirmed in
    the window; Ask Daoris proposes `git-use` and opens the add form, and never touches a secret, an identity's life or access.
14. **Never written outside its home** (§10-§11): no key, token or passphrase in a log line, event, record, answer, instruction or
    tracked file; coded `git.*` machine-log lines with ids, never a user or an address's user-info. The residual is stated: a
    session runs as the person's account, so Daoris governs an agent's ordinary git, not an agent set on getting round it.
15. **The rows** (§14): GITAUTH1a (held and said once), 1b (SSH identities, the terminal, TOOLS6), 1c (Settings → Git), 1d (HTTPS
    through GCM), 1e (which identity a remote uses, own sign-ins, the move), 1f (git access for Daoris's own acts and the landing),
    1g (a session's git judged), 1h (the install, seen; owner).

**Why.** The failure is not a missing setting the person forgot: Daoris has no account of its own on a code host, so it borrowed the
person's, which the git on the path could not use, and nothing remembered that. Identities of Daoris's own, chosen per remote,
are what D125, D175 and D197 already decided for agents. One set with pointers keeps D197's lesson (lists per scope confused) while
letting a scope choose, which a host account needs and an agent's account does not. Git access in the access setup, not a parallel
system, keeps one place the person reads what sessions may do; and judging at the transport, where Daoris already stands to hand
the identity, is the one place every form of git push must pass, which the rules and a hook are not.

**Rejected** (design §12): today's borrowing of the person's credentials; setting `HOME` for sessions; Daoris's keys in the person's
`~/.ssh`, agent or ssh configuration; an ssh agent of Daoris's own; DPAPI-sealed keys or a passphrase; trusting a host key on first
use in the background; `includeIf` per repository; an identity naming the owners it serves; a list of identities per scope; a
`pre-push` hook, a refusing credential helper or the rules alone as the judge; git access as pauses inside `access`; an agent
narrowing its own access; Ask Daoris setting up an identity; signing `gh` and `az` in with the git identity.

**Amends,** once accepted (design §13): D121 §2.5 and §2.6; D72's `no-push`; D184's access setup and its held requests; D37 and D87's
landing (the judge before the plugin); D172's home table; D135's go-aheads (a grant). Each carries a dated note pointing here.

**Held by** (once built): each row's proof in design §14; the resolution, classification, ref-update and stored-shape tables; a
fetch and a push through each transport against a local server in the `Process` half; the person-waits places; `HelpCoverageTests`;
`i18n:check` and `names:check -- --strict`; the install's screenshots (GITAUTH1h).

**What the checks do not cover.** Written from the code at `75bb61805`; nothing was run, no key generated, no sign-in started, and the
person's `~/.ssh` and credential store were not read. The tools' behaviours the design leans on are from their documentation and
owed measurements (design §15).
