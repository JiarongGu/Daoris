## D198 — Daoris's git acts as git identities of its own, one set on the machine that each remote points at, and hands no credential of the person's unless the person chooses it; what it may do on a remote is git access, part of the access setup, judged at the transport for the landing and an agent alike (2026-10-22)

**Decision (GITAUTH1).** **Status: proposed, round 2**, revised by Codex's read of round 1 under D191 (the note below); a foundation
(where credentials live, how every git Daoris starts is wired), so Fable reads it before the steward accepts it. The contract is
`docs/2026-10-22-git-auth-design.md`.

Daoris's sessions reach git remotes and fail: nothing in Daoris sets up how its git signs in, so a session's git and Daoris's own
fetch authenticate with whatever is ambient (the person's configuration, keys and credential store), which the git on the path often
cannot use (WSR7), and nothing remembers a failure, so each path tries again on its own schedule and a pull request's moments say
nothing at all (design §0.3-§0.4). The owner directed git authentication done comprehensively (several accounts, SSH keys, a designed
screen, learned from existing tools), then widened it to a policy for what a repository, a workspace and a session may do on a remote.

1. **Git identities, one set** (design §3.1-§3.2). An identity is a host, a way (an SSH key or an HTTPS sign-in), a label, the user
   the host reports, and optionally the name and email it commits as, kept in `data/git-identities.json`, which holds no secret.
   Several per host. No scope has a list: a repository points per remote, a workspace per host, this machine may choose the person's
   own per host, a host has a default identity; the pointers live in `driver.json`, and the answer names its source.
2. **No credential of the person's is handed** (§3.3) unless the person chooses *Your own git sign-ins* for a scope, a widening
   confirmed before it is written and never applied by a migration. For every other remote Daoris clears what git lets it clear (the
   helpers, extra headers, a password in the address) and holds a remote whose configuration names an input git cannot clear. The one
   read of the person's own is a key file the person names to import.
3. **Secrets in their homes** (§3.4): an SSH private key in `profiles/git/keys/<id>/`, the folder limited to the person's account
   before any key byte is written, plaintext at rest as D67's API keys are; an HTTPS sign-in in the Windows store through Git
   Credential Manager, in a namespace of Daoris's own set per address; host keys in Daoris's own `known_hosts`, trusted only at a
   person's press (D73's rule).
4. **Authorship apart from authentication** (§3.6): a commit carries the `commitsAs` of `origin`'s identity only where the repository
   names no author of its own, handed in the command scope.
5. **Every git serving a repository is wired per repository, and none prompts** (§4): D121 §2.5's git file (TOOLS6), holding no
   identity; each process's command scope, composed for the one repository it serves, carrying what must beat that repository's own
   configuration; `GIT_SSH_COMMAND` naming Daoris's launcher, whose argument contract is fixed; GCM's environment named, never
   inherited; `GIT_TERMINAL_PROMPT=0`, an empty `GIT_ASKPASS`, `GCM_INTERACTIVE=never` and ssh's `BatchMode` under an identity and
   `own` alike. A process that serves no repository gets no identity; the terminal's shells keep the person's own git.
6. **A remote that cannot authenticate is held and said once** (§5): failures classed by the transport's words; a hold keyed by the
   repository, the effective address, what served it and whether it holds reads or writes alone; lifted by any change touching it, a
   passing test or the person's *Try again*; one row in *What needs you*; a session told in its instruction not to try. The network's
   failures and unclassed ones hold nothing.
7. **Git access: read, write, dangerous writes, each allow, ask or deny** (§6.1-§6.2), judged by what an update does (a fast-forward
   or creation is a write; a non-fast-forward, a deletion, a tag or the line is dangerous), per repository, workspace and machine.
   **Daoris's default is today's, door by door**: Read allow; Write answered by the person's yes for the landing and denied for a
   session; Dangerous denied but for the one act a landing rule names. A value the person sets binds the landing and a session alike.
   A session runs under the stricter of its start's and its repository's now; the person may tighten a running session; an agent
   changes no access.
8. **Identity is who, access is what** (§6.3): no identity where the host refuses anonymous use, no act whatever the access; a
   read-only identity on the host denies writes, the one bound no local process lifts.
9. **Part of the access setup, untouched by full access** (§6.4): `gitAccess`, `workspaceGitAccess` and `machineGitAccess` in
   `driver.json`, resolved by `AccessRules`, edited through a route of its own (`SET_GIT_ACCESS`) and `daoris-driver git access`, kept
   on the record; an older build keeps the keys and says it judges none.
10. **One judge, asked at the transport, the doors always installed** (§6.5): Daoris's own acts ask it in process; the harness's rules
    are written from the policy for the flow; the binding check is the ssh launcher and an HTTPS relay through `insteadOf`, which read
    every ref update and judge a push as a whole before any ref moves. Addresses the doors do not reach are said and denied for
    Daoris. A `pre-push` hook and a refusing credential helper are rejected.
11. **An ask ends in an exact, single-use grant** (§6.6): a held call (the hold widened to git access's rules, keeping the call's raw
    input) or, everywhere else, `git_ask`, a git go-ahead kept on the session; the person's yes writes a grant bound to the session,
    address, class and refs, taken once and re-judged when used.
12. **The landing meets the same judge** (§6.7): it asks before starting its plugin and hands it a grant bound to `origin`, the branch
    and the commit judged; *Accept…* and a rule that accepts automatically are the person's yes for exactly that push.
13. **Moving from today** (§6.8): `no-push`'s rules and classifier sentence are composed from git access, so a session starts exactly
    as today under the default; a switched-off `no-push` is read once as the machine's Write *allow*; every remote moves off ambient
    credentials with one row offering an identity or *Keep using my own sign-ins for these*, pre-applying nothing.
14. **The window, the terminal and Ask Daoris** (§7-§9): Settings → Git; each repository's remotes and git access on Setup, a
    workspace's per host; held remotes and git go-aheads in *What needs you*; a session's access and *Tighten…* in its head; the
    `daoris-driver git` family, each sensitive act run only after the window confirms it, the widenings named; Ask Daoris proposes
    `git-use` and opens the add form, and never touches a secret, an identity's life, `own` or access.
15. **One redaction boundary, and the residual stated** (§10-§11): every text from git, ssh, GCM or a plugin passes one redaction
    before it is kept, said or answered; no key, token or passphrase is written outside its home; coded `git.*` machine-log lines.
    A session runs as the person's account, so Daoris governs an agent's ordinary git, not an agent set on getting round it.
16. **The rows** (§14): GITAUTH1a (held and said once), 1b (the doors judging the default, proved first against real git), 1c (git
    access set by the person), 1d (SSH identities from the terminal, TOOLS6), 1e (Settings → Git, the remote rows, the move), 1f
    (HTTPS through GCM, against a real GCM), 1g (the install, seen; owner).

**Why.** The failure is not a missing setting the person forgot: Daoris has no account of its own on a code host, so it borrowed what
was ambient, which the git on the path could not use, and nothing remembered that. Identities of Daoris's own, chosen per remote,
take to git the principle D125, D175 and D197 decided for agents' accounts. One set with pointers keeps D197's lesson (lists per scope
confused) while letting a scope choose, which a host account needs and an agent's account does not. Git access in the access setup,
not a parallel system, keeps one place the person reads what sessions may do; and judging at the transport, where Daoris already stands
to hand the identity, is the one place every form of git push must pass, which the rules and a hook are not. Keeping today's behaviour
as the default, door by door, is what D184 point 5 and D72's widening rule require; once the person sets a value, one value binds both.

**Rejected** (design §12): today's ambient credentials; setting `HOME` for sessions; Daoris's keys in the person's `~/.ssh`, agent or
ssh configuration; an ssh agent of Daoris's own; DPAPI-sealed keys or a passphrase; trusting a host key on first use in the background;
`includeIf` per repository or one machine-wide file of per-address users; a `pre-push` hook, a refusing credential helper or the rules
alone as the judge; Dangerous judged by flags; doors installed only where access asks or denies; git access as pauses or a field on
`SET_ACCESS`; Write *ask* as the sessions' default; a level's Dangerous widened for a landing to the line; D135's go-aheads as the
transport's permission; a list of identities per scope; an agent narrowing its own access; Ask Daoris setting up an identity; `own`
applied by the move; signing `gh` and `az` in with the git identity.

**Amends,** once accepted (design §13): D121 §2.5's precedence for authentication (the command scope and `GIT_SSH_COMMAND`, rejected
there, now carry identity and the doors) and §2.6's terminal; D72's `no-push`; D184's access setup and its held requests; D37 and D87's
landing (the judge before the plugin, an exact grant); D172's home table. D135 is unchanged; the glossary's *go-ahead* widens. Each
amended decision carries a dated note pointing here.

**Held by** (once built): each row's proof in design §14; the resolution, classification, hold, ref-update, grant and stored-shape
tables; a fetch and a push through each door against a local server in the `Process` half; the redaction table; the person-waits and
setting-doors places; `HelpCoverageTests`; `i18n:check` and `names:check -- --strict`; the install's screenshots (GITAUTH1g).

**What the checks do not cover.** Written from the code at `75bb61805`; nothing was run, no key generated, no sign-in started, and the
person's `~/.ssh` and credential store were not read. Every behaviour of git, OpenSSH and GCM the design leans on is from their
documentation and owed a measurement by a named row (design §15).
