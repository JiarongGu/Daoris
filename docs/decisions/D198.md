## D198 — Daoris's git acts as git identities of its own, one set on the machine that each remote points at, applied by Daoris's two doors at each git act, and hands no credential of the person's unless the person chooses it; what it may do on a remote is git access, part of the access setup, judged at those doors for the landing and an agent alike (2026-10-22)

**Decision (GITAUTH1, accepted 2026-10-22).** **Status: accepted** (the steward, under D191), round 4, revised by Codex's two reads and Fable's foundation read under D191 (the notes
below); the steward accepts after reading round 4. The contract is `docs/2026-10-22-git-auth-design.md`.

Daoris's sessions reach git remotes and fail: nothing in Daoris sets up how its git signs in, so a session's git and Daoris's own
fetch authenticate with whatever is ambient (the person's configuration, keys and credential store), which the git on the path often
cannot use (WSR7), and nothing remembers a failure, so each path tries again on its own schedule and a pull request's moments say
nothing at all (design §0.3-§0.4). The owner directed git authentication done comprehensively (several accounts, SSH keys, a designed
screen, learned from existing tools), then widened it to a policy for what a repository, a workspace and a session may do on a remote.

1. **Git identities, one set** (design §3.1-§3.2). An identity is a host, a way (an SSH key or an HTTPS sign-in), a label, the user
   the host reports, and optionally the name and email it commits as, kept in `data/git-identities.json`, which holds no secret.
   Several per host. No scope has a list: a repository points per remote, a workspace per host, this machine may choose the person's
   own per host, a host has a default identity; the pointers live in `driver.json`, and the answer names its source. Two remotes of
   one repository at one address point at one identity.
2. **Two doors apply identity at each act** (§4): Daoris's ssh door, `daoris-git-ssh.exe` named by a bare path in `GIT_SSH_COMMAND`
   so git starts it with no shell (else by `GIT_SSH`, with the repositories it cannot outrank held), and a remote helper of Daoris's
   that every HTTP and HTTPS act reaches through `insteadOf`. Each finds the repository by the act's own working folder, so a `git -C`,
   a clone or a submodule resolves for itself, and is told its home by a variable. `GitWiring.Hand`, beside `Tools.Hand`, hands every
   process only the routing to the doors and the end of every prompt, and removes the `gh` and `az` token variables from a session's
   start; the terminal's shells keep the person's own git. **One reader** takes Daoris's prefix off every address Daoris keeps, says or
   judges; the land frame carries `origin`'s address, and a plugin's tool that reads remotes is named the repository or runs unrouted.
3. **No credential of the person's is handed** (§3.3) unless the person chooses *Your own git sign-ins* for a scope, a widening
   confirmed before it is written and never applied by a migration. At each other act the door removes every authentication input git,
   curl or GCM documents (helpers, extra headers, cookie files, certificate variables, a `_netrc` by an empty home for the HTTPS act,
   an address's user-info), refuses an address carrying a password, and holds a remote whose configuration names a certificate git
   cannot clear. The one read of the person's own is a key file the person names to import.
4. **Secrets in their homes** (§3.4): an SSH private key in `profiles/git/keys/<id>/`, the folder limited to the person's account
   before any key byte is written, plaintext at rest as D67's API keys are; an HTTPS sign-in in the Windows store through Git
   Credential Manager, in a namespace of Daoris's own set for each act; host keys in Daoris's own `known_hosts`, trusted only at a
   person's press (D73's rule).
5. **Authorship apart from authentication** (§3.6): a commit, a session's included, carries the `commitsAs` of `origin`'s identity only
   where the repository names no author of its own, read at the start and handed in the process's command scope.
6. **Nothing prompts** (§4.6): `GIT_TERMINAL_PROMPT=0`, an empty `GIT_ASKPASS`, `GCM_INTERACTIVE=never`, and ssh's `BatchMode` given
   first, under an identity and `own` alike. Below git 2.31 the doors cannot stand, and Daoris's own remote acts refuse, said at the
   start.
7. **A remote that cannot authenticate is held and said once** (§5): failures classed by the transport's words; a hold keyed by the
   repository, the effective address, what served it and whether it holds reads or writes alone; lifted by any change touching it, a
   passing test or the person's *Try again*; one row in *What needs you*; a session told in its instruction not to try. The network's
   failures and unclassed ones hold nothing.
8. **Git access: read, write, dangerous writes, each allow, ask or deny** (§6.1-§6.2), per repository, workspace and machine. Read
   and Write are judged at the doors by the remote command; Dangerous (a non-fast-forward, a deletion, a tag, the line) stays the
   harness's rules' today's denial until the transport judge reads each update, and is set by the person only then. **Daoris's default
   is today's, door by door** (settled by the steward): Read allow; Write answered by the person's yes for the landing and denied for a
   session; Dangerous denied but for the one act a landing rule names. A value the person sets binds the landing and a session alike
   through one judge, and *Use one value for both* sets it in one press. A session runs under the stricter of its start's and its
   repository's now; the person may tighten a running session; an agent changes no access. A Codex session's push refused at the door,
   which nothing refuses today, is a narrowing D72 lets Daoris make.
9. **Identity is who, access is what** (§6.3): no identity where the host refuses anonymous use, no act whatever the access; a
   read-only identity on the host denies writes, the one bound no local process lifts.
10. **Part of the access setup, untouched by full access** (§6.4): `gitAccess`, `workspaceGitAccess` and `machineGitAccess` in
    `driver.json`, resolved by `AccessRules`, edited through a route of its own (`SET_GIT_ACCESS`) and `daoris-driver git access`, kept
    on the record. An older build keeps the keys and enforces none, which the release note says.
11. **One judge, at the doors, always installed** (§6.5): Daoris's own acts ask it in process; the harness's rules deny what is
    denied; the binding check is the two doors, judging each act's class at its remote command. The update-by-update judge (each push's
    updates read, judged whole, the judged object ids forwarded on HTTPS) is a later row, built if still wanted. Addresses the doors do
    not reach are said and denied for Daoris. A `pre-push` hook and a refusing credential helper are rejected.
12. **An ask is asked by the door, while the act waits** (§6.6): the door holds the act and raises a git go-ahead naming the remote and
    the class (with the transport judge, every update), answered *Allow* or *Refuse* in *What needs you* or on the session; an answer
    that comes after the act stopped waiting is kept as a grant for the same act, and the session is started again. The harness is not
    asked a second time.
13. **The landing meets the same judge** (§6.7): it asks before starting its plugin and hands it a grant bound to the plugin's process
    and `origin`'s address (with the transport judge, to the branch and its new commit, the old one judged as a fast-forward); *Accept…*
    and a rule that accepts automatically are the person's yes for exactly that push.
14. **Moving from today** (§6.8): `no-push`'s rules and the push clause of its classifier sentence are composed from git access, its
    publishing and release clause kept, so a session starts exactly as today under the default; a switched-off `no-push` is read once
    as the machine's Write *allow*; every remote moves off ambient credentials once both ways of an identity exist, with one row
    offering an identity or *Keep using my own sign-ins for these*, pre-applying nothing; the row holds work where a landing or a
    session waits on one of its remotes.
15. **The window, the terminal and Ask Daoris** (§7-§9): Settings → Git; each repository's remotes and git access on Setup, a
    workspace's per host; held remotes, refusals by way and git go-aheads in *What needs you*; a session's access and *Tighten…* in its
    head; the `daoris-driver git` family, each sensitive act run only after the window confirms it, the widenings named; Ask Daoris
    proposes `git-use` and opens the add form, and never touches a secret, an identity's life, `own`, access or a go-ahead.
16. **One redaction boundary, and the residual stated** (§10-§11): every text from git, ssh, GCM or a plugin passes one redaction
    before it is kept, said or answered, and a child's own traces are stopped at the child; no key, token or passphrase is written
    outside its home; coded `git.*` machine-log lines. A session runs as the person's account, so Daoris governs an agent's ordinary
    git, not an agent set on getting round it; a session's `gh` and `az` act as the person's own sign-ins, unjudged.
17. **The rows, in the steward's order** (§14): GITAUTH1a (held and said once), 1b (the doors carrying today's credentials and judging
    by command, the address reader and the plugin contract), 1c (SSH identities from the terminal, TOOLS6), 1d (HTTPS identities
    through GCM, against a real GCM), 1e (Settings → Git, the remote rows, the move), 1f (git access set by the person, the door's git
    go-ahead), 1g (the transport judge, if still wanted), 1h (the install, seen; owner).

**Why.** The failure is not a missing setting the person forgot: Daoris has no account of its own on a code host, so it borrowed what
was ambient, which the git on the path could not use, and nothing remembered that. Identities of Daoris's own, chosen per remote,
take to git the principle D125, D175 and D197 decided for agents' accounts. One set with pointers keeps D197's lesson (lists per scope
confused) while letting a scope choose, which a host account needs and an agent's account does not. Applying identity at the doors,
per act, is the only place that sees the repository, the address and the act together. Git access in the access setup, not a
parallel system, keeps one place the person reads what sessions may do; and judging at the transport, where Daoris already stands to
hand the identity, is the one place every form of git push must pass, which the rules and a hook are not. Keeping today's behaviour as
the default, door by door, is what D184 point 5 and D72's widening rule require; once the person sets a value, one value binds both.

**Rejected** (design §12): today's ambient credentials; setting `HOME` for sessions; Daoris's keys in the person's `~/.ssh`, agent or
ssh configuration; an ssh agent of Daoris's own; DPAPI-sealed keys or a passphrase; trusting a host key on first use in the background;
identity composed once per process; `includeIf` per repository or one machine-wide file of per-address users;
`transfer.credentialsInUrl` as the password guard; a `pre-push` hook, a refusing credential helper or the rules alone as the judge; the
harness's held call or a `git_ask` tool as the place an ask is asked; Dangerous judged by flags; doors installed only where access asks
or denies; git access as pauses or a field on `SET_ACCESS`; Write *ask* as the sessions' default; a level's Dangerous widened for a
landing to the line; D135's go-aheads as the transport's permission; a list of identities per scope; an agent narrowing its own access;
Ask Daoris setting up an identity; `own` applied by the move; signing `gh` and `az` in with the git identity; the ssh door as a
shell-form command; `GIT_SSH` alone as the ssh door; the door's home as an argument; Daoris's own read-only git started unrouted; the
update-by-update judge before the identities and the screen.

**Amends,** once accepted (design §13): D121 §2.5's precedence for authentication (the command scope and `GIT_SSH_COMMAND`, rejected
there, now route every act through the doors) and §2.6's terminal; D72's `no-push`; D184's access setup (its held requests unchanged);
D37 and D87's landing and the plugin contract of D100 and D119 (the judge before the plugin, a grant, the land frame's `origin`, a
tool that reads remotes named the repository); D172's home table. D135 is unchanged; the glossary's *go-ahead*
widens. Each amended decision carries a dated note pointing here.

**Held by** (once built): each row's proof in design §14; the resolution, classification, hold, update, grant and stored-shape tables;
a fetch and a push through each door against a local server in the `Process` half; the redaction table; the person-waits and
setting-doors places; the address reader's source scan; `HelpCoverageTests`; `i18n:check` and `names:check -- --strict`; the
install's screenshots (GITAUTH1h).

**What the checks do not cover.** Written from the code at `75bb61805` and read again at `847716cb2`; nothing was run, no key
generated, no sign-in started, and the person's `~/.ssh`, `_netrc` and credential store were not read. Every behaviour of git, curl,
OpenSSH, GCM, gh, az and git-lfs the design leans on is from their documentation (a few from their source as Codex and Fable read it)
and owed a measurement by a named row (design §15).

### 2026-10-22: GITAUTH1a's measurements, and how it was built

Measured with this machine's git (2.53, Git for Windows) and OpenSSH on the loopback only: a raw HTTP host answering 401 or 403,
and a portable Win32-OpenSSH `sshd` serving `127.0.0.1` with keys made for the test. No real host, no key, configuration, agent,
known-hosts file or credential store of the person's was read: each git ran with no system file, an empty global file and a
scratch home, and each ssh with an empty configuration, a key of its own, `IdentitiesOnly`, no agent and a known-hosts file of the
test's. None of it contradicts this decision.

- **The empty `GIT_ASKPASS` survives Windows' environment block into git**, and into git's own child: started as Daoris starts its
  git, `GIT_ASKPASS=` is in the block a `!cmd` alias's `set` prints, and git asks no program `core.askPass` names; without the empty
  value the same program runs (`GitPromptsProcessTests`).
- **The transport's words** (`GitWordsTests`, the rows marked measured): HTTP 401 with nothing to answer, `could not read Username
  … terminal prompts disabled`; with a credential refused, `Authentication failed for`; HTTP 403, `The requested URL returned error:
  403` (a push's is `write-refused`, a fetch's `refused`); OpenSSH's refusal, `Permission denied (publickey).`; an unknown host under
