## D87 — How work lands is a workspace's rule; Daoris merges or makes a branch, and a push is a plugin's (2026-09-28)

**Decision (WSR1, the owner's call).** Asked whether Daoris may ever push a session's branch and open
a pull request, the owner answered: *"this should be configurable, and lets say no push or open pr on
default but we should be able to support later for plugin to control since there will be different
platform for pr"*. So:
- **A workspace has a landing rule, and a repository may override it.** Two forms ship:
  - *merge*: today's door, into the repository's line (D86);
  - *branch*: the session's work is put on a new branch named by the rule's pattern, from the
    session's branch, which grew from the line. The person pushes it and opens the pull request.
  No rule is *merge*, which is today's behaviour.
- **Daoris itself never pushes and never opens a pull request.** D37 stands. The form that does is
  a **plugin's** (D64): the rule will name a plugin, and that plugin, speaking for its platform,
  pushes and opens the pull request. That form is not built yet (WSR4), and until it is, no rule can
  name one.
- **The branch form writes nothing to the checkout.** It creates a branch in the repository and
  moves no checkout, so the root may be dirty or on any branch. An existing branch of that name is
  refused and never moved.
- **The rule reaches every place work lands.** The review screen says what a press would do before
  it is pressed. The door applies the rule. The session's instruction says how its work will land.
  A chain's next step still starts on the step before's branch (D82), so landing the last step
  carries the chain.

**Why.** A shared repository takes work through review on its own platform, and a merge on one
person's machine skips it (the first real workspace, study §1). Platforms differ in how a pull request
is opened, which is the owner's reason for leaving that step to plugins, and a plugin is the seam
Daoris already has for behaviour it does not carry (D64).

**Rejected.**
- **A built-in push and pull request for one host.** It would make one platform the default and
  write a durable push authorisation into core, where D37 keeps push human.
- **Rebasing the work onto the line's current tip.** It rewrites the session's commits. The branch
  form keeps them as they were made, and the person's review shows where they started.

1. **What the line holds is left out.** After SQUASHTIDY1f's whole-tree proof, which still refuses first a tree the line
   holds entirely (its sentence, and *Discard*), the landing judges the tree's commits beyond where it left the line:

   files since, as in the install; (c) every other commit stays in. Patch id judges single commits only (D109's note).
2. **The kept commits are replayed onto the line**, in order, by WSR6's replay in a tree of Daoris's own made for it under

   drops one, and said: *became empty: its changes are already on the line*. WSR6's proof is asked before anything is
   made (only files the line brought may differ between the session's tip and the replay's); then the branch form makes
   its branch, named as before, at the replay's tip, and the merge form merges that tip into the line as D86 does.
3. **Onto which commit.** The branch form builds on the line's latest by REVIEWBASE2-i's rule (origin's where the line
   here is behind it or absent, else the line here); the merge form on the line here. Where the landing advances a branch
   (D145 §3: a chain's, or an entry's, D167), it replays onto that branch's tip what neither it nor the line holds and
   moves it by D145 §3's fast-forward; a branch whose work is on the line by content (its pull request merged) takes
   nothing more, and the landing makes a new branch as a first one does. A branch of the tree's own (TREEFOLLOW1) is
   replayed in place and keeps its name; one on its remote is never rewritten (D109) and is refused as a conflict is.
4. **Said before the press.** The plan (`LANDING`, `trees land --plan`) writes no ref and no tree. It lists what it leaves
   out, each commit's short id, subject and why (*on the line as `<commit>`*, the same change; *on the line by content*,
   the run a squash holds), and what it lands; the press's answer says the same, with any commit the replay found empty.
5. **A conflict is refused, never forced.** A kept commit that conflicts with the line aborts the replay: nothing is made,
   the tree and its branch are as they were, and the refusal names the files in git's words (`RebaseInAsync`'s *CONFLICT*
   lines). No strategy option, and no landing of the commits as made. In Accept's place the review offers one press that
   sends the session words asking it to rebase, shown before the press: that the line moved and holds some of its work,
   the files, and to replay its own commits onto the line, keeping only what the line lacks. They are the person's words,
   sent by D137's say door, so they reopen an ended part as their words do, as the owner's words to the install's
   session did. Accept is offered again once the tree changes.
6. **The fetch.** The plan reaches no network (D109: looking waits for a press). The press fetches the line once, by
   D109's fetch, then judges again, and its answer names any commit it left out that the plan did not; the look's
   automatic landing has no press and fetches nothing. **A fetch that fails is no refusal**: Daoris's git may not reach a
   remote the person's own client does (the install's had no SSH key for it). The landing is judged against what origin
   said when it was last fetched here, said with WSR7's words (*last fetched … ago*, or *never fetched*), git's reason,
   and what the git on the path needs to reach origin.
7. **The session follows what landed.** Once landed, each landed part's tree that stands (no tidy removed it) is moved to
   the landed tip, so its next turn starts in sync: in its own tree as WSR6 moves a session branch (detached, `update-ref`
   from the commit the landing judged, switched back), only while it is clean, nothing runs in it, its branch is not on
   its remote, and WSR6's proof holds (only files the line brought, or the entry's other landed parts changed, differ). A
   branch of its own keeps its name, being what landed. Where any of these fails, the tree stays and the answer says why;
   the landing stands. A session that goes on in a tree whose commits the line came to hold later (a squash on the
   platform after the landing, the install's own order) is LANDSYNC2's: before its turn, REVIEWBASE2-i's one-tree replay
   (`UpdateTreeAsync`, the function REVIEWBASE2-ii's *Bring up to date* presses) brings it up to date where (a) or (b)
   finds commits the line holds, not merely because the line moved. At a start a failed fetch is judged against the last
   one and said, as here, where the person's own press still refuses it (REVIEWBASE2-i point 2); a conflict leaves the
   tree as it was and tells the session in its instruction.
