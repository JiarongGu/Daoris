## D281 — Azure DevOps works through the person's signed-in browser where no token is kept or the kept one is refused: the plugin's own process makes the calls from a tab of its own, never an agent's tool calls (2026-11-12)

**Decision (BROWSERWAY1).** Ten runs of a workspace's pull-request step failed `no-token`, because the plugin's login is refused from
every terminal the person works in, while the person was signed in to Azure DevOps in Daoris's browser. The plugin's calls
(the pull request and its auto-complete, `work/state`, the release watch and the agent's tools) now fall back to that session.

1. **The token is the first way.** A kept token Azure DevOps accepts is used as before. The browser is taken where none is kept or
   Azure DevOps refuses the kept one (401, 403 or its sign-in page); a refused token is not asked again by that process until a
   different one is kept. With no browser handed, the failure is `no-token` or `unauthorized` as it was.
2. **The plugin's process makes the calls, from the page.** A manifest says `hooks.browser`; Daoris hands that plugin's processes the
   in-app browser's DevTools address as `DAORIS_BROWSER` (the shell's browser held in `PluginBrowser`, asked for the address only, as a
   session's server is), and a host with no browser hands none. The plugin opens a tab, holds it by its target and runs each REST call
   as a `fetch` inside that page with the page's own credentials. It never reads a cookie, a storage, a header or the browser's
   cookie store, so no credential reaches its data, logs or evidence.
3. **A tab, not a context.** D277 point 7 gives a session's browser a context of its own. A fresh context was measured against the
   running browser: it carries no sign-in (Azure DevOps redirects it to its sign-in page), so a context cannot serve a call that is
   the person's. The plugin's tab is its own by target: it never selects or navigates another, and another session's navigation moves
   that session's tabs. Point 7's context for a session's Playwright server is unchanged.
4. **A sign-in that lapses** (401, 203, or HTML where JSON was asked) is renewed once by navigating the tab to the organization, which
   renews the single sign-on silently, and the call is made again; a second lapse fails the step as `signed-out` naming it.
5. **The evidence says the way.** Each answer's message ends `Way: the token.`, `Way: the browser.` or `Way: the browser (the kept token
   was refused).`; the tools give `data.way`.
6. **The step's agent is told the step's options.** The goal path gave an agent no options, so a step asking `autoComplete` never set
   it; the ask now carries them, and `create-pull-request` takes them as arguments and sets auto-complete as the step's own
   `work/perform` does.

**Rejected.**
- *The step's agent drives the browser server and fetches itself.* Its calls would be the agent's choice each run: no test could hold
  that the same outputs and evidence come by either way, that a lapse is renewed once, or that no credential is read, and a model's
  reading of a page would stand in the evidence.
- *A browser context of its own for the plugin.* Not signed in, measured (point 3).
- *Reading the page's bearer token to call from the plugin's own `fetch`.* It is the person's credential held by a process that logs
  and stores; the page-side call needs none.
- *A second plugin for the browser way.* One job done two ways (D228): the plugin that opens the pull request does it by the way
  its sign-in allows.

**Supersedes nothing.** D274's plugin-owned sign-in stands: the token the plugin keeps is still the first way.
