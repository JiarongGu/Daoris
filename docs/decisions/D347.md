## D347 — An account id is one hash form, and an older id moves to it once, derived, by a verb run while Daoris is closed (2026-11-20)

**Decision (ACCOUNTID1).** An agent account's id is `acct-` and eight lowercase hex characters, and nothing else: a sign-in into a
new account draws it, and `agent account add <agent> <name>` and the bridge's `profile-add` draw it too, the word becoming the account's name
(`AccountAdd`). An id an earlier
build named by a counter (`account-N`) or by the person's word moves once to that form, with every reference the home has to it,
by `daoris home account-ids --plan|--yes`. The new id is derived, not drawn: the first eight hex characters of the SHA-256 of the
agent and the old id not already taken, so the plan names the very id the apply writes. The apply runs only while nothing of
Daoris runs on the home, beside `home purge`, and a word id stays the account's name where it had none.

**Why.** The id is the folder's name and every store's key; the person reads a name. A person's word as an id is a second way to
name an account, and a counter is a word nobody chose that the window and the terminal then show. A plan that cannot say which id
it will write is not a plan.

**Rejected.**

- *A reader that maps old ids to new ones at every read*: a second reader of an earlier build's record (D323), kept forever.
- *A random id drawn at the apply*: the plan could say only "a fresh id", and a plan read before an apply would not match it.
- *Moving ids at a start, unasked*: a start moves nothing into or within the home (D323's rule 20); the move is the steward's act,
  listed first.
- *Under `daoris agent`*: that family's verbs press the running window for a Confirm; this one refuses while the window runs, as
  `home purge` does, since the window holds the stores open and its sessions run in the folders that move.
- *Rewriting records that say what happened* (a move's row, a hand-over's file, a session's events, the machine log): they keep the
  id they were written with.
