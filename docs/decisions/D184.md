## D184 — A repository's sessions run under an access setup the person sets on its setup page: full access, or each pause chosen; and a session's questions work as Claude Code's do (2026-10-19)

**Decision (the owner's direction).** The owner, 2026-10-19, after an hour in which the installed Daoris's sessions waited on
minutes-long tool runs and on the person: *"if you check the Daoris current process, it's kind of worse than if we just run
the Claude Code console, which is not what I wanted (it keeps pausing the development)"*. Asked which pauses to stop, the owner
answered: *"this entire thing should be able to be configured and shown in the Daoris setup for the repository, similar to Ask
Daoris's permission logic, since I think we can design a full list for permission setup or just simply full access"*, and of
a session's questions: *"this needs to at least be similar to the Claude Code console's logic"*. Measured the same day on the
install: a session waited 41 minutes for go-aheads, another 9 for a permission rule (`Bash(npm start)`, which Claude's auto
mode refused until a rule allowed it), finished work waited up to 44 minutes for *Accept…*, and an ask waited for its route to
be accepted before its session started.

1. **Set where the repository is set up.** A repository's setup page has a section for its sessions' access, beside its line
   and landing. A workspace sets the default for its repositories and the machine sets the default for its workspaces; each
   value shows where it comes from. The terminal has the same verbs, and the effective setup a session started under is kept
   on its record (as D183 keeps Ask Daoris's mode).
2. **Full access, one switch.** Every pause below is off: the harness runs in its own unrestricted mode (D183's full postures:
   Claude's `bypassPermissions`, Codex's `agent-full-access`), an ask goes to the repository the intake chose, finished work
   lands by the repository's landing rule without a press, and go-aheads are not asked for. A harness that cannot run
   unrestricted refuses plainly, as D183 point 1 has it for Ask Daoris.
3. **Or each pause chosen**, the full list, each with what it means:
   - *Permission prompts*: the harness's asking mode, its auto mode (today's, D81), or unrestricted.
   - *Intake routing*: the person accepts the route, or the ask goes where the intake chose (the person may route it again).
   - *Landing*: the person's *Accept…*, or the landing rule lands it (push and pull request as the rule says).
   - *Go-aheads*: asked before the actions the repository names (for example a production system), or never.
   - *Questions*: point 4.
4. **A session's questions work as Claude Code's console does.** A session asks only what it cannot decide (a credential, a
   choice only the person can make), at its turn's end, in its own conversation; the person answers there and it goes on in
   the same conversation. Daoris puts nothing between them but the notice that it is waiting. Whatever a session can decide,
   it decides and records why, and keeps going.
5. **What never changes.** The person's own deny rules hold in every setup (D183 point 1). A go-ahead the ask itself demands is
   asked whatever the setup, since the person wrote it there. The defaults are today's behaviour until the person sets them,
   so nothing loosens by itself.

**Rejected.** Loosening the defaults silently; one global switch with no per-repository choice; a raw rule editor as the only
setup; full access chosen by an agent.

**Amends D81** (each session's harness mode: now the repository's setup), **D89/D183** (Ask Daoris's modes, whose shape this
follows for driven sessions), and the go-ahead and landing decisions it names (each now a setting). **Held by:** the
AUTONOMY1 rows.

**AUTONOMY1e (2026-10-19): point 4, built.** Every quest's instruction tells its session to decide whatever it reasonably
can (a name, which of two sound ways), say it under *Readings* with why and keep going, and to ask the person only for a
credential, an account or a sign-in, a choice the quest or the person's words leave to them, or a go-ahead: for an act
outside its repository or on a production system as before, or one the repository or the quest says needs it. It asks in
its last message, and the answer goes on in that conversation. "A preference nothing records" is gone from the stop and
from *Needs you*: on the install it let a name, and which report a page shows, through to parks that waited 7 to 57 minutes.
Canon's *Look before you ask* says the same for every adopting repository.
- **Nothing stands between the answer and the session.** Words said to a park, in its conversation's box (the say door,
  which wakes the look) or on its card (the service's answer, whose ledger move wakes it), stay on the record; the look plans
  that record before any start, on its own slot, and resumes its harness's own conversation with the words leading the prompt
  (D131). A new session carries them only where that conversation cannot go on, saying why; the person's pause and hold,
  and a cooling account, still hold it.
- **The notice is said once per question.** A park the person answered waits on nobody, so the same session asking again is
  said again though no look saw it working, and a park answered before a look saw it is not said.
- **Follow-ups (2026-10-19, NOTICEPLAIN1, QBENCH2).** A park's balloon says the session's own question: `AttentionEvent.Detail`
  takes the note's agent parts, not Daoris's lead, and says the note whole where a record has no agent part. The question
  bench's *needs the person* now reads as this point does, and its class `S` (a choice the session decides) scores a reading
  as right and asking the person as a needless ask.
- **Nothing loosens by itself (point 5).** No permission, routing, landing or go-ahead moves, and every go-ahead asked before
  is still asked. What a session now decides is a reading committed on its branch and reviewed with its diff before anything
  lands. *Questions* has no choice of its own (point 3 points here), so this is every setup's behaviour, and nothing reads
  AUTONOMY1a's setting for it. The intake's question, the route it asks the person to accept, is intake routing's (AUTONOMY1c).
