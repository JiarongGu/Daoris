## D184 — A repository's sessions run under an access setup the person sets on its setup page: full access, or each pause chosen; and a session's questions work as Claude Code's do (2026-10-19)

**Decision (the owner's direction).** The owner, 2026-10-19, after an hour in which the installed Daoris's sessions waited on
minutes-long tool runs and on the person: *"if you check the Daoris current process, it's kind of worse than if we just run
the Claude Code console, which is not what I wanted (it keeps pausing the development)"*. Asked which pauses to stop, the owner
answered: *"this entire thing should be able to be configured and shown in the Daoris setup for the repository, similar to Ask
Daoris's permission logic, since I think we can design a full list for permission setup or just simply full access"*, and of
a session's questions: *"this needs to at least be similar to the Claude Code console's logic"*. Measured the same day on the
install: a session waited 41 minutes for go-aheads, another 9 for a permission rule (`Bash(npm start)`, which Claude's auto
mode refused until a rule allowed it), finished work waited up to 44 minutes for *Accept…*, and an ask waited for its route to
be accepted before its session started.

1. **Set where the repository is set up.** A repository's setup page has a section for its sessions' access, beside its line
   and landing. A workspace sets the default for its repositories and the machine sets the default for its workspaces; each
   value shows where it comes from. The terminal has the same verbs, and the effective setup a session started under is kept
   on its record (as D183 keeps Ask Daoris's mode).
2. **Full access, one switch.** Every pause below is off: the harness runs in its own unrestricted mode (D183's full postures:
   Claude's `bypassPermissions`, Codex's `agent-full-access`), an ask goes to the repository the intake chose, finished work
   lands by the repository's landing rule without a press, and go-aheads are not asked for. A harness that cannot run
   unrestricted refuses plainly, as D183 point 1 has it for Ask Daoris.
3. **Or each pause chosen**, the full list, each with what it means:
   - *Permission prompts*: the harness's asking mode, its auto mode (today's, D81), or unrestricted.
   - *Intake routing*: the person accepts the route, or the ask goes where the intake chose (the person may route it again).
   - *Landing*: the person's *Accept…*, or the landing rule lands it (push and pull request as the rule says).
   - *Go-aheads*: asked before the actions the repository names (for example a production system), or never.
   - *Questions*: point 4.
4. **A session's questions work as Claude Code's console does.** A session asks only what it cannot decide (a credential, a
   choice only the person can make), at its turn's end, in its own conversation; the person answers there and it goes on in
   the same conversation. Daoris puts nothing between them but the notice that it is waiting. Whatever a session can decide,
   it decides and records why, and keeps going.
5. **What never changes.** The person's own deny rules hold in every setup (D183 point 1). A go-ahead the ask itself demands is
   asked whatever the setup, since the person wrote it there. The defaults are today's behaviour until the person sets them,
   so nothing loosens by itself.

**Rejected.** Loosening the defaults silently; one global switch with no per-repository choice; a raw rule editor as the only
setup; full access chosen by an agent.

**Amends D81** (each session's harness mode: now the repository's setup), **D89/D183** (Ask Daoris's modes, whose shape this
follows for driven sessions), and the go-ahead and landing decisions it names (each now a setting). **Held by:** the
AUTONOMY1 rows.

**AUTONOMY1e (2026-10-19): point 4, built.** Every quest's instruction tells its session to decide whatever it reasonably
can (a name, which of two sound ways), say it under *Readings* with why and keep going, and to ask the person only for a
credential, an account or a sign-in, a choice the quest or the person's words leave to them, or a go-ahead: for an act
outside its repository or on a production system as before, or one the repository or the quest says needs it. It asks in
its last message, and the answer goes on in that conversation. "A preference nothing records" is gone from the stop and
from *Needs you*: on the install it let a name, and which report a page shows, through to parks that waited 7 to 57 minutes.
Canon's *Look before you ask* says the same for every adopting repository.
- **Nothing stands between the answer and the session.** Words said to a park, in its conversation's box (the say door,
  which wakes the look) or on its card (the service's answer, whose ledger move wakes it), stay on the record; the look plans
  that record before any start, on its own slot, and resumes its harness's own conversation with the words leading the prompt
  (D131). A new session carries them only where that conversation cannot go on, saying why; the person's pause and hold,
  and a cooling account, still hold it.
- **The notice is said once per question.** A park the person answered waits on nobody, so the same session asking again is
  said again though no look saw it working, and a park answered before a look saw it is not said.
- **Follow-ups (2026-10-19, NOTICEPLAIN1, QBENCH2).** A park's balloon says the session's own question: `AttentionEvent.Detail`
  takes the note's agent parts, not Daoris's lead, and says the note whole where a record has no agent part. The question
  bench's *needs the person* now reads as this point does, and its class `S` (a choice the session decides) scores a reading
  as right and asking the person as a needless ask.
- **Nothing loosens by itself (point 5).** No permission, routing, landing or go-ahead moves, and every go-ahead asked before
  is still asked. What a session now decides is a reading committed on its branch and reviewed with its diff before anything
  lands. *Questions* has no choice of its own (point 3 points here), so this is every setup's behaviour, and nothing reads
  AUTONOMY1a's setting for it. The intake's question, the route it asks the person to accept, is intake routing's (AUTONOMY1c).

**AUTONOMY1a, built 2026-10-19: the setting, its resolution and its record (points 1, 5).**
- **The setting** is `driver.json`'s `access` (by repository), `workspaceAccess` (by workspace) and `machineAccess`: each level is
  `"full"` or the pauses it names, `permissions` (`asking`, `auto`, `unrestricted`), `routing` (`person`, `intake`), `landing`
  (`person`, `rule`), `goAheads` (`named`, `never`) and `questions` (`claude-code`). `AccessRules` reads, resolves, says and edits it;
  the CLI's `driverconfig.ts` reads and keeps it the same way, held to the same bytes by the keeps table.
- **Each pause resolves on its own**: the repository's, else its workspace's, else this machine's, else today's (`auto`, `person`,
  `person`, `named`, `claude-code`), naming where it came from. A full level gives every pause its open value. Read as a stored shape: a
  pause this build does not know is passed over, and a value it does not know reads as that pause's default at that level, never as the
  next level's, which may be looser. A pause set over full access writes every pause at its open value, then the change, so nothing else
  moves under the person's hand; the last pause taken away clears the level.
- **Go-aheads:** `named` is today's, a go-ahead asked before the acts the repository's own documents name; the setting holds no list of
  names. What the ask itself demands (point 5) is AUTONOMY1c's to keep asking under `never`.
- **Doors.** `SET_ACCESS` {repository, workspace or `machine: true`, `access`: `full`, the pauses, or none to clear}, the driver's
  scope; `STATE` answers each level as set, and `LINES` and the lines slice each repository's pauses as they resolve, with their source.
  `daoris-driver access [<repository>|--workspace <w>] [full|<pause>=<value>…|--clear]` says or sets it, a change under the home's
  lease; the two refuse alike, in `AccessRules`' words. No proposal names it: full access chosen by an agent is rejected above.
- **The record.** Each driven start resolves it once from the file its look read and hands it to the quest's open: the record keeps
  `access`, each pause with its value, machine-local (answered on loopback only, on no feed; a record from before reads none). Its
  transcript notes it in one line after the account's, only where it is not today's behaviour, so an untouched start reads as it did.
  The note is uncoded English until the page's note catalogues word it.

*Not built:* the effects (AUTONOMY1b, 1c, 1e) and the page (AUTONOMY1d: the web's `LINES_FIELDS` and its `Session` type take `access`,
and Ask Daoris's coverage names `SET_ACCESS` exempt, as the person's own). The driver reads the record's `access` back nowhere yet: the
planner's `PriorSession` gains it with the first row that compares a start with the one before.

**AUTONOMY1c, built 2026-10-19: intake routing and go-aheads follow the setup (points 2, 3 and 5); landing is left to its own row.**
- **Intake routing.** Where the declarations do not settle an ask, its intake is told which of the workspace's repositories take its
  choice of route without the person's accept (`IntakePrompt.RoutedByIntake`: each repository's own setup, full access among them,
  since the repository it chooses is the one whose setup counts). It publishes to the best fit among them, beginning the body with
  the route being its own choice, why, and which others could own it; for any other it still asks. The publish is the intake's, so
  the ask's tier reads `intake` and its page says an intake session read it and published it; the person routes it again by
  publishing it elsewhere. `person` is today's: an intake whose declarations settle an ask publishes without asking, as it always
  has. *Reading:* with no intake harness the declarations tier still proposes and never publishes (D65, INT4a), whatever the setup:
  a word match is nobody's choice of route.
- **Go-aheads.** Under `never`, full access among them, a driven session's instruction (`TargetPrompt`'s asking piece) asks a
  go-ahead only where the quest or the person's words demand one before an act. Point 5 holds because the ask's words reach the
  session verbatim beneath the quest, and `go_ahead_ask` still holds such a go-ahead on the ask. An act the work needs on a
  production system or outside its repository it does without asking, and names under *Readings*. The boundary still holds: a
  push, a publish or a release is not the session's, and the landing's push is its rule's. `named` keeps AUTONOMY1e's words byte
  for byte. A set-up step's own section keeps its go-aheads (a deployed environment's deploy, pipeline run, configuration write
  or sign-in), since they are the review environment's procedure (D154), not acts the repository names.
- **Read back.** `PriorSession.Access` reads the setup off the record. A carry-on is composed afresh from the setup as it stands.
  A session going on in its own conversation is not handed its instruction again, so it is told, after the words, where its
  go-aheads changed since it started (`Continuations.GoAheadsChanged`). A record from before the setup was told today's.
- **Landing, not built.** *Accept…* gates only work under a rule without the switch: `autoAccept` on a branch rule (D145) already
  lands a done without a press. Three places read it: `AutoLander.Concluded` (due at the conclusion), `AutoLander`'s judge through
  `WorkflowProcess.Current` (each look), and `TreeLands`' refusal of an automatic landing under a rule that does not accept
  automatically. All but `WorkflowProcess` are in `Driver/Trees/`, which this branch was asked to leave to TREEDEPS1 and TREELINK1,
  so the row stays open. Its shape: one effective rule (the chosen rule, its switch on where it is a branch rule and the
  repository's `landing` resolves `rule`), read at those three and at the session's plan. It is never written to `driver.json` or
  shown as the rule's own switch. A merge rule lands nothing by itself (D51 rule 6; D145 rejected a merge at done), so `rule` over
  a merge rule leaves *Accept…*. The evidence hold, a lost claim and a done turned down hold it as they hold the switch.
- **Held by** `GoAheadSetupTests` (each way, full access, and the ask's own demand under `never`), `IntakeRoutingTests` (each way,
  full access, and the chosen repository's own setup) and `AccessCarriedTests`. `IntakeTests`' new full-access case is in the
  `Process` half and was not run here. *Not covered:* no real intake or session ran under the setup. The words are instruction
  text, which no page catalogue holds.

**AUTONOMY1b, built 2026-10-19: a driven session's permission prompts (points 2, 3 and 5).** Each driven start reads its repository's
`permissions` as it resolves, once, before any tree grows or record opens, and a resume goes on under the same (`DrivenAccess.For`).
- **`auto`** is D81's, unchanged: the protocol door's `auto|acceptEdits` (Codex's `agent`), the native door's `acceptEdits`.
- **`unrestricted`** is the harness's full posture (D183's): `--permission-mode bypassPermissions` on `claude-code`, `bypassPermissions`
  on `claude-code-acp`, `agent-full-access` on `codex-acp`. The protocol door's is required, so an agent that does not offer it fails the
  open naming the repository's setup and its way on (`AcpSession.Unoffered`), never Ask Daoris's words, and never runs auto under it.
- **`asking`** is the harness's asking mode, `ISessionAdapter.AskingPosture`: `default` on both Claude doors, `read-only` (*Ask for
  approval*, read from codex-acp 1.12.0's bundle) on Codex's, required as above. D52's refusal of every ask stands, so an asking session
  uses only what its rules allow and every other tool is refused: over `-p` nothing answers an ask, and on the protocol door Daoris
  refuses it. Codex takes no rules, so it does only what that mode allows unasked. Routing a tool ask to the person as a proposal instead
  needs a held request on the wire, a card, its timeout and an answer back: more than a sentence, so it is left as a row.
- **A harness with no mode for the value** (dsh, the stubs, every plugin-declared harness) is held before any record opens, naming it,
  the value, where it was set and the two ways on: `daoris-driver access <repository> permissions=auto`, or another agent.
- **The person's denies hold in every value.** The spawn's rules are composed beside the mode, never from it (`HandRules` is unchanged):
  the person's denies, the shipped `no-push`, the classifier's hard denials and the lineage hook go on both Claude doors under each
  value. That Claude's `bypassPermissions` honours deny rules and PreToolUse hooks is still the maker's word, not measured: a test
  reaches the spawn's file and arguments, not the harness, and a real run needs an account. Codex takes no rules in any value, and its
  start note says so.
- **The tree guard stays in every value.** PERM3's hook refuses an edit outside the session's tree, and a driven session's tree is its
  place of work: unlike Ask Daoris's full access, whose room is not, unrestricted does not lift it.
- **The note** keeps AUTONOMY1a's setup line and adds the mode the start got (``Permission prompts: unrestricted on `claude-code-acp`,
  the agent's `bypassPermissions` mode, which asks nothing; …``). A start under today's behaviour still notes nothing.
- **Read back.** `PriorSession.Access` reads the record's setup; a record from before, and a value this build does not know, read as
  `auto`. A carry-on's new record and a resume of the same record run under the setup standing now and say the change first
  (``Permission prompts changed since `s1` started: it started under `asking`, and this run goes on under `unrestricted`.``), then
  the mode got. A resumed record keeps the setup it opened under: the ledger has no door to change it yet.

**AUTONOMY1d, built 2026-10-19: the page (points 1-3, 5).** One set of rows (`settings/Access.tsx`) at three levels: *Sessions' access*
on a repository's Setup, after *Line and landing*; the same section on a workspace's Setup, after *Defaults*; and this machine's under
Settings → Driver. A repository's pauses are the driver's resolution (`LINES`' `access`, now composed from the lines slice); a
workspace's and the machine's are resolved on the page from `STATE`'s levels as set, by the same rule as `AccessRules.ResolveLevels`.
- **Full access is one switch, asked once.** Its press opens an inline ask (`InlineConfirm`, the primary's hue on the warning rail)
  naming what it turns off and what stays, and only *Enable full access* sends `access: "full"`; a refusal is said in the ask. On, its
  line wears the warning colour. Off asks nothing, since nothing loosens: it clears the level, or, where the level above is full too
  and clearing would leave full access standing, sets today's four pauses at this level.
- **Each pause** says its value in a sentence, where it was set (this repository, the workspace by name, this machine, Daoris's
  default), its meaning on its glyph and its `daoris-driver access` twin; from above it offers *Set for this …*, its own carries its
  choice and *Clear*, which sends that pause as null, back to the level above. *Questions* is shown with no choice (AUTONOMY1e). A
  pause or a value the page does not know is shown as its code and never read as open, so the switch never reads looser than the file.
- **The words say what each value does now.** *Asking mode* says a tool off the rules is refused, since no prompt reaches the person
  (AUTONOMY1b; AUTONOMY1b3 rewords it when one does), and routing speaks of an ask its declarations do not settle (AUTONOMY1c).
  *Landing rule* is set and shown, and acts once AUTONOMY1c2 lands it.
- **Ask Daoris's coverage** names `useSetAccess` exempt on the repository's and the workspace's place and under Settings → Driver, as
  `useSetHelpMode` is: no proposal names `SET_ACCESS`.
