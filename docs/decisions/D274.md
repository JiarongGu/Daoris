## D274 — A plugin contributes what it adds through declared points, and keeps its own sign-in: Daoris draws and seals, the plugin speaks to its service, and Daoris knows no plugin (2026-11-11)

**Decision (PLUGINEXT1).** A plugin is an extension that can do almost anything, and Daoris holds no knowledge of any particular one.
The contract is `docs/2026-11-11-plugin-ui-design.md`; its later rows settle here as dated notes.

1. **Contributions.** A manifest declares what the plugin adds beside its points: `views`, `commands`, `settings`, `accounts`, `status`
   and `notices`. Daoris reaches a plugin only through what it declares, and every word shown comes from the manifest and the plugin's
   answers. A command is offered in the palette, on the plugin's page, in the menus of the records it names, in the terminal as
   `daoris <plugin> <command>`, and, marked `tool`, to an agent as a tool: one declaration, every surface. An agent-run step will hold
   its plugin's tool commands and the step's goal, and act through the plugin's process.
2. **Accounts.** An account declares its ways (`device-code`, `browser`, `token`). Daoris draws the card and opens the address in the
   person's own browser; the plugin's process speaks to its service; Daoris keeps what it answers as an opaque secret sealed per plugin
   and account, hands it to that plugin's process alone (at `initialize`, and in `accounts/changed`), and never to the page, a session,
   a push, the log or a process's environment.
3. **One way in.** A plugin tells Daoris things only by the notifications it declared. Where Daoris tells a plugin something, it is an
   event the plugin consumes on the existing hook points and the `work/event` relay, never a second channel.
4. **The person's hand.** Every contribution has a switch per plugin and per place (`plugins.json`'s `off`), the plugin still installed.
   Removing a plugin signs it out and forgets its secrets.
5. **One credential.** No git identity's token is handed to a plugin. An identity's API token is offered once to the plugin that
   adopts it, then cleared; the identity's `api` kind and its setters go with the last reader.

**Rejected.** *A git identity's API token handed to the plugin* (`DAORIS_HOST_TOKEN`): a plugin's credential is not git's; it bound the
plugin to the identity serving origin and gave the person no way to sign a plugin in. *A secret field Daoris owns, by the plugin's
name and meaning* (`daoris plugin secret`): Daoris would hold each plugin's concepts, and a device-code or browser sign-in would be a
second way. *The plugin keeping its own plain-text file*: no one place to see, sign out or remove an account. *The OS's credential
manager*: a backend per OS for no gain over the seal Daoris already uses. *A variable the person sets*: unseen and inherited by every
process.

**Note (2026-11-11), the first slice.** Built: `interfaces.commands` (`daoris <plugin> <command>`, rounds at `hook/command/run` with
`said`, `ask`, `open`, `code` and `exit`), `interfaces.storage` (a folder under `profiles/plugins/<id>/`, limited to the account, handed
as `DAORIS_PLUGIN_PRIVATE` to that plugin's processes alone, removed with it), `off` per plugin and interface, the place's hand judging
Write alone, and `adopts` handing an identity's API token to a command once. Both pull-request plugins sign in through `login`,
`logout` and `status`, and `DAORIS_HOST_TOKEN` is gone. Against points 1, 2 and 4 the slice differs and the contract's rows reshape it:
its manifest key (`interfaces`, a problem refusing the plugin) moves to the contribution points, each problem refusing that
contribution; its token entry (`login`'s masked `ask`, kept by the plugin in its storage) moves to an account's `token` way, sealed by
Daoris and handed at `initialize`, after which the storage folder and `ask` are removed; its switch gains places.

**Note (2026-11-11), the rename.** A plugin's id is `<family>-<name>`: Daoris's own plugins are the `daoris-` family, and anyone
else's keeps to its own. The examples are `daoris-azure-devops` (it opens the pull request, sets auto-complete, follows the merge and
the release, and will carry pipelines and work items), `daoris-github` and `daoris-in-app-browser`. A plugin renames itself in its
manifest, `formerly: [<old id>]`, and Daoris, knowing no plugin, moves the old id's copy, switches, data, private storage and
approvals to the new id once. A saved workflow naming `<old>/<step>` is read as the new id's step and is not rewritten: a version is
never edited, and its digest is kept so a run pinned to it goes on. The terminal names a plugin by its id alone. *Rejected:* a new
version written for each saved workflow at the rename (a save the person never pressed, which leaves every pinned run on the old kind
anyway, and asks no consent of the places following the home default); a terminal word apart from the id, by a manifest's `command`
or by dropping the family (a second name for one plugin, and two families' `github` would meet); renaming the steps' schemas (a
schema names its format, and evidence already kept names it).

*Note, 2026-11-11 (a plugin's command by its id's tail):* a plugin's commands may also be addressed by its id without the family prefix where exactly one installed plugin has that tail (`daoris azure-devops login`); a tail two plugins share is refused naming both, and a full id always wins. This replaces the rejection of dropping the family: the short form is the id's own tail, not a second declared name, so Daoris still names no plugin. The kit refuses an id with no family and the `daoris-` family outside Daoris's own examples; `daoris plugin try-again <id>` and the page's *Try again* clear an unsound plugin without a restart.
