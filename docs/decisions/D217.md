## D217 — A render the page's error screen caught is logged with the view the page showed and the first frames of its component stack, by name alone (2026-10-29)

**Decision (PAGELOOP1).** A render that throws anywhere in the page is caught by the page's error screen (`app/PageBoundary.tsx`,
outermost in `app/PageRoot.tsx`, both roots under it), which says the page stopped and offers a reload of the page alone. Its
`page.error` line, `where` `render`, carries two fields beside `message`:

- **`view`**, a name: the view the main window showed (`sessions`, `overview`, `quests`, …), said by the frame at the commit that shows
  it, or a secondary window's own, `window:monitor` or `window:session`, known before anything is drawn. A page that failed before any
  view was shown names none. The module keeps it only as a name (`^[A-Za-z0-9][A-Za-z0-9_.:/-]*$`), so a value with a query or a
  sentence in it is dropped.
- **`stack`**, a text cut at 120 characters: the first five frames of React's component stack, innermost first, each by its component's
  name alone, joined ` < `. A production build's names are minified and kept as they are.

For example, `{"where":"render","message":"Minified React error #185; visit https://react.dev/errors/185 for the full message or use the
non-minified dev environme…","view":"sessions","stack":"Ue < $t < div < Xt < Suspense"}`. `tools/usage-report.mjs` groups it as *the
page (render)* by `where` and `message`, as it groups the window's and the promise's.

**Why.** Twice on the install (2026-10-27 and 2026-10-28) React's update-depth guard (#185) emptied the window seven seconds before a
session ended: the page had no boundary, so React unmounted the whole tree, the window had no reload and a restart of Daoris ends every
running session. The log held the window's `error` line, the minified message alone, which names no component and no view, so nothing on
the machine said where the loop was. React hands the component stack to a boundary alone (`componentDidCatch`'s `info.componentStack`);
the window's `error` event carries the message. D94's page fields were the message only, cut short, never a stack or what was on the
screen (LOG1b). The names are the code's own words and the view is a view's id, neither anyone's words, a file's contents, a secret nor
an address (D94's *What is never logged*); and the runtime's own exceptions already keep their first five frames (`error`'s `stack`,
HOSTLOG1), so the page's line keeps the same depth of its own kind of stack.

**Still never carried**: a frame's location, which is where the page was loaded from (a development build's module path with its `?t=`
query, a production build's column in its bundle); a prop, a state or any text the page drew; the query string a secondary window was
opened with; the attended session, quest or ask.

**Rejected.**
- **The whole component stack**: a paragraph of frames, where the top five say where it broke and the log keeps a clue.
- **Each frame's location**: the page's address, in development a module path with a query; in production a column in a bundle the
  names find anyway, since the install holds the same bytes the line was written from.
- **Shipping source maps**, so a production stack reads as source: the install would carry the page's source to read a line that comes
  rarely.
- **Keeping the functions' names in the production build** (esbuild's `keepNames`): every function of the bundle wrapped at every load
  for the same rare line. A minified name with its view finds the component in the installed bundle, whose catalogue keys survive
  minification. A later row can take it if a line proves unreadable.
- **`createRoot`'s `onUncaughtError` and `onCaughtError` alone**: they hear the component stack too, and leave the window blank.
- **The view read from the remembered key** (`daoris.view`): it remembers Sessions or Overview alone, the landing choice, not the view.

**Note, 2026-10-29: PAGELOOP1 (c) built.** A window whose page is blank past what the page's error screen catches can be reloaded from
outside the page, and the host, the driver, the service and every session keep running.
- **The door is the tray icon's menu** (`SessionNotifier`'s own `NotifyIcon`, which had no menu): one item that reloads the page of every
  open window of this Daoris, main windows and secondary ones. The tray is the one surface outside the page that a blank window
  leaves. The item's words are the page's own, `notifications.system.reloadPage` in both catalogues, handed with the balloons' over
  `SET_NOTICE_WORDS` and read each time the menu opens, so the language is the machine's chosen one; English (the modules' twin
  of the catalogue, `SessionBalloon.English`) before any page has handed words.
- **The reload opens the page again.** The kit's browser (`Shenora.Chromium` 0.24.0 `ChromiumChildBrowser`, the type `ChromiumView.Browser`
  gives) exposes no reload: `Reload()` is on the kit's session browser and web panel, which a view does not reach. The window's
  `ChromiumView` is therefore made again on the same path, on the window's own thread: the same page on the same profile, whose
  bridge handshakes again as it does on any reload. The host, the driver and the service are not in the view, and no session ends.
  A window still on its splash or on its trouble label has no page and reloads nothing (`IReloadableWindow.ReloadPage` is false).
- **The machine log says each reload**, one `page.reloaded` line naming the window, beside the page's `page.error` lines.
- **No key.** The kit gives the host no key hook before the page, and the kit is another repository's: a host-side reload key would be a
  request to the kit (a key hook, or a `Reload` on `ChromiumView`), and nothing is built for it here. **No page command and no bridge
  route**: the page's error screen already reloads the page from inside.
- **Where it is.** `PageReloads` and `IReloadableWindow` (`Daoris.Desktop.Modules/Windows/PageReloads.cs`, tested in
  `PageReloadsTests`), the forms' implementations in `MainForm` and `SecondaryForm`, the menu in `SessionNotifier`.
