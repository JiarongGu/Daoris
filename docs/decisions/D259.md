## D259 — Each graph run that worked a branch governs it, and each run of an entry lands on its own quest's branch (2026-11-10)

**Decision.** An ask that sends two quests to one repository makes two runs in one line of work (`ask:<id>/<repository>`). The later
quest's session can be placed in the tree the earlier one's opened, so one branch carries the quests of two graph runs. Such a branch was
held: neither run governed it, each run's branch-side steps had no subject, and the runs sat on `content` for good while every Accept was
refused *nothing before it holds it*. A branch only graph runs produced is now each of those runs' subject: each run judges it under its
own graph, its holds, its review and its landing, and a landing one of them makes is read by the other as work merged outside it. A branch
Current's work shares with a graph run's stays held, said, as before.

A part's own landing was named for its entry's first part and joined that part's branch, whichever run each part served, so one run's
session landed onto the branch named for another run's quest. It is now named for the first part of its own run in the entry, the run
being the chain's first quest in its repository (`RunParts`), and each run lands on its own quest's branch.

**Rejected.** Binding a branch-side step once the tree frees, or reading its tip with no tree: the tip is read from the branch's ref
already, and what kept the step unbound was the held branch, which no tree's freeing ends. Keeping two graph runs' branch held and saying
so on the run's record: the run would still wait for good, its work done. Joining every part of an entry onto its first part's branch: an
ask's sibling quests are separate runs, each reviewed and landed by its own graph.

**Note, 2026-11-11 (D260).** A later quest of a line that is a run of its own gets a tree and a branch of its own, so no new run shares a
branch; the tolerance above holds for branches shared before, and a plugin's event on one goes to each run whose own node awaits it.
