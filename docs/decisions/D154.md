## D154 — Work is reviewed where it runs before it is offered to land: a review environment, local and shown in Daoris's browser by default or a deployed one, set per workspace, repository and task; a set-up step that is a quest; and a landing that waits for the person's *reviewed* (2026-10-08)

**Decision (REVIEWENV1).** A ticket in the owner's work workspace became a chain through the intake: a quest that built
the change in the reporting app's repository, then a step that checked it in a browser by injecting the new setting into
the page's own network answer. Nothing was written to the development environment. Both quests closed done, and the
chain was offered *Accept…*, toward a pull request into the line that ships to production. The owner: *"I never saw this
set up in dev for me to review"*, and *"a development without any verification and want to merge to prod is not a good
sign; this should also be some process rule set up in Daoris's development cycle"*. The same day they added *"this
should be configurable: some repos need it and some don't, or some tasks need it and some don't"* and *"a lot of
development we all review locally, just like what we are doing with Daoris right now"*. In live work a session proposed a
dev deploy that no document describes, and the person chose to run it locally against dev data. Another session asked to
stop the person's own dev servers to serve a branch on the usual port. The person refused: *"I still don't see it added,
so Daoris should drive the browser just like how Claude Code does with the extension"*. The contract is
`docs/2026-10-08-review-environment-design.md`.

1. **A review environment is where a repository's work runs for the person to look at before it lands.** It has a name,
   a kind, the repository's own procedure, and the address where the app is used. **Local** is the default kind. The
   step builds the work in its own tree and shows it in Daoris's browser at the address where the app normally runs.
   **Deployed** is a shared environment such as `dev`, reached by the repository's documented route. Production is
   never one: a name that reads as production is refused at every door, by the place words `GoAheads.cs` already reads.
   The procedure is a document or a skill in that repository, named by a repository-relative path that Daoris checks
   exists and never reads for meaning. A repository that documents no route has none until it writes one, which is its
   own work, asked as a quest.
2. **It lives in `driver.json`**, in `reviews` (a repository's rule, or `false` for none) and `workspaceReviews`, beside
   the landing rule and ranked apart from it (design §1.2–§1.3). A rule has `environments`, the first being the default,
   and `required`, only `true` being on. A local environment's `address`, where the app normally runs, is required and
   the person's to declare. A local environment may carry `run`, the person's command for work that needs a process of
   its own. A repository's rule replaces its workspace's whole. The doors are `daoris driver review …`, the
   workspace's and a repository's Setup row *Review before landing*, and Ask Daoris's `setting` card. Each says what it
   lets a step do as it is set.
3. **Three levels, each over the one above**: the workspace, the repository, and the task. For a chain's work in one
   repository, the first that speaks decides (design §1.4):
   - the person's *skip* for this work;
   - a set-up step in the chain;
   - the chain's choice (`off`, `on`, or an environment's name);
   - the ask's choice;
   - the repository's rule;
   - the workspace's rule;
   - nothing, which is today.

   The person sets the task level on the composer, the ask's page, a quest's page, at the gate and at a terminal, kept
   with their words. The intake sets it only on the person's own words, a quote the exchange checks as it checks a
   requirement's, and otherwise **proposes** with a reason that only the person's press applies. Where the default says
   review and the work plainly needs none, a change to a document say, the intake proposes `off` and composes no set-up
   step. It does not park to ask. The gate then holds with the proposal beside *Skip review for this work* and *Set it
   up*, and a fact beside them: the paths the chain changed.
4. **The set-up step is a quest**: a chain step to the same repository, directly after its last step, whose `review`
   names the environment. Its tree grows from the branch the step before worked on (D82). The intake composes it where
   the level says review, and the person's *Set it up* publishes it in fixed words, following the chain (a door that sets
   `follows` later, which D149 point 1 allows). The planner sits a step whose environment is not declared here, whose
   procedure is not in its tree, or, for local, that has no window to show it in.
5. **Local: the step shows it, and the person looks** (design §2.3). The shell opens a tab of Daoris's browser for the
   step, since an agent's own tab has no window. The session builds the app against dev's data as the procedure says,
   and asks Daoris to serve that build to its tab (`review_serve`). The shell then holds request interception on that tab
   alone, at the rule's address only. The session navigates to the change, performs the interaction, captures it, leaves
   the tab there, and says what it showed and how to show it again (`review_ready`). Daoris keeps the tab served until
   the person's verdict, because a session's interception dies with it and the next reload would quietly load the
   person's own server. **A step never stops, restarts or takes over a process or a port of the person's.** That is a
   go-ahead at the least, and the default route needs none. Work that needs a process of its own runs as a review run,
   on a port nobody holds, by the person's `run` command or their press. A command the step proposed runs only at that
   press, and only if it stands verbatim in the procedure. Daoris never runs a command a session names.
6. **Deployed: the documented route, under go-aheads.** A deploy, a pipeline run, a configuration write or a sign-in is a
   go-ahead once per ask (KNOWUSE1a), unless the repository's standing answer gives it (KNOWUSE1b). A go-ahead a set-up
   step asks for production is refused by the go-ahead door. A session never pushes (D37). A procedure that needs the
   branch on a remote is the person's to do, recorded as *I set it up myself…*.
7. **The gate.** Wherever the level says review, *Accept…* is replaced by *Waits for your review in `<environment>`*.
   `trees land` refuses, a merge rule waits as a branch rule does, an advance waits, and *Accept automatically* keeps the
   session due as `unreviewed` until the first look after the review. What lets it go is the person's *reviewed* on a
   set-up whose commit holds the landing's tip (`merge-base --is-ancestor`), or their *skip*. The commit is the step's
   tree `HEAD`, read by the driver when the session ends, never reported by it.
8. **The verdict is the person's alone.** No connector tool and no Ask Daoris card gives one. The doors are the app
   strip's chip beside the browser's door (*In review: `<quest>`*, with *Open*, *Reviewed*, *Not yet…* and *Show it
   again*), the set-up step's *Review in `<environment>`* on its page, What needs you, and `daoris-driver quest review
   <quest> reviewed|not-yet|show|stop|set-up`. Never inside the browser: it has no bridge, and an agent driving it could
   press one. *Not yet* needs words. They are kept on the ask, and said to the set-up step's session as its next turn
   (D137). It puts right what they name, in the showing or, until DRIFT1e moves corrections, in its tree with a commit.
   It then shows it again and says a new set-up. *Show it again* re-serves and reopens the tab with no session, or with
   the interaction by fixed words to the session, as *Capture proof* does.
9. **What is recorded.** A set-up step's done closes held, a new cause of D133's hold, after departure and evidence.
   Two operation kinds travel with the quests: the set-up (`look`, `shows`, `again`, `served` or `run`, `commit`, who,
   when) and the verdict (`reviewed` or `skipped`, the set-up, the person's words). D133's yes no longer lifts a review's hold, and a
   *reviewed* lifts nothing else. The words are kept on the ask as their own kinds. The landing record gains `reviewed`
   or `skipped`, the machine log `review.shown`, `review.verdict` and `review.held`, and the captures stay on the machine
   (D146). A local `look` crosses machines only as *local, on `<machine>`*.
10. **The no-model tier.** The step is a quest in fixed words, and the gate is a table, a commit, an ancestry and a
    press. Keeping a tab served, *Show it again*'s first half and a review run on the person's command need no model.
    Following a procedure and driving the app to the change is a session's work. With no harness, a step sits, and *I
    set it up myself…* is the floor. The intake's proposal names its tier. The changed paths beside *Skip* are a report,
    never a decision (D54).
11. **Nothing set anywhere is today's behaviour**, said as such: no step, no hold, *Accept…* and *Accept automatically*
    as D87 and D145 left them. The only new words are the Setup row's *None: work is offered to land once its quest is
    done*, and the room's *no review environment*.

The build is REVIEWENV1a–i, the design's §9. **A canon principle belongs here**, as one bullet of `autonomous-development`
(*See it run before it lands*), with the words in the design's §7. It costs the always-loaded core nothing, and adding it
is the parent's call (REVIEWENV1i).

**Why.** Every check in the owner's case was an agent's, and the one that touched a page stood in for the environment it
checked, so the chain proved its own stand-in and was offered to land. What a person uniquely adds is a look at the
running work, and nothing in Daoris asked for one or waited for it. Most of that looking happens on the person's machine,
and the person asked to be shown, as a browser extension shows them. They did not want to run anything themselves, and
they did not want their own servers stopped to make room. Serving the branch to the step's own tab by interception shows
it at the usual address and touches nothing of theirs. Each piece reuses what exists: a chain step, D82's tree, D133's
hold, KNOWUSE1a's go-ahead, D137's words, D146's proof, D78's browser and D145's look. The new parts are where the rule
lives, the serving, and the fact the gate reads.

**Rejected.**
- **Daoris deploying by itself.** A platform's deploy would sit in core, act outward on Daoris's authority (D37), and
  guess a procedure the repository owns (D32).
- **A gate that reads only CI.** CI runs the checks the repository wrote, and the case passed every check agents ran.
- **Review on by default everywhere.** A documents-only repository has nothing to show. Nothing set stays today's
  behaviour.
- **Local as a fallback.** Most work is reviewed locally, and the owner said so.
- **Stopping or taking over the person's processes or ports**, which the person refused, and **leaving the review for
  the person to set up**, which they asked not to do.
- **The session's own interception left to die with it**, which turns the next reload into the person's own build,
  silently. Also **the set-up session staying alive to keep it shown**, which holds a slot and its timeout for hours and
  fails on the native door.
- **Daoris running a command a session names or reads from the repository's files**: a side channel past the
  permission rules, or a guess.
- **A *Reviewed* inside the browser**, which an agent driving it could press, and **serving to any origin the step
  names** in a browser the person is signed in to.
- **The manifest (D34, D122) as the declaration's home.** It is tracked, absent from an unadopted repository, and the
  wrong owner for the person's process. **The registry (WSP1, WSP2)** is rejected too: it is membership wiring, not a
  choice about finished work.
- **A field on the landing rule.** A repository's rule replaces its workspace's whole, and a review means something for
  either landing form.
- **The intake switching review off on its own reading (D74), or parking to ask** about every change to a document.
- **A park as the gate.** The verdict would be the agent's report of the person's answer. **Holding the build's done.**
  It would stop the chain before its set-up step. **A set-up step that does not gate**, which races the landing.
- **A *reviewed* of an older set-up letting newer work through**, **the task level declaring an environment**, and **a
  model judging the shown page** (D24, D54).
