## D218 — A repository declares its output, and a tree holding only output is tidied (TIDYOUTPUT1, 2026-10-29)

**Decision (accepted 2026-10-29, built the same day).** An unforced removal of a tree, which is what a landing's tidy, the clean-up
and `trees remove` ask, judges each ignored path the tree holds with two more kinds of output that go with it, beside the thirteen build
folders TREEKEEP1 already lets go where the checkout holds them too (D102's note):

1. **A repository's declared output.** The registered checkout's `daoris.gates.json` says `integration.scratch`: globs over
   repository-relative paths, `/` separated and case-insensitive, `*` within one segment, `**` across any, a trailing `/**` the folder
   and all under it. A path the globs cover, or lie under, goes with the tree **whatever the checkout holds**: it is what the
   repository's own checks write again (a verify's `devtools/_test-results/`, `_e2e-*-data/`). The key is the one D215's §4.1 reserves
   for the integration's tidy, so the later row that reads it (the integration design's row d) reads this one declaration, and this
   row does not run ahead of it: nothing but the tidy's judgement reads the key now.
2. **A build's own folders, even where the checkout never built.** A path under `bin`, `obj` or `node_modules` goes with the tree
   whether or not the checkout holds one, since a tool names those, not a person. The other ten of TREEKEEP1's list (`out`, `dist`,
   `build`, `target`, …) stay as they were: they go only where the checkout holds the folder too, since a session also exports
   into them.

**How an ignored path is judged now.** Declared → goes. Else, where the checkout lacks it: under `bin`/`obj`/`node_modules` → goes; a
**folder** is read file by file (at most 5,000, past which it is the tree's own, as TREEKEEP1 does) and each file neither declared nor
under those three is the tree's own, named; a **file** is the tree's own as before. Else, where the checkout holds the folder:
TREEKEEP1's walk, which now also passes over a file under any of the thirteen build folders *inside* it (a `bin/` in a sample project's
ignored folder was kept as a session's own: the two landings of 2026-10-27, 119 files, and the four of 2026-10-28 and -29) and a file
declared. Nothing else changed: an ignored file the repository declared nothing about, written after the tree opened, still keeps it,
and the sentence names it (*the tree at … holds 1 file(s) written in the tree after it opened, which your checkout does not hold as
written: devtools/_extra/export.csv. Removing it would destroy them …*; a landing says *The rule says to clean up, and the tree stays:*
and that). A `local/` note a session wrote is such a file. A read-only copy of a machine-local input (TREELOCAL1, D216) with the
checkout's bytes is no file written the checkout does not hold, as TREEKEEP1 already judged: it keeps nothing.

**Safe by what a pattern may reach.** A glob is passed over, declaring nothing, where it is absolute or carries a drive, goes up with
`..`, or opens with a wildcard (`**`, `*/…`), so no declaration covers a folder the repository did not name; a gates file that is
absent, unreadable or not JSON declares nothing, which keeps a tree. A repository that declares `local/**` has said its `local/` is
output, and that is its call.

**Read from the checkout, never the tree.** The tree holds the session's own copy of the gates file, so a session cannot declare its
scratch disposable in it. Where the work is on the line (every removal here is of a landed tree), the checkout holds the landed
declaration too; a landing branch not yet merged is judged by the declaration the checkout has.

**Rejected.**
- *Every ignored path but `local/` is output.* One name carries the whole safety; a session's export, database or prepared requests
  elsewhere (`devtools/.tmp`, D102's find) is exactly what TREEKEEP1 was built to keep.
- *A write-time or content heuristic* (nothing written by a build tool, files that look compiled): it cannot tell a session's
  authored file from a check's, and a wrong guess destroys work with no trace.
- *Widening the list to a fourteenth, fifteenth name* for each repository's folders (`_test-results`, `_e2e-*`): the names belong to the
  repository, and the list is Daoris's.
- *A new key beside `localInputs` (`daoris.json`, a top-level `outputs`, a file of its own).* The gates file is where a repository
  already says what its checks do and write, and D215's `integration.scratch` is the same list under a name already accepted: a second
  spelling would need a migration.
- *Reading the declaration from the tree or from the line's tip by `git show`.* The tree's copy is the session's; the checkout's
  working file is the owner's, and it is the one read for everything else the removal asks of the checkout.
- *`bin`, `obj` and `node_modules` taking the thirteen's rule inside an absent folder too (all thirteen).* `out/`, `dist/`, `build/` and
  `target/` are where a session exports; with no checkout folder to show a build writes there, the conservative answer keeps the tree.
- *Changing the look's own tidy (`TreeSetAside`, AUTOTIDY2a).* It moves a tree with only ignored paths aside whole for 14 days, so no
  ignored path keeps it already; it reads no declaration and is unchanged. Its manifest of what a tree held takes the same lists
  (`SlimManifest`), so output no longer shows in it either.

**What it does not cover.** A scratch file whose write time a tool set back, which TREEKEEP1 already said. A declared glob that
covers authored work the repository did not mean (the repository's own error). The declaration of a repository that has not landed it
on the line the checkout holds.

Held by `TreeScratchTests` (the globs, their refusals, the folders and the files) and, in `ContentProofLossTests`, five `Process` rows:
a tree holding only declared output and a project's `bin`/`obj` tidied; `bin`/`obj` in an ignored sample folder the checkout holds;
an undeclared file beside declared output keeping the tree, named; a `local/` note keeping it; a read-only copy with the checkout's
bytes keeping nothing.

**Note, 2026-10-29 (INTEGRATE1d part 2; D215 points 2 and 10): a declared scratch counts once its declaration is accepted.** This
narrows point 1 and *Read from the checkout, never the tree*. `integration.scratch` is a list of files an unforced removal deletes
unasked, so it is accepted as a command is: it is read from the blob the owner accepted for the repository's integration
(`integrationGates`), and only while that blob is the declaration at the line's tip, through the declaration's one reader. The
checkout's working file is no longer read for it. The checkout holds the landed declaration, but also whatever the person has in
flight there, and an unaccepted landed declaration is still a session's words until the owner reads it. Where nothing is accepted,
the line's declaration changed since the acceptance, or the line is not known, a tree keeps what it kept before this decision and
names it; point 2 stands, so `bin`, `obj` and `node_modules` still go, since a tool names those. A declaration that breaks any key's
shape now declares no scratch either. The rejection of *reading the declaration from the line's tip by `git show`* is reversed for
the reason above: the tip's blob is the one an acceptance names. Held by `ContentProofLossTests`: the three TIDYOUTPUT1 rows that
declare output now accept the line's declaration first, and two rows keep a tree, naming its declared output while its `bin` and
`obj` go, under a declaration never accepted and under one the line changed after its acceptance; and by `TreeScratchTests`'
broken-shape rows.
