## D180 — Verification runs as a local CI beside the work: only what must never reach history blocks a commit or a merge; every suite and rehearsal runs on a tree of its own, in parallel, and reports back, and what it finds is fixed forward; an install still needs a green run (2026-10-19)

**Decision (the owner's direction).** The owner, 2026-10-19, after the day's merges were measured: *"apart from the
important verification (which should never be included into the commit, like sensitive info), you can always start a
work branch for verification, more like a local CI, and try to run tests in parallel to speed up, and the rest just
keep developing; if we find any issue we go back and fix them when the CI verification reports back, so this is
non-blocking. This will also help Daoris's own process when large quest sets come and some quests need multi-repository
or multi-agent work together, and it fits the fabric idea too: a more flexible and adjustable in-flight system."*

What the day measured: builders finished in 24 to 64 minutes once each ran verify once; merging was the slow part. A
service branch alone paid 11 minutes of light gates and 27 of the family rehearsal; a two-branch batch with one flaky
new test about two hours, most of it two rehearsals run and run again; and while a merge held the main checkout, the
harness refused every dispatch (its isolation could not read the checkout's git state), so finished and ready work
waited behind it.

1. **What blocks.** Only what cannot be taken back once committed, and the cheap consistency of what is generated:
   - `universal`, the devkit's universal verify, which holds the sensitive-patterns scan (`sensitive-info`: a committed
     leak is a history problem);
   - the merge tool's commit check (each commit of its own, with its attribution line; nothing left uncommitted), its
     lane report and its prune;
   - `orient-index` and `code-map`, whose output is generated and checked in seconds.
   A records commit runs the documentation checks it reaches (the doctrine check, the documentation tools, the index)
   and nothing longer.
2. **What runs beside.** Every other gate a change reaches (the suites, the CLI's verify, the tool tests, the
   rehearsals, the `Process` halves, the deployment rehearsal) runs on main's tip in a tree of its own
   (`local/gate-tree`, GATEWT1), never in the main checkout, started by the parent after a merge or a batch: for now
   `node tools/merge-branch.mjs --full --beside`, its lanes in parallel (the light lane several wide, the `Process`
   lane one class group at a time). A newer tip supersedes a run not yet started. Its logs stay in
   `local/scratch/beside-<sha7>/`.
3. **What it finds is fixed forward.** The parent routes each failure as a fix commit, a row, or a flake under FLAKE1,
   as a merge's failure was routed before; a builder merging main meanwhile reports an inherited failure as not its own.
4. **Three lines catch a failure, and none waits on another:** each builder's own gates before it hands back (the suites
   it touched, and verify once); the CI beside after a merge; and the full set before any install is staged, which
   `publish:desktop --from-gated` still requires of the exact commit it publishes.
5. **The cost accepted.** Main may carry a failing commit for as long as the CI takes to report it; a failure is
   bisected over the commits since the last green run rather than one merge; a worker's branch may inherit it for an
   hour. The owner's judgement: the work does not stop for it.
6. **Built next.** The merge tool's default becomes point 1 (`--gated` keeps today's reached set for a merge the parent
   judges risky; GATESLIM1). A CI runner of its own (row CI1): the gates reached since the last green run rather than
   every gate, wider in parallel when the machine is idle, coalescing tips, and a status the parent and the page read.
7. **Daoris's own work takes the same shape** (row FABRIC-VERIFY1, a design before any build). A quest set across
   repositories and agents need not wait step by step on each step's checks: a step's result can be accepted, or land
   under the person's rule, while its verification (its repository's gates, a second opinion, D155) runs as a lane of
   its own and reports back; what it finds reopens or asks, as the person's reopen does (D173 §E5). This is the
   fabric's in-flight adjustment (D173) applied to verification. Which checks still block there (the sensitive scan, a
   repository's own declared blocking set) is that design's to say.

**Rejected.**
- **Every reached gate before every merge** (today's rule): it made the merge the bottleneck and blocked every dispatch.
- **Verification in the main checkout**: it holds the checkout's git state while it runs.
- **Dropping a gate for speed**: nothing is removed; what moves is when it runs and whether the work waits for it.
- **Letting an install out without a green run**: point 4's last line stays a gate.

**Note, 2026-10-19 (the budget: a full set under thirty minutes, and a CI run never starves the work).** The owner, the same
day: *"any CI or verification run over one hour for our current project just doesn't look right, and this blocks any
development"*, and *"we discussed before that verification should not block the development"*. What blocked was load, not a
rule: a full set beside the work took about two hours run one gate after another, and its git half (92 minutes under load,
against 34 alone) slowed every builder's tests to twice their time, made one git command take five seconds so the harness
refused dispatches, and slowed the installed Daoris's own git reads. Measured from the last full set's results: the driver's
`Process` half ran its 575 tests one at a time (27.2 minutes summed, 27.3 wall); the git half averaged 26 seconds a test
(256 minutes summed, 65 wall at four threads), its time chiefly git starts; the rehearsals ran after the suites. So:
1. **A full set's wall is held under thirty minutes**: the driver's `Process` half runs in parallel where its tests are
   isolated (PROCPAR1); the git half starts fewer git processes (PROCSPEED1b, SCRATCHLEAK1) and then runs wider; the
   rehearsals run beside the suites, not after them (REHLANE2).
2. **A CI run is a guest on the machine**: one at a time, at background priority for CPU and I/O (CIPRIO1), and a run whose
   commit a newer tip supersedes is stopped rather than finished. A CI run beside a full slate of workers is not started.
3. **A merge batch's CI runs the gates its paths reach** (CI1), so most runs skip the git half; the full set runs once,
   before an install.
4. **The machine's own cost of small files** (an antivirus scanning each file git writes) is the owner's setting to change
   (DEVDRIVE1), never this repository's.
