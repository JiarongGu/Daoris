## D166 — Daoris's code is cut into domain modules, each layered as an onion, held by a structure gate (2026-10-12)

**Decision (the owner's direction).** The owner, 2026-10-12: *"I also find daoris currently does not have a proper dev
folder structure, since this is growing we do need to properly separate into a good code design in modules (onion
structure + modularized domain)"*. The driver was 299 files of one namespace, about 260 in one folder, with no rule on
what may call what. The design, its facts and its rows are `docs/2026-10-12-code-structure-design.md`.

1. **Modules by domain.** The driver is cut into modules named by the glossary's domains (`Platform`, `Accounts`,
   `Agents`, `Conversations`, `Sessions`, `Trees`, `Quests`, `Review`, `Workflows`, `Plugins`, `Help`, `Service`,
   `Setup`, and `Loop`, the composition root), one folder each, its tests mirrored. The other projects follow (STRUCT5).
2. **Onion layers inside a module**: `Domain` (records and rules, pure: no files, processes, network, environment or
   clock), `Application` (use cases against ports), `Infrastructure` (the I/O behind the ports). Inner layers never name
   outer ones; a module reaches another only through its `Domain` and `Application`; nothing uses `Loop`; the hosts
   (`Driver.Host`, `Modules`, `App`, the service's hosts) are the outer ring.
3. **A structure gate holds it**: a fast test that places every file in a module (an allowlist that only shrinks), keeps
   `Domain` free of I/O by a token table, and refuses a reach into another module's `Infrastructure`.
4. **It moves in steps the gates prove**: path readers made name-based first; one module per branch, moved as it is, while
   no branch in flight touches it; then one module's layers per branch; namespaces per module last, resource names pinned.

**Rejected:** a big-bang move; an assembly per module or layer now (the parallel-development design §7's costs stand, and an
assembly would not make a layer pure); renaming namespaces as files move; leaving the shape to the README's prose.

**Amends:** the parallel-development design §4 (the MOD splits by feature now land in module folders) and §7 (one
assembly stays, with a named internal structure; assemblies measured again at STRUCT6).

Where it differs from §3. Application names its own Infrastructure in one place, `WorkflowPorts` (internal), which composes the
ports over a home: every caller holds only a home (Help's proposals, Review's presses, Trees', Quests' and Sessions' files, the
loop, the modules, the tests), and a port reaches a module only from whoever composes it, which threading through `SessionTrees`,
`OpinionPresses` and `HelpProposals` would be those modules' layering. The gate does not check this edge; a rule for it can come
once the callers hold ports. The old names forward: `WorkflowStore.PlanAdd` and `Text`, `WorkflowRunBindings.Why` and
`WorkflowProcesses.Current` and `Of` name rules now in Domain, so no caller outside the module and no test changed. The commands
stay Application while their `RunAsync` and `SourcesAsync` compose the service client, the configuration, the plugin catalogue and
the clock. The tests stay flat in `Driver.Tests/Workflows/`: the mirror rule reads the module. Named across from here and not yet
layered: `PluginCatalog` (`WorkflowCurrent.PluginsOf` in Domain takes one, `WorkflowRunCommand.SourcesAsync` loads one),
`ServiceClient` (`WorkflowRunSources`), and the reads in `WorkflowRunRecords` (`LandedBranches`, `AutoLandings`, `SessionEvents`):
the reach rule will name each that lands in its module's Infrastructure.

The order that keeps every commit green: rename the pure files into `Domain/` and the use cases into `Application/` first; split a
mixed file where it stands, its I/O to an `Infrastructure/` adapter behind a port and its door keeping its name; and only then
rename a file that named a door into `Domain/`, since the gate reads a Domain file's names the moment it lands there.
