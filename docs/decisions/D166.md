## D166 — Daoris's code is cut into domain modules, each layered as an onion, held by a structure gate (2026-10-12)

**Decision (the owner's direction).** The owner, 2026-10-12: *"I also find daoris currently does not have a proper dev
folder structure, since this is growing we do need to properly separate into a good code design in modules (onion
structure + modularized domain)"*. The driver was 299 files of one namespace, about 260 in one folder, with no rule on
what may call what. The design, its facts and its rows are `docs/2026-10-12-code-structure-design.md`.

1. **Modules by domain.** The driver is cut into modules named by the glossary's domains (`Platform`, `Accounts`,
   `Agents`, `Conversations`, `Sessions`, `Trees`, `Quests`, `Review`, `Workflows`, `Plugins`, `Help`, `Service`,
   `Setup`, and `Loop`, the composition root), one folder each, its tests mirrored. The other projects follow (STRUCT5).
2. **Onion layers inside a module**: `Domain` (records and rules, pure: no files, processes, network, environment or
   clock), `Application` (use cases against ports), `Infrastructure` (the I/O behind the ports). Inner layers never name
   outer ones; a module reaches another only through its `Domain` and `Application`; nothing uses `Loop`; the hosts
   (`Driver.Host`, `Modules`, `App`, the service's hosts) are the outer ring.
3. **A structure gate holds it**: a fast test that places every file in a module (an allowlist that only shrinks), keeps
   `Domain` free of I/O by a token table, and refuses a reach into another module's `Infrastructure`.
4. **It moves in steps the gates prove**: path readers made name-based first; one module per branch, moved as it is, while
   no branch in flight touches it; then one module's layers per branch; namespaces per module last, resource names pinned.

**Rejected:** a big-bang move; an assembly per module or layer now (the parallel-development design §7's costs stand, and an
assembly would not make a layer pure); renaming namespaces as files move; leaving the shape to the README's prose.

**Amends:** the parallel-development design §4 (the MOD splits by feature now land in module folders) and §7 (one
assembly stays, with a named internal structure; assemblies measured again at STRUCT6).

**Note, 2026-10-12 (STRUCT1, the gate and every reader by name).** `StructureTests` runs `StructureCheck`, a pure function
over (path, text) pairs, on the driver's tree with `Driver.Tests/fixtures/structure.json`: the fourteen modules with the layers
each may hold (`Platform` Domain and Infrastructure, `Loop` none, the rest all three) and `root`, the 264 files still at the top,
each with its module. Its rules: `top` (a top file is on the list, and every listed file is still at the top), `module` (a
folder is a module's, a layer folder one its module holds), `pure` (a Domain's token table, `StructureCheck.Impure`), `reach`
(an Infrastructure may name Platform's, `Loop` composes all) and `loop`. The last three read only files in module folders, so
they find nothing until a module moves; `Help/` is the Help module's folder already. The map departs from design §2's table
by domain: a command goes with its verb's domain (`DriverCommand` stays `Loop`'s); `DriverConfig` is `Platform`'s, since 72
of the driver's files name it and the loop rule would refuse each; `Observation` is `Sessions`'; the start's repository knowledge (`CodeMapFile`,
`RepositoryIndexes`, `StandingAnswer`) and the permission rules (`Permissions`, `Across`, `RuleProposals`) are `Agents`'.
Thirteen files are noted in its `split`. Placed as mapped, the loop rule would refuse 18 uses of types `Loop`'s files declare

before its row.

Readers find a file by name at any depth of its project, refusing none and two: the driver's tests through

**Note, 2026-10-14 (STRUCT3a, the first module layered: Plugins).** Every Plugins source sits in a layer, and `structure.json`'s
new `layered` list holds it there: a file of a listed module loose in its folder, or in a folder that is no layer, is a `layer`
breach. Behaviour is unchanged, and no caller outside the module changed but the landing's two starts.
- **What went where.** `Domain` (15 files): the manifest's records (`PluginManifest.cs`), the catalogue as a value with its
  parse, its judge and an id's shape (`PluginCatalog.cs`, which was `Plugins.cs`), the hook wire's words (`HookPoints.cs`:
  `HookDecision`, `HookPoints`, `HookFrames`), the log's events and failure marks, the health's records and rules
  (`PluginHealthRules`), the activity's records and summary, the tools' table, the tool checks' answers, the icon's rules, the
  offer and its README's needs, the source record, its changes and the update plan, the package's records and nuspec rules,
  the page's records, and the kit's and the trial's records. `Infrastructure` (6): `PluginFolders` (the home's plugin folders: the
  catalogue's walk, a manifest's text, the placeholders made paths, copies, moves, counts and walks), `HookProcess`,
  `PluginToolRuns`, `PluginKitFiles` (a new plugin's folder, the templates by their pinned names, a trial's scratch),
  `PluginTrialProcess` and `PluginPackageFile`. `Application` (18): the use cases other modules and the hosts call (the
  catalogue's reads, `PluginState`, install and update, offers, page, activity, the kit and its trial, the tool checks,
  `HookSet`, `HookPeer`, `PluginLog`, `PluginHealth`'s record, `DeclaredAcpAdapter`) and the three commands.
- **Ports** are the Application's: `IHookChannel` (the hook set, the landing and the trial ask through it; `HookPeer` speaks it
  over streams, `HookProcess` is the real one, a test hands a fake), the hook set's and the landing's start, defaulting to the new
  `HookChannels.StartAsync`, and `CheckRunner` (`PluginToolRuns.RunAsync`, or a test's stand-in). Where nothing stands in, the
  Application calls its Infrastructure's helpers directly: a port is made when something needs to stand in, not before.
- **A type lives in one layer**, and its callers keep their calls. A type whose rules are pure and whose callers also ask it to
  read the machine goes to `Domain`, and its I/O members become static members of a C# 14 `extension(T)` block declared in the
  Application (`PluginCatalogReads`: `Load`, `ReadFolder`, `ReadAsWritten`, `Reserved`, `RefusedByThisBuild`;
  `PluginIconReads`: `Read`; `PluginSourceReads`: `FromFolder`, `Read`, `Write`), so `PluginCatalog.Load(home)` reads as before
  in its 98 callers. The gate indexes such a member as `T.Member` in its declaring file's layer, so a Domain that called one, or
  another module calling one declared in an Infrastructure, is refused. A stateful type with a clock (`PluginHealth`) stays in the
  Application and hands its rules to a Domain type, aliasing its constants. A partial class across two layers is refused by the
  gate already, for a Domain naming it would name an Application.
- **How another module reaches Plugins**: its Domain and its Application only. `LandingPlugins.cs` (Trees, still at the top) named
  `HookProcess.StartAsync`, which Trees' move would have made a reach breach; it now calls `HookChannels.StartAsync`.
  `CommandPresence`, which Accounts, Agents, Trees, Setup, Plugins and the modules ask, left `Plugins.cs` for its own file at the
  driver's top, mapped to `Platform`: the one entry the `root` list gained, since Platform's Infrastructure may be named only by
  an Infrastructure and Setup's flat `SetupWorld` names it now.
- **Composition**: `Loop` composes across modules (`Driver.cs` hands the hook set its log and health); within the module, the
  Application is the composition point, naming its Infrastructure as a port's default. The hosts stay the outer ring.
- **Not held by the gate, held here**: the Application does no file, process, network or environment I/O of its own; it may stamp
  the time and time its own calls (`HookSet`'s and the trial's stopwatches, `PluginHealth`'s clock, `plugins activity`'s now), and
  a port's shape may name a process's description (`CheckRunner`, and `DeclaredAcpAdapter`'s `Prepare` for Agents' door). Commands
  (`*Command.cs`) are the Application's: they parse a terminal's words and call the use cases, printing to the writer they are
  handed. The plugin kit's templates stay in `Plugins/plugin-kit/` under their pinned names. The tests stay flat in
  `Driver.Tests/Plugins/`; one (`PluginCatalogTests`, which names the one file that spells an id's shape) followed the rename.
- **For the next modules**: move every file into `Application` first, renames alone; split by area in edit commits, writing a pure
  file straight into `Domain` when all it names is Domain or unplaced; then rename into `Domain` the files whose names were in
  `Application` while their kin were. Before the first split, list what other modules, and the modules in flight, call of the types
  you will put in `Infrastructure`, and give each an Application entry. For a bigger module (Trees, Agents): one branch per area,
  the records and rules out first (other modules' Domains will want them); a partial class (`SessionTrees.*`) becomes an
  Application facade whose I/O moves to Infrastructure types, never parts in two layers; and use the extension members early
  where a static I/O entry has many callers (`Tools.Read`, `DriverConfig.Load`). Platform needs deciding before its row: every
  module's Application names its I/O helpers (`MachineLog`, `MachineLogReader`, `AtomicFile`, `DriverConfig.Load`), and only an
  Infrastructure may name Platform's Infrastructure, so it needs ports in its Domain or an exception for an Application. Done again,
  I would write the gate's extension index and that inventory before the first move rather than after.
