## D149 — Related work is the `follows` chain, and its one branch advances only while its pull request can carry the advance: a branch whose work already reads on the line is not moved on, and a plugin pushes only to a pull request that is still open (2026-10-04)

**Decision (LAND2c).** The owner: *"the PR should be generated one for all those related Daoris work, currently by
approve one by one this creates multiple PR branch for the same work"*. Their TK-2203 was a quest, its verify step and a
follow-up ask's drill-down, accepted one by one into two `feature/` branches, the second containing the first. D145 §3
lands a chain on one branch and advances it. D148 left LAND2c one question: advancing a branch whose pull request
completed would push work no pull request carries. This settles that question and what counts as related work. The
contract is `docs/2026-10-04-landing-and-proof-design.md` §3 and §7.

1. **Related work is the `follows` chain.** A quest that follows another (its `parent`, which the platform shows as
   *follows #…*) is the same piece of work as the quest it follows, whichever ask published it. Walking `follows` up to
   the chain's first quest names one branch per repository (WSR5's `SubjectAsync`). A quest that follows nothing starts
   its own branch, even when a later ask is about the same ticket. Today the service sets `follows` when a close
   publishes a chain's step. A door that sets it later joins this rule, and nothing here changes.
2. **A later done advances the chain's branch, as D145 §3 says.** Only a branch a landing made and recorded (D102), at
   its recorded tip, checked out in no working tree, to a commit that descends from that tip, moved by compare-and-swap
   (`update-ref <branch> <new> <old>`) and never forced. Each other case is refused as `exists`, in its own sentence. The
   landing entry keeps each advance (`advances`: from, to, when, the session, and who accepted it), and its tip moves to
   the new commit. A later session's review reads as landed through its advance. A next step grows from the chain's
   landed branch when the step before's session branch is gone (D82).
3. **A branch whose work already reads on the line is not advanced.** Before anything moves, D102's proof runs on the
   recorded tip: every commit of it on the line (*merged*), or every file it changed reading there as it left it (*on
   the line*, what a squash leaves). Either refuses with the code `completed`, and the session stays in *To review*. The
   sentence says to bring the repository up to date, which replays this session's own commits onto the line (WSR6) and
   removes the merged branch. Then Accept lands the work on a fresh branch of that name, and its plugin opens a new pull
   request. Once PLUGHOOK1a keeps `pullRequestState`, a kept `completed` or `abandoned` refuses in the same way.
4. **A plugin pushes an advance only to a pull request that is still open.** The frame (`hook/work/land`) carries
   `pullRequest`, the one the landing entry holds, and `acceptedBy` (`person` or `auto`). With `pullRequest` set, a
   plugin reads that pull request's state before it pushes. It pushes, and opens no second one, only where the state is
   open. A closed pull request, or a state it cannot read, is `pushed: false` with its own sentence. The branch stands as
   D100 leaves it, and the person pushes by hand or opens a new pull request. Both example plugins do this, and write
   who accepted the work into the description they open.

**Why.** One piece of work, one pull request: that is the owner's ask, and the advance is what keeps it. An advance is
worth something only while the pull request it grows is open. A completed pull request takes no new commits on Azure
DevOps. On either platform, a push to its source branch carries work that nobody reviews, or re-creates a deleted branch
with no pull request at all. Git can see a merge, and a squash while the line has not changed those files since. It
cannot see a squash once the line has moved on. Only the platform can tell then, and the plugin is already speaking to
the platform for the one pull request it is about to push to. So each side refuses on what it knows. `follows` is the
one fact Daoris holds that relates two quests. A tree grows from the work it follows (D82) because of that fact, so a
fast-forward is possible exactly where `follows` says the work is one.

**Rejected.**
- **Advancing whatever the pull request's state.** It pushes work no pull request carries, which is D148's concern.
- **Opening a second pull request from the moved branch.** After a squash, the branch still holds the commits the squash
  replaced, so the new pull request's diff repeats the first's work.
- **A sibling branch for the rest (`…-2`).** Two branches for one piece of work is the owner's complaint, and the sibling
  carries the first's commits as well.
- **Daoris asking the platform before it advances.** D148 asks only at occasions that may remove something. The plugin
  reads the one pull request it pushes to, inside its own act.
- **Relating work by the ask, the ticket's words, the time or the files it touches.** Each is a guess, and a wrong guess
  puts unrelated work into someone's pull request. An ask's quests to one repository grow from the line apart from each
  other, so the second could join the first only by a merge, which Daoris does not make (D87).
- **Relating work by git ancestry alone.** A tree grows from a landed branch only because of `follows`, so ancestry adds
  no fact. It would also join a branch that a person based on Daoris's by hand.

**This amends:**
- **D145 §3.** It names what is related (`follows`) and what an advance refuses (`completed`).
- **D148.** It answers the question D148 left to LAND2c.
- **D82.** A next step grows from the chain's landed branch, as D145 said.
- **D100.** The frame gains its two fields, and a plugin reads the pull request's state before it pushes an advance.
- **D113 §3.** A session whose done advanced a branch reads as landed through that advance.

D87 stands: no force and no rebase at a landing. D51 rule 6, D37 and D46 stand as well.

**What the checks do not cover.** Neither plugin has run against a real platform. The state each reads (`az repos pr
show`'s `status`, `gh pr view`'s `state`) is taken from the tools' documented output, and the tests drive fakes. The
owner's TK-2203 was read from the parent's account in `TASKS.md` and LAND3's note on D102, not from the install. The
built shape, its tests, and what its gates did not run are in the LAND2c note on D145. `verify` checks that this entry
names what it rejected. It checks none of the words.
