## D171 — A terminal finds the Daoris that runs, a second launch opens a window of it, and the running instance answers the terminal's verbs (2026-10-16)

**Decision (the owner's direction; the shape is the steward's, as the owner left it: *"you can decide but this clearly is a
gap"*).** The owner, 2026-10-16, running `daoris-driver setup <repository> --plan` in a PowerShell of their own, from the
install's `data` folder: *"driver: no DAORIS_SERVICE_URL — the driver watches a service, and needs to know where one is…
so we had better have a server, or set it up as an RPC service for Daoris, and this will also support multi-instance Daoris
windows syncing messages (or the second time I click on the exe, we only start a new window from the same instance of
Daoris's current session)"*. The install's launcher (`app/bin/daoris-driver.cmd`, DRIVERDOOR1) sets nothing, so a
terminal outside Daoris's own panel knows neither the home nor the service; the panel's terminal is handed both.

1. **A terminal finds the Daoris that runs, with no variable set.** The driver host, and every other command this
   install carries that needs them, resolve in this order:
   - **The home**: `DAORIS_HOME`, else the install's own `data` folder where the command runs from an install's `app/`
     (D63's layout), else the existing refusal.
   - **The service**: `DAORIS_SERVICE_URL`, else the address the running desktop writes into its home while it holds or
     adopts the service (a small file it writes atomically and removes at a clean exit, naming the address and its
     process), kept only where that process lives and the address answers as this home's service, else the existing
     refusal, which now also says Daoris is not running and how to start it.
   The variables still win, so the dev loop, the rehearsals and a second home keep working as they do.
2. **A second launch of the executable opens a window of the instance that runs.** Windows of one instance already share
   one driver, one loop and one state hub (D169), so a second process would be a second writer of the same home. A second
   launch hands its request to the running instance and exits, and the instance opens a new main window. Where the UI
   kit's single-instance guard cannot hand a launch over, that is a request to the kit's owner, not a workaround here.
3. **The running instance answers the terminal's verbs.** Today a verb run in a terminal acts from its own process on the
   home's files, guarded by its locks, telling the loop through the request folder (`SessionRequestWatch`) and the windows
   through its told notes (STATEHUB1e). The direction is that, while an instance runs, the terminal's verbs are its
   clients over a local channel, running the same handlers its windows' presses run, so there is one writer, every window
   hears it as it happens, and a verb's answer is the press's answer (D50's twins become one path). With no instance
   running, a verb acts alone as it does now. This is designed before it is built: which verbs act outside the loop
   today, what the channel is (a named pipe the bridge's routes answer over, or the local service), and how it is
   secured to this user. Its design document and the rows it yields come first.

### Order

Point 1 first: it is the owner's block today, and small. Point 2 next. Point 3 is a design, then its rows.

### Rejected

- **Requiring the variables**: a person's own terminal is a door (D50), and a door that needs setup nobody did is shut.
- **A second process per launch, each with its own loop**: two writers of one home, which every lock in the driver exists
  to avoid.

**Note, 2026-10-16 (FINDDAORIS1, point 1 as built).** A program the install carries is one running under an install's `app/`
(the folder above it holds `INSTALLED.md`): the driver host in `app/daoris-driver/`, the CLI in `app/cli/node_modules/daoris/`.
Its home is `DAORIS_HOME`, else the install's `data/`; the host takes that as its own process's variable before any door is
routed (`DaorisHome.Adopt`), as the desktop does. The address file is `<home>/running.json` (`RunningAddress`: `url`, `pid`,
`started` as process start ticks, `since`), written whole by the desktop's loop once its supervisor says the service answers, held
or adopted, and removed first thing at its stop, only while it still says what that loop wrote. It is taken only while the process
it names lives (its start time compared, as the driver lock's holder is; the CLI, which cannot read another process's start, asks
only whether it lives), the address is a loopback one, since a terminal's verbs send this machine's paths (D46), and `/api/status`
answers naming its `tier`, the test the supervisor adopts a host by. The refusal keeps its first sentence and adds why: not
running on that home with the install's `Daoris.exe` named, running with nothing answering at its address, or an address on another
machine. 🔴 **A workspace build reads no address file.** On a machine with an install, the account's `DAORIS_HOME` names that
install's live home, so a gate, a rehearsal or a test that cleared `DAORIS_SERVICE_URL` to meet the refusal would otherwise have
reached the running service and acted on it; the dev loop and every gate name the service themselves. The service hosts are
left as they were: the desktop starts them with both variables named, and a session inherits them. The verbs the service is
needed for find it where they ask (`ServiceHttp.FromEnvironment`, the CLI's `endpoint`), so a verb needing none asks nothing.

**Note, 2026-10-16 (ONEINSTANCE1, point 2 as built).** The kit could hand a launch over, so nothing was asked of its owner. Its
guard (`WindowsHostOptions.SingleInstance`, on by default, one instance per install root) already kept a second process from
starting and brought the running main window forward; it then calls `OnActivated` on the window's thread with the launch's
arguments. The application hands that to `SecondLaunch`, which waits for the service to answer (none opens where it never came
up: the main window says why) and opens `main:<n>`, the lowest number from two no open window wears, at the root route, so the
page renders the whole platform. Every launch opens one: Daoris takes no file or link on its command line. The window is a
`SecondaryForm` made frameless with the caption buttons it paints, as the main window is: the kit's window commands
(0.21.1, the version the desktop references) act on the window whose page sent them, its own maximize and caption buttons included, and only `SET_THEME` has no
route there, so the page reads its own name (`anotherMainWindow`) and tells its frame over `DAORIS.WINDOWS` as a utility
window's page does. The taskbar's count stays the first window's. The machine log says `window.launched`.

**Note, 2026-10-16 (WIRING1b, the read as built, and a second opinion's four points).** `SYSTEM_WIRING`, in a new `system`
route domain, and `daoris-driver wiring [--json] [--measure]` call one reader, the driver library's `SystemWiring`, over a
`WiringWorld` each door composes (the window's from its loop and supervisor, a terminal's from its own process), so `--json`
is the route's shape. A second opinion (Codex) tightened the design, and the read is built to it: **(1) redacted at the
reader**, before anything is serialized (`WiringRedact`): a key is `set` and a minted deployment key's audit prefix at most,
none assumed for any other; an address loses its credentials, query and fragment, and one that does not parse is not shown;
a notice is cut the same way; no parser's sentence is passed on; and a last sweep takes every secret the reader saw out of
every string. **(2) An adopted service's environment is unknown**, said as `unknown` with why `adopted`, never as the
window's; a value this process holds that equals the account's or the machine's is `inherited`, since a process cannot tell
which it got. **(3) No walk on the open**: sizes are `WiringSizes`', measured only when asked, in the background, one walk per
folder, kept for the process across windows, cancellable, bounded (files and time) and answering what they counted with
`partial`; no link or junction is followed; no git, program or download, and the window asks no status door, showing its
supervisor's last probe. **(4) The layout as it runs**: each entry of D172's table where it is found, an old place said with
why it stays, and names the table does not hold as left over. Every variable the sources spell is on `WiringVariables`' list,
shown or set aside with its reason, which `SystemWiringTests` holds against a search of `src/`. The shape adds, beside §6's
fields, `reader`, `measuring`, `measured`, `partial`, each fact's `…Why`, and a variable's `set`, `accountSet`, `machine`,
`machineSet`, `instead` and `readBy`. What a new terminal runs is read in Windows' own order, the machine's `PATH` before the
account's (the design's §3.7 said the account's first). `/api/status` answers `version`, the host's informational version.
