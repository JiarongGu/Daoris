## D171 — A terminal finds the Daoris that runs, a second launch opens a window of it, and the running instance answers the terminal's verbs (2026-10-16)

**Decision (the owner's direction; the shape is the steward's, as the owner left it: *"you can decide but this clearly is a
gap"*).** The owner, 2026-10-16, running `daoris-driver setup <repository> --plan` in a PowerShell of their own, from the
install's `data` folder: *"driver: no DAORIS_SERVICE_URL — the driver watches a service, and needs to know where one is…
so we had better have a server, or set it up as an RPC service for Daoris, and this will also support multi-instance Daoris
windows syncing messages (or the second time I click on the exe, we only start a new window from the same instance of
Daoris's current session)"*. The install's launcher (`app/bin/daoris-driver.cmd`, DRIVERDOOR1) sets nothing, so a
terminal outside Daoris's own panel knows neither the home nor the service; the panel's terminal is handed both.

1. **A terminal finds the Daoris that runs, with no variable set.** The driver host, and every other command this
   install carries that needs them, resolve in this order:
   - **The home**: `DAORIS_HOME`, else the install's own `data` folder where the command runs from an install's `app/`
     (D63's layout), else the existing refusal.
   - **The service**: `DAORIS_SERVICE_URL`, else the address the running desktop writes into its home while it holds or
     adopts the service (a small file it writes atomically and removes at a clean exit, naming the address and its
     process), kept only where that process lives and the address answers as this home's service, else the existing
     refusal, which now also says Daoris is not running and how to start it.
   The variables still win, so the dev loop, the rehearsals and a second home keep working as they do.
2. **A second launch of the executable opens a window of the instance that runs.** Windows of one instance already share
   one driver, one loop and one state hub (D169), so a second process would be a second writer of the same home. A second
   launch hands its request to the running instance and exits, and the instance opens a new main window. Where the UI
   kit's single-instance guard cannot hand a launch over, that is a request to the kit's owner, not a workaround here.
3. **The running instance answers the terminal's verbs.** Today a verb run in a terminal acts from its own process on the
   home's files, guarded by its locks, telling the loop through the request folder (`SessionRequestWatch`) and the windows
   through its told notes (STATEHUB1e). The direction is that, while an instance runs, the terminal's verbs are its
   clients over a local channel, running the same handlers its windows' presses run, so there is one writer, every window
   hears it as it happens, and a verb's answer is the press's answer (D50's twins become one path). With no instance
   running, a verb acts alone as it does now. This is designed before it is built: which verbs act outside the loop
   today, what the channel is (a named pipe the bridge's routes answer over, or the local service), and how it is
   secured to this user. Its design document and the rows it yields come first.

### Order

Point 1 first: it is the owner's block today, and small. Point 2 next. Point 3 is a design, then its rows.

### Rejected

- **Requiring the variables**: a person's own terminal is a door (D50), and a door that needs setup nobody did is shut.
- **A second process per launch, each with its own loop**: two writers of one home, which every lock in the driver exists
  to avoid.
