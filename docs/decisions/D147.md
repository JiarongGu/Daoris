## D147 — Git gets a place of its own, organised by branch and commit and never by a file to edit: read through the git the agents run, one process a view, and pushed only on the person's press (2026-10-04)

**Decision (GIT1).** The owner: *"since Daoris will need to use git anyway we will need a self-managed git, also since
we will have self-managed git then we probably need to do a built-in git more like VS Code with GitLens"*. Daoris's
managed Git exists (D121, TOOLS4, TOOLS7), but the install runs the system's, since nothing switches on its own. The
review's diff started one git per changed file and took about 55 s on a 71-file session (REVIEW3 makes it one call).
The owner's work workspace is on Azure DevOps, and LAND2 (D145) lands done work onto `feature/` branches and opens their
pull requests through a plugin. The contract is `docs/2026-10-04-built-in-git-design.md`.

1. **A place on the activity bar, *Git*, after Projects, shell-only.** Its list holds each repository's line and
   branches by kind: the sessions' (`daoris/…`, named by their session), the landed (`landings.json`, pushed or not,
   with the pull request and its state where a plugin answered), the person's own, and origin's on request. The
   repositories are D112's set first and the rest apart (design §2.2). The main area holds a branch with its history
   as a graph, a commit with its changes drawn by the review's molecules and the session that made it (D143), a file's
   history and blame at a commit, and a compare of two refs (§2.3–§2.6). The side bar and the panel do not change
   (D118 §3c).
2. **The organising object is the branch, then the commit** (D55). A file is reached through a commit, a review or a
   preview, and never browsed. There is no editor, file tree, conflict editor or staging, and no checkout, stash,
   reset, rebase, cherry-pick, revert, tag, remote delete, force push or timed fetch (§2.8).
3. **The acts write refs or talk to origin, never a working tree or an index**, so a dirty checkout refuses none of
   them: fetch (`origin --prune`, as the person, D109's bounds), create a branch at a commit, push, open the pull
   request through the hand-off (D102), and delete a local branch. Each is planned before it is pressed and judged
   again at the commit shown. Each refusal is §3.1's. The line is never pushed or deleted. A session branch is never
   pushed: its work is not accepted until it lands, and the clean-up removes only local branches, so its copy would
   outlive it on the team's remote. Nothing is ever forced, and a branch a tree has checked out is never deleted. A
   session branch and a landed branch are deleted only by the doors that already own them.
4. **Pushing is the person's press, and only that** (§3.2). `git push origin <commit>:refs/heads/<name>`, exactly the
   commit shown, with the person's hooks. No rule can name it, and opening the pull request stays a plugin's (D100).
5. **Both doors** (D50): `daoris-driver git branches|fetch|branch|push|delete`, with one judge in the driver library.
   A read's terminal door is git itself: each view names the command that answers it. Ask Daoris owes a `git` kind for
   the acts, and the reads are exempt, as `trace` is (D110).
6. **Read through Tools' git, one process a view, cached by commit id** (§4). The git is `WorkingTree.GitStart`'s, the
   one the agents run (D121 §3). Each view is one call in a machine format with a pure parser, and an answer named only
   by full commit ids is kept in memory. A ref is never a cache key. Nothing is cached on disk, and nothing is written
   into a repository's `.git`.
7. **Managed Git is offered, never switched** (§5). The setup guide gains a first step, *Git*, and the place names the
   git that answered and offers Daoris's own through Settings → Tools. The offer to leave a system git that works waits
   on TOOLS6 and TOOLS10.

**What it keeps** (D143): the reads keep nothing and say which git answered. A push of a landed branch is kept in its
landing entry. A deleted landed branch marks its trace. A pull request's state is kept with when and which plugin. Each
act is one machine log line by its code (§3.4).

**Why.** Daoris already reads git in five places, each for its own slice, and nothing shows a repository's branches,
its history or a file's. A person verifying driven work needs those, and GitLens's core is reading, which needs no
editor. The measured cost was starting git once per file, not git's work (§1: 2.2 s for 1,179 files in one call, about
215 ms a file one by one). Starting git once per view makes the binary as fast as a library could be here, and it keeps
the credentials, `core.sshCommand`, the hooks and the repository formats the agents' git has. A press to push one
branch at a commit the person sees is their say-so, which is what D37 asks of a push.

**Rejected.**
- **LibGit2Sharp in process.** Its official native binaries carry no SSH transport, and it asks for its own
  credentials. libgit2 runs no hooks and opens no partial clone, and it would add a native library to the install.
  Fetch and push would stay on git, so Daoris would keep two implementations (§4.3).
- **Git inside Projects.** Its list is repositories, and Git's is branches across them, with a graph and a commit's
  changes that need the main area whole.
- **The side bar** (D118 §3c).
- **Checking out in the person's checkout, or a tree per branch to check one out.** The checkout is theirs. A branch
  checked out in a tree is one D109's replay keeps. Nothing here needs either.
- **Keeping "Daoris never pushes" by shipping a plugin that pushes.** The authority is the same press, behind a process.
- **Managed Git by default** (D121 stands), and **a different git for the page than for the agents**.
- **Pushing the line**, **`push -u`** (it writes the checkout's branch configuration), **fetching on a timer**,
  **reading `git log --graph`'s drawing**, **a cache on disk**, and **writing a `commit-graph`** (§7).

**This amends** D87, D100 and D109, each of which says Daoris itself never pushes. It still never pushes on its own,
and the glossary's *push* already says so: a person's press may push one branch, and a landing rule still pushes only
through its plugin. It amends D97 with a first step, *Git*. It amends D66 and the platform language §2 and §5 with a
place on the activity bar. It amends D113 by one line at the review's head, and D111 with the preview's *History and
blame*. D121, D55 and D118 are unchanged.

**What the checks do not cover.** Documents only, and nothing is built. The timings are one machine and one repository,
read once. The libgit2 facts are from its trackers and packages, read and not measured. The floor of Git that the
`ahead-behind` and `worktreepath` atoms need was not read: both answered on Git 2.53. That a push of
`<commit>:refs/heads/<name>` moves origin's copy in the checkout's refs is GIT1g's to measure. No real Azure DevOps
remote was pushed to or fetched from. The place's name and four glossary terms wait on D116's check. The amendment to
D87 is the judgement the owner may most want to reverse; reversed, the push is the hand-off's alone, and the rest of
this stands. `verify` checks this entry's place and the design's shape, and none of their words.
