## D265 — A folder's copy lives in the place's own folder in the home, bounded by a third bound of the manifest setting, and every file changed on both sides is the person's (2026-11-11)

**Decision.** PLACEWORK1b's design (§4.4 to §4.6) gives a folder department's sessions working apart a copy each and a `return`
that brings it back. Three of its choices are settled otherwise for row f:

1. **Where the copy lives.** A copy is `copies/c-<8 hex>` under the place's own folder in the home
   (`work/places/<workspace>/<department>/`), beside the manifests and the content store it is read against, with a sidecar naming the
   folder and the records that work in it. What a return replaces or removes is kept beside it under `returns/<copy>/`.
2. **How the bound is set.** The copy bound is the manifest setting's third bound, `manifest.copy` in megabytes (`daoris settings
   manifest copy <megabytes>`, the window's `SET_MANIFEST {copy}`), 2 GB by default, beside a fixed 20,000 files and twice the
   folder's size free on the home's disk. A folder past any, or too large to follow, is not copied: the start is held with words saying
   how to go on, and never works in the folder itself in the copy's place, which would show its edits there before they are accepted.
3. **How both-changed is decided.** A file changed differently in both the folder and the copy since the copy is always the person's
   choice (*Keep yours*, *Take the session's*, *Keep both*), per path, through the node's own acts; the return waits until each is made.

*Rejected:* the design's fall back to working in place over the bound (§4.4), which would reach the step as set apart when nothing
was, and show the work in the folder before its review; a home entry of its own (`work/copies/`, `work/returns/`), which would add two entries to both homes' layouts and a
second folder to find a place's files in; a machine setting of its own (`copyBound`) with a count of files beside the size, a second
setting and its doors for one bound of one read; a three-way merge of text changed on both sides with `git merge-file`, which would
write a merge nobody chose into the person's folder and rest on the content store holding every base blob, which its own bound does
not promise.

**Note (2026-11-11).** What a return replaces or removes is kept beside its journal under the run's record
(`workflows/units/<key>.return/<copy>/kept/`), not the place's `returns/<copy>/`: the journal that says which write each byte belongs
to is the run's, so a return cut off is taken up from one folder. A path the return cannot bring back without guessing (outside the
folder, a link, a file turned folder, a name one file to the disk) is refused and settled by *Keep yours* alone, rather than offered
the three choices. A copy names the runs it worked for, and one whose runs all ended with no return waiting is moved aside by the
look's tidy.

**Amends** the driving area's rule 12 and the workflows area's rule 5. **Held by:** `Departments/Isolation/FolderCopies.cs`,
`Departments/Return/FolderReturn.cs` and `Workflows/Kinds/Return/`.
