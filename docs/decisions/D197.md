## D197 — An agent's accounts signed in for Daoris are one set that serves every workspace, in one order with one set of use settings; the machine's list and the workspaces' lists go, and the person's own sign-in stays theirs, outside it and never asked (2026-10-21)

**Decision (POOL1, accepted 2026-10-21).** **Status: accepted** (the steward, under D191), revised twice under D191:
after Codex's read of round 1 (twenty-one findings, fifteen blocking, all taken in round 2) and after Fable's read of round 2
(thirteen findings, five blocking, all taken in round 3); design §13. On 2026-10-21 the owner, adding
an account on an agent's page, met the add-account dialog's third step, *Let it run work in*: a box for a workspace's own list of
three accounts and a box for *This machine's list*, worded "used by games; its starts run on account-4 instead of Daoris's
accounts, in turn". The owner found the step confusing and the very idea of a machine's list a sign that the model was wrong, and
read the sentence as Daoris moving the machine onto another account. The owner decided one set: every account signed in for
Daoris serves every workspace, with nothing about lists left for the person to reason about; and the machine's own account, the
person's own sign-in, stays the machine's, which Daoris never changes and adding an account never changes. The contract is
`docs/2026-10-21-account-pool-design.md`.

Why it confused (design §0). Each agent's accounts are read per scope, the machine's or one workspace's, each with its own list and
settings (D130 points 3 and 4; `HarnessSettings.ResolveScope`); a scope naming nobody takes every account of Daoris's (D175's
OWNSPACE1a note); and ticking *This machine's list* while the machine names nobody makes a list of that one account
(`WithJoined`, `HarnessSettings.cs:998-1005`), moving every workspace on it from all of Daoris's accounts to one: a narrowing the
dialog offered beside the others as if it were sharing (`joinChoices`, `agents.ts:524-560`; `choiceDetail`,
`AddAccount.tsx:70-79`).

1. **One set per agent, Daoris's accounts** (design §2.1). Every account of the agent that Daoris holds, the folders under the
   home's account homes, serves every workspace on the machine. There is no machine's list and no workspace's list; a start of
   any workspace reads the same accounts. A signed-out account stays in the set and is passed until signed in again; only
   *Remove…* takes one out. The person's pick at a start stays the one exception (D130 point 4).
2. **One order and one set of use settings per agent** (§2.2-§2.4). The order names every account and is written whole at every
   change of the set, so a new account goes last whatever its id; its first is where starts begin under *One by one, in order*,
   and it breaks the last tie under *Make the most of them*. There is no default beside it; every reader of the machine's default
   reads the order's first. The settings, `use`, `keep`, `switch` and `curve`, are one entry for the agent, outliving any change to
   the order. `harnesses.json` is read and written raw as today; one projection, `AccountSet.Of`, answers the set to every reader.
3. **The person's own sign-in is the machine's, outside the set** (§3). Daoris never signs it in or out and never starts work in
   it (D175). It no longer asks it anything: the own row's *Read again*, the own usage read and the roster's whole refresh, which
   asks every agent's own sign-in today, each ran the agent in the person's home, where it may refresh their token beside their
   own terminal's; the `own` parameter leaves the roster's report and the probe, so nothing can ask it. Nothing of Daoris's writes
   it: `agent trust` with no account named trusts the folder for every account of the set (the steward's settlement, below), never
   the tool's own trust file; a trust hold whose file is the own home's offers no press, `TRUST_FOLDER` refuses it, and it says to
   trust the folder with the tool itself at the terminal. Adding an account never touches it. The one run left there is a
   conversation begun there going on there (D175 point 3), which the set never displaces: a record with no account is judged
   against no scope. Its row stays last, says all this, and no word sends the person to Daoris to sign it in again.
4. **Adding an account asks nothing about where it runs** (§4.1). The dialog's *Let it run work in* step goes: at a sign-in's end
   it says *{{account}} joined Daoris's accounts: every workspace's work may run on it* (*{{account}} 已加入 Daoris 的账户，所有工作区的工作
   都可以在它上面运行*) and asks only the name; its first step lists the accounts to sign back in without their lists.
5. **The page shows one set** (§4.2-§4.4). *Runs for*, *Use in a workspace…*, *Add to / Remove from … list*, *Use by default…* and
   the *Workspaces* fold go; *How accounts are used* edits the one order and settings; the start dialog lists the set; the wait
   that asked *Let account-1 run work…* goes, since no account is outside. *This machine's list* (本机的列表), *this machine's
   accounts* (本机账户) and *This machine runs … by default* leave every screen and sentence, and the glossary's new term *Daoris's
   accounts* (Daoris 的账户) holds them out. Old start notes keep their meaning in words without the list's name, and a new reason,
   `opening.why.first-order`, says the set's first.
6. **The doors follow** (§5). `daoris agent profile order` and `use` act on the set and refuse `--workspace`; `profile default`,
   `profile join` and `login`'s `--join` and `--join-machine`, which PUSH1f2e carries into the driver's program as they are, are
   refused, saying what to do instead. `HARNESSES` and `HARNESS_ENDED` lose an account's places and the defaults; `HARNESS_ACTION`
   its `profile-join`, `profile-default` and `join`; `ACCOUNT_USE` its `inherit`, `workspace` and the refusal where no list is;
   `ACCOUNTS` its `inherited`. Ask Daoris's `use` and `order` act on the set and are marked so (`set`); its
   `default` door is retired; a stored proposal without the mark, whose `order` may have meant *only these accounts*, is refused at
   its Apply.
7. **The store folds at its first write, and says what changed** (§6). Every write of `harnesses.json` goes through
   `HarnessSettings.Change`, which folds the file under its keep lock before its edit, so the first writer in any process folds it;
   the driver's come-up is that change with no edit, and one a held lock refuses is logged and tried again at the next look. Per
   agent the order is the union (each scope's first as its starts read it, then its list: the machine's, then each workspace's by
   name; then every other account), nothing signed in dropped and one first kept first; each setting, compared as normalized, is
   the machine's where its entry sets it, read by a start or dormant, else the one value every workspace entry a start read agreed
   on, else the default; an agent whose machine scope named one account and no list is used *One by one, in order*, so its starts
   keep beginning there; the defaults and the workspace sections go. Each fold with anything to say appends a receipt with an id,
   shown on the agent's page and in `agent list` until the person presses *Got it*: which workspaces now run on every account,
   which firsts moved and where, which accounts no order held now run, which settings were not kept, which names were no account. A
   file an older build writes again folds again, with a receipt of its own.
8. **What stays machine-wide** (§7): the cap (D130 point 10), each account's readings and cool-offs, the machine's default agent,
   a workspace's pinned versions, and the person's own sign-in.
9. **The consequence, stated** (§8). A workspace that had its own list now runs on every account of Daoris's; a scope that named
   one account alone now runs on all, and where scopes began at different accounts only one stays first; an account no list held
   now runs; settings two scopes chose differently become the machine's or the default. D130's aim E, *keep work where it belongs*,
   has no setting now: a person who needs a workspace on one account picks it at the start, or keeps the others out of Daoris.
10. **The rows** (§11), all after PUSH1f2e: POOL1a, one set in the driver and on the bridge, with the fold and the own sign-in's
    rules; POOL1b, the terminal and Ask Daoris, the verbs PUSH1f2e builds turned into refusals; POOL1c, the page, after both;
    POOL1d, the install's fold and dialog seen.

**Why.** The lists answered a question the person should not have to hold: which scope a start reads, which accounts that scope
excludes, and what joining it moves. One set is the rule a person already assumes, and the one D175 had already made true wherever
nothing was named (*Daoris's accounts, in turn*); only a list, once made, broke it. The order and one set of settings keep every
choice D130 §16 gave the person except where work may run, which is the choice the owner gave up. The person's own sign-in is the
one account Daoris must not move, since the person works in it at their own terminal (D125's founding observation was the reverse,
the person's sign-in moving Daoris), so Daoris stays out of it but for a conversation already there, and the dialog no longer names
*this machine* at all. Folding rather than asking keeps every start running across the change; folding the raw file under its lock
at every write, before the write's own edit, and projecting it for every reader keeps the fold's baseline; and writing it in the
shape an older build reads as the machine's list keeps a rollback starting the same accounts.

**Rejected** (design §9): a workspace's own list as an opt-in narrowing; the machine's list under another name; a per-account switch
in or out of the set; a default beside the order; folding inside `Load`; a fold at every read, never written; a fold at the come-up
alone; an order absent until edited; asking the person before the fold; the receipts as notices in D196's record now; one receipt
replaced by the next; per-scope settings dropped silently, or merged to the most cautious; the machine's dormant entry judged by
the took-part test; `use` left as it was where the machine scope named one account; keeping the own sign-in's read at the
person's press; applying a stored `order` proposal to the set; `trust` granted in the order's first alone where none is named; an
own-home trust hold granted from the screen.
