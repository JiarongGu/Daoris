## D24 — The model is a deployment choice; features are defined independently of it (2026-08-05)

**Decision.** Daoris **does** use language and embedding models — a real part of it depends on them, and
that is not something to design around. What must never be coupled is *which* model. A feature is
specified by what it does; the provider serving it is chosen by **where the deployment runs**.

| Deployment | What Daoris is there | Which model |
|---|---|---|
| **A local repository** | A devtool set beside the working session | Whatever is local — the coding agent already present, or a local runtime |
| **A server** | A centralised knowledge provider for a team | Whatever suits a service — a hosted model, chosen for cost and throughput |

Same features, same logic, different provider. The two deployments have genuinely different constraints
— one has an agent already in the room and no budget for a network round trip, the other has
throughput and cost to answer for — so a single hard-wired choice would be wrong in at least one of
them.

**Why it is worth stating.** The models turn over faster than this project will, and the right one
differs by deployment *today*, never mind next year. A feature welded to a specific model ages at the
speed of the fastest-moving part of the stack rather than its own — and the parts of a codebase that
encode hard-won judgement should turn over far more slowly than the inference layer beneath them.

**The corollary, earned the hard way.** Decoupled also means a feature must not be *unavailable*
because a particular provider is absent. Convergence detection was built to require an embedder — it
returned null without one — and that gap was then reported as *blocked* rather than as the design
defect it was. It now runs whatever passes it can and names which found each result:

| Tier | Needs a model | Finds |
|---|---|---|
| Identical | no | Byte-identical copies. No threshold, no doubt |
| Restatement | no | Substantially the same words — a copy that has drifted |
| Convergent | **yes** | The same meaning in *different* words, which text comparison provably cannot see (D17) |

That is not a claim that models are optional to Daoris. It is that a feature should deliver whatever it
can with what is present, and say plainly what it could not do — because a caller who cannot tell why a
category is empty will assume a bug, and will be right to.

**How to apply.** Specify the feature without naming a model. Take the provider through a seam and
select it by deployment, never in the feature. Report which tier ran. Where a capability genuinely needs
a model — drafting a merged statement does — make its absence an explicit, informative message rather
than silence or an error.

**Consequence.** Provider selection belongs to the composition root, which is why the cognition
sibling's routing is the right thing to compose (D22) rather than something to reimplement. It is also
why the LLM-assisted merge splits as it does: finding candidates needs no model and ships today,
drafting a merged statement needs one and will take whichever the deployment provides.

**Note, 2026-10-19 (KNOWHOLD1, a running session follows the build).** *Serving never builds* stays; serving now
follows. The server a session started ran its first build until the session ended, so a merge's build reached new
sessions only, and one server kept a host's whole-checkout watch for two days after KNOWWALK1 had fixed it.
`relayServer` now sits between the session and its server and moves the session onto the current
build at a request with nothing owed, or within a minute while it is idle, replaying the session's own handshake and
ending the server it left; a build that does not answer stays unused. The machine's host of a driven session is not
followed, being the install's. Rejected: leaving it to each session to restart its server, which is what kept the old
host for nine days; and moving the rehearsal's scratch out of the checkout, which would only have moved the next fault
somewhere the server does not look. Root cause, fix and proof: the fix log's KNOWHOLD1 entry.

**Note, 2026-10-29 (KNOWCURRENT1, a host over the registered roots stays current and says how current).** ORIENT1c's
re-read belonged to the one-checkout server alone (`rereadAfter` is set only when `DAORIS_KNOWLEDGE_REPOSITORY` names a
checkout). The installed HTTP host and every session's connector name none, so for them a non-empty index was fresh for
ever: the first process to read a root kept that reading, and a decision merged later (D212 beside D210 and D211) was
never found. The contract that said so, `OneCheckoutTests`' *a process with no window reads once*, is narrowed: a
source with no registered roots to judge (a fed host, a bare source) still reads once, and a host over the registered
roots no longer does. Such a host reads every root at its first use, then judges each root at use, at most once a minute,
by a signature of what the index read: the commit its `HEAD` names, and the newest write and the count of the record
files the scan walks (`RootSignature`). A root whose signature moved is read again alone; one unchanged is not; one no
longer registered takes a whole read, which retires what it held. The write time and the count are in the signature
because a record changed in the working tree without a commit is read by the scan too (the index reads the working tree,
never a commit), and a deletion moves the count. The signature reuses `CheckoutFreshness`'s resolution of a worktree's
git folders, not its watcher: a watch per registered root is a handle per folder per root held for the host's life for
a minute's gain, and the signature is two stats per record file. The driver's refresh on a registration change stays;
the service now judges freshness itself, so a landing that only adds records needs no driver change. The index also
says how current it is: per repository, when this process read the checkout and the commit it read, in
`IndexReport.Read`, `RepositorySummary`, `/api/repositories` (`indexedAt`, `indexedCommit`), `POST /api/refresh`
(`read`) and the two knowledge tools' text. Those are this process's readings, kept in memory: an index read by an
earlier process says nothing until the first use re-reads it, which is the point. Rejected: shortening nothing and
telling the driver to refresh at every landing, which leaves a session's connector stale and trusts a trigger that
failed here; and a timer that re-reads every root every minute, which pays a one to two second read of every
repository for no change.
