## D151 — Every repository Daoris drives keeps a generated index of where things are, written and checked by its own tooling so that nothing of it needs Daoris; where Daoris runs, the service indexes it, a hit names its lines, and the driven look starts there (2026-10-04)

**Decision (ORIENT2).** The owner, after ORIENT1: *"so this should also apply to the repositories Daoris drives too, and
an even better knowledge system since Daoris is there"*, and *"it should not break the general workflow if the system
running the code does not have Daoris (this is for sharing repositories)"*. ORIENT1 measured a third of each branch's
calls spent finding its way before the first edit, and built this repository's index. The contract is
`docs/2026-10-04-orientation-everywhere-design.md`: the floor (§1), the set-up's part (§2), Daoris present (§3), a
clone without Daoris (§4), the measure (§5) and the build (§6).

1. **The floor is committed files.** One folder, generated and never edited by hand: a README naming what each file
   answers and listing the indexes kept by hand first; one table per thing sessions look for, each row a file and a
   line; an outline, with line ranges, of each file too long to read whole; and a digest of the decisions record, by
   decision and by dated amendment. The knowledge stays listed where it is (the doctrine's `INDEX.md`, or the
   repository's own), linked and never copied.
2. **It stays true by the repository's own check, so nothing of it needs Daoris.** A generator in the repository's own
   toolchain, deterministic and offline, has a check mode inside the command that means done. The check fails, naming
   each stale file and the command that writes it again: a stale index is a fact (D54). A merge never text-merges the
   folder. A conflict there is resolved by writing it again, and the folder is marked as generated for review.
3. **The canon teaches it on demand.** `development-documents` gains the `index` role and a section; `doc-loader` a
   step, to start every search of the code at the index the brief names; `set-up-documents` a step, its close's clause
   and `templates/index.md`. There is no new canon document, and the canon adds no always-loaded byte. A repository
   that declares the role (point 4) pays one row in *Where things are*: 119 bytes as drafted, so 20,064 of 26,000
   becomes about 20,183 here.
4. **The CLI declares it**: `documents.index`, rendered in *Where things are*, with `check` failing on a declared path
   that is missing. Daoris declares `docs/index/README.md`.
5. **The repository's own session writes it**, in its own quest, *Give this repository an index of where things are*.
   The set-up press publishes it once the set-up has landed, and the workspace plan paces it. The press names the
   generator's path and its two commands from the stack it reads, and grants exactly those, as it grants a set-up's
   verbs. The bounds allow only the generator, the folder, the check's entry, the attributes, the brief's line and the
   role. An index the repository already keeps stays whole: declared if it is generated and checked; listed first,
   with none of its rows restated, if it is kept by hand. The close names each one and how the generated index differs,
   and nothing is moved, rewritten or deleted.
6. **Where Daoris runs, it adds to the same files.** The service reads the declared index as entries of
   a kind of its own, `index`, split at headings. Every entry keeps its lines, so a hit names `path:start-end` and
   `knowledge_get` takes a range. The driven look names the declared index first. The semantic tier is the
   deployment's (`DAORIS_EMBED_MODEL`, with `DAORIS_EMBED_URL` and `DAORIS_EMBED_WINDOW`, read when the service
   starts) and adds where-questions asked in other words. With no model, BM25 answers, saying *matched on words only*
   on every result; with no service, the files answer.
7. **The measure is `orient-report` over the install's driven sessions.** It reads each session's typed events
   (`<home>/sessions/<id>.events.jsonl`), named by the machine log's `session.started`, and never the harness's own
   transcript, which lives in an account's home (D125). The before is every session until a repository's index lands
   on its line. The after must halve calls, characters read, and shell searches and dumps before the first edit. It
   must cut whole reads of outlined files to a quarter, have 8 in 10 sessions open the index first, and leave parks no
   higher.

**Why.** ORIENT1's cost is paid in every repository a session works in, and a driven session pays it in a repository it
has never seen. A second repository already met the need by hand: three indexes and a routing skill that its sessions
open in 20 of 22 runs. So the need has two sources, and the generated form is the one that stays true. The floor
must be files because a clone without Daoris must work (D48's coexistence; canon-authoring's *a file or a service*).
Its freshness must be the repository's own because a decision note stales the digest on most branches: a check that
needed Daoris would stop every contributor who does not run it, which is the critical path D48 forbids. Only the
repository knows what its code is reached through, so its own session writes the generator, as D124 has a set-up
written. Daoris adds what only a running service can: a search across the workspace, by meaning where the deployment
chose a model, with hits that name their lines, since ORIENT1 found decision files read whole 21 times because a
search names the file and not the note.

**Rejected** (the design's §7 has each with its reason):
- **Daoris writing the index** (`sync`, or a verb of its own, even for outlines and the digest): every contributor would
  need Daoris to make a branch pass, and no generic tool knows a repository's entry points.
- **A reference generator in the canon, copied in**: a toolchain on the path of repositories that do not use it, or code
  in stacks the canon cannot test.
- **An index generated at a session's start and ignored by git**: a call and a permission before the first read, nothing
  on the line for the service or a reviewer, and a session that skips it searches as before.
- **The service as the index**, with no files: a dead end without Daoris, and not connected in practice (ORIENT1).
- **The index in the always-loaded region**, **a hand-kept index added by the set-up**, and **the index as a step of the
  set-up quest**.
- **One format the service parses**, **indexing or embedding the source code** (D124's baseline rejection), and **index
  rows or recall pushed into the driven prompt** (D129 §6 holds the push).
- **A new canon document**, **a merge driver** (untracked configuration, D134's reason), and **replacing a repository's
  own index or routing skill** (KNOWUSE1 §2.1, the pilot's mistake).

**ORIENT2e, built 2026-10-07: the service indexes the index, and a hit names its lines.** The scanner reads the declared
`documents.index`: every markdown file in the folder its README is in, and below, split at every heading
(`IndexSections`), as entries of a new kind, `index`, the repository's own, titled by the headings above them.
`RepositoryDocuments.Roles` gains `index` after `router`, row for row with ORIENT2b's `ROLES`, and its twin table holds
ORIENT2b's two rows. Every entry keeps the lines of its file its body is (`KnowledgeEntry.Lines`); a hit names
`path:first-last` and the line its excerpt starts on; `knowledge_get` takes `lines`. A search naming no kinds holds
the index to two entries and says when more matched. The store is schema 5, and the HTTP answers gain `firstLine`,
`lastLine` and `excerptLine`. Choices the design left open:
- **Every heading, not one level**: an index's sections are the places a lookup lands, however deep the generator put
  them. Text before any heading is titled by the file's path. A README declared at the root is read alone, since its
  folder is the whole repository.
- **A deployment's own index folder comes first** (`DAORIS_KNOWLEDGE_INDEX`, ORIENT1c): read a row at a time, as that
  deployment chose, and those rows are of the kind `index` too. So this repository's own server, which names
  `docs/index`, answers as before; the declared reading applies where no deployment names the folder.
- **Lines are the body's**, so a range is cut from what was indexed and never read from the disk: a fed deployment has
  no file, and a file that moved since would name other text. A row labelled by its columns is no line as written and
  names none. Neither does a feed that names none, or lines its body cannot be.
- **Convergence leaves the index out** unless asked for by kind: two indexes generated from one template have learned
  nothing together.

Measured on this checkout's files, words only: all 1,286 scanned entries name lines, each checked against its file. A
copy declaring `docs/index/README.md` read as 151 index entries over 107 files. *Outline of KnowledgeService* answered
first with that file's outline, with kinds and without. 🔴 *Where is the SESSION_GO_ON_NEW handler*, by kind, did not
reach the 102-row section holding the row: BM25 weighs one matching row against a long section, and five small route
sections ranked first. That is ORIENT1c's finding about sections, met again. The same question to the rows (the own
server's reading) answered first with the row, then *more index entries matched*.
