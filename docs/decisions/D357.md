## D357 — Git is one service the bus reaches: reads answered in process by the library, every ask carrying an id and a class, long answers streamed in parts, one scheduler ordering them all (2026-11-22)

**Decision (GITBUS; the owner's direction of 2026-11-22, its choices the steward's in that direction; amending D356 point 3, which
kept git a direct call; GITLIB1 and GITLIB2's in-process reads become the service's engine; `GitScheduler`'s places stay for the git
processes that still run).**

1. **One git service.** Every git read and act of the desktop is asked of one service: an ask carries an id, the repository, the read's
   kind and its arguments by name, the asker (`GitAskers`' callers), its class and its deadline, and is answered by that id: the
   answer, or a typed failure naming why. No caller starts git or opens the library outside it, and a census holds that. The service is
   a participant of the bus (D356 point 3's transports carry it to a plugin or another process later), but its asks and answers run in
   memory: they are not entries of the bus's durable log (point 5).

2. **Reads in process.** A read the library answers exactly (refs, objects, trees, commit walks, merge bases, a patch's equivalence,
   status where it is proved at parity) is answered in the desktop's process: no git process starts and no place is taken. A read it
   cannot answer yet, and every act (a write, a fetch, a push, a command a hook runs under), runs git as today, under the scheduler's
   places. Each read kind moves to the library with its parity proved on real git (GITLIB1's parity classes), one kind per change, the
   hot ones first (point 7).

3. **One scheduler.** Asks queue by class: the person's, then a step's (the run-step consumer, the opinion gate, a check), then the
   background's (a look's sweeps, machine facts); oldest first within a class. An ask past its deadline is answered as failed with its
   reason, never left silent (D356 point 5). Git processes keep today's places (four on the machine, two of one repository's background
   reads); in-process reads have their own bound, set by the processor, never the process places.

4. **Long answers in parts.** An answer bigger than one message (a log walk, a tree's listing, a diff) streams as numbered parts on the
   ask's id, the last marked, so the asker reads as it arrives and stops the read by cancelling the ask. The parts ride the service's own
   lane at the asker's pace; the bus's frames (about 60 a second, D356 point 4) pace envelopes' delivery, never how fast a read runs.

5. **Nothing of git's per ask on disk.** An ask, its parts and its answer are memory only. What reaches disk is the measure: counts and
   waits by caller and by read kind, batched with the bus's measures (`GitAskTally`), and a fact where one is a fact (a ref moved, a check
   ended). Git's thousands of asks a look would otherwise write are the disk wear the owner asked to avoid.

6. **Answers kept by what they rest on.** An answer is kept keyed by the repository, the refs version it read (`CountedRefs`) and the
   ask, in memory and, where it is costly to make again, in the home, bounded; an unchanged ask is answered from it with nothing read.
   The content proof's memo (`ContentProofMemo`, STARTLOAD2) is its first kind and moves under the service.

7. **The order.** (a) The service and its ask, wrapping today's `GitScheduler` with no change of behavior, every caller moved to it and
   counted by a census. (b) The hot reads to the library, measured by the per-caller counts (STARTLOAD2): the content proof's walks
   (cherry, merge bases), branch listings, a tree's status. (c) Classes and deadlines in the scheduler, a step's asks before the
   background's. (d) Parts for walks and listings. (e) The places shrink to the git processes that remain.

**Rejected.** Raising `GitScheduler.RepositoryBound`: it moves the wall, and the machine and the person's other work pay for it. Each
git ask an entry of the durable log: thousands of writes a look, for asks whose answers are cached or thrown away. A second git door
beside the service for a caller in a hurry: one way per job.
