## D139 — An install updates when its work allows: a build staged beside it, a drain that starts nothing new, and the launcher swapping `app/` while the application is closed (2026-10-03)

**Decision (UPDATE1, amending D60's and D93's publish).** On 2026-10-03 four republishes of the owner's install waited on
running sessions, and each was done by hand: `daoris driver hold` on the repository, a script waiting until no session
worked, the window closed, `publish:desktop` over the install, a start, the hold released. One attempt failed on a safety
check that found main's checkout dirty with documents. The contract is `docs/2026-10-03-update-when-idle-design.md`.

1. **A build is staged beside the install, never written over the running one.** `publish:desktop -- --to <install>
   --service --stage` builds exactly what a publish in place builds into `update/staged/` beside `app/`, with
   `build.json`, a manifest naming every file with its size and SHA-256, and swaps the folder in whole. It refuses a
   folder that is not an install, a swap in progress, and an install carrying its HTTP host staged without `--service`.
   It does not refuse a running install: that is what it is for. A publish in place removes anything staged.
2. **The desktop drains by itself.** A staged build is installed when idle unless the person says otherwise: the driver
   loop starts nothing new (every start held, intakes too, a hold the person made keeping its own sentence), the running
   sessions end or park, and when no driven session runs and no conversation's turn is in flight the application closes,
   the launcher swaps, and Daoris starts again. A conversation between turns, a parked session and the person's
   terminal are idle: the close ends a conversation as any close does, and a parked record is never touched, by the close
   or by the next start's sweep, which takes only `working`.
3. ***Update now* is the person closing Daoris.** It does not wait: the close ends what runs the way a close always has,
   each driven session recorded `stopped` and interrupted, so its quest is carried on in its tree at the next start
   (D104, D80), the ending the person's own and owed no interruption. ***Not now*** keeps the staged build and starts
   work again; it holds for that build only, so a newer stage drains again. Both doors (D50): the banner and
   `daoris-driver update --when-idle|--now|--cancel`, both writing `$DAORIS_HOME/update.json`; plain `update` says what
   is staged and how the last swap ended.
4. **The staged build is checked before it replaces anything**, twice: by the application before it closes for it, and
   by the launcher before it moves a file. Every file the manifest names is there with its size and hash, nothing is
   there it does not name, the launcher, the application and its library are among them, and so is the host when the
   install carries one. A refusal leaves the install as it was, says which check failed, and the drain ends.
5. **The launcher swaps, because the application cannot replace itself while it runs.** The application starts
   `Daoris.exe --update --after <pid>` and closes. The launcher waits for that process and for every process running from
   `app/` to end, checks the build, and moves, journalling each move in `update/swap.json` before the next: `app/`,
   `Daoris.exe` (its own running image, which Windows lets be renamed and not overwritten) and `INSTALLED.md` into
   `update/previous/`, then the staged three into place. It starts the new application and waits for it to confirm, which
   it does once composed. A start with a build staged and nothing running from `app/` swaps the same way first, unless
   the person said *Not now* of that build.
6. **A failed swap rolls back to the build before it.** A move that fails undoes the journal in reverse; a new
   application that exits before confirming is moved to `update/failed/` and `update/previous/` moved back; a launcher
   that died mid-swap is undone by the next start, which reads the journal; an update that finds `app/` still held after
   the wait, or meets an error first, refuses the build. The old application starts, and the staged build is not tried
   again: whatever did not install is in `update/failed/`. Confirmed, `update/previous/` is removed. The application says each outcome once, in the
   window and the machine log (`update.installed`, `update.rolled-back`, `update.refused`): the launcher writes no log of
   its own, since it references nothing.
7. **Nothing of Daoris's under the user profile** (D63): the staged build, the journal and the failed build are under
   the install, the request under the home.

**Why.** An update is a person's act about the application, not about the work it drives, so it should wait for the
work rather than the person waiting by hand; and it has to be done by a process that is not the one being replaced. The
launcher already is that process (D93), and a rename of a running executable is the one move Windows allows on it.

**Rejected.**
- **A person's stop for *Update now*** (D126 §3.3): every quest a running session held would sit held after the update,
  which is the opposite of the work carrying on.
- **Holding starts by writing every repository into `holds`.** It is the person's choice, said as theirs, and it was
  what the by-hand update had to undo afterwards.
- **The application swapping itself** through a script it leaves behind: a second program to ship and keep apart from
  the launcher, for what the launcher's rename already allows.
- **Skipping the driver's looks while draining.** The looks also report endings, tell plugins of them and sync; only
  their starts are held.
- **Waiting for a conversation between turns, or for the terminal.** Either can be open all day; the banner shows the
  drain, and *Not now* is one press.

Proof: `StagedBuildTests` (the check's every code; the swap installing and journalling; a new build that ends before it
confirms, will not start, or stays silent; a held file; a launcher that died at each phase; a build refused by the
launcher, or held after the wait, moved aside), `InstallUpdateTests` (the request, the mode per build, the drained config,
the drain's hold said as its own), `UpdateDrainTests` (the watch starting nothing while draining, what runs running on and
its ending reported, the person's hold keeping its sentence), `UpdateCommandTests` and `DriverCommandTests` (the terminal's
door), `InstallUpdaterTests`, `UpdateModuleTests` and `TickConsiderationTests` (the drain, *Update now*, *Not now*, the
application's check, the outcome said once, the routes and refusals), the publish's `--stage` helpers in
`desktop-publish.test.ts`, the banner's states in both languages, and the deployment rehearsal's phase 9 on the artefact,
which the parent runs at the merge: stage beside the running install, drain, swap, start, roll back, refuse.

**What it does not do.** The first install of this build is a publish in place: a launcher from before it does not swap.
The swap is run by the launcher being replaced, so its protocol is the old build's; `build.json` carries a schema, and a
launcher refuses one it does not read. A new application that starts, confirms and fails later is not rolled back.
Settings' row for the update is web-settings' to mount.

*Mounted by UPDATE1b (2026-10-03): Settings → Driver shows what is staged, the drain and what it waits on, the last swap
and the three words, over `STATE` and `SET`. The last swap outlives the banner's *Dismiss* once `STATE` answers `last`,
the journal's record told or not, as the terminal's plain `update` already says it; the modules do not answer it yet.*

*Answered by UPDATE1d (2026-10-03): every `STATE` carries `last` beside the once-said `outcome`, read from the journal at
each look (null with none or while a swap is under way; confirmed by this start, installed), and the row reads only `last`.
UPDATE1e: Ask Daoris's coverage (D110) reads the update's words, exempt as the person's act on the application.*
