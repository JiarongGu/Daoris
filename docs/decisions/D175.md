## D175 — Daoris's sessions keep their agent state in Daoris's own space, never the person's own tool home (2026-10-16)

**Decision (the owner's direction).** The owner, 2026-10-16: *"I also found an issue: Daoris is still using the global
`.claude` space instead of using its own data space."* What it found, read off this machine: the person's own Claude Code
home held 28 project folders the install's sessions wrote (Ask Daoris's room, an intake, and the session trees), beside
the person's own work. An account Daoris names gets its own configuration home (`CLAUDE_CONFIG_DIR` under the home's
`harnesses/`), but the tool's own home (whichever account the person last signed in to, D125 point 5) was run as it is,
so its sessions' transcripts, settings and caches landed in the person's space.

1. **Every session Daoris starts runs in a configuration home Daoris owns**, under its install's profiles (D172's
   `profiles/`): driven sessions, conversations, Ask Daoris's room, an intake, a helper, a reviewer. A harness whose
   configuration home is a variable (`CLAUDE_CONFIG_DIR`, Codex's `CODEX_HOME`) is always handed one; the person's own
   tool home is never Daoris's working space.
2. **The tool's own home becomes a Daoris account the person signs in to once.** Where today a start would run in the
   tool's own home, Daoris offers *Sign in for Daoris* into a profile of its own (the add-account flow), and says why;
   until the person does, the start waits, said once (D125 point 6's wording), never falling back to the person's home.
   Copying the person's credentials into a profile silently stays rejected (D125); signing in is the person's press.
3. **What is already there stays readable and is never moved by Daoris.** A conversation that ran in the person's home
   resumes there, as D125 keeps a harness's conversation in the home it began in; new starts go to Daoris's space. The
   project folders Daoris's sessions left in the person's home are listed on *This Daoris* (WIRING1) as Daoris's, and
   removed only by the person's press after it lists them (D88's rule for what Daoris made).

### Rejected

- **Leaving the tool's own home as Daoris's default account** (D125 point 5's arrangement): it mixes Daoris's sessions
  into the person's own tool home, which the owner found and asked to end.
- **Copying the person's credentials into a profile** (D125's rejection stands): a sign-in is the person's.
- **Moving the existing transcripts out of the person's home**: a harness keys a conversation by its home and folder; a
  move would strand them (D172 point 6's rule until measured).

### Amends

- **D125 point 5**: the tool's own home is no longer an account Daoris starts work in.
- **D172**: `profiles/` holds every configuration home Daoris's sessions use.

**Note, 2026-10-16 (OWNSPACE2).** Point 3's list and its press are built, on *This Daoris* (`SYSTEM_WIRING`'s `toolHome`, the
press `SYSTEM_TOOL_CLEAR`, the card *Left in your own tool home*). `ToolHomeLeftovers` (the driver library) holds the rules:

   *Reworked the same day after a second maker's review blocked the first build, which matched by flattened prefix and judged
   activity by ten minutes of quiet and deleted. Points 1, 2 and 4 below are the reworked rules; a prefix proved nothing.*

1. **Ownership is provenance, by exact equality.** Claude Code keys a project folder under `<its home>/projects/` by the
   session's working directory with every character that is not a letter or a digit turned into `-`, which loses what the
   character was. A folder is Daoris's only where its name EQUALS the flattening of a working directory Daoris's own records hold:
   each session record's `tree`, the help room, and each intake room (from the records' `ask` and workspace, and the rooms on the
   disk), and only where that directory is under one of Daoris's working roots (the places, new and old, of every `work` entry
   of D172's table). No prefix is matched. Two distinct paths that flatten alike are listed for neither (`ambiguous`), paths
   spelled apart by case are never merged (the answer says whether the folder's file system folds case), and a path with a
   non-ASCII letter, over 200 characters, or relative is not proven to flatten as Claude Code does and is not Daoris's
   (`uncertain`; how Claude Code flattens was read from its documented behaviour, never from the real home). What this cannot
   prove: a person's own path, outside Daoris's records, that flattens to the same name as a recorded one. A collision is
   judged over EVERY recorded path, those outside Daoris's roots included (`<home>-trees/…` flattens like `<home>/trees/…`),
   before the roots decide whose a single path is. *Second review:* an unreadable conversation record (access refused, invalid
   JSON) is not an absent one and keeps the folder (`record-unread`); the store's `Read` keeps answering null to its other callers.
2. **The person's tool home** is `CLAUDE_CONFIG_DIR` where they set it (this process's, else the account's), else `.claude`
   in their profile. The page says which. A relative variable, or one inside Daoris's own folder (a Daoris account), is not the
   person's own: nothing is listed and the page says why. A world made by hand names none, so no test reads a machine's.
3. **The read** lists names from the folder's listing alone, and measures each (size, newest file) with the home's existing
   walk when the page asks for a measure; nothing is opened inside a folder. `daoris-driver wiring --json` carries the same.
4. **The press moves aside, never deletes.** It acts on exactly the `{name, id}` sent, each judged again inside the action: still
   in the list, the same folder (its file identity, taken at the list), no link on the way from the tool home up or in where it
   goes, read whole, and written to by no one within ten minutes. A folder stays where Daoris's records say a session may use
   it: a live or waiting session (`session`), a record that began in the person's own home (no account) with a kept
   conversation (`resumable`), or records not read (`records-unread`), whatever the folder's age. What stayed is said with why.
   A folder goes into `trees/.tidied/tool-home/projects/` under Daoris's own home, as `<name>-<8 hex>-<moment>` (the moment
   last, as the trees' moved-aside folders are read), so the look's own purge takes it after fourteen days with nothing written
   in it since. **One rename on one volume, and nothing else:** no copy, no verify, no removal, so a half-done move cannot
   exist. Where the tool home and Daoris's folder are on different volumes the folders are listed and no press is offered
   (`other-volume`, said on the page). The destination must not exist (never used, replaced or removed), and the whole way to
   it, up to the root, is checked for a link before anything is created. Each folder is judged on a listing and on records read
   afresh for it, just before it moves, so a session that resumed during the press keeps its folder. The identity is Windows'

   `Person` in the pipe census and declares nothing (what it moves is outside Daoris's state). What the press cannot prove: a
   folder is not locked between the last check and the rename.
