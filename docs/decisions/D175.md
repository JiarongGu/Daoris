## D175 — Daoris's sessions keep their agent state in Daoris's own space, never the person's own tool home (2026-10-17)

**Decision (the owner's direction).** The owner, 2026-10-17: *"I also found an issue: Daoris is still using the global
`.claude` space instead of using its own data space."* What it found, read off this machine: the person's own Claude Code
home held 28 project folders the install's sessions wrote (Ask Daoris's room, an intake, and the session trees), beside
the person's own work. An account Daoris names gets its own configuration home (`CLAUDE_CONFIG_DIR` under the home's
`harnesses/`), but the tool's own home (whichever account the person last signed in to, D125 point 5) was run as it is,
so its sessions' transcripts, settings and caches landed in the person's space.

1. **Every session Daoris starts runs in a configuration home Daoris owns**, under its install's profiles (D172's
   `profiles/`): driven sessions, conversations, Ask Daoris's room, an intake, a helper, a reviewer. A harness whose
   configuration home is a variable (`CLAUDE_CONFIG_DIR`, Codex's `CODEX_HOME`) is always handed one; the person's own
   tool home is never Daoris's working space.
2. **The tool's own home becomes a Daoris account the person signs in to once.** Where today a start would run in the
   tool's own home, Daoris offers *Sign in for Daoris* into a profile of its own (the add-account flow), and says why;
   until the person does, the start waits, said once (D125 point 6's wording), never falling back to the person's home.
   Copying the person's credentials into a profile silently stays rejected (D125); signing in is the person's press.
3. **What is already there stays readable and is never moved by Daoris.** A conversation that ran in the person's home
   resumes there, as D125 keeps a harness's conversation in the home it began in; new starts go to Daoris's space. The
   project folders Daoris's sessions left in the person's home are listed on *This Daoris* (WIRING1) as Daoris's, and
   removed only by the person's press after it lists them (D88's rule for what Daoris made).

### Rejected

- **Leaving the tool's own home as Daoris's default account** (D125 point 5's arrangement): it mixes Daoris's sessions
  into the person's own tool home, which the owner found and asked to end.
- **Copying the person's credentials into a profile** (D125's rejection stands): a sign-in is the person's.
- **Moving the existing transcripts out of the person's home**: a harness keys a conversation by its home and folder; a
  move would strand them (D172 point 6's rule until measured).

### Amends

- **D125 point 5**: the tool's own home is no longer an account Daoris starts work in.
- **D172**: `profiles/` holds every configuration home Daoris's sessions use.

## Note, 2026-10-17 (OWNSPACE1a): the driver's half, and three settlements

Every start goes through the roster's walk (`HarnessRoster.WalkAsync`), so the rule is kept there once: driven work, a
carry-on, an intake, a conversation, Ask Daoris's room, a helper and a reviewer all take a Daoris account or wait.

   configuration-home variable is exempt by having none, since no account of Daoris's can be handed to it. Every real agent

2. **Accounts that exist but nothing names.** Where neither the machine nor the workspace names a default or a list, the

   walked by the rotation's own order and allowance rules. The start holds only when none is signed in (none exists, or each
   said signed out), with one sentence, `held.no-account` (en and zh), carried as a wait for a sign-in naming the accounts it
   passed, so a look reports it as a wait and says it once (D125 point 6). A cool-off or a refusal still waits as before.
   The page's next start (`Next`) reads the same scope, so it says the wait rather than the own sign-in; it is asked by the
   accounts' owner, whose toolchain is read through its doors (`codex` behind `codex-acp`).
3. **What began in the person's home.** A record whose account is null began in the tool's own home and resumes there
   (`ResumeAsync`, its own-home path); every new start takes a Daoris account. Where its words go to a new record because
   its own conversation cannot go on, that record is a new start and takes the walk (`CarriedOnAsync`).

The trust file a hold reads is the one the session's harness reads (`ClaudeTrust.PathFor`): the account's home, else the own
home as the session inherits it, the configuration-home variable where the person set one. A trust hold on a Daoris account
names Daoris's door alone, since a `claude` run at the person's terminal would trust the folder in their own home and the
hold would come back. The screens (*Sign in for Daoris*, the account words, Ask Daoris's room) are OWNSPACE1b's.
