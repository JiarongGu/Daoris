# The Daoris guide

The reference behind [the README](../../README.md), which is the landing page on GitHub and npm: the
commands, the manifest, the layers of doctrine, the seams and the parts beyond the CLI. The README
holds the pitch, the quickstart, the packages, the status and the rules a coding agent gets wrong;
the last section here holds the text for the repository's settings on GitHub. `<version>` below is
the version you pinned: the README's install lines carry the released one.

## Install

Nothing is published until the first release (D105). Then every command runs as npm's `daoris`, at a
pinned version:

```sh
npx daoris@<version> init     # write daoris.json (and a .gitattributes if none), report available packs
npx daoris@<version> sync     # materialize the doctrine, write daoris.lock
npx daoris@<version> check    # the gate — offline, exit 1 on drift
```

The canon ships **inside the package**, so pinning the package pins the doctrine. Once the package
is present, doctrine commands use that local canon and `check` works offline.

## Commands

One name, `daoris`, and one command tree (D228; the oneway design §11). The package's `daoris` runs the doctrine
commands, offline, and hands every other word, whole, to Daoris's desktop program: the one an install carries, or the one
`DAORIS_DRIVER_PROGRAM` names. An install's own `daoris`, in its `app/bin/`, runs that program, which needs no Node and
hands the doctrine commands back to the package the install carries. `daoris help [<group>]` prints the tree, or one
group.

`sync` accepts `--dry-run` (print the plan, write nothing) and `--force`; both pass over a file `daoris.json` keeps.
`init --harness <claude-code|agents>` chooses the layout it writes: `claude-code`, the default, puts knowledge and skills under
`.claude/`; `agents` puts them under `.agents/`, mirrored for Claude Code. `analyze` and `status` accept `--json`.
`upstream` accepts `--all` to propose every locally-edited canonical file at once. `repository connect` accepts
`--workspace <name>`, and `agent login` accepts `--account <account>` (an account already here, by its id or its name),
`--new [--name <name>]` and `--device-code` (Codex's device code, in place of its browser).

**A workspace is the unit of sharing**: knowledge, quests and session records cross between repositories
within one and never across one. Membership is **wiring, like a git remote** — `daoris repository connect --workspace
aurora` records it in this machine's registry and writes nothing into the repository, so a fork and a
second machine may each wire it differently. Omitting the flag leaves existing wiring alone; a
repository nobody ever wired is in `default`.

**A workspace's sharing has two halves, and they live apart.** Whether a repository's material *may*
leave the machine is its own `daoris.json` — tracked, reviewed, and silent by default. *Where* it would
go is this machine's map, `profiles/remotes.json` beside the home: one deployment per workspace, because a shared
deployment serves exactly one circle and refuses a registration declaring another. `daoris remote`
edits and lists that map, and a workspace with no entry syncs nowhere — which is
what every machine does until someone says otherwise. A key is never printed back, only its audit
prefix.

**One agent, many accounts.** An agent holds one login per configuration home, so `daoris agent`
makes accounts **named profiles**: isolated configuration directories whose *location* Daoris owns
(`profiles/agents/<agent>/<profile>/`, beside the home's `data/`), selected at spawn through the variable that agent
already has. Logging in runs the agent's own flow inside one, so **Daoris never
sees, stores or copies a sign-in**; `agent key` keeps an API key, and `agent rules` what a
session may do (D72). By default that is Daoris's connector, through which it works its quest, says or
answers a second opinion, talks on its ask's channel and reads the earlier parts of the line it continues (`line_read`),
a commit in its own tree, and never a push or a write outside it. Pick one per machine, per
workspace, or for a single conversation, or `--clear` it; the session record names the account and tool
version it ran as. A spawn onto a missing agent, a profile nobody signed into, or a workspace the agent
has never been trusted in refuses **naming the action that fixes it**. `agent list` says what each account's
agent last said of its windows, and the tool's own sign-in's once a press on its page read them (D125), each leading `read <age>:` for Daoris's own no-prompt read of the plan's usage or `said <age>:` for what a
session reported (D165). Two sign-ins of one email in different organisations list apart, the organisation after the email
(D125). `agent account use` says what passes an account at a start, its limit reached, usage credits or
its use over its curve, and marks a reading over the scope's curve with the curve's value now (D165).

**Git identities of Daoris's own** (D198). `daoris git identity add-ssh <host>` makes an SSH key in
`profiles/git/keys/`, its folder limited to your account before a key byte is written; `git identity test` reads the host's
greeting and a host key is trusted only at your press; `git use <repository> <identity>` points a repository at one. The list
(`data/git-identities.json`) holds no secret. They take effect only on an install published with Daoris's git doors, which
are left out until their measurements pass on an install; until then a remote keeps your own git as it was.
`docs/2026-09-22-toolchain-design.md` is the contract.

**`repository connect`, `repository retire` and `repository import` are management commands** — opt-in, they talk to a
service, and no gate ever runs them; `brainstorm` too, to this machine's own service only. Every group the desktop's program
runs is management (`remote`, `agent`, `place`, `settings`, `plugin`, `browser` and `tool` among them); they edit files under
**the Daoris home** (`DAORIS_HOME` — the installed application's own `data/`, set once for your
account, never your profile; D63), refusing with none set. A `daoris` the install carries needs neither that nor
`DAORIS_SERVICE_URL`: it takes its install's `data/`, and the service the running Daoris holds (D171). A service that is busy and answers late is said as busy (SERVICESTALL1): the status door, and a read the command makes, are asked a second time after a second, and a refusal names the address it tried, the bound (two seconds for the status door, sixty for a request) and that it asked twice, and says `DAORIS_SERVICE_URL` is not the cause where the address came from the home's own record; a press that changes the registry is never asked again blindly and says what to look at. While Daoris runs on that
home, the program sends what a command changes to it over its own pipe, where its window asks you to confirm it and every
window shows it at once; with none running it edits the files itself, holding the home's lease (D171's PUSH1f note).
The CLI's table of the home's entries (`home.ts`, a twin of the driver's and the service's) names the desktop's own store, `data/desktop.db` (FOUNDATION1 z-i, D212), as it names every place a home holds, and never opens it: the driver library alone does, so these commands reach it through the desktop's program as they reach the rest.
A place's standing choices, the settings, the workflows, the cycles and the brainstorm policy alike are that program's: the one
the install carries in `app/daoris-driver/`, or the build `DAORIS_DRIVER_PROGRAM` names; a `daoris` with neither, a checkout's
among them, says so and does nothing. A tool's download holds nothing while it fetches, and is
made the version under the home's lease, which it waits for. From a terminal Daoris started for a session (`DAORIS_SESSION_ID`), a change no window confirms is
refused: it is yours to make, in the window or in your own terminal. The home's `notices.json` is what Notifications keeps of
what ended, failed or went unanswered (NOTIFY2f), and of each conversation that answered you (NOTIFY2g); no command writes it.
`agent` runs each agent's own installer,
updater or login flow, `agent pin` fetches from a maker's verified channel, and `agent trust --yes`
and `agent settings` edit the agent's files (D73, D98). Every other
command above is offline by construction. **The machine's registry
is the authority** on who is in the family: being in a folder is not being a member, so a repository
joins by connecting and leaves by retiring. `import` is safe to re-run: unstated wiring is
preserved. A never-managed store imports its
configured root **once**, and says so. A registered checkout that is no longer
where the registry says it is gets **named** by the next refresh rather than silently skipped.

**Doctrine `sync --force` can overwrite or discard owned material**, so it names those files.
Without it, sync refuses in all three destructive cases — a file you edited, a file you wrote before
adopting, and a file being retired upstream that you had improved. A file `daoris.json` keeps is never
written, `--force` included; a core file kept with no text here is refused, since only a pack's switch takes a
core rule out. An older daoris's `sync` and `upstream`
refuse a repository a newer one synced, `--force` or not, naming `npx daoris@<that version>`.

`analyze` answers the question a repository has *before* it adopts: what already exists here, what
would collide, what already says the same thing under another name, and what the always-loaded budget
becomes. It writes nothing, and `--json` gives an agent the exact facts to act on.

Daoris reports collisions, possible duplicates and budget costs. The agent judges pack fit and resolves
collisions; the person selects what to adopt.

`analyze` compares against the canon rather than the lock, finding renamed twins before adoption.

`doctor` reports local documents that may restate canonical ones under another name. It uses measured
word overlap, which cannot find independently reached conclusions with different vocabulary. Its
findings are advisory and adoption still requires a read-through.

## The manifest

```json
{
  "source": "daoris@<version>",
  "packs": ["dotnet-library"],
  "target": ".claude",
  "coreBudgetBytes": 30000,
  "domain": {
    "summary": "One line: what this repository is, for someone who has never opened it.",
    "owns": ["the areas where a change belongs here rather than anywhere else"],
    "accepts": ["the kinds of work worth asking of it"],
    "uses": ["the repositories it depends on, by name"]
  },
  "remote": { "join": true, "knowledge": false }
}
```

A manifest may also carry `harness` (the layout `init --harness` chose), `rooms`, `documents`, `kept` and `switchedOff`, set where a
repository needs them.

`daoris.lock` sits beside it, generated: one entry per materialized document, recording its pack,
canonical path, version, and content hash — plus, for the always-loaded ones, the file whose region
holds it — and the digest of the canon it was written from, which tells two canons of one version apart.
Both are tracked, so a reviewer sees exactly what changed.

`domain` is the repository's declaration to the family — it makes a quest addressable rather than a
guess, and `daoris repository connect` refuses to register without one; `uses`, optional, is what the map draws as
dependencies. `remote` is the one **disclosure**
control: whether this repository joins a team's remote deployment (its registration, quests and
session records become visible there), and — a second, separate declaration — whether its indexed
knowledge content feeds too. It lives in the manifest, tracked and reviewed, because disclosure is the
repository's call, not one person's local toggle; **absence means local, silently**, and `knowledge`
without `join` is refused. `daoris status` reports the declaration.

## Three layers

- **Core** — universal workflow rules and discovery skills. Every repository gets these, unless a selected
  pack offers to switch one off and the manifest confirms it under `switchedOff` (D71); `sync`, `check`
  and `status` all say so.
- **Packs** — stack-specific sets, named in the manifest.
- **Local** — the repository's own documents: never synced or touched, and its knowledge and skills
  are indexed as `(local)`. A knowledge document with no frontmatter is listed by its first heading, and
  `check` says how many there are without failing on them (D128 §3). The manifest's `documents` may also
  carry `present`, the documents that state the present rather than history (D220), which `check` accepts
  beside the roles and leaves to the repository's own report to read.

The lock identifies **materialized doctrine Daoris owns**. Local knowledge and skills can be read
and indexed, but sync does not replace them as canonical copies. Adoption also writes generated
indexes and instruction regions; `init` writes the manifest and may create `.gitattributes`. A
repository-owned file colliding with a canonical path is refused unless force is explicitly chosen.

## Two things worth knowing

**The tier is the location.** The always-loaded rules land in a region of `AGENTS.md` that Daoris owns —
the one file every harness this family drives actually reads — with `CLAUDE.md` carrying a one-line
`@AGENTS.md` import; files in `knowledge/` are read on demand; `skills/<name>/SKILL.md` is invoked by
name. The agent harness decides that by location, so Daoris does not carry a redundant `tier` field — and
because a region has a byte count exactly as a directory did, `check` still reports the
always-loaded footprint against the budget the manifest declares. It reports and never fails on it
(D54): drift is a fact, size is a judgement, and a build stopped by a judgement teaches people to
raise the number rather than read it. When `AGENTS.md` as a whole passes the 32,768 bytes Codex reads,
`check` says what to trim: the repository's own part against the doctrine region, by how much it is
over, and the region's largest rules, so the remedy is a shorter own brief or a rule split to the
on-demand tier, never a raised limit (CANONSIZE1, D28).

**Canonical skills are parameter-free.** A skill states only the procedure that holds in every
repository and sends the reader to the generated index for anything local — there is no substitution map
in the manifest. Surveying twelve repositories showed why: copies of the same skill ranged over a 6.6×
size spread, and the shared part was ~15 lines. The rest was each repository's own routing content, which
no placeholder could have supplied.

**Every vendored file carries a one-line provenance header.** Not decoration: an agent that opens a rule
needing a tweak will otherwise simply edit it, which is exactly how the copies diverged. The header says
where the file came from and to use `daoris upstream`; the lock's hash catches the edit either way, and
`daoris reconcile` is where the repository decides to keep it, with its reason, or propose it.

## Lanes

A repository's **lanes** are the domains inside it that work is handed to, each owning its paths. They are declared in a
`daoris.lanes.json` at the repository's root: an `id` (lower-case letters, digits and dashes; how a quest addresses the lane, as
`repository:id`), a `title`, a `summary` and path globs, with one **steward** lane that keeps the repository's records (D115).
With no file the repository has no lanes.

What lanes do for the work, on a machine where the person has opted the repository in to being driven:

- A session of the repository can publish a quest to one of its own lanes, and the driver starts it as a further part of that
  session's line of work. Without lanes there is nothing to publish to, and a session works its rows itself.
- **Trees.** A repository that opens a tree for each session (`daoris place trees <repository> on`) can run such a part beside the
  session that published it. One that does not runs it only after the publishing session ends, so a quest to its lanes waits.
- **Not driven here.** A repository the person has not opted in on this machine starts nothing, lanes or not.

The session view's *At work* tab says which of these holds where a session ran subagents and the way to hand rows on is not open.

## Extending it

Daoris loads **no code into any host**, and has four seams, each a *declaration* or a *wire*, so none
can break the tool that reads it:

| To add | Write |
|---|---|
| **Doctrine** for a stack | a pack — `canon/packs/<name>/pack.json` + its tiers |
| **A gate** | a row in `daoris.gates.json` |
| **A harness** to drive sessions on | nothing — speak the **Agent Client Protocol** |
| **A plugin** on one machine | a folder under the home's `plugins/` with a `plugin.json` (D64): it *declares* ACP-door configurations (each may name its tool's `product` and `maker`, D155), the servers and skills sessions or Ask Daoris are handed (D170), the steps it adds to a piece of work and the resources they create (D173), and may *speak* from its own process |

A pack and a plugin each declare the API they need (`"apiVersion"`), read first. The harness seam is
a protocol, not a registry; a plugin a folder, not a catalogue. `docs/2026-09-23-plugin-design.md`
is the contract, which the CLI and the driver's `PluginCatalog.cs` read alike.

## Beyond the CLI: the service, the platform, the driver

The CLI is the doctrine half. **`Daoris.Service`** indexes what every adopting repository has learned,
finds where two repositories reached the same conclusion in different words, holds the **registry** —
what each repository owns and accepts — and carries **quests**: how one repository asks another for
work instead of reaching in. **`Daoris.Web`** is the platform over it — knowledge, quests and projects
in one window, with doctrine read-only everywhere. **`Daoris.Desktop`** is the driver (D45): the
desktop shell hosts the local service, carries the same platform bundle, and runs the loop that turns
the quest queue into an execution queue — a fresh agent session per open quest, one per repository,
onto a clean tree, claiming its own quest so driven and outside work are indistinguishable. The same
HTTP host in **shared mode** is the team
remote (D47): every route gated by minted per-person per-machine keys, fed by each desktop's sync
loop, never required by anything local. Each artefact's own README carries the rest.

**Worked example:** [`examples/`](../../examples/README.md) is a two-project family — an engine and a game —
and `npm run rehearse:family` drives the whole arrangement through the real artefacts — adoption,
registration, a quest's full life, a driven session, a two-machine remote — with no model in the gate.
