# Daoris

> **Engineering Cultivation Framework for LLMs**
>
> *Inspired by the Daoist concept of **道衍** — the continual unfolding and evolution of engineering knowledge.*

---

# Overview

Daoris is an **LLM Software Engineering Cultivation Framework**.

Its purpose is not to build another coding agent, prompt library, or RAG toolkit.

Its purpose is to provide the reusable **engineering doctrine** that teaches Large Language Models how to practice software engineering.

Daoris provides the surrounding engineering intelligence that enables LLMs to become reliable software engineers through knowledge, context, tools, validation, and continuous refinement.

The model generates code.

**Daoris cultivates the engineer.**

---

# Vision

Modern LLMs already know how to write code.

What they lack is engineering discipline.

They do not naturally understand:

- Large software systems
- Architectural intent
- Engineering conventions
- Repository history
- Validation workflows
- Iterative development
- Organizational knowledge

These capabilities should not exist only inside prompts.

They should exist as a reusable engineering doctrine.

Daoris exists to provide that doctrine.

---

# Philosophy

Engineering is not prompt execution.

Engineering is a continuous process of learning, reasoning, validation, and refinement.

Daoris treats software engineering as a cultivation process.

Every completed task should improve future tasks.

Every discovered convention should strengthen future reasoning.

Every successful solution should become reusable engineering knowledge.

# Core Concepts

## Engineering Doctrine

The canonical representation of how software should be engineered.

Examples include:

- Architecture principles
- Coding conventions
- Naming rules
- Design patterns
- Domain knowledge
- Testing practices
- Security practices
- Review guidelines

The doctrine evolves continuously.

Every agent built upon Daoris benefits from its evolution.

---

## Repository Intelligence

Understand projects beyond raw files.

Examples:

- Solution structure
- Dependency graph
- Symbol graph
- Architecture graph
- Git history
- Ownership
- APIs
- Project metadata

---

## Context Engineering

Assemble the most relevant engineering context for each task.

Possible sources:

- Source code
- Documentation
- Repository intelligence
- Engineering doctrine
- Previous tasks
- Semantic retrieval
- Organizational knowledge

The objective is engineering understanding rather than maximum token usage.

---

## Engineering Techniques

The doctrine is expressed through reusable techniques.

Examples include:

- Prompt composition
- Context assembly
- Retrieval (RAG)
- Planning
- Reflection
- Self-review
- Retry strategies
- Workflow orchestration

Techniques evolve.

The doctrine remains.

---

## Engineering Tools

Software engineers require tools.

Daoris exposes structured engineering capabilities including:

- Build
- Restore
- Testing
- Git
- Shell
- Formatting
- Static analysis
- Diagnostics
- Repository inspection

Tools should be abstracted so different execution environments can share the same engineering workflow.

---

## Engineering Harness

Provide reusable execution environments for engineering agents.

Responsibilities include:

- Task lifecycle
- Tool orchestration
- Progress reporting
- Tracing
- Retry
- Cancellation
- Resource management

Harnesses coordinate engineering workflows rather than individual prompts.

---

## Validation

Engineering work must be verified.

Validation may include:

- Compilation
- Unit tests
- Integration tests
- Static analyzers
- Formatting
- Diagnostics
- Benchmarks

Validation produces structured feedback for future reasoning.

---

## Engineering Memory

Every engineering task contributes knowledge.

Examples:

- Successful implementations
- Common failures
- Architectural decisions
- Coding conventions
- Project knowledge
- Team practices

Engineering memory continuously strengthens the doctrine.
