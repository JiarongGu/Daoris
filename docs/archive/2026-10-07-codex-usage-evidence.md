# CODEXUSE1: what Codex says about an account's windows, and where (evidence note)

**Carried by:** D125's CODEXUSE1 note, which builds on it, and D130 §5.1's row for Codex's app server, which it
answers. It is a record of the version below, not a contract: a Codex that moves is read again.

> Measured 2026-10-07 with **codex-cli 0.160.0**, outside Daoris, and given to this branch, which ran no Codex. No
> account id, no reset credit's id and no machine time is written here: each id is left out and each reset is
> written `<reset>`.

## The answer

1. 🔴 **Codex's own app server answers an account's windows on request, and the request spends no model usage.**
   `codex app-server` speaks JSON-RPC 2.0 over stdio, one JSON object per line, and `account/rateLimits/read`
   answers each window's use as a whole percent, its length in minutes and its reset in Unix seconds (§1, §2).
2. **Two windows were answered: 300 minutes and 10,080.** Five hours and a week, the two Claude Code's frame names
   `five_hour` and `seven_day` and Daoris names `session` and `weekly`. No other length was seen.
3. **No door of Daoris's carries it.** `codex-acp` keeps the server's pushes for its own `/status` text and forwards
   none (limit-signals evidence §4), and `codex exec --json` carries a turn's token counts and no window (§3).
4. **The account is the one `CODEX_HOME` names**, the variable Daoris's toolchain already sets for a Codex account
   (`ProfileVariable`). The tool's own sign-in is the server started with it unset.

## 1. The protocol

The client's lines, in order, each answered before the next where it is a request:

| # | Sent | Answered |
|---|---|---|
| 1 | `{"id":1,"method":"initialize","params":{"clientInfo":{"name":…,"version":…}}}` | a response to `id` 1 |
| 2 | `{"method":"initialized"}` | nothing: a notification |
| 3 | `{"id":2,"method":"account/rateLimits/read","params":null}` | a response to `id` 2, §2 |

The server also pushes `account/rateLimits/updated`, a notification, which a reader of the answer reads past. The
lines carry no `jsonrpc` member, and the client's were sent without one. The server does not end by itself.

## 2. The read's answer

```json
{ "accountId": "…", "ordinaryUsageAllowed": true,
  "rateLimits": {
    "limitId": "codex", "limitName": "…", "normalModelSlug": "…",
    "primary":   { "usedPercent": 1,  "windowDurationMins": 300,   "resetsAt": <reset> },
    "secondary": { "usedPercent": 15, "windowDurationMins": 10080, "resetsAt": <reset> },
    "credits": { "hasCredits": …, "unlimited": …, "balance": … },
    "individualLimit": …, "spendControlReached": false, "planType": "…", "rateLimitReachedType": null },
  "rateLimitsByLimitId": { "codex": { …the same… } },
  "rateLimitResetCredits": { "availableCount": …, "credits": [
    { "id": "…", "resetType": "codexRateLimits", "status": "available", "grantedAt": …, "expiresAt": …,
      "title": "…", "description": "…" } ] },
  "rateLimitUpsell": … }
```

The schema is generated by `codex app-server generate-json-schema --out <dir>`: `GetAccountRateLimitsResponse`,
`RateLimitSnapshot`, `RateLimitWindow { usedPercent, windowDurationMins, resetsAt }` and
`SpendControlLimitSnapshot`.

## 5. What this note does not establish

- **Whether the read refreshes an expired token.** A status question can (TOOL6g), so CODEXUSE1 asks under the
  account's lock and never while a session of Daoris's runs on it.
- **An API-key account's answer, a refused sign-in's, and a Pro plan's**, which the maker says has no five-hour
  limit (D130 §0.3, X1). Each is read as unknown, or by its window's own length, never guessed.
- **What `rateLimitReachedType`, `spendControlReached`, `individualLimit` and `credits` say at a limit.** Only their
  values on an account far from one were seen, so nothing reads them.
- **What a reset credit does.** It is counted and listed by the server; Daoris neither reads nor redeems one.
- **How long the server takes to answer.** CODEXUSE1's patience, 15 seconds, is a bound, not a measurement.
