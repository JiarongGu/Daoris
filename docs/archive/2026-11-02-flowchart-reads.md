# FLOWCHART2 — Codex's read of the design, and the steward's settlement

Read-only source review of the synthesis, brief, both proposals, and the named implementation. No files changed; no builds or tests run.

**1. Blocking findings**

1. **“Earlier” must mean an ancestor, and the connection table must retain multiple targets.** The synthesis derives a wire from where its target “stands” and gives each outcome one target (`docs/2026-11-02-flowchart-design.md:32`, `:38`). The driver instead requires a `back` target reachable upstream through `after`, `trigger`, `data`, or `when`; a visually earlier sibling does not qualify (`src/Daoris.Desktop/Daoris.Desktop.Driver/Workflows/Nodes/NodeWires.cs:265`, `:488`). Multiple eligibility wires and their groups also affect execution (`NodeWires.cs:305`).

   Restore the ancestor definition, **Also to…**, individual wire removal, and an explicit home for advanced connections. Removing `WayForm` otherwise loses today’s ability to add `trigger` wires and manage multiple outgoing wires (`src/Daoris.Web/src/workflow/edit/WorkflowEditor.tsx:429`, `:457`). Keep wire kinds hidden behind meaningful actions, without reducing the graph’s semantics.

2. **The removal rule authorizes more rewiring than the proposal intended; choosing the configured end also disappears.** The synthesis offers *Remove and join* whenever there is one incoming and one outgoing way (`docs/2026-11-02-flowchart-design.md:41`). That includes combinations of success, failure, outcome, or grouped dependencies for which there is no unambiguous replacement. The Opus proposal restricted this to a straight `after` chain (`docs/archive/2026-11-02-flowchart-proposal-opus.md:358`).

   Require plain, compatible `after` links and preview the replacement; preserve other dependencies explicitly. Also retain **Work is done here** when deleting the old cards: today they contain that action (`src/Daoris.Web/src/workflow/edit/WorkflowEditor.tsx:407`). Removing the end step clears `draft.end`, so the person needs a visible way to repair it (`src/Daoris.Web/src/workflow/edit/graphDraft.ts:163`). Keep the configured end as a marker on its actual step, as built today, rather than a separate terminal (`src/Daoris.Web/src/workflow/graphFlow.ts:230`).

3. **A palette digest is insufficient context for Ask Daoris to compose.** The synthesis’s attachment contains the graph, fingerprint, place, and palette digest (`docs/2026-11-02-flowchart-design.md:53`). A digest cannot tell the helper which installed steps, options, schemas, or outcome-specific outputs are available. The room’s allowed tools contain no palette reader (`src/Daoris.Desktop/Daoris.Desktop.Driver/Help/HelpRoom.cs:57`); that information exists in `WorkflowPalette` (`src/Daoris.Desktop/Daoris.Desktop.Driver/Workflows/WorkflowPalette.cs:47`).

   Restore the compact palette snapshot, sent initially and when its digest changes, plus source/save target, base version, route, pipeline, selected element, and current problems. Source identity matters: save planning uses the stored pipeline mark and refuses a moved base (`src/Daoris.Desktop/Daoris.Desktop.Driver/Workflows/WorkflowOperations.cs:615`, `:728`). Freeze this context with the person’s submitted message; “sent when the fingerprint changes” must not mean automatically starting assistant turns on edits. Today the preface is attached during message delivery (`src/Daoris.Web/src/help/AskConversation.tsx:348`).

4. **Row 2e needs a complete, explicitly weaker Apply path—including modules.** Its declared lanes are service and driver, but the modules bridge explicitly filters workflow cards and currently sends neither candidate graph nor structured changes (`src/Daoris.Desktop/Daoris.Desktop.Modules/Bridge/Routes/HelpRoutes.cs:984`). Row 2f cannot draw its proposal from that answer.

   There is also a concrete save trap: putting the candidate into today’s `HelpWorkflowCard.Graph` makes `Saves` true (`src/Daoris.Desktop/Daoris.Desktop.Driver/Help/Proposals/HelpWorkflowProposals.cs:682`), and the current Apply path then calls `WorkflowStore.Add` (`:329`). Introduce the draft branch before legacy save/use handling, with a discriminated payload and modules serialization. Draft mode must reject mixed legacy instructions such as `choose`, route-only use, or saved-base substitutions. Prove the no-save/no-choice boundary through the bridge, not only the proposal class. The existing navigation-only precedent is `HelpSetupProposals.ApplyAsync` (`src/Daoris.Desktop/Daoris.Desktop.Driver/Help/Proposals/HelpSetupProposals.cs:152`).

5. **“Ways by structure then id” must not hide execution changes.** The synthesis adopts that matching rule without defining what constitutes a change (`docs/2026-11-02-flowchart-design.md:57`). Wire IDs are semantic: they determine `anyOf` witness order and trigger deduplication (`src/Daoris.Desktop/Daoris.Desktop.Driver/Workflows/Nodes/NodeWires.cs:109`). Renumbering structurally identical wires is therefore not automatically harmless.

   Structural matching may improve presentation, but it must either preserve existing identities or show identity changes. Compare every wire field, including groups, ports, `outcome`, and `on`; include graph fields such as `entries` and `end`. Today’s `GraphLines` misses modifications to a wire retaining its ID (`src/Daoris.Desktop/Daoris.Desktop.Driver/Help/Proposals/HelpWorkflowProposals.cs:543`), while the draft preserves fields outside its visible controls (`src/Daoris.Web/src/workflow/edit/graphDraft.ts:105`).

6. **Partial acceptance needs a transaction and settlement contract.** “Take change by change with `needs`” leaves unresolved whether the first take stales the rest, when a proposal becomes applied, and how undo restores acceptance state (`docs/2026-11-02-flowchart-design.md:59`, `:104`). Existing `HELP_APPLY` accepts only a still-proposed card and checks its plan revision; that revision does not check the open editor’s state (`src/Daoris.Desktop/Daoris.Desktop.Modules/Bridge/Routes/HelpRoutes.cs:537`, `:553`).

   Specify immutable base/preconditions, dependency closure, atomic application, accepted/left entries, and matching undo history. Dependencies must include incident-wire removals, landing tails, groups, and replacement end references. Opening the editor must not prematurely settle a proposal whose changes remain undecided. Either proposal’s fuller protocol provides the missing detail; their different staleness policies should be deliberately reconciled.

7. **The build order asks for proof before its prerequisites exist.** Row 2b must compose the release workflow, while options, tails, and inputs arrive afterward in SETUPUX1r (`docs/2026-11-02-flowchart-design.md:97`). The shipped release graph requires two data connections (`src/Daoris.Desktop/Daoris.Desktop.Driver/Defaults/workflows/release.json:55`), and the existing composition regression explicitly supplies both (`src/Daoris.Web/src/workflow/edit/WorkflowEditor.test.tsx:151`).

   Put basic *Carries* editing into 2b or move the complete composition proof after r. Add 2c as a dependency of 2d, which consumes its fingerprint. Exact-draft validation must invalidate synchronously and remain invalid after a failed request: today the debounce leaves a window with an old answer, and a failed request retains that answer (`src/Daoris.Web/src/workflow/edit/WorkflowEditor.tsx:142`; `src/Daoris.Web/src/bridge/repositories/workflowEdit.ts:106`). Test those cases alongside out-of-order responses.

**2. Non-blocking findings**

- **Port routing needs a same-target regression.** Layout currently bundles edges sharing endpoints and style (`src/Daoris.Web/src/design/flowLayout.ts:107`). Two outcomes reaching the same step must still leave their respective ports and remain individually selectable. Add that fixture to 2a’s measured proof; shipped graphs alone do not establish it.

- **An outcome routed backward must not also acquire “No further step.”** The current adapter detects only `when` routes when creating that terminal (`src/Daoris.Web/src/workflow/graphFlow.ts:241`). Extend the test to a `back` with `on: <outcome>` as the new editor makes that route convenient.

- **Shared components must respect incomplete run data.** The run answer supplies wires and reached outcomes, not the full saved node declarations or data-port metadata (`src/Daoris.Desktop/Daoris.Desktop.Modules/Bridge/Routes/WorkflowRoutes.cs:733`). Preserve the adapter’s distinction between known routes and the returned outcome (`src/Daoris.Web/src/workflow/workflowFlow.ts:96`); do not manufacture undeclared outcomes from today’s palette. Keep run records, controls, limits, and source doors as explicit parity checks—the existing chart injects these separately (`src/Daoris.Web/src/workflow/WorkflowChart.tsx:399`).

- **The measurement bound exceeds 24 displayed nodes.** The limit counts authored nodes separately from synthetic ones (`src/Daoris.Desktop/Daoris.Desktop.Driver/Workflows/Nodes/NodeGraphs.cs:233`); a proposal union adds another source of growth. Measure those presentations, long outcome labels, and selection-dependent data ink. Selection must not change layout merely by showing a data edge: edge membership currently participates in the shape key (`src/Daoris.Web/src/design/Flow.tsx:218`).

- **Keep the library rationale evidential.** D186 supports retaining the measured engine against the tested dagre version (`docs/decisions/D186.md:150`). It does not establish all the synthesis’s React Flow claims. The proposals labelled those claims unverified and proposed interaction/performance measurements before locking the extension (`docs/archive/2026-11-02-flowchart-proposal-codex.md:284`; `docs/archive/2026-11-02-flowchart-proposal-opus.md:457`).

**3. What the synthesis dropped and should keep**

- **The concrete narrow-screen and keyboard contracts.** Codex specifies sizing by the editor’s remaining region, restoration of selection/scroll, and avoiding competing inspector/Ask drawers (`docs/archive/2026-11-02-flowchart-proposal-codex.md:147`, `:189`). Opus specifies equivalent rail editing at 25rem (`docs/archive/2026-11-02-flowchart-proposal-opus.md:397`). These matter because the existing primitive already has branch-following, roving focus, and IME protection (`src/Daoris.Web/src/design/Flow.tsx:282`).

- **Insertion and movement previews.** Codex explains which connection is replaced and explicitly forbids guessing transfers of data, groups, or exception routes (`docs/archive/2026-11-02-flowchart-proposal-codex.md:233`). This is the detail that turns a convenient press into an understandable graph edit.

- **The defined local clipboard transaction.** Codex specifies fresh identities, internal wires, omitted external connections, and attachment review (`docs/archive/2026-11-02-flowchart-proposal-codex.md:228`). The synthesis adopts copy/paste without those rules; today’s removal and identity helpers do not supply them automatically (`src/Daoris.Web/src/workflow/edit/graphDraft.ts:144`, `:163`).

- **Unavailable-helper and older-host behavior, plus actual model attribution.** Codex explicitly refuses fallback to a legacy saving proposal (`docs/archive/2026-11-02-flowchart-proposal-codex.md:334`); Opus puts the agent/model that ran on the proposal bar (`docs/archive/2026-11-02-flowchart-proposal-opus.md:526`). Manual inspection, editing, and validation must remain useful without the helper.

First rows should carry lossless connection semantics, restricted rewiring and end selection, complete frozen draft context, a bridge-complete non-saving proposal door, semantic diffs with atomic partial acceptance, and corrected prerequisites and proofs.
