# Daoris (道衍) — project brief

## What this is

Daoris coordinates agent development across repositories. Its desktop hosts the local service and
driver, presents the shared React platform, and lets a person set targets and review outcomes.
The CLI distributes engineering doctrine; the service indexes knowledge and exchanges quests.
The direction is [D45](docs/decisions/D45.md), read through [D193](docs/decisions/D193.md)'s picture of a development company run by agents. Detailed contributor procedures are in
[docs/development.md](docs/development.md).

## The constraint every change serves

Orchestration is central; ownership is local. A session changes its own repository, and requests
work from another through a quest. Local operation does not require a remote. Doctrine works
without a service. Model-dependent capabilities state the tier that actually ran.

## Before changing anything

- Keep canon content project-agnostic. Edit `canon/`, then sync this repository and both examples;
  do not patch generated doctrine copies. Read `.claude/knowledge/canon-authoring.md` first.
- Drift compares disk with the lock, not the newest canon. Read D19 before changing sync's
  lock × disk × canon behavior. The CLI's doctrine commands remain offline and have no runtime
  dependencies; management operations use the explicit service/toolchain seams.
- Machine-local streams, accounts, browser state and filesystem actions stay on the desktop.
  Shared hosts exchange permitted records, serve no UI and answer no machine paths.
- UI chrome translates through a catalogue per shipped language (today English and Chinese); authored content,
  configuration included, stays as written and asks for no language (D222). Read the translation and UI contracts
  before changing visible text or screens.
- Do each thing one way (D228). A change that supersedes an older way removes it — code, doors, words and
  defaults — in the same chunk; an older record still read keeps its path only with the condition that ends it
  and the row that deletes it. A second way to do one job is a defect.
- Keep project facts in versioned records. Rewrite a present fact where it lives (D220); append
  amendments to decisions as history, and move completed tasks from the backlog to the archive.
- Do not hand-edit versions or release headings. The release workflow owns their stamping.
  Local commits follow green gates; push, publication and history rewrites remain the owner's call.
- Keep Codex execution defaults in `.codex/config.toml`. Authorized scratch cleanup follows
  [the repository cleanup procedure](docs/development.md#repository-scratch-cleanup); do not repeat
  an already-granted approval or work around a tool rejection.

## Layout

`canon/` is the source; `.claude/` and the doctrine region below are its materialized copies.
`daoris.lock` records owned doctrine. `CLAUDE.md` imports this shared brief. The current target is
`.claude`; the broader agent-layout migration is governed by D117 and its remaining tasks.

The CLI package stages `canon/`, the root README, LICENSE and CHANGELOG at pack time; its staged copies and
compiled `dist/` are ignored. The web build writes the HTTP host's `wwwroot/`, also ignored.
`docs/code-map.json` is generated by its tool: regenerate it rather than editing it. `docs/index/` is
never committed: each checkout writes its own (`node tools/orient-index.mjs`; the checkout hooks and the
knowledge server write it when the tree moves). `.gitattributes` marks generated and union-merged records.

There are no declared folder rooms in this repository. Read the relevant component README and
the router's contract before editing a component. Gitignored `local/` holds private context;
`_fixtures/` holds repository scratch. Never use OS temp for repository work.

## Build, test, verify

Run from the workspace root. Development uses Node 24 and the .NET 10 SDK; the packaged CLI supports
Node ≥22. Install root and web dependencies from their lockfiles (`npm ci` and
`npm --prefix src/Daoris.Web ci`). [docs/development.md](docs/development.md) gives the focused loops.

`npm run verify` is the baseline check: CLI types/tests, doctrine, documentation, release references
and universal gates. It is not the whole product test set. `daoris.gates.json` declares the component
gates; use the reached checks while working, and the full set at an integration boundary. Real-process
suites and rehearsals run serially (the merge tool runs the family rehearsal beside the git half, each on its own
build output); they may start subprocesses or windows. Read the development
guide before running the full set. Do not stop an unrelated or installed process to unblock a build.

## Conventions

TypeScript is ESM; source imports use `.ts`, and publishing rewrites them to `.js`. Node 24 runs
source tests without an emit, so typechecking is a separate gate. CLI files are written atomically
as BOM-less UTF-8 with LF. Tools with importable helpers guard their runner with `isMain` from
`tools/fsx.mjs`. Exit codes are `0` clean, `1` policy failure, `2` tool error.

Make every change through the `change` skill. Open `docs/index/README.md` before searching code, then
read its named ranges. Code changes need their relevant regression tests and checks. Installed-window
proof remains distinct from a story or mocked bridge.

# Use the file tools — and never route around an approval

**Read, search and edit files with the dedicated tools, and keep the shell for builds, tests, version
control and running programs. Never send a command through another channel to avoid an approval
prompt.**

A scripted edit passes your text through another language's escaping, and a pattern that stops matching
changes nothing and reports nothing; a bulk edit scripted anyway asserts its count. Delete only the text
you matched, never a region found by offsets. Where a harness has no file tools, its shell's read-only
commands read and a program's file API writes. A destructive command (a recursive delete, a hard reset,
a force push, a skipped hook, a killed process) deserves a pause exactly where it no longer prompts.
If a prompt is wrong, change the policy openly; hiding a command from it circumvents a safety control.

# Never write into another repository

**Do not touch another repository: not its code, its files or its backlog. Publish the request and let
whoever works there take it, as a quest where a request system exists and as a message to its owner
where none does. Writing across anyway is the user's explicit call, never your judgement.**

The knowledge is not portable but the request is: why a rule is worded as it is and what was tried and
rejected live with that repository, and an outside edit skips its review. Say what is needed and why,
with the evidence, not the change you would make. A change spanning two repositories is two changes and
a request. Already touched one? Stop and say so; do not repair it (`reaching-in`). Initializing a
repository that has no owner yet is setup, until it has anything of its own.

# Sensitive info — keep machine specifics and private names out of tracked files

**Never put a developer machine's absolute path, a private repository's name, or any credential into a
tracked file or a commit message.**

Once committed it lives in the history, where deleting the line does not remove it, and a commit message
is history too. Use repository-relative paths or a neutral placeholder, name a sibling project neutrally
unless it is public under that name, and keep private context in an untracked directory. Credentials
belong in the environment or a secret store; tests use a deterministic stub. A leak already committed
needs a history rewrite, with a backup first (`leak-repair`).
