# Twins — how two artefacts agree without sharing code

**The CLI, the service and the driver share no code, by design. Where two of them must agree on a
fact, the FILE is the contract: each reads it with its own code, each carries a test table the other
must keep matching, and a change to one side is a change to both, in the same commit.**

## Why

The artefacts are different runtimes shipped to different places. The CLI is a zero-dependency Node
package, the service a .NET host that may run on a server, and the driver a .NET library the desktop
and the headless host carry. A shared library would make every one of them ship the others'
dependencies, and it would make the CLI's zero-dependency guarantee a claim about code it does not
own. So a machine-local file is read twice, or three times, on purpose.

The risk of that is drift, and it is the only risk. A rule enforced in one reader and not the other
is a rule the other will contradict, in front of a person, on a machine where both run. The remotes
map found this first (WSP3), and every twin since was built the same way for the same reason.

## How to apply

- **Name the file and its rules once, in the design or decision that introduces them.** Each reader's
  header names its twins by file.
- **Each twin carries a test table of the rules**, written so the other side's table can be compared
  line by line: the same cases, the same answers, including what absence means. A rule one table
  has and the other lacks is the drift, found before a person meets it.
- **Change both sides in the same commit**, tables included. A commit that changes one reader of a
  twinned file is incomplete, whatever its tests say.
- **Absence is a rule, not a default.** "No profile means the harness's own home", "no home means
  refuse", "half a remote pair is no remote": the answers for a missing file or field are where the
  twins drifted most.
- **An editor preserves what it has no field for.** A twin that rewrote the file from its own idea of
  the shape would delete what the other side wrote. `driver.json`'s writers show the way (FABRIC-GRAPH1's
  review): the edit is the set of key paths that differ between the file as read and understood and the
  edited choices, made onto the file read again at write, holding the file's lock to the rename, and touching those paths alone
  (`JsonKeeping.cs`, `jsonkeep.ts`, `KeepLock.cs`, `keeplock.ts`; D173's re-checks and CONFIG1 note), so another writer's change made
  in between stays, a set both writers added to keeps both writers' names, an object it took out
  never comes back with its old keys, and a file that does not read then, or an object it made a scalar, is
  refused, never overwritten. A file missing at the read is the text `{}`, never a licence to write whole.
  Both twins write their maps in one order, or an added entry lands apart. Prove it on a file the writer
  did not write, with keys neither side knows at each level, and with another writer's change between the
  read and the write: a byte test whose input the new writer made proves only idempotence.
- **A key `driver.json` gains is added at each of these, in one commit**: the driver's property, `Parse` and `Written` (its place
  in the order); the CLI's `DriverChoices` type, `EMPTY`, `choicesOf`'s answer for no file, its destructuring (a key left in
  `rest` overwrites what its writer writes), its reader, and its writer at the driver's place; then the keeps table's `file`,
  a row, and the `op` both `configkeeps.test.ts` and `DriverConfigKeepsTests` make (AUTONOMY1a's `access`, HEAVYRUN1b2a's
  `heavyGates`).
- **A constant both sides need is duplicated deliberately**, with a comment naming the other copy,
  never imported across.
- **A twin reads the other side's file by its name, never its folder** (STRUCT1, D166): the CLI's `driverFile` and
  `driverTestFile` (`_csharp.ts`), the page's `driverSource`, the driver's `SourceFiles`; `driver-names.test.ts` refuses a
  fixed folder, so a module's move edits no reader.
- **A page test that reads a driver source names that file to the merge tool.** `tools/merge-branch.mjs`'s
  MOD9e row lists each driver file a vitest parses, so a change to it runs the web gate; `tool-test/merge-branch.test.ts`'s
  SESSDEL1c case fails a merge whose page test reads one the row lacks (MSG1g3's say twin, 2026-10-11).
- **A shared table among the CLI's fixtures that a driver test reads names itself to the merge tool too**: its own
  REACH row beside `account-reads.json`'s, so a change to it runs the driver's gate, and a case in
  `tool-test/merge-branch.test.ts` holding that row (SWITCH1a's `rotation-use.json`; it runs in the `tool-tests` gate, which
  `verify` does not, so run `npm run tooltests` when you add such a row, GATESLIM1). Where a page test reads it too, the row names
  `web` beside `driver`, or the SESSDEL1c case fails once the page test is tracked (SWITCH1d's `rotation-use.json` and
  `usage-curves.json`; `verify` passes before `git add` and fails after, since the case reads tracked files).
  `tool-test/merge-branch.test.ts` holding that row (SWITCH1a's `rotation-use.json`).
- **A file taken by whoever creates it first is put in place with no overwrite, on both sides.** C# moves the written file
  in with `File.Move(…, overwrite: false)`; Node's `renameSync` replaces on Windows, so the CLI links it in (`linkSync`,
  which refuses where a file is) and removes the one it wrote. `writeFileSync(…, { flag: 'wx' })` is exclusive but leaves a
  moment where the file is empty, which the other side reads as a file that does not read (HOMEID1's `home.json`,
  HOMELEASE1's `home.lease`).
